## Financial Integrity: Scope Boundary (Read Before the Table Below)

The sprint brief asks to confirm the full chain "Coupon → Checkout → Webhook → Receipt → Receipt PDF → Customer Download" behaves exactly as tested, in production. **This Board deliberately did not complete this chain with a real payment.** Doing so would require either initiating a real Paystack transaction (spending real money - outside this Board's authority and outside what any release-verification step should ever do) or hand-inserting fabricated receipt/webhook-derived data directly into production (which would not actually verify the webhook logic at all, only prove that already-correct data renders correctly - something already proven by the automated test suite, and which risks polluting real financial/audit records if not perfectly reverted).

**What was verified instead, safely:**

| Stage | Verification performed |
|---|---|
| Coupon | Real `/api/coupons/validate` call against the real product - correct discount computed |
| Checkout | Real `/api/checkout/sessions` call with a real coupon code - discount correctly locked into a real (pending) purchase_sessions row, confirmed by direct query |
| Webhook | A deliberately invalid-signature request was sent to the live `/api/webhooks/paystack` endpoint - correctly rejected with `INVALID_SIGNATURE`, confirming the endpoint is live, reachable, and the safety-critical signature-verification boundary is intact, without ever touching real payment data |
| Receipt / Receipt PDF / Customer Download | **Not exercised in production.** Exhaustively verified end-to-end (real HTTP checkout → real signed webhook → real database-driven receipt → real guest download flow → real PDF decompression and content assertion) by `couponReceiptPipeline.test.ts`, added specifically to close this gap at M4E closeout and independently re-run as part of this sprint's own pre-release audit (221/221 passing) |

This is the same class of judgment call this project's own M3E Production Deployment Report made explicitly (seeding data directly in D1 "rather than a live payment-gateway transaction") - applied here with the additional constraint that M4, unlike M3, does touch the payment-amount-locking code path, making the case for avoiding a real transaction even stronger, not weaker.
