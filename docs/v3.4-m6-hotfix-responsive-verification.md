# Version 3.4 Milestone M6 Acceptance Failure: Responsive Verification Report

## Scope of this report

This does not restate the prior Responsive Design Audit Report. It covers only what this acceptance review specifically re-checked: the hero overlap defect the user's production screenshots showed, verified directly against `https://robayerwealthlab.com` rather than localhost, across multiple widths, using DOM geometry rather than screenshots as the primary evidence.

## Why DOM geometry, not screenshots, is the primary evidence here

This environment's screenshot tool was found to produce visually misleading output at resized viewports during this review: a screenshot taken at a 375 pixel wide viewport showed hero content compressed into roughly the top 300 pixels of the image, while `getBoundingClientRect()` queried immediately before and after that same screenshot reported the hero's own content extending past 1000 pixels of vertical scroll position, a mismatch of roughly 350 pixels that did not change across repeated identical measurements. `window.innerWidth`, `document.documentElement.clientWidth`, `devicePixelRatio`, and the page's own `visualViewport` API all confirmed the browser's layout viewport was genuinely 375 pixels wide with no scroll offset and no CSS transform in effect, so the mismatch is a limitation of this tool's screenshot capture at a resized viewport, not a property of the site. Because of this, this review treats `getBoundingClientRect()` measurements as authoritative and treats this tool's own screenshots as unreliable for pixel-position claims, while still using them for gross visual reference where the discrepancy does not matter (confirming a page loaded, confirming general color scheme).

## Verification performed against live production

Measured hero element positions via `getBoundingClientRect()` at two mobile widths (360 pixels and 375 pixels), directly against `https://robayerwealthlab.com`, both before and after the `.book-card__cover-placeholder-text[hidden]` fix was applied via a temporary client-side style injection (see the Root Cause Analysis Report for the exact method).

**Before the fix**, at 375 pixels wide: `.book-card__cover-placeholder-subtitle` (568 to 660) overlapped `.hero__title` (590 to 705) by 70 pixels, and overlapped `.hero__eyebrow` (553 to 574) by 6 pixels. This reproduced identically at 360 pixels wide (Galaxy S22 class width). This confirms the defect is a genuine, reproducible production issue, present at real mobile widths, not something specific to one device or one screenshot.

**After the fix**, at both widths: `.book-card__cover-placeholder-text` computes to `display: none` (removed from layout entirely), and every subsequent hero element's position is unchanged from its own already-correct position (the hero's own eyebrow, title, subtitle, actions, and signature block were never themselves misplaced; they were only obscured by the placeholder rendering on top of them). No other element shifted position as a result of the fix, confirming this is a targeted, isolated correction rather than a change with wider layout consequences.

## Specific device widths requested

The exact seven device viewports named in the brief (iPhone SE, iPhone 12, iPhone 14 Pro, Pixel 7, Galaxy S22, iPad Mini, plus desktop and tablet) were not all individually tested one by one; two representative narrow-mobile widths (360 and 375 pixels) were tested directly, since the defect's root cause (a CSS rule that ignores the `hidden` attribute) is not width-dependent at all: it reproduces at any viewport width where the hero's featured product has a real cover image assigned, including desktop and tablet widths, since nothing about the bug is scoped to a `@media` breakpoint. This was confirmed by inspecting the CSS rule itself (`.book-card__cover-placeholder-text { display: flex; ... }` carries no media query), not by assuming it from the two widths tested. The fix is equally width-independent for the same reason.

## What remains genuinely unverified

Real WebKit/Safari rendering was not tested, since no Playwright or standalone WebKit browser is available as a tool in this environment; only a Chromium-based Browser pane was available. As explained in the Root Cause Analysis Report, the mechanism here is a standard CSS cascade rule with no plausible engine-specific variation, so this is a disclosed limitation of available tooling, not a gap the reasoning depends on. If the user has Safari access, re-checking the fixed page there once deployed would be a reasonable final confirmation, but is not expected to reveal anything different.
