# Version 3.3 Sprint M5D: Review Reminder Validation Report

Independently verifies scheduled execution, one-reminder-per-purchase, opt-out, duplicate prevention, and audit logging for `services/customer/reviewReminderService.ts` and `worker/index.ts`'s new `scheduled()` handler. **This report contains this review's central Blocking finding.**

---

## Scheduled Execution — Verified Working (Resolves a Disclosed Known Limitation)

The M5C Known Limitations doc discloses that the `scheduled()` handler was never exercised end-to-end locally (the dev launch configuration doesn't pass `--test-scheduled`). This Board performed that exact verification: started a temporary `wrangler dev --port 8788 --test-scheduled` instance and called the real `/__scheduled` endpoint directly. **Result: the handler fires correctly, logs correctly, and completes without error.** This specific Known Limitation is resolved by this review — no further action needed on that item.

## One Reminder Per Purchase — Verified for Sequential Re-Runs, Disproven for Failed Sends and Concurrent Runs

### Sequential re-run (the common case): correct

A due purchase reminded once, then checked again on a later sequential run (after the first email genuinely **sent successfully**), is correctly excluded the second time. Confirmed via the M5C unit suite (independently re-run, passing) and consistent with the eligibility query's `NOT EXISTS` check against `email_log`.

### Finding 1 (Blocking): a single failed send attempt permanently and silently suppresses all future reminders for that purchase

Reproduced live via `wrangler dev --test-scheduled` against a genuinely due, seeded purchase, with the project's own placeholder Resend API key (an intentionally realistic transient-failure scenario, not a contrived one):

1. First `/__scheduled` call: `{"eligible":1,"sent":0}` — the send attempt failed (`401`, invalid API key), and `sendEmail()`'s own existing, correct discipline recorded this as an `email_log` row with `status = 'permanently_failed'`.
2. Second `/__scheduled` call, immediately after: `{"eligible":0,"sent":0}`.

**The purchase became permanently ineligible after its first attempt failed, despite the customer never having actually received the email.** The eligibility query's `NOT EXISTS (SELECT 1 FROM email_log WHERE entity_type = 'purchase_session' AND entity_id = ps.id AND template = 'customer-review-reminder')` does not distinguish `status = 'sent'` from `status = 'failed'` or `'permanently_failed'` — any row at all, regardless of outcome, marks the purchase as "already handled."

**Why this is Blocking, not merely Non-blocking:** `v3.3-risk-assessment.md` (M5A) explicitly names this exact mitigation as required before production release: *"verify the Cron Trigger's idempotency (never double-sends a review-request email to the same purchase) before production release, the same discipline already applied to every webhook-idempotency case in this platform's history."* This Board's testing shows the opposite failure mode is also unguarded: not a double-send, but a **permanent, silent, un-alerted zero-send** for any purchase whose first attempt happens to fail for a transient, non-customer-caused reason (a Resend outage, a misconfigured key, a brief rate limit at Resend's end — none of which are rare in the lifetime of a recurring daily job). Given the entire business reason this feature exists (per `v3.3-customer-journey-review.md` and `v3.3-product-review.md`) is that **zero reviews have ever been submitted in this platform's history**, a defect that can cause the fix for that exact problem to silently never fire for some purchases is a direct threat to the milestone's own stated purpose, not a cosmetic edge case.

### Finding 2 (Blocking, same root cause, different manifestation): genuine concurrent invocation sends duplicate emails

Cloudflare's own documented Cron Trigger guarantee is **at-least-once delivery, for both free and paid plans** (confirmed via the `cloudflare` skill's `references/cron-triggers/gotchas.md`: *"Duplicate Executions — Cause: At-least-once delivery — Solution: Track execution IDs in KV"*). This is not a theoretical edge case this project's own documented risk mitigation ignored — it is Cloudflare's stated platform behavior for every Cron Trigger, including a daily one.

This Board reproduced the corresponding failure mode directly: two genuinely concurrent (`Promise.all`) invocations of `sendDueReviewReminders()` against a single due purchase both read the same "eligible" state (since neither has yet written an `email_log` row when the other reads), and **both proceed to send.** Reproduced result: `A.sent=1 B.sent=1 totalEmailLogRows=2` — the same customer receives two identical "How's it going?" emails for the same purchase.

**Combined assessment:** the Implementation Report's own claim — *"Idempotent by construction: a re-run (retry, overlapping invocation, or a customer reconciling a purchase mid-run) simply finds fewer or zero eligible rows the second time"* and *"safe against Cloudflare's documented at-least-once scheduled-event delivery with no separate lock or dedupe needed here"* (this exact sentence appears verbatim in `worker/index.ts`'s own code comment) — **is false for both a failed first attempt and a genuinely concurrent overlapping invocation.** It is true only for the narrower case of a clean, sequential, successful first run followed by a later sequential re-run.

## Opt-Out — Verified Working

Live-tested end to end: seeded a customer with a known opt-out token, called `GET /api/customer/review-reminders/opt-out?token=...`, confirmed `review_reminder_opt_out` flips from `0` to `1` in D1 and the route returns a 200 confirmation page. An unrecognized token also returns 200 with the identical generic confirmation (no enumeration signal), confirmed live.

## Audit Logging — Gap Found

`customer.review_reminder_sent` is only written when `result.sent === true`. **A failed send attempt (Finding 1 above) leaves zero audit trail of any kind** — not even a record that an attempt was made and failed. Combined with Finding 1, this means the failure mode is not just silent to the customer; it is invisible to any admin or future investigation relying on the audit log, since `email_log` itself is the only record, and nothing in this milestone's own admin dashboard surfaces `email_log` failures for this specific template. Classified as part of the same Blocking finding, not a separate one — it is what makes Finding 1 practically undiscoverable in production without this review's own direct database inspection.

## Recommended Fix (For the Implementation Team, Not Applied by This Review)

The eligibility gate should distinguish `status = 'sent'` (or `'skipped'`, since a disabled template is an intentional non-send) from `'failed'`/`'permanently_failed'` — only the former should suppress future eligibility; the latter should remain eligible for a bounded number of retries on a later run. Separately, genuine concurrent-invocation duplication should be closed with an atomic claim (e.g., an `INSERT`-based lock row per purchase, checked via its own unique constraint, claimed before the email send is attempted, not after).

---

## Verdict

**Blocking.** The feature is well-architected and mostly correct, but does not currently satisfy the explicit, pre-named idempotency requirement this exact feature was required to meet before production release. This must be fixed and re-verified before the Cron Trigger is ever enabled against production data.
