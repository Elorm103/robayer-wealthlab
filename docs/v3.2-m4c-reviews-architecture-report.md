# Version 3.2 - Milestone M4C Reviews Architecture Report

**Milestone:** M4 - Commerce & Trust Foundations
**Sprint:** M4C

---

## Purpose

This report documents the product-reviews feature's architecture as actually built - the purchase-gating mechanism, the moderation workflow, and the split between server-rendered display and client-rendered submission.

## Purchase-Gating: Never Trust the Client for What Matters

The one design decision this feature had to get right: a review must never be creatable without a real, owned, verified purchase behind it, and the client must never be the source of truth for which purchase that is. `submitOrUpdateReview(env, logger, customerId, { productSlug, rating, body })` takes only a `customerId` (resolved server-side from the authenticated session, never from the request body) and a `productSlug`. It looks up the customer's own latest `status = 'verified'` `purchase_sessions` row for that product itself:

```sql
SELECT id FROM purchase_sessions
WHERE customer_id = ? AND product_slug = ? AND status = 'verified'
ORDER BY id DESC LIMIT 1
```

If nothing matches, the submission is rejected with `NO_VERIFIED_PURCHASE` before any row is written. This is the same "never trust the client for what matters" discipline `commerceService.ts` already applies to price - here applied to purchase ownership instead.

## One Review Per (Product, Customer), Enforced at the Database Layer

`product_reviews.UNIQUE(product_id, customer_id)` is not just an application-level check - it's a real database constraint, and the write path is built around it: a single atomic statement,

```sql
INSERT INTO product_reviews (product_id, customer_id, purchase_session_id, rating, body, status)
VALUES (?, ?, ?, ?, ?, 'pending')
ON CONFLICT(product_id, customer_id) DO UPDATE SET
  purchase_session_id = excluded.purchase_session_id,
  rating = excluded.rating,
  body = excluded.body,
  status = 'pending',
  moderated_by = NULL,
  moderated_at = NULL,
  updated_at = datetime('now')
```

never a separate check-then-insert-or-update branch. A repurchase or a resubmission is the same call, always safe under concurrent requests, and always resets the review to `pending` - edited content requires re-moderation, matching this codebase's existing "moderation reflects current content" expectation applied everywhere else an admin approves something (blog posts, resources, products).

## Public Visibility: Approved-Only, No Identity Exposed

`listPublicReviews(env, productSlug)` selects only `status = 'approved'` rows, and its `PublicReview` shape is deliberately narrow - `id`, `rating`, `body`, `createdAt`. No customer name, no email, nothing that could identify who wrote it. This matches this project's general "no unnecessary customer PII on public pages" posture; a future milestone that wants attributed reviews (e.g. "verified purchaser" badges with a first name) would need a deliberate, separate decision to expose that, not an accidental leak through this endpoint.

The average rating is computed at read time (`Math.round((sum / count) * 10) / 10`, one decimal place) rather than stored and maintained incrementally - with the realistic review volumes this catalog will see for the foreseeable future, recomputing on every read is simpler and can never drift from the underlying approved rows, at a cost this scale will never notice.

## Moderation Workflow

Every new review starts `pending`. An admin with `editor` or `super_admin` role (`EDITOR_ROLES`, matching the Orders refund-action precedent - a moderation decision has real customer-facing/trust consequences) calls `moderateReview(env, logger, actorId, id, status)`, which sets `status`, `moderated_by`, `moderated_at`, and writes an audit log entry (`review.approved` or `review.rejected`) via the existing `auditService.record()` - the same audit trail every other admin mutation in this codebase already writes to. Viewing the moderation queue (`listReviewsForModeration`, paginated, status-filterable) is open to every authenticated admin role, including `support` - only the moderation decision itself is gated.

The admin UI (`admin/reviews/index.html` + `admin-reviews.js`) is deliberately a flat table with inline Approve/Reject buttons, not a detail drawer like Consultations. A review is a rating, a body, and a decision - there's no multi-field record worth a dedicated drawer view for, and adding one would only add clicks.

## Why Submission Is Client-Rendered but Display Is Not

Every other page under `/books/*` is fully server-rendered from D1 on each request (`backend/routes/books.ts` - see that file's own header comment on why: no client hydration, no build step, this project's established convention for public content). Reviews follow that same pattern for the *read* side: `renderBookDetail()` calls `listPublicReviews()` directly and renders the aggregate rating and the approved-reviews list into the HTML response itself, the same way it already renders related products.

The *write* side genuinely can't follow that pattern, though - "can this visitor write a review" depends on their customer-session cookie, which the product page's own server-side handler never inspects (it's intentionally a fully public route with no auth check at all). Rather than adding session-verification to an otherwise-public page - a real architectural change with its own caching/security implications - `js/components/product-reviews.js` handles just this one piece client-side: it calls `GET /api/customer/auth/session` (a lightweight, non-redirecting probe - unlike `dashboard-auth.js`'s `requireSession()`, which forces a redirect on a missing session, correct for `/dashboard/*` but wrong here) and renders either a sign-in prompt or the submit/edit form accordingly. This is a narrow, deliberate exception to the "no client hydration on public pages" convention, scoped to exactly the one piece of the page that cannot be resolved without knowing who's asking.

## Structured Data

`backend/routes/books.ts`'s existing `Book` JSON-LD block gains an `aggregateRating` sub-object (`ratingValue`, `reviewCount`), emitted only when at least one approved review exists - schema.org disallows a fabricated or empty `aggregateRating`, and this codebase's existing JSON-LD discipline (see the same file's `faqJsonLd`/`breadcrumbJsonLd`) is to only ever emit structured data that matches what's genuinely rendered on the page.
