# Version 3.2 - Sprint M4D - Security Review

Independent security assessment of M4C's delivered code, performed as an adversarial exercise (attempting to discover vulnerabilities) rather than a checklist confirmation of the implementation's own security-review claims.

---

## Authorization & Ownership

- **Review submission cannot target another customer's identity.** `submitOrUpdateReview()` takes `customerId` only from the authenticated session (`requireCustomerAuth`), never from the request body - confirmed by reading `routes/customer/reviews.ts`'s body-destructuring, which reads only `productSlug`/`rating`/`body`.
- **Review moderation is `EDITOR_ROLES`-gated**, confirmed via `adminReviews.test.ts`'s support-role-rejection test, independently re-run.
- **Coupon mutation is `EDITOR_ROLES`-gated**, confirmed via `adminCoupons.test.ts`'s equivalent test, independently re-run.
- **No IDOR surface found in the review-submission endpoint** - there is no "review id" parameter a customer ever supplies; the upsert target is determined entirely by `(product_id, customer_id)`, and `customer_id` is session-derived. A customer cannot reference or affect any row but their own for a given product.

## Coupon Abuse Scenarios (Attempted)

- **Redemption-limit race** - the primary named threat. Independently re-verified via true-concurrency test (`couponRaceConditions.test.ts`), not merely trusted from the implementation's own claim. Confirmed: `redemptions_count` cannot exceed `max_redemptions` under genuine concurrent load; no payment is ever reversed as a side effect of losing the race.
- **Price/discount tampering via forged request fields** - attempted via the existing `coupons.test.ts` adversarial test (`discountPesewas: 999999`, `amountPesewas: 1` in the checkout body); confirmed both fields are silently ignored, and independently confirmed by re-reading `commerceService.ts`'s `createCheckoutSession()` body-destructuring, which never reads either field name at all - they are not merely validated-and-rejected, they are not part of the function's input type.
- **Coupon-code brute-forcing / enumeration** - `POST /api/coupons/validate` is rate-limited (30/60s, presumably per-IP per this codebase's established `isRateLimited()` convention). This Board considers this an acceptable residual risk, not a vulnerability: coupon codes are admin-chosen promotional strings intended to become public via marketing distribution, not secrets: discovering another valid code via brute-force yields no more information than the code itself, which the platform intends to eventually publish anyway. Consistent with the security review's own "Unauthorized application - not a security boundary, public promo codes" reasoning, which this Board independently agrees with.
- **Stacking (applying a coupon twice, or two coupons to one purchase)** - the checkout API accepts exactly one `couponCode` field; there is no mechanism to submit more than one. `coupon_redemptions.UNIQUE(purchase_session_id)` additionally guarantees at most one redemption record per purchase at the database layer, independent of application logic.
- **Replay** - a `purchase_reference` cannot be reused to re-trigger `redeemCoupon()`: `handlePaymentWebhook()`'s own pre-existing idempotency layer (unchanged by M4C) prevents a purchase session from being verified twice; `redeemCoupon()` is only ever reached once per session, on the first successful verification.
- **`first_purchase_only` bypass via a fresh email per purchase** - this Board confirms this is a real, structural limitation of guest checkout (a customer can always use a new email), not a defect - it is explicitly detection-only by design (see Amendment Compliance Report), matching a risk category this project's own ARB already accepted in the original V3.0 checkout architecture review.
- **Expired-coupon race** (a coupon expires between preview and checkout submission) - `validateCoupon()` is called independently, a second time, inside `createCheckoutSession()` itself - a coupon that expired between the preview call and the actual checkout submission is correctly re-rejected at checkout time, never trusting the earlier preview result.

## Cross-Site Scripting (XSS)

**Adversarial test performed:** seeded a real, approved review with the body `This guide genuinely changed how I think about investing in Ghana. <script>alert(1)</script> Highly recommend!` and loaded the live product page in-browser.

- **Server-rendered path** (`routes/books.ts`): confirmed the payload renders as literal, visible, escaped text (`&lt;script&gt;alert(1)&lt;/script&gt;`) via `escapeHtml(r.body)` - the script tag never executes, confirmed by the absence of any console error/alert and direct inspection of the rendered DOM's `innerHTML`.
- **Client-rendered path** (`js/components/product-reviews.js`): the review-edit form's prefilled textarea value uses `escapeHtml(existing.body)` before insertion via `innerHTML` - confirmed correct by code inspection. Every other dynamic value in this file (error messages, status text) is set via `.textContent`, never `.innerHTML`.
- **Admin review table** (`js/components/admin/admin-reviews.js`): review body is rendered via `bodyCell.textContent = item.body` - DOM text-node assignment, inherently immune to markup injection regardless of content.

**No XSS vulnerability found.**

## SQL Injection

**Adversarial review performed:** grepped every new M4C service/route file for template-literal SQL containing `${...}` interpolation, then manually inspected each match.

- `couponService.ts:333` (`UPDATE coupons SET ${sets.join(', ')} WHERE id = ?`) - `sets` is built exclusively from hardcoded, developer-authored strings (`'status = ?'`, `'max_redemptions = ?'`, `'expires_at = ?'`, `"updated_at = datetime('now')"`); every actual value passes through `.bind()`. No user input reaches the interpolated SQL structure itself.
- `reviewService.ts:187,201` (`WHERE ${conditions.join(' AND ')}`) - identical pattern; the only pushed condition is the hardcoded literal `'pr.status = ?'`, with `query.status` (already validated against a fixed enum by the route handler before this function is ever called) passed through `.bind()`.

Every other query across every new file uses `.prepare(...).bind(...)` parameterization with no exceptions found. **No SQL injection vulnerability found.**

## CSRF

Independently re-confirmed via test re-execution, not merely code reading: every mutating M4C endpoint (`POST /api/customer/reviews`, `POST /api/admin/reviews/:id/moderate`, `POST /api/admin/coupons`, `PATCH /api/admin/coupons/:id`) has a dedicated "rejects a request without the CSRF header" or equivalent test, all independently re-run and passing.

## Input Validation

- Rating: `isValidRating` restricts to integer 1-5, independently confirmed to reject `0`, `6`, `3.5`, and the string `"3"`.
- Review body: length-bounded (1-3000 chars after trim), independently confirmed via a 3001-character adversarial test.
- Coupon code: `/^[A-Z0-9_-]{3,32}$/`, independently confirmed to reject a 2-character code.
- Discount value: integer-only, capped at 100 for `percentage`, independently confirmed via a 150% adversarial test.

## Overall Security Verdict

**No exploitable vulnerability found.** This Board's adversarial pass, conducted independently rather than as confirmation of the implementation's own security-review document, corroborates every specific claim `v3.2-m4c-amendment-2-coupon-security-review.md` makes, and additionally probed XSS and SQL injection surfaces that document does not explicitly walk through (both confirmed safe). **No Blocking security finding.**
