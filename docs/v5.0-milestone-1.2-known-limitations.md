# Version 5.0 Milestone 1.2 — AI Governance & Safety

**Known Limitations**

Restated plainly, in order of how much they matter. Several of these are named across the other six reports; this is the single consolidated list.

1. **The pre-call cost estimate is a heuristic, not an exact prediction.** `estimateInputTokens()` uses ~4 characters per token as an approximation — there is no real tokenizer dependency in this project. It deliberately over-estimates (rounds up) to bias toward safety, but a real prompt that tokenizes unusually densely could still under-predict actual cost. The post-call safety net exists specifically to catch this remaining gap, but by the time it fires, the provider has already been billed for that one call. This is a fundamental property of any non-streaming, pay-per-response-token API — not fixable without either a real tokenizer dependency or switching to a streaming architecture with mid-stream cancellation, neither of which is in this milestone's scope.

2. **The provider policy table's actual content is a placeholder, not a completed compliance review.** Every classification currently allows `openai` because it's the only integrated provider — not because each classification's risk with OpenAI has been individually assessed against a real data-processing agreement. The enforcement mechanism is real; the policy content needs a genuine decision before it means what a compliance-minded reader would assume it means.

3. **Sensitive-data masking is best-effort regex matching, not a guarantee.** It will miss any secret without a recognizable structural pattern (a bare high-entropy string with no `api_key=`-style label, for instance). It also has a deliberately broad payment-card-number pattern that will false-positive on other 13-19 digit sequences (long IDs, some phone number formats). Over-masking is the safer failure mode for a compliance-sensitive category, but it is worth knowing this will occasionally redact benign text.

4. **No fallback-provider data-policy gate exists for the moment a second provider is added.** Moot today (one provider, one candidate per feature — no fallback has ever actually run in production), but before a second provider is wired into `routingConfig.ts`, a real decision is needed about whether a given feature's data is allowed to reach a *different* company's servers on fallback, not just the primary one.

5. **`ai_usage_log` is shared between real usage rows and governance-rejection rows**, distinguished only by column values (`succeeded = 0` + `budget_decision`/`provider_decision` text), not a dedicated row type. Reused deliberately (one audited mechanism, not two), but means a rejection and a genuine provider failure look similar at the schema level until you read the decision text.

6. **Storing prompt/response text (even encrypted) widens this table's sensitive-data surface**, and the default `metadata_only` mode exists specifically to avoid this until an admin deliberately opts in. There is still no automatic key-rotation mechanism for `AI_PROMPT_ENCRYPTION_KEY` — rotating it would leave previously-encrypted rows undecryptable under the new key (no re-encryption-on-rotation exists). Not needed yet at today's volume; worth designing before this key is ever actually rotated in production.

7. **Default budget dollar figures are engineering judgment, not founder-approved business numbers.** Restated here because it is the single most likely thing to cause a surprised admin: real usage could hit the $1.00/day or $20.00/month defaults and start seeing calls preventively blocked, with no warning beyond the dashboard's own "Blocking" badge.

8. **The scheduled cleanup job runs once daily** (piggybacking the existing Cron Trigger), meaning a row can sit past its `cleanup_eligible_date` for up to ~24 hours before actually being purged. Not a correctness issue (retention is measured in days, not hours), but worth knowing it is not instantaneous.

9. **No per-feature or per-classification budget** exists yet — every layer (per-request, daily, monthly, provider, platform) is either global or per-provider, never scoped to a specific feature or a specific classification. Once more than one real AI feature exists, this may become a real gap (a runaway Knowledge Base feature could exhaust the platform budget a completely unrelated feature also depends on).
