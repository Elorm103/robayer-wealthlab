# Version 3.5: Dashboard Performance Report

## Query strategy

Every one of the six new endpoints issues its underlying queries via a single `Promise.all()`, matching the existing convention already established in `analyticsService.ts`'s `getSummary()`/`getActivationSummary()` — independent aggregates run concurrently against D1 rather than sequentially, so total latency is bounded by the slowest single query, not the sum of all of them.

No new table, index, or pre-aggregation was added. Every query is a direct aggregate over existing tables (`purchase_sessions`, `customers`, `products`, etc.), consistent with this project's stated position (see `docs/v2-analytics-spec.md`'s "Refresh & caching" section) that real row counts at this stage of the business don't yet justify the complexity of a caching or pre-aggregation layer. This was re-confirmed, not just assumed: every new endpoint was smoke-tested against live production data during Phase 15 and returned well under a second.

## Where caching was and was not used

**Health only** (`GET /api/admin/dashboard/health`) is cached — 60 seconds, in the existing `RATE_LIMIT_KV` namespace. This is the one endpoint making live outbound HTTP calls on every uncached request (a real, safe API call to both Paystack and Resend, plus the site's own homepage), so it is also the one endpoint where repeated dashboard loads or a page left open and polling would otherwise generate real external network traffic on every request. A stale cache window of up to 60 seconds is an explicit, deliberate tradeoff: "is the site down right now" is never meaningfully wrong by under a minute for a human looking at a dashboard, and the alternative (no cache) would mean every dashboard page load makes two live third-party API calls plus a self-fetch.

Every other endpoint is intentionally **not** cached. They are pure D1 reads with no outbound network calls, no per-request cost beyond the query itself, and (per the "no caching layer yet" position above) caching them would add real complexity — cache invalidation on every write path that touches these tables (checkout, admin edits, reviews, coupons) — for a performance problem that does not yet exist at this data volume.

## Avoiding unnecessary polling

The dashboard fetches each section exactly once on page load. There is no auto-refresh timer, no `setInterval` anywhere in `admin-dashboard.js`. The only re-fetch a user can trigger is the sales-analytics/customer-analytics date-range preset buttons (7/30/90 days), which re-request only those two endpoints, not the whole page. This matches the brief's explicit "avoid unnecessary polling" instruction directly — an admin who wants fresher data reloads the page, exactly like every other admin list page in this codebase already works.

## Rendering cost

Charts remain the project's existing dependency-free inline-SVG approach (`timeseries-chart.js`), extended with one new function (`renderBarChart`) using the same technique — no charting library was added, keeping this page's JS payload unchanged in kind (a few more component scripts, zero new third-party dependencies). At this data volume (tens of points per chart, not thousands), SVG generation cost is negligible; this was not separately profiled, since the existing chart component was already accepted at this same complexity level for the Analytics page.

## Live measurements

During Phase 15 verification, all six endpoints were called directly against production (`robayerwealthlab.com`) with a real authenticated admin session. Every response returned promptly with no visible delay in the browser, and the rendered page (health panel through operational feeds, roughly 15 sections) painted with no jank on desktop, tablet, or mobile viewports. No formal Lighthouse/Web Vitals run was performed as part of this milestone — the brief's own Phase 13 instructions ("avoid unnecessary polling," "aggregate queries," "cache only where safe") were treated as an architecture constraint to satisfy during design, not a numeric budget to hit after the fact, and the qualitative result (fast, no visible stalls, six lightweight parallel fetches) satisfies that constraint.
