# Version 3.2 - Sprint M4A - M4 Scope Recommendation

---

## Recommended M4: "Commerce & Trust Foundations"

**Two features, both High business value / S effort / Low-Medium risk per the Prioritization Matrix:**

1. **Product Reviews & Ratings** - one new table (`product_reviews`, shape-identical to the existing `consultation_requests`/`contact_messages` precedent), a public display component on product pages, a customer-facing "leave a review" flow (session-gated, tied to a verified purchase - no review without a real purchase, closing the most obvious abuse vector by construction rather than by moderation alone), and an admin moderation page following the exact list/detail/status pattern already proven three times (`admin/consultations.ts`, `admin/contacts.ts`, and now this).
2. **Coupon Engine** - implements the already-ratified, already-designed (`v3-database-design.md`), already-approved-as-"Ready" (Sprint Readiness Report) M4 from the existing Blueprint, unchanged. `coupons`/`coupon_redemptions` tables, checkout-flow integration (percentage/fixed, expiry, first-purchase-only), admin coupon management page.

**Explicitly excluded from M4** (per the Prioritization Matrix): notifications, email automation, wishlist, customer profiles, search, recommendations, and everything in the course-platform cluster - all recommended for M5/M6/M7+ instead.

## Why This Combination, and Not a Larger or Different M4

- **Both features are independently ready today.** Coupons has zero open design questions (already fully schema-designed and pre-approved). Reviews requires only a small, well-precedented design pass, not a novel architecture decision.
- **Both are additive, low-risk changes** that fit the proven route-file/D1-table/dashboard-page pattern exactly - the Architecture Review found no redesign is justified for either.
- **Together they close the two highest-leverage gaps this review found**: Coupons directly monetizes and converts (a checkout-stage lever); Reviews directly builds the trust that gets a cold visitor to the checkout stage in the first place (a top-of-funnel lever). They are complementary, not redundant.
- **Neither requires the VAT question to be resolved first**, though Coupons' interaction with tax display should be kept simple (a coupon reduces the pre-tax subtotal; since `computeTaxBreakdown()` returns an empty array today regardless, there is no real interaction to design around yet).
- **A course platform, video lessons, or any of that cluster would be a strictly worse M4 choice today**: XL effort, High risk, zero demand evidence, and this project's own historical planning has twice already reached the same conclusion independently. Choosing it now would repeat a mistake this project has specifically avoided making before.

## Scope Discipline (matching this project's own established pattern)

**Explicitly NOT in M4:**
- No coupon-fraud-prevention system beyond what the ARB already reviewed and accepted (the `first_purchase_only` multi-account weakness remains a known, accepted risk - not this milestone's problem to solve).
- No review-moderation automation (spam filtering, sentiment analysis) - manual admin moderation only, matching the existing consultations/contacts precedent exactly.
- No notifications, no email automation, no in-dashboard "you have a new coupon" surface - Reviews and Coupons are visible through existing pages (product pages, checkout, a new dashboard "My Reviews" page if scoped in), not a new notification system.
- No multi-item cart or bundle support - Coupons apply to the existing single-product checkout flow unchanged.
- No AI-generated review summaries, no automated review-response suggestions - out of scope, no AI infrastructure exists and none should be introduced for this milestone.

## Deliverables (draft, to be refined in M4B planning)

1. Migration: `product_reviews` table (customer_id, product_id, purchase_session_id FK for purchase-verification, rating, body, status, moderated_at/moderated_by).
2. Migration: `coupons`/`coupon_redemptions` tables, per `v3-database-design.md`'s existing design.
3. Backend: review submission/list endpoints (customer-facing, purchase-gated), admin review-moderation routes, coupon validation/redemption logic wired into the existing checkout flow, admin coupon CRUD routes.
4. Frontend: review display + submission UI on product pages and/or a new dashboard page; coupon-code entry field at checkout; two new admin pages.
5. Tests: full coverage for both new feature areas, explicitly including the admin-panel test coverage this review's Technical Debt Review names as overdue - this milestone should not repeat the pattern of an external review finding a self-imposed test gap.
6. Documentation: the same 9-document M4A-equivalent planning set this project produces for every milestone (architecture review, UX strategy, API gap analysis, security review, database impact assessment, risk assessment, testing strategy, implementation roadmap), scoped specifically to Reviews + Coupons.

## Required Governance Action Before M4B Begins

This recommendation **keeps M4 = Coupons** (matching ADR-005/the ratified Blueprint exactly) but **adds Reviews to M4's scope**, and separately recommends re-sequencing M5/M6 relative to the ratified plan (see the Version 3.2 Roadmap for the full justification). Per the Blueprint's own governance statement ("any deviation requires a new ADR"), **this review recommends the Product Owner ratify a short amendment** covering: (a) Reviews added to M4's scope, and (b) the M5/M6 re-sequencing (Retention/Engagement pulled ahead of Support Ticketing). This is a small, explicit governance step, not a reason to delay - the same discipline this project applied to every prior architecture decision.
