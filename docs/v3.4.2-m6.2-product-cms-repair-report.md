# Version 3.4.2 Milestone M6.2: Product CMS Repair Report

## Reported symptom

The admin-reported failure was: cover changes do not appear after saving, price changes do not appear after saving, the save appears to do nothing, and the admin displays "Media asset 20 could not be found."

## Root cause, traced end to end

The trace followed Admin Form to Request Payload to API Endpoint to Validation to Database Update to Media Reference to Product API to Homepage to Book Details Page to Checkout, per the brief's required path.

1. `backend/services/productService.ts`'s `validateProductInput()` already checked that every non-null media reference (cover, thumbnail, preview, OG image) points to a real, non-deleted `media_assets` row. This check was correct and was working as designed.
2. When a stale media id was present in the payload, this validation correctly rejected the entire save (the whole update is atomic, so a bad media reference blocks title, price, and every other field in the same request, not just the image). This is why price and cover changes appeared to silently fail together.
3. The failure was never surfaced to the admin. `admin/products/edit/index.html` had no error slot near the cover picker, and `js/components/admin-product-editor.js`'s save() handler had no code path that displayed a `media`-field validation error at all. The request failed with a 400 and a real message, and the UI showed nothing.
4. Even if the error had been shown, the admin had no way to recover: the dead media id stayed in `state.mediaRefs` and every retry re-sent the identical stale reference, so Save would keep failing the same way.

The bug was not a broken save. It was a correctly working validation with no error UI and no recovery path.

## Fix

- Added `<span class="field__error" data-pe-error-field="media" hidden>` to the cover picker section in `admin/products/edit/index.html` and `admin/products/new/index.html`.
- `js/components/admin/admin-product-editor.js`'s `save()` now displays the real backend message for a `media` field error, appended with "Please choose a different image below."
- Added `clearDeadMediaReference(message)`, which parses the dead id out of the "Media asset N could not be found" message, nulls out any picker slot (cover, thumbnail, preview, OG) currently holding that id, re-renders the slot, and refreshes the live preview, so a retry sends a clean payload instead of repeating the same failure.

## A second, deeper finding during live verification

While verifying the fix against the real flagship product (id 1, "Small Cedis, Big Wealth") on production, saving failed with "Media asset 17 could not be found" and "Media asset 20 could not be found" against its thumbnail and OG image references, and a separate, unrelated 400 came back from `PUT /api/admin/products/1/files` for "Media asset 13 could not be found" against its actual downloadable PDF.

Checking `media_assets` showed all three (13, 17, 20) were soft-deleted on 2026-07-30, during earlier testing in this same session, before the media in-use protection built in this milestone's Media Library Repair existed. Checking R2 directly confirmed all three underlying files (`ebooks/starting-to-invest-with-gh100.pdf` and two cover images) were still physically present and untouched; only the database metadata row had been incorrectly marked deleted.

This was repaired by restoring the three `media_assets` rows (clearing `deleted_at`), not by re-uploading or reconstructing anything, since nothing was actually lost. See the Media Library Repair Report for the accompanying architectural fix that prevents this from happening again.
