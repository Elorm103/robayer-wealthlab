# Version 3.3 Sprint M5D: Customer Activation Validation Report

Independently validates the `PASSWORD_NOT_SET` flow, activation email/links, the first-login dashboard banner, and repeat-login behavior, for new, reconciled, and existing customers — live, not from documentation.

---

## PASSWORD_NOT_SET Flow

**Verified live end-to-end.** Seeded a customer with `password_hash IS NULL`. Called `POST /api/customer/auth/login` directly: response was `{"success":false,"error":{"code":"PASSWORD_NOT_SET","message":"This account hasn't set a password yet..."}}`, a distinct machine-readable code, not the generic `INVALID_CREDENTIALS` used for a genuinely wrong password or nonexistent account (confirmed both return `INVALID_CREDENTIALS` still, unchanged). Re-checked every pre-existing test in the suite asserting `INVALID_CREDENTIALS` (`rateLimiting.test.ts`, `rateLimitingM3.test.ts`, `negative.test.ts`, `dashboardM3.test.ts`) and confirmed none of them exercise the `password_not_set` path specifically — the code change introduced no regression.

## Activation Link (Sign-In Form)

Loaded `/checkout/sign-in/` in the browser and submitted the no-password account's credentials through the real form. The rendered error banner correctly included a "Send me a setup link." link pointing to `/checkout/forgot-password/`, generated client-side from the new `PASSWORD_NOT_SET` code rather than parsed from the message text (confirmed by reading `js/components/sign-in-form.js` — the check is `error.code === 'PASSWORD_NOT_SET'`, not a string match on the message, which is the more robust and correct implementation choice).

## isFirstSession — New, Reconciled, and Existing Customers

Tested all three cases live, not only via unit test:

- **New customer (webhook-provisioned equivalent):** first `GET /api/customer/auth/session` after first login returns `isFirstSession: true`; a second login for the same customer returns `isFirstSession: false`. Confirmed via direct HTTP calls.
- **Reconciled customer:** seeded an orphaned purchase, reconciled it via the real `POST /api/customer/reconcile-purchases` endpoint, redeemed the resulting password-setup token via `POST /api/customer/auth/set-password`, then logged in for the first time. Result: `isFirstSession: true` on this first login, and confirmed the reconciled purchase actually appears in `GET /api/customer/purchases` (the customer's real library) — the full reconciliation-to-dashboard-access journey works end to end, not just the reconciliation step in isolation. A second login for the same reconciled customer correctly returned `isFirstSession: false`.
- **Existing customer:** unaffected — `countSessionsForCustomer()` counts every `customer_sessions` row ever created for that customer regardless of cause, so an existing customer with prior sessions correctly never sees `isFirstSession: true` again.

## Dashboard Banner

Verified in the browser: logging in as a genuine first-time customer and loading `/dashboard/` renders the "Welcome to your account!" banner with links to Receipts and Security; a second login for the same customer does not render it (confirmed via `get_page_text`, not just code inspection). The banner's markup uses `.textContent`/static template strings only — no user-controlled data is interpolated into `innerHTML`, so it introduces no XSS surface.

## Repeat Login Behaviour

Confirmed correct in all cases tested above: the signal is derived from a real, persistent count of `customer_sessions` rows, not a client-side flag, so it survives page reloads within the same session and correctly flips only on an actual new login, not on every page view.

## Verdict

**Fully verified, no findings.** Every activation-related claim in the M5C Implementation Report was independently reproduced against live code and a live server, including the three distinct onboarding paths (new, reconciled, existing) this review was specifically asked to check.
