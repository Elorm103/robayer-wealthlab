# Version 3.0.2 - Sprint M2A - M2 Implementation Roadmap

Planning only. Nothing in this document was executed. It exists so Sprint M2B can begin building with minimal open questions.

---

## Security review, consolidated (requested by the sprint brief; folded here rather than as a ninth standalone document, since the sprint's own numbered Deliverables list names eight)

- **Receipt authorization**: two tiers, matching ADR-013 exactly - authenticated customer session (direct stream, no token) for the Customer Library path; single-use, short-TTL, randomly-generated token (new `receipt_download_tokens` table) for the guest reference-scoped path. Never bearer-credential-free access to a receipt PDF.
- **Customer ownership validation**: every authenticated M2 query filters by the session's own `customerId`, server-side, never a client-supplied identifier - identical discipline to every M1 customer-auth check.
- **Download authorization**: reuses the existing `deliveries.status != 'revoked'` gate (already live since M1, per ADR-003), extended with the new revocation-sync writer, never a new, separate gate that could drift out of sync with the existing one.
- **ID enumeration prevention**: a purchase/receipt/license belonging to another customer returns the identical response a nonexistent one would, at every authenticated endpoint - no distinct "forbidden" signal anywhere in M2's new surface, matching M1's own no-enumeration precedent (login, forgot-password).
- **Receipt privacy**: receipts contain the same class of information `purchase_sessions`/`email_log` already store (email, product, amount) - no new sensitive-data category is introduced. Retention follows the Data Governance section's existing rule ("financial records - never deleted") without modification.
- **API security**: rate limiting on the one new unauthenticated mint endpoint (guest receipt-download request); every new admin endpoint reuses existing admin auth/CSRF unchanged; every new customer endpoint reuses `requireCustomerAuth` unchanged. No new authentication mechanism, no new token generation approach beyond the proven `crypto.getRandomValues`-based one already used everywhere in this codebase.

## Pre-implementation action items (must be resolved before M2B writes code)

1. **Product Owner sign-off on the refund/revocation scope boundary** (Architecture Compliance Report) - confirm that a minimal admin revoke action satisfies M2's obligation under ADR-003/the ratified success criteria, with the full `refund_requests` workflow explicitly deferred.
2. **`pdf-lib`-in-`workerd` spike** (Receipt Architecture Plan) - a same-day technical check, with the HTML-receipt fallback ready to invoke if it fails.
3. **VAT-registration status** - flagged to the business owner in parallel with implementation start, not blocking schema/non-tax-computation work, exactly as the Sprint Readiness Report already recommends. This is now the third consecutive milestone-planning pass that has surfaced this same open question - worth escalating as a standalone, time-boxed ask rather than continuing to carry it forward silently.
4. **Confirm the next migration number** by checking `backend/database/migrations/` directly at implementation time (not assumed in this planning pass, since no repository file was inspected for write purposes).

## Build order

1. Migration: `order_items`, `licenses`, `receipts`, `receipt_download_tokens` (Database Planning Report) - additive only, applied locally first, tested against the full local suite before any remote action is even considered.
2. Receipt-numbering utility (`formatReceiptNumber`), mirroring `purchaseReference.ts` - smallest, most isolated piece, natural first implementation task.
3. `pdf-lib` spike (see action item 2 above) - resolved before the real receipt-generation service is written, not discovered mid-build.
4. Revocation-sync service function + minimal admin trigger endpoint - second-smallest isolated piece, and the one item with a named ratified success criterion, worth proving early.
5. Fulfilment-pass extension: `order_items`/`licenses`/`receipts` creation wired into the existing webhook flow, following `fulfilPurchase()`'s exact "log, never undo a real payment" discipline.
6. Customer-facing read APIs (`GET /api/customer/purchases`, `/purchases/:reference`, `/receipts`, `/receipts/:receiptNumber/download`, `/licenses`) - depend on step 5's data existing, natural next step.
7. Guest reference-scoped receipt-download mint/redeem pair - depends on step 5, independent of step 6.
8. Full test suite (Testing Strategy) written alongside each step above, not batched at the end - matching M1's own proven practice of building tests as part of each service, not as an afterthought.
9. Documentation: updated M2 Implementation Report, Database Changes doc, API Reference, following the exact template M1's own documentation set established.
10. Independent Milestone Acceptance Review, mirroring M1's MARB process exactly - this planning report is not a substitute for that independent review once M2B's code exists.

## What M2B must explicitly NOT do

Per this sprint's own scope instruction, unchanged: no coupons, no promotions, no DRM, no license-type expansion beyond `'personal'`, no marketplace/creator/affiliate work, no analytics beyond what the Library/Purchase History views themselves need (i.e., no new admin-facing analytics dashboard), no Customer Library *pages* (M3 scope - M2B ships APIs only), no full `refund_requests` customer-facing workflow (pending the scope-boundary decision above), no chargeback handling (M8).

## Dependencies and sequencing relative to other milestones

- M2 depends on M1 (customer identity) - already satisfied, M1 is production-deployed and verified.
- M2 must complete, and its production deployment verified, before M3 (dashboard MVP) begins - M3's pages consume M2's APIs directly; starting M3 against an unfinished or undeployed M2 would compound risk rather than resolve it, the same reasoning the M1 Closeout Report already applied to sequencing M2 after M1's own deployment.
- M2's minimal admin revoke action has no dependency on M5 (Support Ticketing) but is naturally close to it in spirit - if M5's own planning later decides to build a fuller refund-request UI, it should reuse M2's revocation-sync function rather than duplicating it.

## Final Decision

## Milestone M2 Approved for Implementation

Every requirement M2 needs is already specified in the ratified architecture - no new ADR, no architecture change, no redesign is required. The current production codebase (M1) provides everything M2 needs to build on: the customer identity/session layer, the proven webhook-fulfilment pipeline, the reference-scoped guest-access pattern, and a fully proven test infrastructure, all confirmed by direct inspection rather than assumed from documentation.

Approval is conditioned on the four pre-implementation action items above being resolved at the *start* of M2B, not treated as open questions to discover mid-implementation:

1. Product Owner sign-off on the refund/revocation scope boundary.
2. The `pdf-lib` compatibility spike (with its fallback already planned, so this cannot become a blocker, only a fork in the technical approach).
3. The VAT-registration business question escalated for a real answer, in parallel with (not blocking) the rest of the build.
4. Confirming the actual next migration number against the real repository state at build time.

None of these four is a reason to delay *starting* M2B - each has a clear owner, a clear resolution path, and (for items 2-4) does not block the majority of the implementation work from beginning immediately, exactly as the Sprint Readiness Report's own original M2 recommendation already anticipated ("begin schema and non-tax-computation work immediately; flag the VAT question... in parallel").
