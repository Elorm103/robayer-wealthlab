# Version 3.4.2 Milestone M6.2: Dynamic Pricing Implementation Report

## Schema

Migration `0023_product_sale_pricing.sql` adds four columns to `products`:

- `sale_price_pesewas INTEGER`
- `sale_enabled INTEGER NOT NULL DEFAULT 0`
- `sale_starts_at TEXT`
- `sale_ends_at TEXT`

`price_pesewas` keeps its existing meaning (the regular price) everywhere it is already used; nothing that reads it needed to change. `compare_at_price_pesewas` was deliberately left alone rather than repurposed for the sale price, since it already has its own distinct meaning (an informational "was more expensive elsewhere" marker) and reusing it for an actual, chargeable sale price would have silently changed what every existing caller of that field means.

## Single source of truth

`computeSaleState(product, now)` in `backend/services/productService.ts` is the one place "is a sale active right now" is decided. It is a pure function computed fresh on every call, from the product's regular price, sale price, `sale_enabled`, and the optional start/end dates, against the instant it is called with. There is no cron job or background flag flip: a sale becomes active the moment `now` passes its start date and becomes inactive the moment `now` passes its end date, by construction, with no window in which the flag and the clock can disagree.

Every place that needs to know the price a customer actually pays calls this same function:

- `backend/routes/products.ts` (public product API)
- `backend/routes/admin/products.ts` (admin API, including a `saleState` preview object)
- `backend/routes/books.ts` (the server-rendered book detail page and listing page)
- `backend/services/productCatalogService.ts` (checkout's own price lookup, via `effectivePrice`)

## Validation

`validateProductInput()` rejects:

- a negative or non-integer sale price
- a sale price greater than or equal to the regular price
- enabling a sale with no sale price set, or with no regular price set
- an unparseable sale start or end date
- an end date that is not after the start date
- (added this milestone, see the Product CMS Repair Report) publishing a product as `active` with no cover image

## Display layer

- `js/components/product-loader.js`'s `renderCard()` and a matching `renderProductCard()` in `backend/routes/books.ts` both render: category badge, subtitle, author, a star rating (only shown once a product has at least one approved review), and a price block that shows either a plain regular price or, when a sale is active, a struck-through regular price, a "Now" sale price, a "Save GH₵X" and "X% OFF" badge, and a live countdown.
- The book detail page hero mirrors the same price block, with a star rating and review count above the title when reviews exist.
- `js/components/countdown.js` is a generic, product-agnostic client-side timer keyed off a `data-sale-ends-at` UTC timestamp. It requires no server round-trip to expire correctly: reaching that exact instant is definitionally the same computation `computeSaleState()` already performs server-side, so the client-side expiry (hiding the sale badge/countdown/strikethrough, restoring the plain price) always agrees with what the next real page load from the server would already show.
- The `[hidden]`-defeated-by-`display` bug already documented in this codebase (any class that sets `display` unconditionally overrides the browser's own `[hidden]{display:none}` rule) was checked against every new class this milestone touches. `.countdown`, `.price-block__discount-badge`, `.price-block__saved`, and `.editor-field-row` (used for the new admin sale-pricing fields) all needed and received the `.class[hidden]{display:none}` override; classes that never set `display` (`.book-card__price`, `.price-block__regular-strike`, `.field__hint`) did not.
