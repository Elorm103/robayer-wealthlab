## Approved M5 Scope, Restated (for reference)

Per `v3.3-m5-recommended-scope.md` (M5A) and `v3.3-m5b-architecture-approval-report.md` (M5B, Option B, Scope Approved with Required Amendments): exactly three items — (1) legacy guest-purchase account reconciliation, (2) visitor and marketing analytics via **Cloudflare Web Analytics specifically, "added as a lightweight script tag with no backend change required"**, (3) one triggered post-purchase review-request email via Cron Trigger.

## Verification Method

Every claim below was checked against the actual current codebase (`backend/services/`, `backend/routes/`, `backend/worker/index.ts`, `database/schema.sql`, migration `0021`), the actual test suite (independently re-run, not trusted from the M5C Test Results doc), and live HTTP/D1 queries against both the local dev environment and, where read-only and safe, the real production D1 (`wrangler d1 execute --remote`).

## Findings, By Approved Item

### 1. Legacy Guest-Purchase Account Reconciliation — Implemented, Verified Working

`services/customer/reconciliationService.ts`, `routes/customer/reconciliation.ts`, `/checkout/claim-purchase/`. Independently confirmed live: a seeded orphaned purchase is correctly linked; an already-claimed purchase cannot be re-linked to a different customer (ownership-hijack attempt made and blocked); rate limiting genuinely engages (verified via side-effect, not response body, since the no-enumeration design makes both outcomes look identical externally); the no-enumeration response is byte-identical across a real-purchase and no-purchase email. See the Customer Reconciliation Validation Report for full detail, including one genuine (non-blocking) concurrency finding.

### 2. Visitor and Marketing Analytics — Partially Implemented, Scope Exceeded Without Governance Disclosure

**This is this Board's most significant Scope finding.** M5B approved, specifically and narrowly, "Cloudflare Web Analytics (or an equivalent privacy-respecting, native option), added as a lightweight script tag with no backend change required." What was actually built:

- The Cloudflare Web Analytics beacon itself: implemented correctly as a genuine conditional load (`js/main.js`), gated on a real, currently-null token — no fabricated data source, consistent with this project's own "never faked here" principle. This part matches the approved scope.
- **A materially larger, un-approved addition:** eight new D1-backed business metrics (`services/admin/analyticsService.ts`'s `getActivationSummary()`) and a full new "Activation & customer growth" section on the admin analytics dashboard. This is real backend work (a new service function, a new authenticated API route, new frontend cards) — the opposite of "no backend change required." **No document in this repository (M5A, M5B, or any M5C deliverable) shows this expansion was ever proposed to, or approved by, the M5B Architecture Approval Board.** The M5C Implementation Report describes this work as "Phase 4" and "Phase 6" of "the M5C sprint brief" without ever cross-checking it against what M5B actually approved, and without disclosing the discrepancy anywhere.

This Board's judgment: the work itself is technically sound (see the Analytics Validation Report), low-risk, and arguably good business value — reusing already-existing tables, no new authentication surface, no destructive schema change. The finding is a **governance-process gap, not a quality defect**: implementation exceeded specifically-approved scope without the same "amendment" discipline this project applied to the Platform Fee Engine question one sprint earlier. Classified **Non-blocking** for this milestone's acceptance (the work is sound and low-risk), but this Board recommends the release authorizer explicitly ratify this scope expansion in writing before M5E closeout, so the project's own governance record accurately reflects what was actually built and approved, matching the discipline `v3.3-m5-recommended-scope.md`'s own "Security and Governance Note" calls for on identity-adjacent changes.

**Sub-finding — partial delivery even within the expanded scope:** the M5C brief's own Phase 4 lists nine metrics to measure, including "landing-page visits" and "product views." Neither is implemented as real, queryable data today — both are deferred entirely to the Cloudflare Web Analytics beacon, which is a functional no-op until a human manually generates a real site-tag token (disclosed in the M5C Known Limitations doc). Seven of the nine named metrics are real; two are not yet measurable by anything. Classified **Non-blocking** (honestly disclosed, not fabricated), but this is a partial implementation of Phase 4's own stated requirement, not a complete one.

**Sub-finding — a named requirement not delivered at all:** the M5C brief's Phase 6 asks the dashboard extension to cover "customer growth" specifically. No metric measuring new customer-account creation over time exists anywhere in this codebase, before or after M5C (the closest existing metric, "new subscribers," measures newsletter sign-ups, a different thing). Classified **Non-blocking** (a gap in an already-out-of-approved-scope addition, not a regression), but a real, specific gap against the brief's own stated requirement.

### 3. Triggered Post-Purchase Review-Request Email — Implemented, Genuine Correctness Defect Found

`services/customer/reviewReminderService.ts`, `worker/index.ts`'s `scheduled()` handler, `wrangler.jsonc`'s new Cron Trigger. Confirmed working for the ordinary case: eligibility correctly excludes opted-out customers, orphaned (unreconciled) purchases, already-reviewed purchases, and purchases not yet 5 days old; the scheduled handler itself was independently exercised end-to-end via `wrangler dev --test-scheduled` and fires correctly. **However, this Board reproduced two genuine violations of the "one reminder per purchase" and "idempotent" requirements this exact feature was explicitly required to satisfy** (per `v3.3-risk-assessment.md`'s own mitigation: "verify the Cron Trigger's idempotency... before production release"). See the Review Reminder Validation Report for full reproduction steps. **Classified Blocking.**

## Missing Functionality

None found against the three approved M5 items themselves, beyond the partial/undelivered sub-items noted above (landing-page visits, product views, customer growth).

## Scope Creep

Confirmed and detailed above: the D1-backed "Business Dashboard" analytics work (Phases 4 and 6 of the M5C brief) is real, sound engineering, but was never part of M5A's recommendation or M5B's approval, and this discrepancy was never surfaced by the implementation team.

## Partial Implementation

Two instances, both disclosed in the M5C Known Limitations doc but not framed as partial delivery against a named requirement: landing-page visits/product views (Phase 4), and the review-reminder Cron Trigger's idempotency guarantee (Phase 5/6), which is asserted as complete but is not.

---

**Verdict for this report:** the three M5B-approved items are all substantively implemented. One (reconciliation) is sound with a minor non-blocking finding. One (analytics) mixes a correctly-scoped delivery (the beacon) with a materially larger, un-disclosed scope expansion (the D1 dashboard). One (review reminders) has a real, reproduced Blocking correctness defect. See the Acceptance Summary for how these combine into an overall recommendation.
