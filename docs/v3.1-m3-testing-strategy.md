# Version 3.1 - Sprint M3A - M3 Testing Strategy

Planning only. No test file was written. This strategy describes what M3B should build, reusing the proven M1/M2 test infrastructure, and separately resolves the browser-automation question this sprint was specifically asked to review.

---

## Reused infrastructure (no new tooling decisions needed for backend tests)

Unchanged from M2: `@cloudflare/vitest-pool-workers` against real D1/KV bindings inside real `workerd`, `tests/helpers.ts`'s seed/cleanup pattern, `tests/outboundMock.ts` for any outbound call (none expected - M3's four new endpoints are all first-party D1 reads/writes, no external provider call). M3B should extend the existing `tests/` directory.

## Backend test plan (the four API Gap Analysis additions)

### Unit tests

- `listCustomerPurchases()`/`getCustomerPurchase()` extended with `assets` - verify the returned asset list matches `deliveries` exactly for a multi-asset product, and is correctly empty/absent for a `processing`/`unavailable` purchase (never partially populated).
- The new session-listing service function - given a customer with 3 active sessions and 1 revoked one, returns exactly the 3 active, correctly flags which one is "current."
- The new session-revoke-by-id function - revoking a session that does not belong to the calling customer must fail cleanly (not silently succeed on the wrong row), tested directly at the service layer, not only at the route layer.
- `change-password` - correct-current-password succeeds and revokes all other sessions; incorrect-current-password fails without changing anything; new-password-fails-strength-policy returns the existing `VALIDATION_ERROR` shape unchanged.

### Integration tests

- `GET /api/customer/purchases`/`:reference` - the extended response includes correct `assets`/download-usage data for the requesting customer's own purchase, and (critically, per the Security Review) a *different* customer's purchase continues to return the identical not-found response as before - the additive field must never become a new enumeration surface.
- `GET /api/customer/sessions` - returns only the requesting customer's own sessions; a customer with zero other sessions gets a clean list of one (the current session), never an error.
- `POST /api/customer/sessions/:sessionId/revoke` - **the one endpoint this strategy names as needing its own dedicated ownership test, not an assumed extension of the customer-id pattern**: a customer attempting to revoke a session id belonging to a *different* customer must be rejected (same not-found/forbidden treatment as every other cross-customer access attempt in this codebase), verified by a real cross-customer test seeding two customers exactly as M2's own `customerPurchases.test.ts` already does.
- `POST /api/customer/auth/change-password` - full flow: session established, current password verified, new password accepted, all *other* sessions revoked, the *current* session (the one making the request) remains valid - this last assertion matters specifically because a naive "revoke all sessions" implementation could accidentally log the customer out of the very request that just changed their password.

### Negative/adversarial tests

- Malformed/oversized `:sessionId` path parameter on the revoke endpoint, mirroring the exact pattern `tests/integration/negativeM2.test.ts` already established for `:reference`/`:receiptNumber`.
- SQL-injection-shaped values in the `change-password` request body, confirmed safely parameterized.

### Regression tests

- Full re-run of the existing 106 M1/M2 tests after every M3 backend change, zero expected change in outcome.
- The existing guest, reference-scoped download and receipt-download paths (unauthenticated) must remain completely unaffected by any of M3's new customer-authenticated additions - the single most important regression check, mirroring the exact discipline M2's own Testing Strategy already applied to the email-link path.

## Frontend/UI test plan

### What can be tested with the existing tooling, unchanged

M3's own pages are same-origin, first-party HTML/JS - **not** the cross-origin, PCI-compliant iframe that blocked M2's Paystack verification. The Browser pane tool used throughout this release (`read_page`, `computer`, `form_input`, `get_page_text`) worked correctly against every first-party page exercised in M1 and M2's own verification passes (the `checkout/*` pages, the homepage) - the failure mode M2 hit was specific to Paystack's hosted, cross-origin payment form and a same-session screenshot-rendering issue, not a general limitation of testing this project's own pages.

**Recommendation: confirm this directly, cheaply, at the start of M3B**, before assuming any new tooling is required - navigate the Browser pane to an existing, unrelated first-party page (e.g. the homepage or an existing `checkout/*` page) and confirm `read_page`/`computer`/screenshot all function normally in that session. If they do (as they did throughout M1 and M2's own work on `checkout/*` pages earlier in this same overall project), the existing tool is sufficient for M3's own six new pages, and no new tooling investment is needed for this milestone specifically.

### What to test, once tooling is confirmed

- Each of the five new routes (My Library, Purchase History, Receipts, Licenses, Account Security) renders its populated, empty, and loading states correctly for a real, seeded test customer.
- The dashboard auth guard correctly redirects an unauthenticated visitor from any `/dashboard/*` URL to `/checkout/sign-in/`.
- The Library page's Download button mints and redeems a real token exactly as `fulfilment-status.js`'s existing, already-proven flow does - verifiable by navigating the Browser pane to a real (test-mode-seeded) dashboard session and clicking the button, checking network requests for the mint-then-redirect sequence, exactly as this project's own release process already did for M1/M2's backend verification.
- Account Security's two confirmation dialogs (change password, log out other sessions) actually block the underlying action until confirmed - a real UI interaction test, not just a backend test proving the API itself requires no confirmation step (the API doesn't need one; the *UI* must supply it, per AR-009).
- Keyboard-only navigation through the dashboard nav and every action button, confirming focus rings render (Accessibility, Priority 1 per the UX Strategy).

### If the existing tooling genuinely proves insufficient for some part of M3 (contingency, not the expected outcome)

Per the Version 3.0.2 Retrospective's own Lessons Learned (L8), the specific failure mode observed was (a) a same-session screenshot-rendering issue with the Browser pane, and (b) a cross-origin iframe blocking DOM/accessibility-tree access - neither should recur for M3's own same-origin pages. If (a) recurs for reasons unrelated to iframes, the fallback used successfully throughout this entire release (`get_page_text`, `read_page` with `filter: all`, `read_network_requests`, all of which do not depend on screenshot rendering) remains fully available and was proven sufficient for verifying page content and interaction outcomes without a rendered screenshot. A dedicated, heavier tool (Playwright/Cypress in a proper CI runner) should only be considered if this fallback also proves insufficient in practice - not assumed necessary in advance.

## Acceptance tests

Directly against this planning sprint's own stated M3 objectives, each mapped to a concrete, checkable test:

1. "Every dashboard page requires authentication" - covered by the auth-guard redirect test.
2. "A customer sees only their own data" - covered by the cross-customer integration tests (purchases, sessions).
3. "Empty states render correctly for a zero-purchase customer" - covered by a dedicated frontend test per page.
4. "The one new authorization shape (session-id-scoped revoke) cannot be exploited across customers" - covered by its own named integration test, not inferred from the customer-id-filtering pattern used elsewhere.
5. "M3 introduces zero regression to M1/M2's existing, deployed behavior" - covered by the full 106-test regression re-run, plus the guest-path-unaffected check.

M3B should not be considered feature-complete until all five map to a passing test, not merely a manual verification - the same bar the Version 3.0.2 Retrospective's own Lessons Learned (L3) explicitly recommends carrying forward: cross-check every bullet in this Testing Strategy against an actual test file/test name before declaring implementation done, rather than relying on an external review to notice a self-imposed requirement was skipped.
