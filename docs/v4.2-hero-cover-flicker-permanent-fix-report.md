# Version 4.2 Part 1.1 — Hero Cover Flicker: Permanent Fix Report

## 1. Root cause analysis

The Part 1 fix was correct as far as it went, but it only ever looked at the `<img>` element itself. It never examined the element **wrapping** it.

`index.html`'s hero markup nests the entire visual block inside the same container as the hero text:

```html
<div class="hero__content" data-reveal>
  <div class="hero__text">...</div>
  <div class="hero__visual" data-feature-banner>...cover...</div>
</div>
```

`data-reveal` is the hook for `js/components/scroll-reveal.js`, a sitewide fade-in-on-scroll effect: an `IntersectionObserver` (`threshold: 0.15`) adds `.is-visible` the first time an element enters the viewport, and `css/components.css` transitions it from `opacity: 0; transform: translateY(16px)` to `opacity: 1; transform: translateY(0)` over 300ms (`--duration-slow`/`--ease-standard`).

Both `initScrollReveal()` and `initFeatureBanners()` (the cover-loading code) bind to `DOMContentLoaded`. From there the two run on completely different clocks:

- **The observer fires almost immediately.** The hero is the first thing on the page, always inside the initial viewport, so `IntersectionObserver` reports it as intersecting within roughly a frame of being observed — no network involved.
- **The cover load is network-bound.** `initFeatureBanners()` has to fetch `/api/products`, wait for the response, set `.src`, and wait for `decode()` to resolve — reliably slower than a frame, and much slower on a cold/hard-refreshed connection where the JS itself is also being fetched fresh.

Because `.hero__visual` is a **child** of `.hero__content`, it inherited that opacity/transform animation regardless of its own loading state. The result is a race, and the visible symptom depends on exactly when the fetch/decode resolves relative to the 300ms window:

- If it resolves **before** the fade starts or **after** it finishes: the container fades in showing whatever the cover currently is — usually the typographic placeholder, since the fetch is almost always still in flight when the fade begins. The user sees the *entire hero* perform a fade-in, then, moments later, an instant, un-animated pop as the placeholder is hard-swapped for the real cover. That pop, arriving after everything else has already settled, is exactly "an obvious loading transition."
- If it resolves **during** the 300ms fade: the `<img>` gets un-hidden while its ancestor is still ramping from `opacity: 0` to `opacity: 1`, so the newly-revealed cover renders at partial opacity, blended with the translateY offset — this is the "partially rendered image" symptom.

This also explains why the bug is worst on a hard refresh specifically: a cold cache slows the network side of the race (fetch, and even the JS/CSS files themselves) while the observer's timing is unaffected, widening the gap between "hero has visually settled" and "cover is actually ready."

## 2. Why Part 1 did not fully solve it

Part 1 fixed two real, independently-confirmed bugs: duplicate uncached `/api/products` fetches, and revealing the image before `decode()` had confirmed it was actually paintable. Both fixes were about the **image element's own internal reveal timing** — they made the placeholder→cover swap itself instantaneous and correct. Neither fix touched, or had any way to touch, the **ancestor container's own independent opacity/transform animation**, which is a separate system (`scroll-reveal.js`) that has nothing to do with image loading and was never audited in Part 1. Fixing the swap doesn't help if the swap is happening underneath an unrelated fade that's already mid-flight or already finished — the two systems were never coordinated because nothing in the codebase coordinated them.

## 3. The permanent fix

One change, confined to `index.html`: `data-reveal` was moved off `.hero__content` (the shared wrapper) and onto `.hero__text` only.

```html
<div class="hero__content">
  <div class="hero__text" data-reveal>...</div>
  <div class="hero__visual" data-feature-banner>...cover...</div>
</div>
```

`.hero__visual` is now a plain sibling with no `[data-reveal]` rule applying to it at all — it renders at its natural `opacity: 1`, no transform, from first paint, and is never part of any animation system. The only thing that ever happens to it is the existing, already-correct Part 1 mechanism: `.src` is set, `decode()` is awaited, and the placeholder/image are swapped with a hard, instant `[hidden]` toggle — now with nothing else layered on top of it.

This is a decoupling, not a new mechanism: the book cover, being the page's primary visual and LCP candidate, simply stops being treated as a decorative scroll-reveal element, which it was never meant to be in the first place — the hero is always in the initial viewport, so the "reveal on scroll into view" premise never actually applied to it. The hero **text** keeps its existing fade-in exactly as before; nothing about its behavior changed.

No `setTimeout`, no forced opacity animation, no new CSS, no new JS, and no hack — the fix is removing one attribute from one element and moving it to a sibling that should have carried it independently in the first place.

### A related, un-fixed finding (flagged, not changed)

The "Featured eBook" section further down the homepage has the identical structural pattern — the section element itself carries both `data-feature-banner` and `data-reveal` directly, so its cover `<img>` is also a `[data-reveal]` descendant. It was **not** changed in this fix, because:
- The reported bug is specifically about the Hero, and the brief's stop condition is to change only what's required to eliminate it.
- Being below the fold, its `IntersectionObserver` entry doesn't fire until the user scrolls to it — by which point the `/api/products` fetch (started at the same `DOMContentLoaded` as the Hero's) has almost always already resolved, so the race window that makes the Hero's version visible is much narrower there in practice.

It carries the same latent risk on a very fast scroll + very slow connection. Recommended, not applied: give that section's cover the same treatment (move `data-reveal` off the section and onto a wrapper around the text content only) as a small follow-up, not a hero-fix dependency.

## 4. Cloudflare / caching investigation

Re-examined the caching layers named in the brief specifically for this investigation:
- **Product API** (`/api/products`): still no `Cache-Control` header (unchanged since Part 1) — a genuine, real network round-trip every load, not a stale-cache artifact. No Cloudflare zone-level rule was found overriding this; the Worker's own response headers are what's served.
- **Cover image files**: served with `Cache-Control: public, max-age=31536000, immutable`, but each upload gets a distinct content-addressed URL (`mediaService.ts`), so there is no ETag/304/stale-redirect risk to investigate — a *different* image is never reachable at an *old* image's URL. A hard refresh forces the browser to revalidate/re-fetch everything regardless, which is consistent with the bug being fully explained by the timing race above rather than by any edge-cache staleness.

No evidence of stale edge caching, incorrect ETags, or cached redirects contributing to this bug — the root cause is entirely a client-side animation/timing race, not a caching problem.

## 5. Production verification

Verified the mechanism directly (not assumed) using a local static server serving the exact modified files (`js`/`css` unchanged, only `index.html`'s hero markup changed), with the Browser pane at a real 1280×900 viewport:

| Check | Result |
|---|---|
| `.hero__visual` has `data-reveal` | No (removed) |
| `.hero__visual` computed opacity, immediately on load | `1` — never `0` at any point |
| `.hero__text` has `data-reveal` | Yes (moved here) |
| `.hero__text` still fades in via the scroll-reveal system | Yes — `.is-visible` is added and opacity reaches `1` once in view, exactly as before |
| Any other CSS animation/transition affecting the hero or cover | None found — grepped the full stylesheet for `@keyframes`/`animation` and confirmed the only matches are admin-panel-only (spinner, skeleton loader), unrelated to the homepage |

Local D1 remains in the broken migration state noted in Part 1, so the live `/api/products` → real-image → `decode()` path itself could not be exercised end-to-end locally; that mechanism is unchanged code from Part 1 (already verified live in production during that milestone) and was not touched by this fix. Full end-to-end confirmation on the live cover will happen on deploy, the same verification pattern used for Part 1.

## 6. Regression verification

- `scripts/bump-asset-versions.mjs` re-run: 0 reference changes needed (no CSS/JS file content changed, only an HTML attribute moved), confirming the cache-busting system is untouched and consistent.
- `git status` confirms only `index.html` is modified; no other file touched.
- The hero's grid layout (`.hero--split .hero__content { display: grid; grid-template-columns: 1fr 1fr; }`) is untouched by this change — `data-reveal` never affected layout, only opacity/transform, so removing it from the grid container has no layout effect, confirmed visually in the Browser pane check above.
- The Featured eBook section, Books listing, and Product page were not modified and are not expected to change behavior.

## 7. Performance impact and before/after

No performance cost — this removes an attribute, it doesn't add code, requests, or computation. If anything, the hero's cover now paints at its final opacity as soon as it's ready, rather than being gated behind an animation timeline, which can only help perceived load time for the page's primary visual.

**Before**: the entire hero (text + cover) faded in together via `scroll-reveal.js`, on a clock unrelated to whether the cover image had actually loaded — producing a visible race between "hero has faded in" and "cover has finished loading," whose exact visual artifact (placeholder pop-in, partial-opacity image, or a plain late pop) varied by network timing and was most pronounced on a cold/hard-refreshed load.

**After**: the cover renders at full, final opacity immediately; only the hero's text column performs the scroll-reveal fade (unchanged from before, and appropriate for text that plays a supporting role, not the primary above-the-fold LCP visual). The only visual change the cover itself ever undergoes is the Part 1 decode-gated hard swap from placeholder to real image — once, with nothing else happening around it.
