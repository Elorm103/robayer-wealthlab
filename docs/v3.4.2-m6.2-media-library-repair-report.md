# Version 3.4.2 Milestone M6.2: Media Library Repair Report

## What was broken

The Media Library had no protection against deleting an asset that was still in active use. `mediaService.ts`'s `softDeleteMedia()` performed the soft delete unconditionally. This is the direct cause of the Product CMS failure described in the Product CMS Repair Report: three real, in-use media assets (13, 17, 20) were soft-deleted during earlier testing this session, silently breaking product 1's thumbnail, OG image, and downloadable PDF reference.

## Architectural fix, not a suppressed warning

Added `findMediaUsage(env, id)` to `backend/services/mediaService.ts`, which checks real foreign-key references before allowing a delete:

- `products` (cover, thumbnail, preview, and OG image columns)
- `product_gallery`
- `blog_posts` (cover)
- `resources` (file, cover, and thumbnail columns)
- `product_files` (a product's actual downloadable file, added after the live gap described below)

`softDeleteMedia()` now returns `{ ok: false, reason: 'in_use', usages: [...] }` when any usage is found, and the delete is refused. `backend/routes/admin/media.ts`'s delete handler surfaces this as a `MEDIA_IN_USE` (409) error with a message naming exactly where the asset is used (for example, "This image is still in use by a product downloadable file. Remove it from there first, or replace it instead of deleting it.").

## A real gap found during live Phase 9 verification, and fixed

`findMediaUsage()` initially did not check `product_files`, the table that stores a product's actual downloadable file (its `media_id` column). This was found live: saving product 1's sale-pricing test in the real admin editor produced a 400 from `PUT /api/admin/products/1/files` for "Media asset 13 could not be found", which was the product's real ebook PDF. The asset had been soft-deleted before this protection existed and nothing had caught it.

`findMediaUsage()` was extended to also check `product_files.media_id`, so this specific class of deletion can no longer happen again for a product's downloadable file, matching every other real reference type already covered.

## Recovery of the three already-broken assets

Checked R2 directly for all three affected assets before touching anything:

| id | storage key | R2 object present |
|----|---|---|
| 13 | `ebooks/starting-to-invest-with-gh100.pdf` | yes, 949,532 bytes |
| 17 | `media/images/books/1e789997-d0ad-4341-a289-5d2c4891dece.png` | yes, 23,473 bytes |
| 20 | `media/images/books/0313b261-00ed-48b3-92fe-0debc80eefdb.png` | yes, 42,442 bytes |

All three files were intact; only the `media_assets.deleted_at` metadata was wrong. Restored by clearing `deleted_at` on all three rows. No file was re-uploaded or reconstructed, since nothing was actually lost.

One side effect: while the product 1 editor's dead-reference auto-clear was doing its job (correctly, as designed), it had already nulled out the product's `thumbnail_media_id` and `og_media_id` before the underlying assets were restored, and that null was saved. The admin will need to reselect a thumbnail and OG image from the Media Library (both media assets 17 and 20 are now valid again and available to pick). The cover image and the downloadable file were never affected by this, since the cover reference stayed valid throughout and the file record's `media_id` was never changed, only its target's `deleted_at` flag.

## Verification performed on live production

- Confirmed, live, that attempting to delete an asset genuinely referenced by a product now returns `MEDIA_IN_USE` and is blocked.
- Confirmed, live, that a genuinely unused asset (23, in an earlier pass of this milestone) can still be deleted normally, then restored as a control, so the new check has no false positives.
- Confirmed, live, that after restoring assets 13, 17, and 20, `PUT /api/admin/products/1/files` returns 200, and `wrangler r2 object get --remote` for `ebooks/starting-to-invest-with-gh100.pdf` still returns the correct file.

## Status

Repaired and verified on live production, including a genuine gap found and closed during this same milestone's live testing rather than left for a future pass.
