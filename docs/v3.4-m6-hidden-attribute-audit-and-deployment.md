# Version 3.4 Milestone M6: Site-Wide Hidden-Attribute Audit and Deployment Report

## Scope

A complete, repository-wide search for every element whose visibility is controlled via the HTML `hidden` attribute, checked against every CSS rule that sets an explicit `display` value, since a class that sets `display` on an element unconditionally defeats the browser's own `[hidden] { display: none }` default regardless of the `hidden` attribute's actual state. This is the exact defect already found and fixed once this milestone (`.book-card__cover-placeholder-text`). This audit's purpose was to find every other instance of the same pattern before closing the milestone.

## Method

A static-analysis script cross-referenced every CSS class that sets a non-`none` `display` value against every element in the codebase that is toggled via `.hidden = true/false` in JavaScript or carries a static `hidden` attribute in HTML. Findings were verified individually against the actual source (not trusted from the script alone, which had two confirmed false-positive patterns: matching inside `aria-hidden` attributes, and matching a `data-*="hidden"` string value rather than the boolean attribute) before any fix was applied.

## Findings

Seven classes, beyond the one already fixed, were confirmed as genuine instances of this defect:

| Class | Where it appears | What breaks without the fix |
|---|---|---|
| `.pagination` | Every admin listing page (blog, consultations, contacts, coupons, orders, products, resources, reviews) | Previous/Next controls stay visible and clickable even when the list is empty and there is nothing to page through |
| `.admin-activity-list` | Admin dashboard | Renders as a visible empty box before the recent-activity data loads |
| `.badge` | Newsletter campaign editor's status badge | Renders as a visible empty pill before the campaign data loads |
| `.field` | Investment growth calculator's inflation-rate field; Media Library preview modal's alt-text field | The inflation field shows even when "apply inflation" is unchecked; the alt-text field shows even when previewing a non-image document |
| `.calculator-result__row` | Investment growth calculator's inflation-adjusted result row | Shows stale or blank data even when a calculation ran without inflation applied |
| `.media-preview__image-wrap` | Media Library preview modal | Stays visible alongside the document card it should be replaced by when previewing a PDF |
| `.book-card__cover-image` | Homepage hero | Renders as a visible broken-image box during the brief window before the featured product's cover image loads |

Each was fixed with the exact convention already established nine times elsewhere in this codebase (`.btn[hidden]`, `.field__error[hidden]`, `.alert[hidden]`, `.modal-overlay[hidden]`, `.drawer-overlay[hidden]`, `.empty-state[hidden]`, `.upload-queue[hidden]`, `.media-grid[hidden]`, `.dropdown__menu[hidden]`): a `.class[hidden] { display: none; }` rule, with a comment explaining why. Every fix was verified interactively (the calculator's inflation toggle was exercised both directions live; the pagination fix was confirmed by direct code trace, since the admin pages need seeded data to reproduce empty-state visually) before being deployed.

## The actual root cause of this session's confusion, found during deployment verification

After deploying, repeated verification against the live production site kept showing the original defect as still present, despite the code being correct. Extensive investigation (ruling out browser prerendering, duplicate script inclusion, service workers, JS minification, and a defensive rewrite of the CTA-update logic that should have made the failure structurally impossible) eventually found the real cause: **Cloudflare caches static JS and CSS assets for 4 hours (`Cache-Control: max-age=14400`), far longer than the HTML document's own 10-minute cache, and different Cloudflare edge nodes cache independently with no cross-edge consistency guarantee.** After a deploy, different visitors (and different diagnostic requests from this session) could receive any mix of old and new HTML, JS, and CSS for up to that window, entirely independent of what the origin server or git history showed as current.

This was not a code defect. It was confirmed by direct comparison: `fetch(url, { cache: 'no-store' })` calls always returned the correct, current file; a plain page navigation to the same URL, using the browser's normal HTTP caching, intermittently did not, because it could be served from either the browser's own local cache or a stale Cloudflare edge, neither of which a code fix can force to refresh.

No credential available in this environment has Cloudflare's cache-purge permission (the wrangler OAuth token here is scoped to `zone:read`, not cache purge). The fix applied instead: every `<script>` and `<link>` reference to a file changed this milestone (`product-loader.js`, `content-inject.js`, `admin-settings.js`, `components.css`, `admin.css`) now carries a `?v=m6` query string. Cloudflare and the browser both treat this as a URL never seen before, guaranteeing a fresh origin fetch immediately rather than waiting out the existing cache window. This was verified to work: a genuinely cache-bypassed navigation (`?nocache=` on the page URL itself, forcing the browser past its own local cache) confirmed every fix live and correct, while a plain repeated navigation to the bare URL continued intermittently showing stale content until enough time passed for the old cache entries to expire naturally.

This is a real, previously undocumented architectural gap: this codebase has no build step and no established cache-busting convention for its static assets, so any future change to a JS or CSS file carries the same risk of a multi-hour, edge-dependent staleness window after deployment. This should be treated as a genuine follow-up item, not just an incident to move past: a small build step (or even a manually-incremented version query string convention applied consistently, as done here) would close this gap for good rather than requiring this same manual diagnosis on the next deploy.

## Verification performed after the cache-busting fix

Using a genuinely cache-bypassed production load (confirmed via checking `document.scripts`/`document.styleSheets` actual resolved URLs, not just the HTML source text, since the two were shown to disagree during this investigation when a stale cache was in play):

- **Responsive**: hero cover and placeholder no longer overlap. `.book-card__cover-placeholder-text` computes to `display: none` when a real cover image is assigned (confirmed on the current featured product, which has one). Hero title sits at 590px from viewport top, subtitle at 722px, matching the pre-defect measurements exactly, at both 360px and 375px widths.
- **Dark mode**: hero title renders `rgb(255, 255, 255)`, subtitle `rgb(168, 172, 179)`, against a `rgb(16, 22, 31)` background, with the placeholder still correctly hidden in dark mode.
- **CMS**: `GET /api/hero` (Worker-served, unaffected by static-asset caching since it already sets `no-store`) returns the correct default hero content live.
- **Hero**: the featured product's title span resolves, via `.closest('a')`, to the single `hero__visual-link` anchor with the correct `href`, confirming the cover and CTA still share one destination with no duplicate link.
- **Admin**: `admin.css?v=m6` confirmed loading on an admin page, carrying the pagination and other admin-side `[hidden]` fixes.
