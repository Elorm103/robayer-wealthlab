Production is therefore in a **consistent, unaffected state** - not a partially-shipped one. Nothing currently live depends on migration 0018, and migration 0018 is additive-only, so applying it does not require the new Worker code to already be live, and deploying the new Worker code requires the migration to already be applied (the Worker code references `customer_id` and the consent columns on `purchase_sessions`, and the five new tables).

**Required order of operations when deployment is authorized:**

1. Apply the migration to production D1 first (`wrangler d1 migrations apply robayer-wealthlab-db --remote`).
2. Deploy the updated Worker (`wrangler deploy`, from `backend/`).
3. Deploy the updated static site (the new `/checkout/sign-in/`, `/checkout/set-password/`, `/checkout/forgot-password/`, `/legal/license-agreement/` pages, and the updated `/legal/terms-of-use/` and book-detail consent markup) via whatever the project's existing static-site deployment mechanism is (not run or inspected as part of this backend-focused sprint - confirm the current mechanism before executing).

Deploying the Worker before the migration would break every checkout/webhook/customer-auth request (the code references columns/tables that would not yet exist). Deploying the migration without the Worker update is safe on its own (purely additive, and the old Worker code never references the new columns/tables) - so if these two steps must be split across a maintenance window, applying the migration first and deploying the Worker second is the only safe order, never the reverse.

## 4. Rollback procedure

**Schema rollback (if needed after the migration is applied but before/without the Worker deploy):** Every change in migration 0018 is additive only - 5 new tables, 6 new nullable-or-defaulted columns on `purchase_sessions`, 8 new indexes. No existing column, table, row, or constraint is altered or dropped. Because of this:

- **Preferred rollback path:** do nothing to the schema. An additive-only migration left in place causes no harm even if the Worker deploy is rolled back separately - the old Worker code simply never reads or writes the new columns/tables. Rolling back the *Worker* to the pre-M1 version (`wrangler rollback` to the 2026-07-24T22:57:43Z deployment, or any deployment before it) is sufficient to fully undo M1's user-facing behavior without touching the database at all.
- **Full schema rollback (only if the new tables/columns must be physically removed, e.g. for a compliance reason):**
  ```sql
  DROP INDEX IF EXISTS idx_purchase_sessions_customer;
  ALTER TABLE purchase_sessions DROP COLUMN marketing_opt_in;
  ALTER TABLE purchase_sessions DROP COLUMN license_version;
  ALTER TABLE purchase_sessions DROP COLUMN license_accepted_at;
  ALTER TABLE purchase_sessions DROP COLUMN terms_version;
  ALTER TABLE purchase_sessions DROP COLUMN terms_accepted_at;
  ALTER TABLE purchase_sessions DROP COLUMN customer_id;
  DROP TABLE IF EXISTS customer_password_tokens;
  DROP TABLE IF EXISTS customer_sessions;
  DROP TABLE IF EXISTS customer_profiles;
  DROP TABLE IF EXISTS customers;
  ```
  This must only be run after the Worker has already been rolled back to a pre-M1 version (running it while M1's Worker code is still live would break every checkout/customer-auth request immediately). Not tested against a live D1 instance in this sprint (per the "do not apply remote migrations" instruction) - verify `DROP COLUMN` support against the production D1/SQLite version in use before relying on this path.

**Rollback readiness verdict: Ready.** The additive-only schema design means the low-risk rollback path (Worker-only rollback, leave schema in place) requires no database action at all and is always available.

## 6. Verification checklist after deployment

To be run by the operator after both the migration and the Worker/static-site deploy complete. None of these were run against production during this sprint.

1. `wrangler d1 migrations list robayer-wealthlab-db --remote` returns "No migrations to apply" (confirms the migration landed).
2. `GET /api/health` (or the site's existing health-check route) returns `200` (confirms the new Worker build started cleanly - a bad build/import error would show up here immediately, matching the same failure mode this sprint's own local test-tooling investigation uncovered and worked around).
3. Load the flagship book's product page in a real browser; confirm the consent statement, Terms of Service link, License Agreement link, and marketing checkbox all render.
4. Load `/checkout/sign-in/`, `/checkout/forgot-password/`, and `/checkout/set-password/` (with no token) directly; confirm all three render without a console error and the set-password page's no-token empty state displays correctly.
5. Load `/legal/license-agreement/`; confirm it renders.
6. Perform one real, small-value test purchase through Paystack's actual Live or Test mode (whichever is configured) and confirm: the purchase completes, the webhook is received and verified, a `customers` row is created (check via `wrangler d1 execute robayer-wealthlab-db --remote --command "SELECT id, email, created_at FROM customers ORDER BY id DESC LIMIT 1"`), and the welcome/password-setup email arrives.
7. Using the password-setup link from that real email, complete the set-password flow and confirm login succeeds afterward.
8. Confirm the existing, unrelated purchase/download flow (a purchase made by a customer who never sets a password) still works unchanged - the email-link download path must be completely unaffected by this deploy.
9. Watch `wrangler tail` (or the dashboard's real-time logs) for the first few minutes after deploy for any unexpected error rate on `/api/checkout/sessions`, `/api/webhooks/paystack`, or `/api/customer/auth/*`.
