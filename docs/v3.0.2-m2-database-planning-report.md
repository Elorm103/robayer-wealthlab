# Version 3.0.2 - Sprint M2A - M2 Database Planning Report

Planning only. No migration file was created. No schema change was applied to any environment.

---

## Current schema, as it actually exists in production (verified directly, not assumed)

Confirmed via direct inspection of `backend/database/schema.sql` (current as of migration 0018) and a live query against production D1: `order_items`, `licenses`, and `receipts` do not exist yet. The tables M2 will build on are already live and unchanged since M1:

- `purchase_sessions` - the order-of-record (ADR-001), now carrying `customer_id` and the four M1 consent columns.
- `payment_transactions` - append-only webhook ledger, `purchase_session_id` FK.
- `deliveries` - the download entitlement, `purchase_session_id` FK, `UNIQUE(purchase_session_id, asset_id)`, `status IN ('ready', 'delivered', 'revoked')` - `'revoked'` is already a valid, live enum value, just never set by any code path yet.
- `download_tokens` - `delivery_id` FK.
- `customers`, `customer_profiles`, `customer_sessions`, `customer_password_tokens` - M1's identity layer.
- `products` - includes `price_pesewas`, `currency`, `tax_behavior` (`'inclusive' | 'exclusive' | 'exempt'`, already live), `pricing_model` (currently `'one-time'`-only).

## New tables

### `order_items`

Per Blueprint Deliverable 3 and ADR-009.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `purchase_session_id` | INTEGER NOT NULL REFERENCES purchase_sessions(id) | |
| `product_id` | TEXT NOT NULL | matches `purchase_sessions.product_id`'s own convention (references `content/products/{slug}.json`'s `id` field, not a D1 `products.id` - see the schema's own deprecation note on why `purchase_sessions` doesn't FK to `products` today) |
| `product_title` | TEXT NOT NULL | snapshotted at creation, same discipline as `purchase_sessions.product_title` |
| `unit_price_pesewas` | INTEGER NOT NULL CHECK (>= 0) | snapshotted |
| `quantity` | INTEGER NOT NULL DEFAULT 1 CHECK (quantity >= 1) | ADR-009: quantity > 1 means fulfilment loops N times, never a shared license |
| `asset_id` | TEXT | nullable - matches `deliveries.asset_id`'s convention |

Indexes: `idx_order_items_session`, `idx_order_items_product`.

**Population note:** every product in this catalog is single-item today (no bundle exists) - one `order_items` row per `purchase_sessions` row in practice, `quantity = 1`, until a bundle or multi-seat product is created. The table exists for correctness and future-readiness now, per ADR-001's own reasoning for `order_items`' introduction, not because current volume needs it.

### `licenses`

Per Blueprint Deliverable 3 and ADR-003/ADR-009.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `purchase_session_id` | INTEGER NOT NULL REFERENCES purchase_sessions(id) | |
| `product_id` | TEXT NOT NULL | same convention as `order_items.product_id` |
| `customer_id` | INTEGER REFERENCES customers(id) | **nullable** - a purchase can in principle verify with no confirmed email (existing, rare M1 edge case already handled by `commerceService.ts`'s "provisioning_skipped_no_email" path); a license must still be creatable in that case, just unlinked to a customer, mirroring how `deliveries` already never depends on `customer_id` existing |
| `license_key` | TEXT NOT NULL UNIQUE | generated with the same `crypto.getRandomValues`-based approach as every other token in this codebase - not a bearer credential (ADR-003 note: "the license key is explicitly never a bearer credential for access") |
| `license_type` | TEXT NOT NULL DEFAULT `'personal'` CHECK (`license_type` IN (`'personal'`)) | Blueprint names `commercial`/`educational` as future values (Deliverable 9) - **explicitly excluded from M2** per this sprint's "Licensing Enhancements" exclusion; the CHECK constraint should list only `'personal'` for M2, with the enum widened in a later migration when those types actually ship, not pre-declared now |
| `terms_version` | TEXT | copies `purchase_sessions.license_version`, already captured at checkout by M1 - no new capture needed, just carried forward |
| `issued_at` | TEXT NOT NULL DEFAULT (datetime('now')) | |
| `revoked_at` | TEXT | nullable; set only by the revocation-sync function, always in the same operation as the corresponding `deliveries.status = 'revoked'` update |

Indexes: `UNIQUE(license_key)`, `idx_licenses_customer`, `idx_licenses_purchase_session`.

**Cardinality note (ADR-009):** one `licenses` row per seat, i.e. per `order_items.quantity` unit - the fulfilment loop creates `quantity` independent `licenses` rows (and `quantity` independent `deliveries` rows, already the case structurally since `deliveries` has no quantity concept of its own today and would need the same loop treatment). See the API Planning Report for the exact loop design.

### `receipts`

Per Blueprint Deliverable 3 and ADR-008.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `receipt_number` | TEXT NOT NULL UNIQUE | see numbering scheme below |
| `purchase_session_id` | INTEGER NOT NULL REFERENCES purchase_sessions(id) | 1:1 - one receipt per verified purchase session (not per order_item; a multi-item order gets one receipt with multiple line items, matching how a real invoice works) |
| `customer_id` | INTEGER REFERENCES customers(id) | nullable, same reasoning as `licenses.customer_id` |
| `issued_at` | TEXT NOT NULL DEFAULT (datetime('now')) | |
| `line_items` | TEXT NOT NULL | JSON array, one entry per `order_items` row for this session (title, quantity, unit price, line total) - denormalized snapshot, not a live join, so a receipt never changes after issuance even if `order_items` were ever edited (it shouldn't be, but the receipt must not depend on that) |
| `subtotal_pesewas` | INTEGER NOT NULL CHECK (>= 0) | |
| `discount_pesewas` | INTEGER NOT NULL DEFAULT 0 CHECK (>= 0) | always 0 in M2 - no coupon system exists yet; column exists now so a future coupon milestone never needs a receipts migration |
| `tax_breakdown` | TEXT NOT NULL DEFAULT `'[]'` | JSON array of `{label, rate_percent, amount_pesewas}` per ADR-008; empty array is the valid degenerate case for a non-VAT-registered business |
| `tax_pesewas` | INTEGER NOT NULL DEFAULT 0 CHECK (>= 0) | derived sum of `tax_breakdown`'s `amount_pesewas` entries, computed and stored at issuance time, never entered independently |
| `total_pesewas` | INTEGER NOT NULL CHECK (>= 0) | must equal `purchase_sessions.amount_pesewas` for that session - a receipt whose total disagrees with the actual charged amount is a data-integrity bug, worth a CHECK-adjacent application-level assertion even though SQLite can't cross-reference another table in a CHECK constraint |
| `tax_behavior` | TEXT NOT NULL | copied from `products.tax_behavior` at issuance (already a live field: `'inclusive' | 'exclusive' | 'exempt'`) |
| `currency` | TEXT NOT NULL DEFAULT `'GHS'` | present now for future multi-currency readiness (ADR-008-adjacent reasoning); no multi-currency logic ships in M2 |

Indexes: `UNIQUE(receipt_number)`, `idx_receipts_customer`, `idx_receipts_purchase_session` (also usable as a de facto uniqueness check at the application level, though not DB-enforced 1:1 - see Testing Strategy for why an explicit test covers this instead of a schema-level constraint).

**Receipt numbering, reusing the proven pattern exactly:** `backend/utils/purchaseReference.ts` already solves this identical problem for `purchase_sessions.purchase_reference` - format the row's own AUTOINCREMENT `id` with a year prefix, no separate counter table, no race condition, because SQLite's own AUTOINCREMENT uniqueness is the only atomicity primitive needed. Recommended: `formatReceiptNumber(id, issuedAt) => "RWL-RCT-{year}-{6-digit id}"`, implemented as a near-identical sibling function, not a generalization of the existing one (this codebase's own convention, seen throughout M1, is direct pattern-mirroring over premature abstraction).

### `receipt_download_tokens`

Needed to support the guest, reference-scoped receipt download described in the API Planning Report (mint-then-redeem, mirroring `download_tokens` exactly). A **separate table**, not a reuse of `download_tokens`, was chosen deliberately: `download_tokens.delivery_id` is `NOT NULL REFERENCES deliveries(id)` - widening it to also (optionally) point at a receipt would mean either making that FK nullable (weakening a constraint on a live, security-critical table for no benefit to its existing use) or adding a second nullable `receipt_id` column with an application-level "exactly one of these two must be set" rule SQLite cannot enforce declaratively. A small sibling table costs nothing and touches nothing already live - the same reasoning this codebase already applied when it built `customer_password_tokens` as a sibling of `password_reset_tokens` rather than generalizing one table to serve both purposes.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `token` | TEXT NOT NULL UNIQUE | same generation approach as `download_tokens.token` |
| `receipt_id` | INTEGER NOT NULL REFERENCES receipts(id) | |
| `expires_at` | TEXT NOT NULL | short TTL, same order of magnitude as `download_tokens.expires_at` |
| `used_at` | TEXT | nullable; single-use, same discipline throughout this codebase |
| `created_at` | TEXT NOT NULL DEFAULT (datetime('now')) | |

Index: `idx_receipt_download_tokens_receipt`.

## Modified tables

**None required.** `purchase_sessions`, `deliveries`, `payment_transactions`, `customers` all already carry every field M2's new tables need to reference. `deliveries.status`'s `'revoked'` value is already live in the schema's CHECK constraint (added when `deliveries` was first designed, per that table's own header comment referencing the eventual ADR-003 need) - no ALTER TABLE needed there either.

## Foreign keys, summarized

```
order_items.purchase_session_id  -> purchase_sessions.id
licenses.purchase_session_id     -> purchase_sessions.id
licenses.customer_id             -> customers.id (nullable)
receipts.purchase_session_id     -> purchase_sessions.id
receipts.customer_id             -> customers.id (nullable)
```

No new foreign key targets any M2 table from an existing table - these three tables are pure leaves off `purchase_sessions`, matching the existing `deliveries`/`payment_transactions` pattern exactly. No circular reference, no ambiguity in drop order.

## Migration plan

**One migration** (next number after 0018 - confirm the exact number at implementation time by checking `backend/database/migrations/` directly, not assumed here), purely additive:

1. `CREATE TABLE order_items` + its two indexes.
2. `CREATE TABLE licenses` + its three indexes/unique constraint.
3. `CREATE TABLE receipts` + its two indexes/unique constraint.
4. `CREATE TABLE receipt_download_tokens` + its index.

No `ALTER TABLE` statements. No data backfill - every existing `purchase_sessions` row that verified before this migration runs will simply have no `order_items`/`licenses`/`receipts` row, which is correct and expected (retroactive receipt generation for pre-M2 purchases is explicitly out of scope unless separately requested; it is not named in this sprint's scope list). This should be stated plainly in the migration's own header comment and in the M2 documentation, so it is never mistaken for an oversight later.

Order within the migration file matters only for readability, not correctness - none of the three tables reference each other, so any creation order is equally safe. Recommended order: `order_items`, `licenses`, `receipts` (matches the order data is produced during fulfilment).

## Rollback strategy

Identical shape to migration 0018's own, already-proven approach:

- **Preferred path:** none needed at the schema level if a Worker-code rollback is sufficient - an unused, additive table causes no harm. Rolling back the Worker deployment alone (to the pre-M2 version) fully undoes M2's user-facing behavior without touching the database.
- **Full schema rollback**, only if physical removal is required:
  ```sql
  DROP TABLE IF EXISTS receipt_download_tokens;
  DROP TABLE IF EXISTS receipts;
  DROP TABLE IF EXISTS licenses;
  DROP TABLE IF EXISTS order_items;
  ```
  Reverse creation order. Must only run after the Worker has already been rolled back to a pre-M2 version, same discipline documented for migration 0018. Given these tables are financial/audit records (Data Governance & Compliance section: "Financial records - Never deleted"), a full DROP should be treated as an exceptional, deliberately-authorized action, not a routine rollback step - the "leave it in place, roll back the Worker" path is the one actually expected to be used in practice.

## Duplication check

No duplication introduced. `order_items.product_title`/`unit_price_pesewas` mirror `purchase_sessions.product_title`/`amount_pesewas`'s existing snapshot discipline rather than inventing a new one. `receipts.tax_behavior` copies a value that already lives on `products` rather than requiring a fresh input. `licenses.terms_version` copies a value M1 already captures on `purchase_sessions.license_version` rather than asking the customer to re-consent. Every new table reuses the existing `purchase_sessions` row as its single source of "which purchase is this," never introducing a second concept of "order."
