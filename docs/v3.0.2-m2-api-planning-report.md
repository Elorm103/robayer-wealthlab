# Version 3.0.2 - Sprint M2A - M2 API Planning Report

Planning only. No route file was created or modified.

---

## Existing conventions confirmed (to be followed, not reinvented)

Read directly from `backend/worker/index.ts`, `backend/routes/customer/auth.ts`, `backend/middleware/requireCustomerAuth.ts`, `backend/utils/responses.ts`:

- Every route is a thin function taking `(request, env, logger)`, registered in `worker/index.ts`'s route table via `URLPattern`.
- Every response uses `jsonSuccess()`/`jsonError()` from `utils/responses.ts` - never a raw `Response` object - so the envelope (`{success, data}` / `{success, error: {code, message}}`) and HTTP status mapping (`ERROR_STATUS` in that same file) can never drift between endpoints.
- Customer-authenticated routes call `requireCustomerAuth(request, env, logger)` first, exactly as `handleCustomerSession`/`handleCustomerLogout` already do; state-changing authenticated routes additionally call `requireCustomerCsrf`.
- The existing guest-accessible, reference-scoped pattern already lives at `GET /api/purchases/:reference` (view, ADR-013 tier 1) and `POST /api/purchases/:reference/downloads` -> `GET /api/download/:token` (action, ADR-013 tier 2, single-use minted token). M2's receipt-download design should mirror this exact two-step mint-then-redeem shape, not invent a new one.
- Rate limiting via `middleware/rateLimit.ts`'s `isRateLimited()`, one named bucket per endpoint, applied as the first check in the handler.

## New endpoints

### Guest/reference-scoped (unauthenticated, ADR-013 tier 1 and 2 - preserves "no account ever required" for ADR-003)

| Endpoint | Method | Purpose | Auth |
|---|---|---|---|
| `GET /api/purchases/:reference` | GET | **Modify existing handler**, not a new endpoint - extend `handleGetPurchaseStatus`'s response to include `receiptNumber` (if issued) alongside the fields it already returns, so the confirmation page can show/link to the receipt without a second round-trip. | None (reference-scoped, existing pattern) |
| `POST /api/purchases/:reference/receipt-download` | POST | Mints a single-use, short-TTL token for the receipt PDF, mirroring `handleRequestDownload`'s exact mechanism for the product file. | None (reference-scoped) - this is an *action* per ADR-013, so it must still validate the reference resolves to a `verified` session with an issued receipt, same ownership-adjacent check `handleRequestDownload` already performs for entitlements |
| `GET /api/download-receipt/:token` | GET | Streams the receipt PDF, redeeming the single-use token. Separate path prefix from `/api/download/:token` (which is entitlement-scoped, tied to `deliveries`), backed by the new `receipt_download_tokens` table (see Database Planning Report) rather than overloading `download_tokens`'s existing NOT NULL `delivery_id` FK. | Single-use token in URL |

### Customer-authenticated (Customer Library data layer - consumed by M3's dashboard pages, but the APIs themselves are this sprint's explicit scope)

| Endpoint | Method | Purpose | Auth |
|---|---|---|---|
| `GET /api/customer/purchases` | GET | Paginated purchase history for the logged-in customer: reference, product title, date, amount, status, receipt number if issued. Ownership enforced by filtering on `purchase_sessions.customer_id = session.customerId` - never by trusting a client-supplied customer ID. | `requireCustomerAuth` |
| `GET /api/customer/purchases/:reference` | GET | Single purchase detail, same ownership filter. | `GET /api/customer/licenses` | GET | List of the customer's own licenses (key, type, product, issue date, status). | `requireCustomerAuth` |

## Authentication and authorization requirements

- Every customer-authenticated M2 endpoint uses the exact same `requireCustomerAuth` middleware M1 already built - no new session mechanism, no new cookie, no new CSRF scheme. This is a direct compatibility requirement from this sprint's own instruction and is trivially satisfiable since M2 adds no new auth concept.
- Ownership is always enforced server-side by filtering on the session's own `customerId`, never accepted as a request parameter. A customer cannot view another customer's purchase, receipt, or license by guessing an ID or reference - see the Security Review below for the specific enumeration-prevention mechanics.
- The two new guest/reference-scoped endpoints (`receipt-download` mint, and the redeem endpoint) require no session, by design, matching the existing entitlement-download pattern and ADR-003's "email-link access preserved permanently" guarantee - a guest who never sets a password must still be able to get their receipt.
- The one admin endpoint reuses the existing admin session/CSRF middleware unchanged.

## Validation

- `:reference` and `:receiptNumber` path parameters validated against their known format (`RWL-{year}-{6 digits}` / `RWL-RCT-{year}-{6 digits}`) before any database query, same discipline `services/customer/sessionService.ts`'s `SESSION_TOKEN_PATTERN` regex-gate already applies to session tokens - cheap rejection of garbage input before it ever reaches D1.
- Pagination parameters (`page`/`limit` on `GET /api/customer/purchases`) validated as positive integers within a sane bound (e.g. `limit` capped at 50), rejecting anything else with `VALIDATION_ERROR` rather than silently clamping - clamping can mask a client bug; an explicit rejection surfaces it.
- No new customer-supplied free-text field is introduced anywhere in M2's request surface - every new endpoint is read-only from the customer's perspective (list/view/download), except the admin revoke action, which takes only a path parameter, no body.

## Error handling

- New error codes needed in `types/api-contracts.ts`'s `ApiErrorCode` union and `utils/responses.ts`'s `ERROR_STATUS` map: `RECEIPT_NOT_FOUND` (404), `LICENSE_REVOKED` (403, for a download attempt against a revoked entitlement - though this already exists implicitly via the current download-token flow's entitlement check; confirm whether a distinct code is needed or the existing `DOWNLOAD_NOT_AVAILABLE`/`ASSET_UNAVAILABLE` codes already cover it before adding a new one).
- A purchase reference that exists but belongs to a different customer, when queried through the *authenticated* `/api/customer/purchases/:reference` endpoint, returns the same `NOT_FOUND` a genuinely nonexistent reference would - never a distinct "forbidden" response, which would itself leak that the reference is real (see Security Review).
- Every new handler follows the existing pattern: expected business-logic failures throw a typed error class (mirroring `CommerceError`) caught at the route layer and mapped to a safe, specific message; anything unexpected falls through to the existing generic `INTERNAL_ERROR` envelope via `middleware/errorHandler.ts`, never a raw stack trace.

## Compatibility confirmation

Every new and modified endpoint above is additive or backward-compatible with M1's live API surface. No existing endpoint's request shape changes. No existing endpoint's response shape loses a field. `POST /api/checkout/sessions`, all five `/api/customer/auth/*` routes, and the existing `/api/purchases/:reference` / `/api/purchases/:reference/downloads` / `/api/download/:token` routes all continue to function exactly as M1 shipped them.
