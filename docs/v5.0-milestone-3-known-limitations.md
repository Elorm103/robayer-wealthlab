# Version 5.0 Milestone 3 — Customer AI v1: Known Limitations

Honest, complete list. Nothing here blocks certification — each item is either an accepted design tradeoff (documented as such at the time it was decided) or a gap disclosed for future milestones to pick up.

## 1. Admin-only content visibility filter not yet exercised against real classified data

`answerCustomerQuestion()` hardcodes `visibility: 'public'` on every retrieval call, and `searchKnowledge()` filters strictly on `visibility === requested visibility` plus `data_classification === 'PRODUCTION'`. This is verified at the code level and via the Knowledge Base's own test suite. However, as of this milestone's certification, **all 39 indexed documents in production are `public`/`PRODUCTION`** — there is currently no real admin-only document to attempt to leak. The control is structurally sound but has not been empirically red-teamed against live classified content, simply because none exists yet. If/when admin-only content is ever indexed, this should be spot-checked.

## 2. "Streaming" is a client-side simulation, not true token streaming

This was an explicit, approved architecture decision (not an oversight): the AI Gateway call is synchronous, and the complete, already-governed answer is revealed progressively in the browser via word-chunked `setTimeout` reveals. The benefit is that the safety/governance pipeline always sees and validates the full response before any of it reaches the customer — a malformed or policy-violating partial response can never be shown mid-stream, because there is no mid-stream from the server's perspective. The tradeoff is that the customer waits for the full generation (observed avg. 3.2s LLM latency for high-confidence answers in production, up to ~7.8s max) before the reveal begins, rather than seeing tokens arrive immediately.

## 3. Reranking title/keyword boosts occasionally surface secondary chunks

Because `answerCustomerQuestion()` retrieves up to 5 results and cites up to 4, a question can occasionally cite two chunks from the same source document (observed in production for the Treasury Bills question: 2 of 4 citations were different chunks of the same blog post). This is inherited, unmodified behavior from the Knowledge Base's Milestone 2.2 ranking logic — not something this milestone changed — and is a reasonable tradeoff (showing the two most relevant excerpts of one strong source rather than diluting with a weaker fourth source).

## 4. No account-level personalization, by design

Per the founder's explicit stop conditions for this milestone, there is no persistent memory, no customer profile awareness, and no personalization of any kind. A returning customer is treated identically to a first-time visitor. This is intentional scope for this milestone, not a defect — later milestones may revisit it.

## 5. Citation titles occasionally carry raw HTML entities

At least one observed citation title displayed as `Financial Coaching &amp; Advisory Services` rather than `Financial Coaching & Advisory Services`. This is inherited directly from how that document's `title` was stored in `knowledge_documents` during Milestone 2 indexing — Customer AI displays whatever title the Knowledge Base already has, unmodified. Fixing it would mean touching Knowledge Base indexing, which is out of this milestone's frozen scope; worth a small, low-risk fix whenever the Knowledge Base is next legitimately revisited.

## 6. Admin analytics dashboard rendering not visually re-verified in this pass

The admin analytics page (`/admin/customer-ai/`) and its API were confirmed to load and be correctly gated behind super-admin authentication (`NOT_AUTHENTICATED` when unauthenticated, as expected). Because this verification session did not have admin login credentials, the dashboard's actual rendered charts/tables were not visually re-checked against a logged-in session — instead, the exact same aggregation queries the dashboard runs were run directly against production D1 and confirmed correct. The dashboard code itself is a thin read-only layer over those same queries (`services/admin/customerAiAnalyticsService.ts`), so this is a low-risk gap, but it is disclosed rather than silently assumed.

## 7. Rate limiting is IP-based, shared infrastructure

Customer AI's rate limits use the same KV-backed, per-IP fixed-window limiter as every other public endpoint in this project (newsletter, contact, etc.) — documented in `docs/backend-security.md` as appropriate for this project's realistic traffic volume, not a hardened anti-abuse boundary. Multiple customers behind the same NAT/corporate IP share one bucket. This is an accepted, pre-existing project-wide tradeoff, not something newly introduced by this milestone.
