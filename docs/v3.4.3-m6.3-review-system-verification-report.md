# Version 3.4.3 M6.3: Review System Verification Report

## Question

Why could the completed purchase not submit a review?

## Trace

`backend/routes/customer/reviews.ts`'s `handleSubmitReview()` runs, in order:

1. `requireCustomerAuth(request, env, logger)` -- requires a valid, signed-in customer session.
2. `requireCustomerCsrf(...)` -- requires a matching CSRF token.
3. Rate limiting.
4. Body validation (`productSlug`, `rating`, `body`).
5. `submitOrUpdateReview(env, logger, auth.auth.customerId, ...)` -- the actual ownership/eligibility check (does this customer have a verified purchase of this product).

Step 1 is the blocker. A customer with no session can never reach step 5. The customer in question (id 9, the real completed purchase) had `password_hash: null` and had never redeemed a password-setup token, so no session could ever exist for them. Every request to this endpoint on their behalf would fail at `requireCustomerAuth()` before any purchase-ownership logic ever ran.

## Verification of each item the brief asked to check

- **Ownership**: `submitOrUpdateReview()`'s purchase-ownership check was never reached during the failure, so it could not have been the cause. Verified separately, post-repair (see below), that it correctly allows a review once authentication succeeds.
- **Authentication**: confirmed as the actual blocker. `requireCustomerAuth()` correctly rejects a request with no valid session; the customer never had one because they never had a password.
- **Purchase lookup**: not reached during the failure. Verified post-repair that `submitOrUpdateReview()` correctly finds the real, verified purchase (`RWL-2026-000046`) linking this customer to this product.
- **Review eligibility**: not reached during the failure. Verified post-repair: the review was accepted, confirming the eligibility check correctly recognized a genuine verified purchase.
- **Customer session**: this was the root cause. No session existed because no password had ever been set, because the password-setup email was sent to an address the customer never controlled (see the Authentication Root Cause Report).

## Conclusion

There is no defect in the review system itself. `requireCustomerAuth()`, `requireCustomerCsrf()`, and `submitOrUpdateReview()` all behave correctly. The review system was unreachable purely as a downstream consequence of the checkout email defect; fixing that defect, and completing password setup and sign-in for the affected customer, was sufficient to resolve review submission with no changes to any review-related code.

## Live verification performed

After repairing the customer's email and completing the real password-setup and sign-in flow (see the Authentication Root Cause Report for the exact steps):

- `POST /api/customer/reviews` was called with a real, valid customer session and CSRF token, `productSlug: "starting-to-invest-with-gh100"` (the product this customer actually purchased), a rating, and a review body.
- The request succeeded: `{"reviewId": 2, "status": "pending"}`.
- This confirms ownership, purchase lookup, and eligibility all function correctly once a real, authenticated customer session exists.

No code changes were made to any review-related file (`routes/customer/reviews.ts`, `services/reviewService.ts`) as part of this milestone. None were needed.
