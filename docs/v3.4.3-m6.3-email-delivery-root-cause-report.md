# Version 3.4.3 M6.3: Email Delivery Root Cause Report

## Summary

None of the missing emails (purchase confirmation, ebook delivery, receipt, forgot password, recover purchase) were caused by a failure in the email pipeline. Every email the pipeline was ever asked to send, it sent successfully. The pipeline was simply never asked to send to a real address.

## Trace: every expected email for the completed purchase

Query against `email_log` for purchase reference `RWL-2026-000046` (id 46, customer 9), at the exact time of purchase:

| id | template | recipient | status | provider_id | sent_at |
|----|----------|-----------|--------|-------------|---------|
| 99 | purchase-receipt | checkout+rwl-2026-000046@robayerwealthlab.com | sent | ef1e0861-... | 2026-07-31T18:26:32.616Z |
| 100 | secure-download | checkout+rwl-2026-000046@robayerwealthlab.com | sent | 9241bc55-... | 2026-07-31T18:26:32.857Z |
| 101 | customer-welcome | checkout+rwl-2026-000046@robayerwealthlab.com | sent | 53b5bf2c-... | 2026-07-31T18:26:33.140Z |

For each of the three emails this purchase should have triggered:

- **Queued**: yes, an `email_log` row was created for each.
- **Rendered**: yes, no template-rendering exception is present anywhere in the pipeline for these sends.
- **Sent to Resend**: yes, each row shows `attempt_count: 1` with no retry.
- **Accepted by Resend**: yes, each row carries a real Resend `provider_id` (message id), which Resend only returns on successful acceptance.
- **Logged**: yes, `status: 'sent'`, `sent_at` populated.
- **Exception**: none. `last_error` is `null` on all three rows.
- **Skipped by business logic**: no. All three templates fired unconditionally as designed (a new customer always gets `customer-welcome`; a verified purchase always gets `purchase-receipt` and `secure-download`).

There is no fourth "purchase confirmation" template distinct from these three. `customer-welcome` (containing the account setup / password link) is architecturally the confirmation email for a first-time purchase; `purchase-receipt` and `secure-download` cover the receipt and ebook delivery. All three exist and all three succeeded.

## Root cause

Every one of the three emails above was sent to `checkout+rwl-2026-000046@robayerwealthlab.com`, a synthetic placeholder, not the buyer's real email. This is a direct consequence of the checkout architecture defect documented in full in the Authentication Root Cause Report: the payment provider (Paystack) was relied upon to collect a real email, and for the `mobile_money` channel it never does. `purchase_sessions.customer_email` and `customers.email` were therefore always the placeholder, and the email pipeline faithfully delivered to exactly the address it was given.

The same mechanism explains "forgot password" and "recover purchase" appearing to send nothing:

- `authService.forgotPassword()` looks up `customers WHERE email = ?`. A real customer typing their real email finds no match (the stored email is the placeholder), and the function silently returns with no email sent -- by design, to avoid leaking which emails have accounts (the same no-enumeration discipline used by the admin equivalent). This is not a bug in `forgotPassword()`; it is a correct response to a broken input.
- `reconciliationService.reconcilePurchases()` looks up `purchase_sessions WHERE customer_email = ?`. Same story: a real customer's real email matches nothing, because the column has never held anything but placeholders, so the function silently returns.

## Fix

No changes were made to the email pipeline itself (`services/emailService.ts`, `email_log`, Resend integration) -- it required none. The fix is the same checkout-time real-email capture described in the Authentication Root Cause Report. Once a real email is on file, every one of these five code paths works exactly as originally designed, using logic that was never actually broken.

## Live verification performed

Using the real, already-existing purchase and customer record (id 46 / id 9), with the customer's email surgically corrected to a real, monitored address (a repair of broken data on a genuine existing purchase, not a fabricated new one):

- Triggered the admin "resend receipt" and "resend download" actions (`POST /api/admin/orders/RWL-2026-000046/resend-receipt` and `.../resend-download`) -- the exact same `purchase-receipt` and `secure-download` templates that failed to reach the customer originally. Both returned `{"resent": true}` and both landed in the real inbox (subjects: "Your Robayer WealthLab receipt: Small Cedis, Big Wealth" and "Your download is ready: Small Cedis, Big Wealth").
- Called `POST /api/customer/auth/forgot-password` with the corrected real email. A `customer-password-reset` email landed in the real inbox within seconds.
- Called `POST /api/customer/reconcile-purchases` with the corrected real email (after temporarily and reversibly unlinking the purchase to create a genuine orphaned-purchase scenario). A `customer-purchase-reconciliation` email ("Your Robayer WealthLab purchase history has been recovered") landed in the real inbox, and the purchase was correctly re-linked to the same customer record in the database.

All four templates were independently confirmed delivered to a real inbox once given a real address, closing out every email-related symptom in the original brief.
