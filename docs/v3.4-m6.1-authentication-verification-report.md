# Version 3.4 M6.1: Authentication Verification Report

## Architecture, confirmed by direct inspection

There is no standalone customer registration form. A customer record is created only through a completed purchase (Paystack's hosted checkout page collects the buyer's real email). "Activation" is the customer using an emailed set-password link for the first time, exactly the same mechanism as a password reset. This was confirmed by reading every route `backend/routes/customer/auth.ts` exports: `login`, `logout`, `session`, `forgot-password`, `set-password`, `change-password`. No register or activate endpoint exists anywhere in the codebase.

## Execution log

A test customer was inserted directly into production D1 with the email `lohrobert11+pfat-test@gmail.com` (the user's own address, plus-addressed, so nothing was sent to a third party), then exercised entirely through the real production API, then deleted afterward along with every record it created.

| Step | Result |
|---|---|
| `POST /api/customer/auth/forgot-password` | `{"success":true,"data":{"requested":true}}` |
| Token row created in `customer_password_tokens` | Confirmed: id 7, correct 30-minute expiry window |
| Email logged in `email_log` | template `customer-password-reset`, status `sent`, real Resend `provider_id` returned |
| `POST /api/customer/auth/set-password` with the real token | `{"success":true,"data":{"passwordSet":true}}` |
| Same token reused | `{"success":false,"error":{"code":"INVALID_TOKEN", ...}}`, confirming single-use enforcement |
| `POST /api/customer/auth/login` | Succeeded, returned `customerId`, `email`, `expiresAt` |
| `GET /api/customer/auth/session` while logged in | Correctly returned the authenticated customer |
| `POST /api/customer/auth/logout` | Required the `X-Customer-CSRF-Token` header matching the `customer_csrf` cookie (double-submit CSRF protection); the correct header name is customer-specific and different from the admin panel's `X-CSRF-Token`, which cost two failed attempts before finding the right one in `middleware/customerCsrf.ts`. Once used correctly: `{"success":true,"data":{"loggedOut":true}}` |
| `GET /api/customer/auth/session` after logout | Correctly returned `NOT_AUTHENTICATED`, confirming the session was invalidated server-side, not just a client-side cookie clear |

## Token generation, expiration, single-use: proven, not assumed

The token stored in `customer_password_tokens` was read directly from the database (not from an email) and used against the live API, confirming the full mechanism: a real 256-bit token is generated, stored with a real expiry, consumed exactly once, and rejected on any subsequent use.

## Email delivery: proven for this specific email

The password reset email's `email_log` row showed `status: 'sent'` with a genuine Resend message ID (`provider_id`), which means Resend's API accepted and is attempting delivery. See the Email Delivery Verification Report for what this does and does not prove about final inbox delivery, and for the SPF/DKIM/DMARC findings relevant to "if password emails are not received, why."

## Session behavior

Session issuance, persistence across requests via cookies, and correct invalidation on logout were all confirmed live. Session expiration and "remember me" specifically were not separately exercised (both would require waiting out a real session TTL or inspecting a specific remember-me flag's effect, neither of which was done this pass); the underlying session issuance and invalidation mechanism proven here is the same mechanism either feature would depend on.

## Customer Library Access and Review Eligibility

Not testable against a genuinely new real customer, because no customer in production has ever completed checkout with a real email address (every completed transaction used Paystack's test-mode synthetic email). The download and receipt mechanisms behind Customer Library access were instead verified using an existing real order, documented in the Production Functional Acceptance Report and the Launch Readiness Report.

## Verdict

PASS. Every step of the lifecycle that exists in this codebase was executed successfully against production, including the two failure-mode checks (token reuse, CSRF rejection) that prove the security controls are real, not merely present in code.
