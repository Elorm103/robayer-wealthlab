# Version 5.0 Milestone 1.1 — AI Gateway Operational Hardening

**Engineering Report**

Status: Implementation and local verification complete. Migration application to remote D1 and production deployment are pending explicit founder confirmation (see "Verification performed" below).

Scope: this milestone is operational hardening of the AI Gateway shipped in Milestone 1 — a real-time operations dashboard, a dedicated AI Usage Log admin page with search/filter/export, derived health monitoring, usage analytics charts, a security audit, and architectural preparation (not implementation) for a future shared AI memory layer. No new AI product, no new AI feature, and no expansion beyond what Milestone 1 already shipped (`internal.gateway-diagnostic` remains the only registered feature).

---

## 1. Architecture improvements made

- **Prompt/response capture.** `ai_usage_log` now stores the exact rendered prompt (`prompt_text`) and the provider's response (`response_text`) for every call, gated behind a super_admin-only single-row detail endpoint — never returned by the list endpoint or the CSV export. This is the one genuinely new piece of storage this milestone adds, and it exists solely to satisfy the explicit "a Super Admin may optionally expand a row to inspect: Prompt, Response, Metadata" requirement.
- **Real session attribution.** `ai_usage_log.session_id` now references the actual `admin_sessions` row the call happened under (`requireAuth`'s `AdminAuthContext.sessionId`), threaded through `AiGatewayRequest`. Previously there was no way to tie a call to a specific login session.
- **The diagnostic feature now uses a real stored, versioned prompt.** Until this milestone, the one feature that exists (`internal.gateway-diagnostic`) passed raw `systemPrompt`/`userPrompt` text directly, never exercising `ai_prompts` resolution at all — "Prompt Version" was a dashboard field with nothing real behind it. Migration `0034` seeds `ai_prompts` with `internal.gateway-diagnostic` v1, and `routes/admin/settings.ts` now resolves it via `promptKey` instead of inlining the text. This is a real behavior change to the one existing feature, done deliberately so the dashboard's prompt-version fields report something true rather than a placeholder.
- **The per-call cost cap moved from a hardcoded literal to admin-configurable settings.** `services/ai/aiGateway.ts` itself is unchanged in this respect — `maxCostUsdMicros` is still an optional parameter the caller supplies. What changed is that `handleAiGatewayTest` now reads the cap from `site_settings` (`settingsService.getAiGatewayBudgetConfig()`) instead of the literal `1000` that used to live only in that one route file.
- **Daily/monthly budgets are new, warning-only concepts.** Per an explicit founder decision during this milestone's scoping, these are informational thresholds surfaced on the dashboard and folded into the derived `warnings` array — they never block a call. See "Known limitations" for why this matters.
- **Health status is derived from real usage history, not a synthetic ping.** Per an explicit founder decision, no scheduled heartbeat call to OpenAI was added (a real ping would cost real money on every tick, forever, for a milestone that's about visibility, not spend). `healthStatus` (`healthy`/`warning`/`offline`) and `consecutiveFailures` are computed from the last 50 `ai_usage_log` rows and the API-key-configured flag — see `getAiGatewayDiagnostics()` in `services/admin/settingsService.ts` for the exact derivation rule, reproduced here:
  - **Offline** — API key not configured, or the 3 most recent calls all failed.
  - **Warning** — zero calls ever recorded, or any warning condition is active (elevated 30-day failure rate, cost-cap rejections or rate-limit mentions in the last 7 days, a latency spike, or spend approaching a configured budget).
  - **Healthy** — otherwise.
- **Provider registry snapshot exposed read-only.** `services/ai/routingConfig.ts` gained `getAllRoutingConfig()` — a defensive-copy snapshot of the routing table, used only by the dashboard to show which provider/model (and fallback, if any) serves each registered feature. `callAi()` itself still only ever uses `getRoutingCandidates()`.
- **Reserved (no-op) `memoryContext` field — the "shared memory layer" bonus requirement.** `AiGatewayRequest` gained an optional `memoryContext?: string[]` field, fully documented, read by nothing. This is architecture preparation only, exactly as instructed ("do not implement long-term memory yet"). See "Future recommendations" for what actually implementing it would require.

## 2. New endpoints

All new endpoints are `super_admin`-only (`requireRole(['super_admin'])`), matching the posture Settings already established for Payment/AI Gateway diagnostics — this is stricter than the letter of the brief ("a Super Admin may optionally expand a row"), and the reasoning is in the Security Review below.

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/admin/ai-usage` | Paginated, filterable list (search, date range, feature, provider, status). Never returns prompt/response text. |
| GET | `/api/admin/ai-usage/:id` | Single-row detail, including `promptText`/`responseText`. |
| GET | `/api/admin/ai-usage/export` | CSV export of every row matching the current filters (not paginated). Same exclusion as the list endpoint. |
| GET | `/api/admin/ai-usage/analytics` | Chart-ready aggregates over a rolling window (default 30 days): calls/cost/tokens/latency/success-rate per day, calls per feature, calls per provider. |

`POST /api/admin/settings/ai-gateway/test` (Milestone 1) is unchanged in shape, but now resolves a stored prompt and reads the cap from settings instead of hardcoding both.

`GET /api/admin/settings/status` (Milestone 1) is unchanged in shape at the top level, but its `aiGateway` field grew from 5 fields to 24 — see `AiGatewayDiagnostics` in `services/admin/settingsService.ts` for the full shape.

## 3. New database objects

Migration `0034_ai_gateway_hardening.sql` (additive only, applied to local test DB via the existing Vitest migration runner; **not yet applied to remote D1** — pending confirmation):

```sql
ALTER TABLE ai_usage_log ADD COLUMN session_id INTEGER REFERENCES admin_sessions(id);
ALTER TABLE ai_usage_log ADD COLUMN prompt_text TEXT;
ALTER TABLE ai_usage_log ADD COLUMN response_text TEXT;
CREATE INDEX idx_ai_usage_log_actor ON ai_usage_log(actor_type, actor_id);
CREATE INDEX idx_ai_usage_log_provider ON ai_usage_log(provider);
INSERT INTO ai_prompts (prompt_key, version, template, created_by)
VALUES ('internal.gateway-diagnostic', 1, 'You are a diagnostic health check. Reply with exactly one word: OK.', NULL);
```

No new tables. Three new `site_settings` keys, added to the existing generic key-value settings mechanism (no schema change required for these — `site_settings` already stores arbitrary JSON-typed values): `ai_gateway_cost_cap_usd_micros` (default `1000`, i.e. $0.001), `ai_gateway_daily_budget_usd_micros` (default `null`, unconfigured), `ai_gateway_monthly_budget_usd_micros` (default `null`, unconfigured).

Rollback (documented in the migration's own header): drop the seeded `ai_prompts` row and the two indexes; the three added `ai_usage_log` columns are additive/nullable and safe to leave in place, or removed via SQLite's standard recreate-copy-swap pattern if a true rollback is ever needed.

## 4. Performance impact

- **`GET /api/admin/settings/status`** now runs 9 queries against `ai_usage_log` in parallel (`Promise.all`) instead of 3, to compute the expanded diagnostics. All are indexed (`created_at`, the new `actor_type`/`provider` indexes) and scoped to small windows (today, 7 days, 30 days, or `LIMIT 1`/`LIMIT 50`), except the lifetime `COUNT`/`SUM`, which is an unavoidable full-table aggregate that will grow linearly with total AI Gateway usage — acceptable at today's volume (a handful of diagnostic-test rows), worth revisiting if this table reaches millions of rows.
- **The AI Usage list/export endpoints** are straightforward indexed `SELECT`s with `LIMIT`/`OFFSET` pagination, the same pattern already used by every other paginated admin list in this codebase (Coupons, Orders, Media). CSV export deliberately has no row cap — a filtered export of the entire matching set. At current volume this is trivial; if usage grows into the tens of thousands of rows, an unfiltered export could become a genuinely large response and may need a row-count warning or a background-job pattern later.
- **No change to the hot path.** `callAi()`'s only new per-call work is building one extra string (`promptText`) and binding four more parameters into an `INSERT` it already performs — immaterial.

## 5. Security review

Audited against the seven items requested, each verified directly against the code rather than assumed:

1. **API keys never leave Cloudflare Secrets — confirmed.** `env.OPENAI_API_KEY` is read in exactly one place (`openAiProvider.ts`'s `Authorization` header) and is never logged, never included in any diagnostics field (`openAiConfigured` is a boolean derived from its presence, never its value — same pattern as the pre-existing Payment diagnostics), and never written to `ai_usage_log` (prompt/response text is caller-supplied content, not the secret itself).
2. **Prompt injection protections remain intact — confirmed, and the reason is structural, not a filter.** `callAi()` never passes tool/function-calling capability to the provider (`openAiProvider.ts`'s request body is `{model, messages, max_tokens, temperature}` only — no `tools`/`function_call`), so the model has no mechanism to trigger a privileged action regardless of what it's told to say. The only caller today (`handleAiGatewayTest`) treats the response as opaque display text; nothing parses or executes it. This matches `docs/v5.0-security-architecture.md`'s stated defense: injection can't escalate privilege because the model's output was never wired to a data/action accessor. Note this has not yet been tested against a real feature that accepts untrusted user input into a prompt, because none exists yet — this remains a design principle to hold, not something Milestone 1.1 could exercise end-to-end.
3. **Usage logs cannot expose secrets — confirmed for today's code paths, with one process note.** No code path interpolates a secret value into `prompt_text`, `response_text`, or `error_message`; `openAiProvider.ts`'s error messages are built from the provider's own response body or a generic `fetch()` failure message, never from request headers. This is a per-provider discipline, not something the Gateway enforces structurally — a future, carelessly-written provider implementation *could* accidentally echo a header into an error message. Worth a one-line note in `services/ai/types.ts`'s `AiProvider` interface doc for whoever writes the second provider.
4. **CSRF protections remain — confirmed, consistent with existing convention.** The one mutating AI Gateway endpoint (`POST .../ai-gateway/test`) keeps `requireCsrf`. The four new AI Usage endpoints are all `GET` (pure reads, no state change) and carry no CSRF check, exactly matching every other read-only admin list in this codebase (e.g. `GET /api/admin/coupons`) — CSRF tokens protect state-changing requests; a forged cross-origin GET still can't read the JSON response due to the browser's same-origin policy, and still requires the session cookie, which a third-party page cannot supply.
5. **RBAC remains enforced — confirmed, and slightly stricter than required.** Every new route requires `super_admin`, including the plain list (the brief only required gating the prompt/response expand). This was a deliberate choice: AI cost data is financially sensitive in the same way Payment diagnostics already are, and Settings already gates that entire section at `super_admin`. Practical effect: the "Super Admin may expand a row" requirement is automatically satisfied, since only a super_admin can reach the page at all.
6. **Cost limits cannot be bypassed — mostly true, with one real, honest limitation worth flagging prominently.** The cap check in `callAi()` happens *after* the provider call already completed — meaning the actual OpenAI charge for that call has already been incurred by the time the Gateway decides the response was over budget; the cap prevents the Gateway from treating that response as a normal success and (in a future multi-candidate routing table) tries the next, typically cheaper, candidate instead. It does not, and structurally cannot with today's non-streaming request/response architecture, prevent the underlying provider charge for a single already-made call. Separately: `maxCostUsdMicros` is an **optional** parameter on `AiGatewayRequest` — a future feature that forgets to pass it gets no cap at all. Today's only caller passes it correctly (reading the configured default), but the Gateway itself does not enforce a default when one is omitted. See Future Recommendations.
7. **Provider fallback cannot leak sensitive data — not yet exercisable, and a real forward-looking gap.** Milestone 1.1 ships with exactly one routing candidate per feature (still true after this milestone — `getAllRoutingConfig()` confirms it), so no fallback has ever actually run in production. When a second provider is eventually added, the *current* fallback loop resends the identical prompt to the next candidate on any failure — appropriate for functional continuity, but there is no policy gate today that would stop, say, a PII-bearing prompt from being sent to a second company's servers on fallback without an explicit decision that both providers' data-processing terms permit it. This needs a real design decision before a second provider is wired in, not a code fix now.

## 6. Cost implications

- **No new recurring cost.** Per the founder's explicit decision, health monitoring derives from real call history rather than a scheduled synthetic ping — this milestone adds zero new AI provider spend.
- **The diagnostic test button's cost is unchanged** (a few-cent fraction of a cent per click, gpt-4o-mini pricing, same as Milestone 1).
- **Budgets are informational only** — configuring a daily/monthly figure changes nothing about actual spend; it only changes what shows up in the `warnings` array on the dashboard.

## 8. Known limitations

Restated plainly, in order of how much they matter:

1. **The cost cap is post-hoc, not preventive** — the real provider charge for an over-cap call has already happened by the time the Gateway rejects it. This is a fundamental property of any non-streaming, pay-per-response-token API, not a bug specific to this implementation, but it should not be described to anyone as "spend cannot exceed the cap."
2. **`maxCostUsdMicros` is optional and has no Gateway-enforced default** — a future feature that omits it is uncapped. Today's only caller passes it correctly.
3. **Daily/monthly budgets never block anything** — by explicit design decision this milestone, not an oversight, but worth restating since "budget" ordinarily implies a limit.
4. **No fallback-provider data-policy gate exists yet** — moot today (one provider), a real decision needed before a second one is added.
5. **Storing `prompt_text`/`response_text` widens this table's sensitive-data surface** — arbitrary business/user text now lives in D1 indefinitely, with no retention or purge policy. Acceptable today (the only feature's prompt/response is a fixed, non-sensitive diagnostic string), but this needs a real retention policy decision before a customer-facing feature with PII-bearing prompts ships.
6. **CSV export has no row cap.** Fine at today's volume; worth revisiting if usage grows large.
7. **The lifetime cost/call-count aggregate query is a full-table scan** with no time bound — acceptable at today's volume, will need a materialized/cached figure if this table grows into the millions of rows.

## 9. Future recommendations

- **Decide, deliberately, whether the cost cap should default from `site_settings` when a caller omits it**, and if so, how to do that without creating a circular import between `services/ai/` and `services/admin/` (`settingsService.ts` already imports from `services/ai/routingConfig.ts` in this milestone — the reverse direction needs a different mechanism, e.g. passing the resolved cap down from the route layer, which is the "always require it" fix, or restructuring where cap configuration lives).
- **Before a second AI provider is added,** design the fallback data-policy gate referenced in Security Review item 7 — likely a per-feature or per-provider flag on `routingConfig.ts` entries stating which providers a given feature's data is allowed to reach.
- **Before any customer-facing or PII-bearing prompt ships,** decide a retention/purge policy for `ai_usage_log.prompt_text`/`response_text` — a fixed TTL, a periodic purge job, or excluding certain features from text capture entirely.
- **The reserved `memoryContext` field** (this milestone's bonus architecture prep) is intentionally unimplemented. Actually building it would mean: a new table (or Vectorize index, for retrieval-style memory) to persist conversation turns/retrieved documents/preferences; a real decision about per-actor scoping (customer memory vs. admin memory vs. shared business-knowledge memory are different trust domains and probably need different storage); and a decision about whether memory injection happens inside `callAi()` itself or is resolved by the calling feature before the request is built (the latter keeps the Gateway simpler and matches how `promptKey` resolution already works — the Gateway resolves a *stored* thing, but a feature decides *what* to resolve). None of this is scoped for the next milestone by this report; it's flagged here only so the field's existence doesn't get forgotten.
- **Consider a lightweight materialized "AI Gateway daily rollup" table** once usage volume makes the lifetime aggregate query noticeably slow — not needed yet.
