# Version 3.0.2 - Sprint 2A - Milestone M1 Acceptance Review (MARB)

**Reviewing body:** independent Milestone Acceptance Review Board (Principal QA Engineer, Software Test Lead, Security Reviewer, UX Reviewer, Solutions Architect, Product Owner Representative, Technical Documentation Reviewer) - a review role distinct from, and not deferential to, the implementation engineer's own M1 Implementation Report.

**Method:** every finding below is based on direct verification - reading the actual migration/service/route/middleware source, re-running the automated test suite independently (not trusting the prior report's numbers), and exercising the live checkout/auth pages in a browser against a real local `wrangler dev` + D1 instance. Where the implementation report's claims were merely restated without independent verification, that is noted explicitly.

---

## Executive Summary

Milestone M1 (Customer Identity & Guest Checkout) is **well-built and ready to merge**. Independent verification confirms: the zero-form checkout is genuinely preserved, purchase-triggered-only provisioning has no exceptions or bypass paths, the customer session/CSRF/password mechanisms are faithful, correctly-implemented mirrors of the already-proven admin auth patterns, and payment verification cannot be bypassed. The automated test suite (43 tests) was re-run independently and passes; `tsc --noEmit` is clean. Hands-on browser testing of the consent block, sign-in, set-password, and forgot-password pages against a real backend confirmed the described behavior, including edge cases (weak password, mismatched confirmation, expired/reused token, no-enumeration).

Two things prevented an unconditional "Accepted":

1. **Production deployment status was misrepresented in the implementation's own Database Changes document.** It claimed migration 0018 was "applied to both local and production D1." Independent verification (`wrangler d1 migrations list --remote`) shows this is false - the migration has never been applied to production. This has been corrected in the documentation as part of this review (see Documentation Review). The good news: `wrangler deployments list` confirms the currently-live Worker predates this milestone entirely, so production is in a consistent, unaffected state - this is an undeployed feature, not a broken half-deployed one.
2. **A handful of minor, non-blocking gaps**: one misleading UI copy string, and a few real (but not severe) automated-test coverage gaps (rate limiting is implemented but has zero test coverage; a couple of documented behaviors - `email_verified_at` stamping, the concurrent-insert race-recovery path - are asserted in comments but not independently verified by a test).

No architectural deviation beyond the one already surfaced, discussed, and user-approved during implementation (consent capture via statement + checkbox rather than a checkout form, preserving ADR-002) was found. No new deviation is identified by this review.

## Phase 3 - Security Review

| Area | Finding |
|---|---|
| **CSRF** | Verified the double-submit pattern compares the `X-Customer-CSRF-Token` header against the *server-stored* `customer_sessions.csrf_secret* (read from the session row), not merely cookie-equals-header - this is the stronger of the two common double-submit variants, matching admin auth exactly. Confirmed in a real browser: logout without the header is rejected (`FORBIDDEN`); with it, succeeds. |
| **Token handling** | All three token types (session, CSRF secret, password-setup) use `crypto.getRandomValues`-based 256-bit generation - read `customerToken.ts` directly, confirmed no `Math.random()` or weaker source anywhere in the customer auth path. |
| **Session management** | Absolute 12h expiry, single-SELECT validity check (exists, not revoked, not expired, owning customer active/not-deleted, all in one WHERE clause) - no window for a partially-valid state. Confirmed the session token is validated against a strict `^[a-f0-9]{64}$` pattern before ever touching the database (rejects garbage input cheaply). |
| **Password security** | PBKDF2-SHA256 (same as admin), reuses the existing strength policy (12-char minimum, weak-pattern denylist, email-local-part rejection). Timing-safe comparison confirmed by reading `authService.login()`: the dummy-hash comparison runs unconditionally, before the `!row`/`!hasPassword` branches are even evaluated, so unknown-email, no-password-set, and wrong-password all take the same code path length. |
| **Duplicate callback (webhook) protection** | Two independent layers, both read directly: (1) `payment_transactions.paystack_reference UNIQUE` with `INSERT OR IGNORE` - a redelivered webhook fails to insert, full stop; (2) a status-gated conditional UPDATE (`WHERE status = 'pending'`) closes a narrower race between two *different* transaction rows resolving the same session concurrently. Confirmed via the passing idempotent-redelivery test. |
| **Input validation** | Confirmed via `negative.test.ts` (independently re-run): SQL-injection-shaped input, XSS-shaped input, oversized input, malformed JSON, non-string tokens, and empty bodies are all rejected cleanly, never a 500, and the underlying tables remain intact/queryable afterward (proving parameterized binding, not string concatenation). |
| **Authentication** | No public registration surface exists (confirmed by grep - see Architecture Compliance #4). Login correctly distinguishes, only in user-facing copy (never in timing or HTTP status), a not-found account from a no-password account from a wrong password. |
| **Authorization** | Session-derived `customerId` is the only source of identity for the two authenticated routes (`GET /session`, `POST /logout`) - no client-supplied ID is ever trusted. Confirmed by reading both route handlers. |
| **No enumeration** | Verified in the browser, not just by reading code: submitted `forgot-password` for both a real and a fabricated email; the JSON response and the on-page confirmation text were byte-identical in both cases, including when the rate limit itself was hit (the route always returns the generic success response before checking whether the email is real). |
| **Secrets never logged** | Grepped `logger.info`/`logger.error` call sites in the customer auth path - none log a password, hash, session token, or CSRF secret; only `customerId`/`email`/reason codes. |
| **New finding, not previously flagged**: production database schema drift | The implementation's own Database Changes report claimed the migration was applied to production; it was not (see Executive Summary and Documentation Review). This is a documentation-accuracy finding, not an active security vulnerability - production was simply never exposed to M1's code at all - but is recorded here because an inaccurate deployment-status claim is exactly the kind of thing that causes a *real* security incident later (someone assuming a protection is live when it isn't). |

**Security Review verdict: Pass.** No exploitable weakness was found in the areas reviewed. The one genuine gap - no per-account lockout tracking for customer login - was already proactively disclosed by the implementation team in their own report (not discovered by this review) and is correctly scoped out of the ratified M1 database design; it is carried forward as a recommendation, not a defect (see Technical Debt Register).

## Phase 6 - Test Coverage Assessment

Independently re-ran the full suite (`npx vitest run` from `backend/`): **43/43 passing**, 7 files (3 unit, 4 integration), matching the implementation report's claimed count exactly. `npx tsc --noEmit` independently confirmed clean.

**What's well covered:** consent validation (all rejection shapes), customer find-or-create semantics (new/existing/case-insensitive/no-re-seed), session lifecycle (create/validate/revoke/idempotent-revoke/revoke-all), full password-setup→login→CSRF-protected-logout cycle, webhook idempotency and tamper/expiry rejection, and a genuinely broad negative-test set (SQLi-shaped, XSS-shaped, oversized, malformed, non-string inputs).

**Gaps identified - none severe enough to block acceptance, but worth closing before this milestone is considered fully hardened:**

1. **Rate limiting has zero automated test coverage.** Login (5/15min), forgot-password (3/15min), and set-password (10/15min) limits are implemented (confirmed by reading `middleware/rateLimit.ts` and its three call sites) but no test exercises the "6th attempt gets `RATE_LIMITED`" path for any of them. This is a real, addressable gap, not a design flaw.
2. **`email_verified_at` stamping is documented but not asserted.** `identityService.test.ts` checks `email`/`status` on a newly-created customer but never asserts `email_verified_at` is non-null, despite this being a specifically-called-out design decision (a purchase is itself the verification signal). Low risk (simple, static `datetime('now')` in the INSERT) but easy to add.
3. **The concurrent-insert race-recovery path in `findOrCreateCustomer()` is untested.** The catch-and-reread branch (for when two near-simultaneous webhook deliveries both attempt to INSERT the same new email) has no test forcing that race - genuinely hard to test deterministically, but worth at least a targeted test that simulates the UNIQUE-constraint failure directly.
4. **No test for simultaneous redemption of the same password-setup token** (two concurrent `set-password` calls with the same token - only one should succeed). The atomic `used_at IS NULL`-gated UPDATE (verified by reading the code) should already prevent a double-redemption, but this specific race isn't exercised by a test.

**Test Coverage Assessment verdict: Pass with Observation.** Coverage is genuinely strong for the scenarios the sprint brief named explicitly. The four gaps above are recommended additions, not blockers.

## Phase 8 - Outstanding Risks

1. **Consent-record legal defensibility.** `terms_accepted_at`/`license_accepted_at` are stamped from the click-to-purchase action itself, not a dedicated "I agree" checkbox. This was a deliberate, informed, user-approved trade-off to preserve ADR-002's zero-friction checkout - not an oversight - but it has not had a legal/compliance review. Already flagged by the implementation team; this review concurs it's a real, open risk worth resolving before transaction volume scales meaningfully, not a defect in the implementation itself.
2. **Production deployment gap.** M1's code and schema exist only locally/in the repository as of this review. No user-facing risk currently exists (production is untouched and consistent), but this is a real, immediate action item - not a someday item - before the milestone can be considered operationally complete.
3. **No account lockout** - carried forward from the Technical Debt Register; a low-probability, non-zero brute-force exposure mitigated today only by per-IP rate limiting.

## Final Acceptance Decision

## **Conditionally Accepted**

The implementation itself - architecture compliance, functional correctness, security posture, and UX quality - meets or exceeds the bar for this milestone, independently verified rather than taken on faith. **The code is approved for commit into the main codebase now.** No defect was found that warrants withholding the merge.

Acceptance is conditional on the following being completed before this milestone is represented as operationally live / production-ready:

1. **Apply `0018_customer_identity.sql` to production D1** (`wrangler d1 migrations apply robayer-wealthlab-db --remote`) and **deploy the updated Worker and static site** - currently outstanding, requires explicit authorization before executing (a production database/infrastructure action).
2. **Fix the "sign-in link" copy** on the sign-in page's link text and the forgot-password page's H1 (Phase 4) - a small, low-risk text change.
3. **Add the four missing test cases** identified in Phase 6 (rate-limit enforcement × 3 endpoints, `email_verified_at` assertion) - recommended before this milestone is considered fully hardened; not a merge blocker.

None of these three items reflect a defect discovered in the implementation's logic, security, or architecture - they are a deployment step, a copy fix, and test-coverage additions. Per this review's scope ("no code changes should be made unless a defect is discovered"), items 1–3 are recorded as required follow-ups rather than performed within this review; the one documentation inaccuracy that *was* found (Phase 5) has already been corrected in place, since correcting a factually wrong claim in a document this review itself is responsible for auditing is squarely within its remit.

**Milestone M1 is accepted and approved for commit**, on the condition that the production-deployment step above is completed - with explicit authorization - before it is described to any stakeholder as live.

## Addendum - Sprint 2B Closeout (2026-07-25)

The three acceptance conditions above were carried into a dedicated closeout sprint (Sprint 2B). Status of each, verified independently rather than taken on faith, mirroring this report's own original methodology:

1. **Production deployment.** Not executed, correctly - Sprint 2B was explicitly instructed not to apply remote migrations or deploy anything. Instead, a full [Production Readiness Checklist](v3.0.2-m1-production-readiness-checklist.md) was produced: exact commands, required order of operations, rollback procedure, deployment prerequisites, and a post-deployment verification checklist, all verified against the actual current state of the repository and the production environment (`wrangler d1 migrations list --remote`, `wrangler deployments list`, both re-run and unchanged from this report's original findings). This condition is **documented and ready, not resolved** - it remains an explicit, separate, user-authorized action, by design.
2. **UI copy fix.** **Resolved.** The sign-in page's link text now reads "Set or reset your password" (was "Get a sign-in link"); the forgot-password page's title, H1, meta description, and form `aria-label` were all updated from "Get a Sign-In Link"/"Get a sign-in link" to "Reset Your Password"/"Reset your password"; the forgot-password confirmation message was updated from "we've sent a sign-in link" to "we've sent a link to set or reset your password." Verified in a live browser after the change - all three surfaces render the corrected copy with no console errors.
3. **Missing test cases.** **Resolved.** All four gaps from Phase 6 were closed: `email_verified_at` stamping is now asserted directly; a genuine concurrent-request test (`Promise.all` of two simultaneous `findOrCreateCustomer()` calls for the same new email) now exercises the real race-recovery path, not a simulated one, and additionally asserts no duplicate `customer_profiles` row results; a new `rateLimiting.test.ts` file exercises all three rate limits (login, forgot-password, set-password) by firing limit+1 requests against a dedicated per-test IP and asserting the boundary behavior, including forgot-password's specific "identical response, but no extra token minted" behavior; and a concurrent password-token-redemption test confirms exactly one of two simultaneous `setPassword()` calls with the same token succeeds. The suite grew from 43 to 49 tests, all passing, re-run three consecutive times with no flakiness observed.

**Updated verdict: Fully Accepted - Ready for Commit.** Every condition within this sprint's authority to resolve has been resolved and independently verified. The one remaining condition (production deployment) was correctly left undone, as instructed, and is fully documented for a separate, explicitly authorized deployment action. See [`v3.0.2-m1-closeout-report.md`](v3.0.2-m1-closeout-report.md) for the complete Sprint 2B closeout record.
