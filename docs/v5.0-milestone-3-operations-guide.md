# Customer AI v1 — Operations Guide

**For: whoever operates/maintains this system going forward**

## What runs where

| Component | Location | Notes |
|---|---|---|
| Public chat page | `ai-assistant/index.html` + `js/components/ai-assistant.js` | Static, GitHub Pages |
| Ask/feedback API | `backend/routes/customer/aiAssistant.ts` → `backend/services/customerAi/answerService.ts` | Cloudflare Worker |
| Admin analytics page | `admin/customer-ai/index.html` + `js/components/admin/admin-customer-ai.js` | Super-admin only, GitHub Pages |
| Admin analytics API | `backend/routes/admin/customerAi.ts` → `backend/services/admin/customerAiAnalyticsService.ts` | Cloudflare Worker |
| Data | D1 tables `customer_ai_messages`, `customer_ai_message_citations`, `customer_ai_feedback` | Migration `0039_customer_ai.sql` |

## Day-to-day monitoring

Log in as a super-admin and visit **`/admin/customer-ai/`**. It shows, reading from real production data:
- Total messages, and the answered/declined/error split
- Confidence distribution across all four tiers (high/medium/low/very_low)
- Feedback totals (helpful vs. not helpful)
- Average and p95 latency, broken into retrieval time vs. LLM time
- The 25 most recent conversations, with status/confidence/latency/feedback per turn

A rising **`declined` (very_low)** rate over time is the single most useful signal that customers are asking things the Knowledge Base doesn't cover yet — see "What to do when declines are high" below.

A rising **`error`** rate points to an AI Gateway or upstream provider problem, not a Knowledge Base gap — check `ai_usage_log` for the `customer.chat` feature (same governance/audit trail every other AI Gateway caller uses) for the underlying provider error.

## Cost and budget

Every Customer AI turn that reaches the LLM (i.e., every tier except `very_low`) is a real, governed `callAi()` invocation under the `customer.chat` feature key, routed to `openai/gpt-4o-mini` (`services/ai/routingConfig.ts`). It is subject to the exact same budget/cost controls as every other AI Gateway caller (Milestone 1.2) — preventive per-request cap, post-call safety net, and (if configured) a daily platform-wide budget. No separate budget mechanism was built for Customer AI; it inherits the platform's existing one.

The `very_low` tier costs nothing beyond one small embedding call (retrieval always runs; generation does not).

## Rate limiting

- `POST /ask`: 15 requests / 5 minutes / IP (`middleware/rateLimit.ts`, KV-backed, endpoint key `customer-ai-ask`)
- `POST /feedback`: 30 requests / 5 minutes / IP (endpoint key `customer-ai-feedback`)

If a legitimate high-traffic period is expected, these limits live in `backend/routes/customer/aiAssistant.ts`'s `ASK_RATE_LIMIT`/`FEEDBACK_RATE_LIMIT` constants — adjust and redeploy, same as any other rate-limited endpoint in this codebase.

## What to do when declines (`very_low`) are high

This means customers are asking about topics the Knowledge Base genuinely doesn't cover — not a bug. Steps:
1. Check `/admin/customer-ai/`'s recent-conversations table for the actual declined questions.
2. If a pattern emerges (e.g., many questions about a topic Robayer WealthLab doesn't yet publish on), that's a content gap, not an engineering one — flag it for the content/knowledge team.
3. If the questions ARE covered by existing content but still declining, that's a retrieval-quality regression — this would be a Knowledge Base issue (Milestone 2/2.1/2.2), and per the founder's standing instruction, the Knowledge Base should only be revisited if a genuine production defect is found there. Use the Knowledge Base's own Search Diagnostics tool (`/admin/knowledge-base/`) to investigate before concluding it's a defect.

## Content changes and re-indexing

Customer AI does not index anything itself — it only ever calls the existing `searchKnowledge()`. If new content is published on the site, it needs to go through the Knowledge Base's own indexing pipeline (Milestone 2/2.1), same as before this milestone existed. Nothing in Customer AI needs to be touched or redeployed when Knowledge Base content changes.

## Redeploying

Standard flow, same as every other milestone in this project:
```bash
cd backend
npx wrangler deploy
```
Frontend changes: commit and `git push origin main` — GitHub Pages builds automatically. There is no separate Customer AI deploy step; it deploys as part of the normal Worker/Pages deploy.

## Rolling back

- **Worker**: `wrangler rollback` (or `wrangler rollback <VERSION_ID>`) to the pre-Milestone-3 version. The new routes will simply stop resolving; the frontend page will show its error state gracefully (it never assumes the API exists).
- **Migration**: per `0039_customer_ai.sql`'s own header comment, rollback is `DROP TABLE customer_ai_feedback; DROP TABLE customer_ai_message_citations; DROP TABLE customer_ai_messages;` — safe, since nothing outside this milestone's code reads these tables.
- **Frontend**: revert the commit and push; GitHub Pages rebuilds from the reverted state.

## Known operational caveat

Production currently has no admin-only Knowledge Base content indexed, so the visibility filter that keeps admin-only content out of customer answers has been verified at the code level but not against real classified data in production. If admin-only content is ever indexed, spot-check a few customer-facing questions related to that content's topic to confirm it stays excluded — see [Known Limitations](v5.0-milestone-3-known-limitations.md).
