# Version 3.1 - Milestone M3 Frontend Component Inventory & Reference

Checkout Auto-Provisioning & Dashboard MVP. Covers every new frontend
page and component shipped in Sprint M3B, plus the two small existing
files that were modified. No framework, build step, or router was
introduced - every page below is static HTML using the site's existing
`data-include`/`partials:loaded` progressive-enhancement pattern,
matching `admin/`'s established conventions exactly.

## Pages (new)

| Page | Route | Requires session | Description |
|---|---|---|---|
| `dashboard/index.html` | `/dashboard/` | Yes | My Library - one card per purchased product, with download and receipt actions |
| `dashboard/purchases/index.html` | `/dashboard/purchases/` | Yes | Purchase History - transaction-facts list (date, reference, amount, status) |
| `dashboard/receipts/index.html` | `/dashboard/receipts/` | Yes | Receipts - list with direct PDF download links |
| `dashboard/licenses/index.html` | `/dashboard/licenses/` | Yes | Licenses - truncated license key per purchase, with copy-to-clipboard |
| `dashboard/security/index.html` | `/dashboard/security/` | Yes | Account Security - profile, change password, active sessions |

Every page includes, in this order: `header.html` (site header, shared
sitewide), `dashboard-nav.html` (dashboard-only nav), then its own
`data-account-*`/`data-*-root` markup, then `footer.html`. All five
share the identical `<script>` include order: `includes.js`, `nav.js`,
`theme-toggle.js`, `branding.js`, `content-inject.js`,
`dashboard-auth.js`, `dashboard-shell.js`, the page's own component
script, `main.js`.

## Partials (new)

### `partials/dashboard-nav.html`
Five-link nav (My Library / Purchase History / Receipts / Licenses /
Account Security) plus the signed-in email and a logout control.
Hooks: `data-dashboard-nav-link` (one per link, `aria-current="page"`
set by `dashboard-shell.js` based on the current path),
`data-dashboard-nav-email`, `data-dashboard-nav-logout`.

## Scripts / Components (new)

### `js/components/dashboard-auth.js`
Pure library, no DOM wiring - direct mirror of
`js/components/admin/admin-auth.js`. Exposes `window.CustomerDashboard
= { customerFetch, requireSession, logout, getCsrfToken }`.
`customerFetch()` is a CSRF-aware `fetch` wrapper that unwraps the
`{success,data}`/`{success:false,error}` envelope into a resolved
value or a thrown `Error` carrying `.code`. `requireSession()` calls
the session-check endpoint and redirects to
`/checkout/sign-in/?redirect=<current-path>` on failure, never
resolving after issuing that redirect (so calling code never
accidentally continues to run against an unauthenticated state).

### `js/components/dashboard-shell.js`
The UI-wiring counterpart to `dashboard-auth.js` - mirrors
`admin-shell.js`. Runs on `partials:loaded`: calls
`requireSession()`, renders the signed-in email into the nav, marks
the active nav link, binds the logout control, then dispatches a
`dashboard:ready` CustomEvent (with `{ detail: { email } }`) that
every page-specific component below listens for exactly once before
doing its own first data fetch.

### `js/components/library-list.js`
Drives `dashboard/index.html`. On `dashboard:ready`, fetches the
purchase list and renders one `.library-row` card per purchase: title,
status badge (`ready` -> `badge--success`, `processing` ->
`badge--info`, `refunded` -> `badge--warning`, `unavailable` ->
`badge--error`), a Download button per asset (mints a fresh single-use
token via `POST /api/purchases/:reference/downloads`, then navigates
to the redeem URL - the response itself is the file), and a "View
receipt" link (direct `<a>` to
`/api/customer/receipts/:receiptNumber/download`, no mint step needed
since receipt download is not single-use). Empty, loading, and error
states all present via `hidden` toggling on dedicated markup blocks,
matching this site's existing progressive-enhancement convention.

### `js/components/purchase-history-list.js`
Drives `dashboard/purchases/index.html`. Same underlying
`/api/customer/purchases` data as My Library, rendered instead as a
transaction list: date, purchase reference (monospace), amount,
status badge.

### `js/components/receipts-list.js`
Drives `dashboard/receipts/index.html`. Fetches
`GET /api/customer/receipts`, renders direct download links to the
existing M2 receipt-download endpoint.

### `js/components/licenses-list.js`
Drives `dashboard/licenses/index.html`. Fetches
`GET /api/customer/licenses`, renders a truncated license key per row
with a copy button (`navigator.clipboard`, falling back to
`document.execCommand('copy')` where unavailable) - mirrors
`admin-media.js`'s own existing copy-to-clipboard implementation.

### `js/components/account-security.js`
Drives `dashboard/security/index.html`. Structural mirror of
`admin-account.js`: renders the signed-in email; binds the
change-password form (`POST /api/customer/auth/change-password`,
mismatched-confirmation caught client-side before any request is
sent); loads and renders the active-sessions list
(`GET /api/customer/sessions`), with a "Sign out" button per
non-current session that calls
`POST /api/customer/sessions/:id/revoke` after an explicit
`window.confirm()` (AR-009 - the one deliberate difference from the
admin equivalent, added specifically for this customer-facing
destructive action). Reuses `admin-account.js`'s own
`formatDate()`-style mixed-timestamp-format normalization (see
"Notable Fix Reused Proactively" below).

## CSS (extended, additive-only)

`css/components.css` - one new section ("DASHBOARD", appended before
the existing dark-mode-override block): `.dashboard-nav`,
`.dashboard-nav__links` (+ `a[aria-current="page"]` active-state
styling), `.dashboard-nav__account`, `.library-row` (+ `__meta`,
`__title`, `__actions`, `__usage`), `.library-empty-state`,
`.session-row`. Built entirely from existing design tokens (`.card`,
`.btn`, `.badge`, `.field` families) - no new visual language, per
`v3.1-m3-ux-strategy.md`'s "reuse, do not reinvent" rule. One token
misuse was found and fixed during this sprint's own browser
verification: see the Implementation Report's Testing Results section
for the dark-mode contrast defect and fix.

## Notable Fix Reused Proactively

`admin-account.js`'s own header comment documents a real,
previously-discovered bug: `last_seen_at` can be written in two
different timestamp formats (`datetime('now')`'s space-separated SQL
form, or JS's `toISOString()`'s `T`/`Z`-suffixed form) depending on
the write path, and naively parsing the SQL form produces
`Invalid Date`. Since `customer_sessions.last_seen_at` has the
identical dual-write-path shape, the same normalization fix
(`isoString.includes('T') ? isoString : isoString.replace(' ', 'T') +
'Z'`) was proactively applied to every new M3 component's own
`formatDate()` (`library-list.js`, `purchase-history-list.js`,
`receipts-list.js`, `licenses-list.js`, `account-security.js`) before
it could cause the same bug to resurface here.
