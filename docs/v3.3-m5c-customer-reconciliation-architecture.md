# Version 3.3 Milestone M5C: Customer Reconciliation Architecture

Covers Phase 2 of the M5C sprint brief: historical guest purchase recovery, verified ownership by payment email, secure account claiming, duplicate prevention, and audit logging.

## Problem

Milestone M1 (Version 3.0.2) introduced purchase-triggered account auto-provisioning: every verified purchase since M1 automatically gets a `customers` row via `identityService.findOrCreateCustomer()`, called from `commerceService.ts`'s webhook handler. Purchases verified before M1 shipped (and any other historical edge case that left `purchase_sessions.customer_id` unset) have no account behind them at all, even though the purchase itself is real and verified. These customers can download nothing from a dashboard and cannot log in, because no account exists for them to log into.

## Design

### ADR-006 compliance

Docs/v3.0.2-architecture-decision-register.md's ADR-006 ("Purchase-triggered account provisioning only") states there is no public registration endpoint anywhere in this project. Reconciliation does not violate this. `reconciliationService.reconcilePurchases()` is a second call site for `findOrCreateCustomer()`, gated exclusively on at least one already-existing `purchase_sessions` row with `status = 'verified'` and `customer_id IS NULL` for the submitted email. An email with no matching purchase creates nothing. This is purchase-triggered provisioning, contemporaneous (the webhook) or historical (this flow), never registration-triggered.

Both `services/customer/identityService.ts` and `routes/customer/auth.ts`'s header comments were updated to describe this second call site accurately, rather than left claiming "the one place" and "no public registration endpoint anywhere," which would now be stale and misleading.

### Ownership verification

`purchase_sessions.customer_email` is populated only from Paystack's own confirmed payer email at verification time (`commerceService.ts`'s webhook handler), never trusted from the client. This is the identical trust boundary the existing password-reset flow already relies on (a token emailed to the address on file, never a claim accepted on the strength of a typed-in email alone) — a boundary that has already survived independent security review at Milestones M3 and M4. Reconciliation introduces no new, weaker trust level.

### Two-step effective security, one-step implementation

The actual sequence is:

1. A visitor submits an email to `POST /api/customer/reconcile-purchases` (unauthenticated, rate-limited 3/15min, no-enumeration — see below).
2. If any unclaimed verified purchase exists for that email, the matching rows are immediately linked (`customer_id` set) and a customer row is created if one doesn't already exist. An audit log entry is written.
3. A password-setup email (`customer-purchase-reconciliation` template) is sent to that same provider-verified email, via the existing `issuePasswordToken()` mechanism (30-minute single-use token).
4. The account cannot actually be used by anyone until step 3's link is redeemed and a password is set — an account with `password_hash IS NULL` cannot log in (ADR-002/ADR-006, unchanged).

Step 2 happening before step 3's link is clicked might look like "ownership transfer without proof of inbox access," but it isn't: linking a purchase to a customer row is not itself an access grant. Only a successful login is, and login requires a password, and setting a password requires redeeming the emailed link, which requires inbox access. This mirrors the existing webhook auto-provisioning flow exactly (customer row created immediately at verification, password set later via an emailed link) rather than introducing a new pattern.

### Duplicate prevention

The linking `UPDATE` is gated on `customer_id IS NULL`. A second call to reconcile the same email finds zero unlinked rows and is a structural no-op — no separate "already reconciled" flag, no extra bookkeeping. Verified directly: calling `reconcilePurchases()` twice for the same email produces exactly one `audit_logs` row, not two (`tests/unit/reconciliationService.test.ts`).

### No unauthorized ownership transfer

A `purchase_sessions` row that already has a `customer_id` set is never touched by reconciliation (the `customer_id IS NULL` gate excludes it entirely) — an attacker who knows a victim's email cannot cause an already-claimed purchase to move to a different account by calling this endpoint. Verified directly in `tests/unit/reconciliationService.test.ts`'s "never touches a purchase that already belongs to a different customer" test.

### No-enumeration

`POST /api/customer/reconcile-purchases` always returns the identical generic `{ requested: true }` response, whether or not the submitted email had any unclaimed purchase — replicating `handleCustomerForgotPassword()`'s exact discipline in `routes/customer/auth.ts`, including under rate-limiting (the rate-limited branch returns the same shape, not a distinct error).

## Email

A new email template, `customer-purchase-reconciliation`, distinct from both `customer-welcome` (a fresh checkout, not a recovered historical one) and `customer-password-reset` (not a forgotten password) — `authService.issuePasswordToken()`'s `template` union was extended with a third value to select it.

## Frontend

`/checkout/claim-purchase/` — a new page mirroring `/checkout/forgot-password/`'s structure and progressive-enhancement pattern exactly (`js/components/claim-purchase-form.js` mirrors `forgot-password-form.js`). Linked from both `/checkout/sign-in/` and `/checkout/forgot-password/` so a customer with no account and no memory of ever setting a password can find it.

## Testing

`tests/unit/reconciliationService.test.ts` (9 tests) and `tests/integration/m5cActivation.test.ts`'s reconciliation-route tests cover: new-customer creation, multi-purchase linking, no-op for no match, reuse of an existing customer, duplicate prevention, cross-customer isolation, audit logging, unverified-purchase exclusion, and case-insensitive email matching.
