# Version 5.0 — Milestone 2.2 Engineering Report

**Retrieval Quality Calibration & Search Optimization**

## 1. Scope and Constraint

Per the brief: improve retrieval quality, ranking, confidence scoring, and diagnostics using evidence from Milestone 2.1's real production search results — explicitly **not** an architecture redesign. Every task below either operates inside `services/knowledge/searchService.ts`'s existing pipeline or adds narrowly-scoped, additive infrastructure (one new module, one migration, one new admin service) without touching the queue/Vectorize/D1 architecture Milestone 2.1 already validated in production.

## 2. Task 1 — Confidence Threshold Recalibration

**File:** `backend/services/knowledge/ranking.ts`

The original thresholds (`high ≥ 0.75`, `medium ≥ 0.5`) were Milestone 2's own documented placeholders, set before any real query had run. Milestone 2.1's verification produced 35 real scored results across 7 representative queries — the actual calibration dataset for this task.

The key finding that shaped the new thresholds: raw cosine similarity in this corpus (a single site's own short, topically-overlapping pages, embedded with `text-embedding-3-small`) does not range up near 0.8–0.95 the way generic cosine-similarity intuition suggests — even an unambiguous exact match (Privacy Policy page, for the query "What does the Privacy Policy say?") scored 0.482 raw cosine. Recalibrating against raw cosine alone would have required an uncomfortably low "high" cutoff that also captures weaker matches.

Instead, thresholds were recalibrated against the **blended** score (post-reranking, see Task 2) — real, hand-verified boost contributions for known-correct results (Privacy Policy, Terms of Use, Treasury Bills, Investment Centre) landed in the 0.61–1.0 range once title/keyword boosts were included, while the known-imperfect "resources" query's best result blended to ~0.50. This put the boundary between "confidently correct" and "plausible but uncertain" at:

```
CONFIDENCE_HIGH_THRESHOLD = 0.6
CONFIDENCE_MEDIUM_THRESHOLD = 0.45
```

These are documented in code as a **first, evidence-grounded pass, not a final answer** — real production re-verification (§6) confirmed the pass/fail outcomes the hand-estimates predicted, but the underlying dataset is still only 7 queries. Task 4's analytics (14-day low-confidence trend) exist specifically so these can be revisited against a larger real sample over time.

## 3. Task 2 — Lightweight Hybrid Reranking

**File:** `backend/services/knowledge/ranking.ts` (`computeRankingSignals`)

No external rerank API, per the brief. Implemented as a blend of Vectorize's cosine similarity with three cheap, in-repo lexical signals computed from data `searchService.ts` already has from its D1 join — no extra queries:

```
finalScore = min(1, vectorSimilarity + titleBoost + keywordBoost + sourceBoost)

titleBoost   = (query tokens found in document title / total query tokens) × 0.25
keywordBoost = (query tokens found in chunk text / total query tokens)     × 0.15
sourceBoost  = 0.08 if the query contains a trigger word for the chunk's source_type, else 0
```

Tokenization (`tokenize()`) lowercases, strips punctuation, drops ~60 stopwords, and applies a deliberately crude singular/plural normalization (strip one trailing "s" on words ≥4 characters) — enough to match "resources" against a document containing "resource" without a stemming library or over-matching short words.

The source-type boost directly implements the brief's own suggestion ("boost source relevance"): a small, generic trigger-word map (`resource → resource/guide/download/template/freebie/checklist`, `product → book/ebook`, `blog_post → blog/article/post`), not hardcoded to any single example query.

**Real, measured limitation, not a hypothetical one:** the source-type boost only applies to candidates Vectorize already returned in its top-K. Production re-verification (§6) confirmed the Resources query's actual resource document never enters that candidate pool at all — `source boost +0.000` appeared on every one of the 5 returned results, none of which were the resource item, because the boost had nothing to apply to. Reranking cannot rescue a document that was never fetched.

## 4. Task 3 — Search Diagnostics Score Breakdown

**Files:** `backend/services/knowledge/searchService.ts`, `admin/knowledge-base/index.html`, `js/components/admin/admin-knowledge-base.js`

`KnowledgeSearchResult` gained four fields (`vectorSimilarity`, `titleBoost`, `keywordBoost`, `sourceBoost`) alongside the existing `score`/`confidence`, all computed once in `searchKnowledge()` and passed straight through — no duplicate computation. The admin UI renders each result with an inline breakdown line (`vector similarity X · title boost +Y · keyword boost +Z · source boost +W · final N → confidence`), directly answering "why did this rank here" without needing to read logs or code.

## 5. Task 4 — Search Analytics

**File:** `backend/services/admin/knowledgeSearchAnalyticsService.ts` (new)

Aggregates entirely from `knowledge_search_log` (no new logging path — every field was already being written, or is now written via migration 0038's `top_document_id` addition):

- Total searches, success rate (non-zero-result / total), average confidence score
- Latency p50/p95/max
- Confidence distribution (high/medium/low/zero-result counts)
- Most common searches (`GROUP BY query_text`)
- Zero-result searches
- Most retrieved documents (`GROUP BY top_document_id`, requires the new column)
- 14-day low-confidence trend (daily count of searches whose top result was low-confidence)

Explicitly scoped as "the beginning of search observability, not a full analytics suite" in both code comments and the admin UI's own copy — matching the brief's "prefer correctness... over complexity."

## 6. Task 5 — Embedding Version Tracking

**Migration:** `0038_knowledge_base_quality.sql` — `knowledge_documents` gains `embedding_model`, `embedding_version`, `embedded_at`, `embedding_refreshed_at`.

`embedding_version` is deliberately a distinct, app-level string from `embedding_model` (the raw provider model name already tracked per-chunk) — bumped only when this project changes its own chunking/embedding *strategy*, not when OpenAI changes a model name. `embedded_at` is set once via `COALESCE(embedded_at, datetime('now'))` (first successful index only); `embedding_refreshed_at` updates on every successful (re-)index. Written in `indexingService.ts`'s `writeDocumentIndexedState()`, in the same UPDATE that already sets `status = 'indexed'` — no extra D1 call.

**Honest note confirmed during production verification:** all 38 documents currently show "Not yet embedded" for these new fields. This is expected, not a bug — those documents were indexed by the last Full Rebuild, which ran *before* this milestone's code (and migration) existed. The fields populate retroactively on each document's next reindex; this is precisely the intended behavior for a "which documents need attention after a future model upgrade" feature.

## 7. Task 6 — Content-Change Re-Index Infrastructure (Built, Not Activated)

**File:** `backend/services/knowledge/indexingService.ts` — `enqueueContentChangeReindex(env, logger, sourceType, sourceId, sourceUrl)`

Given a single document identity, this builds and enqueues one `KnowledgeIndexQueueMessage` exactly as the planning phase would, creates its own single-document `knowledge_indexing_runs` row (`trigger_type: 'content_change'`, a value migration 0036 already anticipated in its own CHECK constraint), and returns immediately. Fully tested (planning, enqueue, and — via the existing consumer — indexing all verified). **Not called from any CMS save/update route** — no blog, resource, product, or settings handler invokes it. This is deliberate: the brief asked for the infrastructure to exist and remain disabled, not to change how content edits behave today.

## 8. Task 7 — Dead Letter Handling (Redesigned Mid-Milestone)

**Files:** `backend/services/knowledge/indexingService.ts`, `backend/worker/index.ts`, `backend/wrangler.jsonc`, migration `0038`.

The first implementation provisioned a second Cloudflare Queue (`robayer-knowledge-index-dlq`) with its own consumer, using Cloudflare's built-in `dead_letter_queue` config. Before deploying, this was recognized as conflicting with the brief's own explicit instruction — "Use the existing Queue... Do not create unnecessary infrastructure" — and reconsidered: because every *document-level* failure in `embedAndFinalizeAll()` is already caught and recorded without ever throwing, the queue's retry mechanism only ever engages for a genuinely rare infrastructure-level error. A second queue purely to catch that rare case was disproportionate.

**Final design:** `worker/index.ts`'s `queue()` handler wraps `processIndexingQueueBatch()` in a `try/catch`. On an uncaught error, it checks each message's own `attempts` field (native to Cloudflare Queues, no new binding) against `INDEXING_QUEUE_MAX_RETRIES` (3, matching `wrangler.jsonc`). If every message in the batch has exhausted its retries, `recordDeadLetters()` writes each to the new `knowledge_indexing_dead_letters` table (payload, reason, run/document linkage) and marks the document `'failed'` with a clear, admin-visible message; otherwise the error is re-thrown and Cloudflare's own retry redelivers the batch normally. `retryDeadLetter()` lets an admin re-enqueue a dead-lettered message onto the **same** existing queue. No second queue, no second consumer, no `dead_letter_queue` config.

This is a genuine example of catching an over-engineered first draft against the brief's own stated constraint before it ever reached production — see the Known Limitations report for the trade-off this accepted.

## 11. A Mid-Milestone Deployment Incident, Diagnosed Rigorously

During the post-certification refinement pass (measuring the Resources gap, fixing the analytics refresh bug), two small frontend commits appeared not to take effect after deployment. Rather than guessing, the actual cause was traced through four layers before reaching ground truth:

1. Confirmed via direct `curl` that the live JS file's content lagged the latest commits.
2. Ruled out simple propagation delay by fetching a URL with a never-before-used cache-busting query string and observing `cf-cache-status: HIT` — proving Cloudflare's edge was ignoring query strings entirely for cache-key purposes (not a timing issue).
3. After a full cache purge still showed stale content, checked GitHub's own Deployments and Actions Workflow Runs APIs directly, finding one deploy **cancelled** (superseded by a rapid follow-up push, a GitHub Actions concurrency behavior) and the next stuck **queued**, then completed with **failure** — annotated with *"The job was not acquired by Runner of type hosted even after multiple attempts"* and *"Internal server error."*
4. Confirmed via GitHub's public status API (`githubstatus.com`) that this matched an active, ongoing, platform-wide incident affecting both Actions and Pages (`major_outage`), not anything in this project's workflow configuration.

Documented in full in the Deployment Guide and Known Limitations report — the two frontend fixes are code-complete and merged to `main`; only the Pages build step is pending, on GitHub's infrastructure, not this project's.
