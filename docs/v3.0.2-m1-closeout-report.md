## Acceptance Conditions

Every condition below is copied from the Milestone Acceptance Review's Final Acceptance Decision, in the same order, with this sprint's resolution status and supporting evidence.

### Condition 1: Apply migration 0018 to production D1 and deploy the updated Worker and static site

**Status: Not Applicable to this sprint (by design).**

This sprint's own governing instruction was explicit: "Do not deploy anything. Do not apply remote migrations. Only document the required production steps." Executing this condition would have directly violated that instruction, so it was deliberately left undone.

Evidence of what was done instead: `v3.0.2-m1-production-readiness-checklist.md` was produced, documenting the exact commands (`wrangler d1 migrations apply robayer-wealthlab-db --remote`, followed by `wrangler deploy`, followed by the static-site deploy), the required order of operations and why it matters, the rollback procedure, a deployment-prerequisites checklist, and a nine-point post-deployment verification checklist. Current state was re-verified as part of this sprint (read-only commands only): `wrangler d1 migrations list robayer-wealthlab-db --remote` still shows `0018_customer_identity.sql` pending, and `wrangler deployments list` still shows the most recent production deployment at 2026-07-24T22:57:43Z, predating all M1 and Sprint 2B work. Production remains in the same consistent, unaffected state the Milestone Acceptance Review found.

### Condition 2: Fix the "sign-in link" copy

**Status: Resolved.**

Evidence:

- `checkout/sign-in/index.html`: the link text "Get a sign-in link" was changed to "Set or reset your password."
- `checkout/forgot-password/index.html`: the `<title>` was changed from "Get a Sign-In Link" to "Reset Your Password"; the meta description was updated to describe setting or resetting a password rather than signing in; the H1 was changed from "Get a sign-in link" to "Reset your password"; the form's `aria-label` was updated to match.
- `js/components/forgot-password-form.js`: the confirmation message was changed from "we've sent a sign-in link" to "we've sent a link to set or reset your password."
- Verified live in a browser after the change: navigated to both pages, confirmed the corrected text renders (including the browser tab title), confirmed no console errors, and confirmed the sign-in page's link now reads "Set or reset your password" pointing at the corrected forgot-password page.

### Condition 3: Add the four missing test cases

**Status: Resolved.**

Evidence, one item per gap identified in the Milestone Acceptance Review's Phase 6:

1. **`email_verified_at` stamping.** New test added to `tests/unit/identityService.test.ts` asserting the column is non-null immediately after `findOrCreateCustomer()` creates a new customer.
2. **Concurrent customer-creation race recovery.** New test added to the same file: two `findOrCreateCustomer()` calls for the same brand-new email, fired via `Promise.all`, asserting both resolve to the same `customerId`, exactly one of the two reports `isNewCustomer: true`, exactly one `customers` row exists afterward, and exactly one `customer_profiles` row exists (no duplicate from the losing side of the race). This exercises the real race, not a simulated one.
3. **Rate limiting.** New file `tests/integration/rateLimiting.test.ts` with three tests: login's 6th attempt within the window returns `RATE_LIMITED` (limit is 5/15min); set-password's 11th attempt returns `RATE_LIMITED` (limit is 10/15min); forgot-password's 4th attempt within the window (limit is 3/15min) returns the same generic success response as the first three (by design, for no-enumeration), but is verified to not have minted a fourth password-setup token, confirming the request was genuinely rejected server-side rather than merely appearing identical.
4. **Password-token double-redemption race.** New test added to `tests/unit/authService.test.ts`: two `setPassword()` calls with the same valid token, fired via `Promise.all`, asserting exactly one succeeds, exactly one of the two candidate passwords actually takes effect (verified by attempting login with both afterward), and the token is marked used.

The suite was re-run three consecutive times after these additions with identical results each time (49/49 passing), confirming the new concurrency-based tests are deterministic in this environment, not flaky.

## Final Recommendation

Milestone M1 Fully Accepted - Ready for Commit

The repository is ready for:

1. **Git commit.** Yes. Every acceptance condition within this sprint's authority has been resolved and independently verified: the misleading UI copy is corrected, all identified test-coverage gaps are closed, the automated suite passes in full with no regressions, and TypeScript typechecking is clean. Documentation is accurate and consistent with the actual repository and environment state.
2. **Version tag (`v3.0.2-M1`).** Yes, once committed. The codebase represents a complete, independently reviewed, and now fully closed-out implementation of Milestone M1 as ratified. Nothing in the tagged code depends on the pending production migration to be internally consistent - the code, schema, and tests are self-consistent as a unit.
3. **Commencement of Milestone M2.** Not yet, and not because of anything found in this sprint. Per the ratified Sprint Readiness Report, Milestone M2 (Ownership Layer: Orders, Licenses, Receipts) depends on M1 and additionally has its own outstanding prerequisite unrelated to M1's own completeness: confirmation of this business's VAT-registration status, needed before M2's `receipts.tax_breakdown` computation logic can be finalized (the schema structure itself has no such dependency and may be built regardless, per ADR-008). M2 should not begin until that business question is answered, and until the production deployment of M1 (Condition 1 above) has actually happened and been verified using the checklist this sprint produced - starting M2 against a production database that does not yet have M1's schema would compound the deployment gap rather than resolve it.

The one item still outstanding before Milestone M1 can be considered fully live is production deployment, which requires explicit authorization and is not a code, test, or documentation gap. It is fully documented and ready to execute.
