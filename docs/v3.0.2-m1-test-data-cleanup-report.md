## What was explicitly preserved

- **`email_log`** - not touched. All three rows generated by the test purchase (`purchase-receipt`, `secure-download`, `customer-welcome`, all `status = sent`, recipient `checkout+rwl-2026-000029@robayerwealthlab.com`) are still present, verified by direct query after cleanup. These rows now reference a deleted `purchase_session`/`customer` by ID, which is expected and safe: `email_log.entity_id` is a polymorphic reference (paired with `entity_type`), not a database-enforced foreign key, so historical log entries are designed to outlive the entities they describe.
- **Production configuration** - no secret, binding, variable, or `wrangler.jsonc` setting was touched.
- **Every other production row** - confirmed by count after cleanup: `purchase_sessions` (25), `payment_transactions` (15), `deliveries` (13) all remain at their real, pre-existing counts (one added by the test, now removed, netting back to the original numbers).

## Integrity verification

- Each of the 8 deletes reported exactly `changes: 1` - no cascading or unexpected row loss.
- Post-cleanup queries confirm zero remaining rows for `customers`, the `RWL-2026-000029` purchase session, and all related `customer_sessions`/`customer_password_tokens`/`customer_profiles`.
- `PRAGMA integrity_check` is not available through D1's remote HTTP execute API, so it could not be run directly; row-level verification (exact counts before and after, on every affected table) was used instead as the equivalent check.
- No other customer, purchase, transaction, or delivery record in production was read, modified, or removed.

Production database is now in the same state it was in immediately before the M1 deployment verification purchase, with the deployment itself (schema, Worker, static site) fully intact and unaffected.
