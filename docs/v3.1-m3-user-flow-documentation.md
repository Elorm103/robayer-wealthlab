# Version 3.1 - Milestone M3 User Flow Documentation

Checkout Auto-Provisioning & Dashboard MVP. Describes the customer-facing
flows M3 adds or extends. All flows below reuse M1's existing
provisioning/authentication mechanics unchanged - M3's contribution is
almost entirely "give the customer somewhere real to land."

## Flow 1: Post-purchase, first-time buyer

1. Customer completes checkout -> lands on `/checkout/callback/?ref=...`.
2. `fulfilment-status.js` polls and renders the ready state: product
   name, purchase reference, download button(s) (unchanged, M1/M2).
3. Page copy (unchanged wording, M1) tells them a welcome email is on
   its way with an *optional* password-setup link - never required,
   and the download above works the same either way.
4. **New in M3B**: the same paragraph now also says "Already have a
   password? Sign in to your library" with a link to
   `/checkout/sign-in/` - relevant to a returning buyer reading this
   same page on a second purchase, not this first-time buyer, but
   shown unconditionally since the page cannot honestly determine
   client-side which case applies (see `checkout/callback/index.html`'s
   own comment).
5. If the customer follows the emailed password-setup link (M1,
   unchanged): sets a password -> redirected to
   `/checkout/sign-in/?redirect=%2Fdashboard%2F` (or straight in,
   depending on M1's existing set-password-then-session behaviour) ->
   **new in M3B**: lands on `/dashboard/` (My Library), not the bare
   homepage M1/M2 redirected to before this milestone.

## Flow 2: Returning customer signs in

1. Customer visits `/checkout/sign-in/` (directly, or via a link like
   the one added in Flow 1 step 4).
2. Submits email/password -> `POST /api/customer/auth/login`
   (unchanged, M1) -> sets `customer_session`/`customer_csrf` cookies.
3. **New in M3B**: `sign-in-form.js` reads an optional `?redirect=`
   query param. If present and it matches `^/dashboard/(?!/)` exactly,
   the customer is sent there; otherwise (no param, or a
   non-dashboard/malformed value) they land on `/dashboard/` (My
   Library) by default. A value like `//evil.example.com` or
   `https://evil.example.com` is never honored - it falls through to
   the same default, per `sanitizeRedirectPath()`.

## Flow 3: Unauthenticated visitor hits a dashboard page directly

1. Customer navigates straight to e.g. `/dashboard/security/` without
   an active session (bookmarked link, expired session, etc).
2. `dashboard-shell.js`'s `requireSession()` call fails ->
   redirects to `/checkout/sign-in/?redirect=%2Fdashboard%2Fsecurity%2F`.
3. After a successful sign-in, Flow 2 step 3 applies: the customer is
   returned to the exact page they originally tried to reach, not
   dumped back on My Library.

## Flow 4: Browsing My Library and downloading a purchase

1. Customer signs in, lands on `/dashboard/` (or navigates there via
   the dashboard nav from any other dashboard page).
2. `library-list.js` fetches `GET /api/customer/purchases` on
   `dashboard:ready`, renders one card per purchase.
3. A `ready` purchase shows a Download button per digital asset. A
   `processing` purchase shows its status badge with no download yet
   available. A `refunded`/`unavailable` purchase shows its status
   badge with no download action. A customer with zero purchases sees
   the empty state, not an error.
4. Clicking Download: `POST /api/purchases/:reference/downloads` mints
   a fresh single-use token (unchanged, M1/M2 mechanism) ->
   `window.location.href` navigates to the redeem URL -> the browser's
   own download handling takes over (`Content-Disposition: attachment`
   response) - no blob/fetch handling in JS.
5. Clicking "View receipt": a direct link straight to
   `/api/customer/receipts/:receiptNumber/download`, no mint step (the
   receipt-download endpoint is not single-use).

## Flow 5: Reviewing purchase history and receipts

1. From the dashboard nav, customer selects Purchase History or
   Receipts.
2. Purchase History (`purchase-history-list.js`) shows the same
   purchases as My Library, framed as transaction records (date,
   reference, amount, status) rather than actionable cards.
3. Receipts (`receipts-list.js`) lists every issued receipt with a
   direct PDF download link (M2's existing receipt PDF pipeline,
   unchanged).

## Flow 6: Changing password

1. Customer navigates to Account Security, fills in current password,
   new password, and confirmation.
2. Client-side check: new password and confirmation must match, or the
   form shows an inline error before any request is sent.
3. `POST /api/customer/auth/change-password` (CSRF-protected). On
   success: form clears, a success message shows, and the active
   sessions list is immediately re-fetched.
4. **Important behavioural detail**: every session *other* than the
   one making this request is revoked as a server-side side effect of
   a successful change. The customer's current browser tab/device
   stays signed in - they are never logged out mid-action by their own
   password change. This is why step 3's "re-fetch the sessions list"
   matters: without it, the UI would keep showing now-stale, no-longer-
   valid sessions.
5. On failure (wrong current password, or new password fails the
   strength policy): an inline error shows; no session is revoked, no
   password is changed.

## Flow 7: Reviewing and revoking active sessions

1. Account Security's Active Sessions section loads on
   `dashboard:ready`, showing every currently-active session for this
   customer: a device/browser summary, "last active" timestamp, and a
   "This device" badge on whichever session is the one making the
   current request.
2. The current session has no revoke control - only every *other*
   session shows a "Sign out" button.
3. Clicking "Sign out" on another session: a `window.confirm()` prompt
   appears first ("Sign out this session? That device will need to
   sign in again."). Cancelling makes no network request and leaves
   the list unchanged.
4. Confirming: `POST /api/customer/sessions/:id/revoke` (CSRF-protected)
   -> on success, the sessions list re-fetches and the revoked session
   disappears. On failure, an alert shows the error and the button
   re-enables.
5. The revoked device's own next request (page load or API call) using
   its now-invalid `customer_session` cookie is rejected exactly as any
   expired/invalid session already is - unchanged, M1's existing
   session-validation logic.

## Flow 8: Logging out

1. Customer clicks "Log out" in the dashboard nav (present on every
   dashboard page).
2. `dashboard-auth.js`'s `logout()` calls the existing M1 logout
   endpoint, then redirects to the homepage. Unchanged mechanism -
   only the nav placement is new in M3.
