# Version 3.2 Roadmap

Designs the next three milestones. Builds on, and in two places deliberately amends, the existing ratified sequence (ADR-005: M4=Coupons → M5=Support → M6=Notifications → M7=Marketplace → M8=Go-Live). Every amendment is named explicitly, with justification, per the Blueprint's own governance requirement - nothing below is a silent deviation.

---

## M4 - Commerce & Trust Foundations

**Purpose:** Complete and monetize the existing commerce loop, and close the top-of-funnel trust gap, before investing in anything structurally new.

**Scope:** Product Reviews & Ratings (new); Coupon Engine (ratified, unchanged from the existing Blueprint). Full detail in `v3.2-m4-scope-recommendation.md`.

**Deliverables:** 2 migrations (additive only), ~6-8 new backend routes across customer/admin surfaces, 2 new admin pages, product-page review display + submission UI, checkout-flow coupon integration, full test coverage including the previously-absent admin-panel coverage for these specific new surfaces.

**Risks:** Coupon multi-account abuse (already reviewed, accepted by the ARB - monitor post-launch, do not attempt to solve now). Review-authenticity (mitigated by construction - purchase-gated submission, not by moderation alone). Both Low-Medium per the Prioritization Matrix.

**Dependencies:** None blocking. Independent of the VAT question (escalate in parallel, not a gate).

**Estimated complexity:** Comparable to M3 (two cohesive, well-precedented feature areas, no schema redesign) - one implementation sprint, one independent acceptance review, one closeout, one deployment, matching the exact M(x)A→B→C→D→E→F cadence this project has now run three times successfully.

---

## M5 - Retention & Engagement *(amended from the ratified plan)*

**Ratified plan said:** M5 = Support Ticketing.
**This roadmap recommends instead:** Retention & Engagement (Email Automation on top of the existing newsletter-campaign system; Customer Notifications, pulled forward from the ratified M6 slot; Customer Profile enrichment; Wishlist, contingent on resolving its ADR-006 tension).

**Justification for the amendment:** Support Ticketing primarily reduces cost/friction for already-converted customers with problems - valuable, but its urgency scales with support-request *volume*, which this platform's current real customer count does not yet generate meaningfully. Retention & Engagement, by contrast, directly compounds revenue from the customer base M4 will have just made more trustworthy (via Reviews) and better-monetized (via Coupons) - and it does so almost entirely on top of infrastructure that already exists (the real newsletter-campaign system), making it unusually cheap for its value relative to where this platform is today. This is the single clearest instance in this entire planning package of "build on what already exists" beating "build what was originally scheduled next."

**Purpose:** Turn the newsletter-sending capability that already exists into an actual retention engine, and close the "Long-term Engagement" gap identified as the customer journey's single weakest point.

**Scope:** Purchase-triggered nurture email sequence; review-request trigger (feeding M4's Reviews feature); win-back sequence for lapsed customers; `notification_queue` table + in-dashboard notification surface (the ratified M6 scope, implemented here instead, unchanged in design); customer profile fields beyond email; Wishlist, only if the ADR-006 design question (does adding a wishlist require any exception to purchase-triggered-only account creation?) is resolved during M5A planning - if not resolved cleanly, defer Wishlist alone to M6 without blocking the rest of M5.

**Deliverables:** This project's first genuinely triggered (not just admin-clicked) email behavior - a real increase in operational surface area, matching the Sprint Readiness Report's own "new operational territory" caution for what was originally the M6 slot. `notification_queue` migration. Dashboard notification-center UI. Updated `monitoring-and-alerting.md`/`backup-and-recovery.md` as part of this milestone's own deliverables (the exact procedural condition the Sprint Readiness Report attached to this scope, regardless of which milestone number it lands in).

**Risks:** Medium - the first-ever triggered/scheduled backend behavior in this project's history; get the monitoring/alerting story right the first time rather than retrofitting it, per the Sprint Readiness Report's own explicit condition.

**Dependencies:** M4's Reviews feature (for the review-request trigger specifically - the rest of M5 does not depend on M4 completing first, and could in principle proceed in parallel if resourcing allowed, matching the Sprint Readiness Report's own finding that several milestones are parallel-capable).

**Estimated complexity:** Larger than M4 - new operational territory (first triggered behavior) plus several distinct sub-features. Likely the largest of the three milestones in this roadmap.

## M6 - Discovery & Growth Readiness

**Purpose:** Improve discovery for a catalog that (by this point, assuming the independent eBook-expansion content track has progressed) is larger than today's single flagship product, and gather real evidence on whether a course platform is worth building - without building it yet.

**Scope:** Search improvements (ranking, cross-content-type); a simple heuristic Recommendation engine v1 ("more from this category," not yet behavior-based); Sales Analytics extension (cohort/repeat-purchase views on top of the existing analytics dashboard); **a lightweight "course interest" signal-gathering feature** (an opt-in on relevant pages, tracked in a small new table - the recommended addition from the Prioritization Matrix, not a course platform itself).

**Deliverables:** Improved search/ranking logic, a recommendation component reused across product/dashboard pages, an analytics extension, and - critically - a real, measured answer to "does demand for a course exist" before any M7+ decision commits to building one.

**Risks:** Low across the board - every item here is an extension of proven, existing patterns (search/analytics already exist in basic form; the interest-signal feature is intentionally tiny).

**Dependencies:** Benefits from the independent eBook-content-expansion track having shipped a few more real SKUs by this point (not an M4/M5 engineering dependency - a parallel, non-engineering workstream this roadmap assumes continues throughout, per the Product Review's own finding that this track requires no M4-M6 engineering time at all).

**Estimated complexity:** Smallest of the three milestones - each item is individually small; the value is in the aggregate discovery improvement plus the strategic option value of the interest-signal data.

## Beyond M6 (named, not detailed, per the Prioritization Matrix)

- **M7 - Marketplace Schema Activation**, unchanged from the ratified Blueprint (creators, affiliates, `platform_users` rename) - still correctly gated on ADR-011's required migration/rollback plan, which should be planned in parallel starting now (see Technical Debt Review), so it is not still outstanding when M7 is reached.
- **Course Platform** (course/lesson model, video lessons, progress tracking, certificates) - contingent on M6's interest-signal data showing real demand. If demand is confirmed, this becomes its own dedicated planning cycle (its own "M(course)A" architecture-and-UX planning sprint, mirroring every prior milestone in this project's history), not a feature bolted onto an existing milestone. If demand is not confirmed, this project's own historical guidance (defer past the 12-month mark) should be followed rather than overridden by ambition alone.
- **Instructor Portal** - folds into M7's Marketplace work; not a separate feature.
- **Go-Live Readiness Review (M8 in the ratified plan)** - unchanged, still the correct gate before Paystack Live mode, still carrying the chargeback-handling requirement (ADR-010).
