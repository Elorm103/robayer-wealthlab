# Version 3.3 Milestone M5C: Known Limitations

## Cloudflare Web Analytics token is not yet set

`assets/config/site.json`'s `analytics.webAnalyticsToken` is `null`. `js/main.js`'s beacon-loading logic is real and functional but is currently a no-op, because generating a real Cloudflare Web Analytics site-tag requires a one-time manual action in the Cloudflare dashboard (Analytics & Logs → Web Analytics → Add a site) that this project's current Cloudflare API token scope does not grant, and there is no API for this action regardless (confirmed via `wrangler whoami`'s scope list in an earlier sprint). **Required follow-up:** a human with Cloudflare dashboard access must create the site-tag and set the resulting token as `analytics.webAnalyticsToken` in `assets/config/site.json`. Until then, the admin dashboard's existing "Visitors, sessions & traffic sources" card continues to link to a Cloudflare Web Analytics view with no data behind it — unchanged from before this sprint, not made worse by it.

## Review-reminder Cron Trigger not exercised end-to-end locally

`services/customer/reviewReminderService.ts`'s `sendDueReviewReminders()` is fully unit-tested (11 tests). The `scheduled()` handler that Cloudflare's Cron Trigger actually invokes was not tested end-to-end via `wrangler dev --test-scheduled` in this sprint, since the project's `.claude/launch.json` dev-server configuration does not pass that flag. **Recommended follow-up:** either add `--test-scheduled` to the local dev configuration, or verify the scheduled handler fires correctly against a real deployment via `wrangler tail` once M5C is deployed.

## Review-reminder batch size is capped, not queued

`MAX_REMINDERS_PER_RUN = 200` bounds how many reminders a single scheduled invocation sends, to avoid an unbounded first run against months of historical unreminded purchases exceeding Workers' CPU/wall-time limits. Any remainder is picked up by the next day's scheduled run — the eligibility query is idempotent, not a one-shot queue, so nothing is lost, only delayed by up to a day per 200-purchase batch. At this platform's current, low purchase volume this is not a practical concern; it would become one only at a scale this platform has not yet reached.

## Review-reminder delivery is sequential, not parallel

`sendDueReviewReminders()` sends one email at a time, awaiting each `sendEmail()` call before starting the next, rather than batching concurrent sends. This is deliberate: parallelizing would risk tripping Resend's own rate limits and would complicate the existing one-retry-then-log-and-continue error handling `sendEmail()` already provides. At current volume this is not a performance concern.

## Repeat-purchase metric counts events, not customers

`repeatPurchasesInRange()` counts repeat-purchase *events* in the selected date range (a verified purchase by a customer who already had an earlier one), not a lifetime count of "customers who have ever repurchased." A customer who repurchases three times in one period contributes three to this metric that period. This was a deliberate choice to keep the metric consistent with every other `KpiMetric` in this sprint (a current-vs-previous-period comparison), not an oversight — documented here so a future analytics consumer doesn't assume it means something it doesn't.

## Reconciliation opt-out UX has no dedicated frontend page

`GET /api/customer/review-reminders/opt-out` renders its confirmation directly as server-rendered HTML from the Worker (matching `routes/free-guide.ts`'s existing precedent for a simple standalone page), rather than a static frontend page under a `checkout/` or `newsletter/`-style directory with its own design-system styling. This was a deliberate scope decision: the newsletter unsubscribe flow's two-step, styled page exists because it is a real compliance surface; this opt-out is a low-stakes preference with no equivalent requirement. If this needs visual consistency with the rest of the site in the future, that is a small, isolated follow-up, not a redesign.
