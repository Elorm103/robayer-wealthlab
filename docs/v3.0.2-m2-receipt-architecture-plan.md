# Version 3.0.2 - Sprint M2A - M2 Receipt Architecture Plan

Planning only. No PDF generation code was written. No receipt was generated.

## Receipt numbering

Already specified in full in the Database Planning Report: `formatReceiptNumber(id, issuedAt) => "RWL-RCT-{year}-{6-digit id}"`, reusing `receipts.id`'s own AUTOINCREMENT uniqueness exactly the way `backend/utils/purchaseReference.ts` already does for `purchase_sessions.purchase_reference` - same file-header-level documentation discipline (explicitly noting the sequence is the row's own id, not a per-year-reset counter, so a future reader never misreads "000001" as "the first receipt of the year").

## Receipt rendering: the technical question this plan resolves

The task asks for a "downloadable PDF architecture." Before recommending one, the actual technical constraints of this Worker were checked directly rather than assumed:

- `backend/wrangler.jsonc` has **no `compatibility_flags`** entry at all - confirmed by direct inspection, with the file's own header comment explaining why: "this Worker has zero runtime npm dependencies (only fetch/crypto/D1/R2/KV - all native Workers Web APIs)... not by default." This is a deliberate, stated architectural discipline, not an oversight.
- `puppeteer-core` (a devDependency) is used exactly once in this codebase, in `backend/scripts/render-toc-page.mjs`, which calls `puppeteer.launch({executablePath, headless: true})` - a **local, Node.js-only, real-browser-binary** invocation. This script is run by hand, on a developer's machine, to help build the flagship eBook's static PDF file once, ahead of time. **It cannot run inside a deployed Cloudflare Worker** - there is no browser binary available in the Workers runtime, and no Cloudflare Browser Rendering binding exists anywhere in `wrangler.jsonc`'s bindings list today. Any receipt-PDF design that assumes HTML-to-PDF rendering via a headless browser is not buildable without first provisioning a new, paid Cloudflare binding - a real infrastructure decision, not something M2 should assume silently.
- `pdf-lib` (also a devDependency) is used in three scripts (`fix-book-cover-and-author-page.mjs`, `pdf-links.mjs`, `pdf-outline.mjs`, `rebuild-book-toc.mjs`) - all likewise local, Node.js, build-time scripts, editing the flagship eBook's static PDF file. **However**, unlike `puppeteer-core`, `pdf-lib` is a pure-JavaScript library with no Node.js built-in dependency - it manipulates PDF byte structures directly (`PDFDocument`, `PDFPage`, low-level object APIs, per `pdf-outline.mjs`'s own comments) and is widely used in browser and edge-runtime contexts precisely because it has no such dependency. This makes it the credible candidate for **runtime, in-Worker** receipt generation - but it has not yet been exercised inside *this* Worker's actual `workerd` runtime, so this is presented as a strong technical hypothesis requiring a brief spike, not a proven fact.

### Recommended architecture

1. **At receipt-issuance time** (inside the webhook fulfilment pass), generate the receipt PDF's bytes directly in the Worker using `pdf-lib`, constructing a simple, single-page, programmatic layout (header/logo, purchase details table, line items, tax breakdown, total, footer) - not an HTML-to-PDF conversion. This mirrors the flagship eBook's own local scripts' use of `pdf-lib`'s low-level API, just moved into the runtime path instead of a build-time one.
2. **Store the generated PDF in R2** (`STORAGE`, the binding already used for every other digital asset in this project), keyed by `receipts/{receiptNumber}.pdf`, at issuance time - generate once, serve many times, never regenerate on every download request. This matches the existing digital-fulfilment pattern exactly: assets live in R2, never regenerated per request, streamed via a token-gated route.
3. **Serve it** via the two download routes already specified in the API Planning Report (`GET /api/customer/receipts/:receiptNumber/download` for authenticated customers, `GET /api/download-receipt/:token` for the guest reference-scoped path) - both stream the already-generated R2 object, neither regenerates the PDF on the fly.

### Required spike before M2B commits to this approach

A small, throwaway proof-of-concept - construct one minimal PDF with `pdf-lib` inside a real `@cloudflare/vitest-pool-workers` test (the same test infrastructure M1 already built and proved reliable) or a real local `wrangler dev` request - confirming `pdf-lib`'s `PDFDocument.create()`/`.save()` path runs cleanly inside `workerd` with no unavailable API. This is a same-day check, not a research project - M1's own test infrastructure work already demonstrated this project's tooling can validate a Workers-runtime compatibility question directly rather than by inference. See the Risk Assessment for what happens if the spike fails.

### Fallback if the spike fails

Generate a styled **HTML receipt** instead (reusing `emailService.ts`'s existing `renderTemplate()`/`.html`-as-text-module pattern M1 already proved works), served as a normal web page rather than a PDF file. This satisfies "receipt download" in substance (a customer can save it or print-to-PDF from their own browser, which every modern browser supports natively) while deferring true server-generated PDF to a fast-follow once either `pdf-lib`'s compatibility is fixed or a Browser Rendering binding is deliberately provisioned. This fallback is explicitly not the preferred path - it is documented here so M2B is never blocked by a single failed technical assumption.

## Tax breakdown

Schema already fully specified (Database Planning Report): `receipts.tax_breakdown`, a JSON array of `{label, rate_percent, amount_pesewas}`, `receipts.tax_pesewas` as its derived sum. Per ADR-008, the **structure** ships in M2 regardless of the VAT question's answer - an empty array (or a single `{label: "No VAT applicable", rate_percent: 0, amount_pesewas: 0}` entry, whichever reads more honestly on a real customer-facing receipt) is the valid, complete answer for a non-VAT-registered business, and costs nothing to leave in that state indefinitely.

**The computation logic that decides what goes into that array is gated on the same open business question the Sprint Readiness Report already named**: is this business VAT-registered under Ghana's tax regime. This has not been answered anywhere in this project's documentation as of this review - confirmed by a direct search across `docs/` for "VAT-registration"/"VAT registered," which returns only the same handful of documents that already state the question is open, none that answer it. **This is not a new finding - it is the same prerequisite the ratified Blueprint already flagged - restated here because it directly gates one specific piece of M2's own scope (the tax-computation function), not the receipt feature as a whole.**

## VAT readiness

The schema is VAT-ready today, independent of the answer: `tax_breakdown`'s array shape can represent Ghana's actual multi-layered indirect tax stack (standard VAT, NHIL, GETFund Levy, and any other applicable levy, each as its own `{label, rate_percent, amount_pesewas}` entry) the moment the business confirms registration and the applicable rates. No schema change will be needed at that point - only the computation function that populates the array, which should be written as a small, isolated, easily-swappable module (e.g. `computeTaxBreakdown(product, amountPesewas): TaxBreakdownEntry[]`) specifically so that "we now know the real answer" is a one-function change, not a receipt-architecture change.

## Future multi-currency compatibility

`receipts.currency` exists from the start (Database Planning Report), defaulting to `'GHS'`, copying `products.currency`. No multi-currency logic - conversion, multi-currency display, locale-aware number formatting - ships in M2; every product and every purchase in this catalog is GHS-only today. The column's presence is the same "costs nothing to leave unused" reasoning ADR-008 already applies to `tax_breakdown` itself, extended to currency for the same reason: retrofitting a currency column onto already-issued, never-deleted financial records later would be materially more expensive than including it now.

## Summary of what M2B needs to decide, in order

1. Run the `pdf-lib`-in-`workerd` spike (day one of implementation, before writing the real receipt-generation service).
2. If it passes: build the R2-backed, generate-once-serve-many PDF architecture described above.
3. If it fails: build the HTML-receipt fallback instead, and record the `pdf-lib` incompatibility as a known limitation (matching this project's own established practice of documenting, not hiding, a genuine tooling constraint - see the M1 Implementation Report's own precedent for the `undici`/`MockAgent` incompatibility finding).
4. Either way, the tax-breakdown computation function stays isolated and swappable pending the VAT-registration answer, and the schema itself needs no further change once that answer arrives.
