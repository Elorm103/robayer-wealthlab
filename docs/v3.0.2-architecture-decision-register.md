# Robayer WealthLab — Version 3.0.2 Architecture Decision Register

**Status:** Ratified. This register is permanent project governance documentation — see [`docs/v3.0.2-commerce-architecture-blueprint.md`](v3.0.2-commerce-architecture-blueprint.md)'s Governance Statement for the deviation process any future change to a decision here must follow.
**Origin:** Consolidates and finalizes the decisions examined in [`docs/v3.0.2-arb-review-report.md`](v3.0.2-arb-review-report.md) Phase 3 and Phase 10, resolving the two the ARB left open (ADR-007, on email-retry automation, and the customer/creator identity bridge folded into ADR-004) and adding the ADRs the ARB identified as needed but did not itself draft in full (ADR-008 through ADR-013).
**Numbering note:** This register renumbers and consolidates the ARB report's own provisional ADR-001–006 into a clean, non-duplicative sequence — e.g. the ARB's "Decision 3" (email access) and its separately-added "ADR-004" (revocation sync) are one coherent decision here (ADR-003), not two. The ARB report remains the historical record of *how* the panel reasoned; this register is the *ratified outcome*.

---

### ADR-001: Orders are modeled as an extended `purchase_sessions`, not a new `orders` table

- **Status:** Accepted, with a scheduled follow-up.
- **Context:** A prior `orders` table existed in this codebase's history and was removed in migration 0008 as unused; `purchase_sessions` already functions as the order record in every live service. The Blueprint proposed extending it with `customer_id` rather than introducing a parallel table.
- **Decision:** `purchase_sessions` remains the single order-of-record table, extended with `customer_id` (Version 3.0.2) and, later, the marketplace columns from `docs/v3-database-design.md` (`creator_id`, `affiliate_product_link_id`, `coupon_id`, `discount_pesewas`, commission fields) at Milestone M7.
- **Alternatives considered:** (a) A genuinely separate `orders` table, created only at verification, leaving `purchase_sessions` as a purely transient pre-payment table. (b) Unmodified status quo with no `customer_id` at all.
- **Rationale:** The ARB's independent review confirmed the migration-cost and conceptual-clarity cost of reintroducing a second table outweighs the naming imprecision of keeping one — provided the naming imprecision is scheduled to be resolved, not left permanent.
- **Consequences:** `purchase_sessions` will continue accumulating fields from both this project's customer-identity work and the marketplace work. Retention/archival policy for `pending`/`failed`/`expired` rows cannot be cleanly separated from the permanent order record while both live in one table.
- **Future considerations:** A rename to reflect the table's true role (e.g. `orders`, with `purchase_sessions` retained only as a conceptual alias in documentation, or vice versa) is scheduled for Milestone M7, when the marketplace columns land anyway — the natural, lowest-incremental-cost point to also rename. If, by M7, real usage data shows query complexity or genuine confusion has become an operational problem (not just a naming one), this ADR should be reopened and the physical-split alternative reconsidered with that data in hand.

### ADR-002: Guest-first checkout with automatic, optional account provisioning after payment

- **Status:** Accepted, unchanged from the original Blueprint.
- **Context:** Every additional pre-payment field measurably reduces checkout conversion; Paystack's own hosted checkout already collects a provider-confirmed email more securely than a custom pre-payment form could.
- **Decision:** Robayer's own checkout page collects zero customer-identity fields. The instant a payment verifies, the system finds-or-creates a `customers` row keyed on the provider-confirmed email, with no password set. Setting a password is always a separate, later, explicitly optional action.
- **Alternatives considered:** Forced pre-payment registration (rejected — conversion cost is well-established and not close). Optional pre-payment sign-in for a customer who already has an account (accommodated without special-case code — they simply already have a `customer_id` by checkout time).
- **Rationale:** The ARB's independent review found no defensible alternative and rated this the strongest single decision in the architecture.
- **Consequences:** Account creation is always a system-triggered side effect of a successful purchase in the current scope — see ADR-006 for the explicit boundary against self-registration.
- **Future considerations:** None beyond ADR-006's boundary.

### ADR-003: Email-based purchase access is preserved permanently alongside customer accounts, with entitlement revocation synchronized to license revocation

- **Status:** Accepted (revocation-synchronization clause added at ratification; the ARB's review had identified this as a gap in the original Blueprint, tracked there as its own "ADR-004").
- **Context:** The original email-link download flow (unchanged since Version 1.2 Sprint 2.5) must never break for a customer who never sets a password. Separately, the Blueprint introduces `licenses` (a customer-facing ownership document) deliberately kept apart from `deliveries` (the access-control entitlement) — but the original Blueprint never specified what happens to `deliveries` when a `licenses` row is revoked.
- **Decision:** Two parts, both binding: (1) the existing email-link download path continues to function indefinitely and unconditionally for any entitlement in `ready`/`delivered` status — no feature in this architecture may require an account to receive or access a purchase. (2) Any process that sets `licenses.revoked_at` (refund approval, chargeback — see ADR-010) must, in the same operation, set the corresponding `deliveries.status = 'revoked'` (an existing, valid value in the live schema's `CHECK` constraint). Download-token issuance must check `deliveries.status != 'revoked'` regardless of which surface (email link or dashboard) requested it.
- **Alternatives considered:** Leaving `deliveries` untouched on refund/chargeback and relying on manual admin intervention to revoke access (rejected — too easy to forget, a real financial-control risk).
- **Rationale:** A refund or chargeback is not complete, from a security standpoint, until access is actually revoked — a license document saying "revoked" while the file remains downloadable is a real control gap, not a cosmetic inconsistency.
- **Consequences:** The refund-processing and chargeback-processing code paths (Milestone M2 for the mechanism, M8 for chargebacks specifically — see ADR-010) must both write to two tables in one logical operation, not one.
- **Future considerations:** None — this is a small, fully specified addition to an already-sound table design.

### ADR-004: `customers` and `platform_users` remain permanently separate identities, with an explicit bridge for dual-role accounts

- **Status:** Accepted (bridging mechanism specified at ratification; the ARB's review had flagged this as an open question).
- **Context:** A single unified "users" table with a role flag would require every future authorization check to correctly exclude the customer role — a structural privilege-escalation risk. Separately, `docs/v3-database-design.md`'s `user_roles` table already anticipates one identity holding multiple marketplace roles (creator + affiliate), but that design predates `customers` and does not address a customer who later becomes a creator or affiliate.
- **Decision:** `customers` and `platform_users` (the Version 3.0.2-ratified rename target of `admin_users`, per `docs/v3-database-design.md`, landing at Milestone M7) remain two permanently separate tables with no merge, ever. A customer who becomes a creator or affiliate is represented by a new `platform_users` row that references `customer_id` (a nullable FK on `platform_users`, added at M7 alongside the rename) — two linked rows, one identity in the business sense, never one merged database row. Login/session continuity across the two roles (e.g., does a creator-who-is-also-a-customer need to switch accounts to see their own purchase history) is explicitly deferred as a UX question for M7's own design work, not resolved here.
- **Alternatives considered:** A single unified identity table with a capability system from day one (rejected — disproportionate scope for the actual gap this project needs to close now).
- **Rationale:** Preserves the hard security boundary ADR's original reasoning established, while giving the previously-open "what happens when someone is both" question a concrete, minimal answer that doesn't require redesigning either table.
- **Consequences:** `platform_users.customer_id` is a new column to add at M7, alongside the rename already planned there.
- **Future considerations:** The cross-role dashboard UX (does a creator/customer see one unified account view or two) is explicitly out of scope for Version 3.0.2 and must be designed as part of M7's own scope, not assumed.

### ADR-005: Customer-identity work is sequenced before coupons, promotions, and support

- **Status:** Accepted, unchanged.
- **Context:** Coupons' `first_purchase_only` logic and support tickets' customer-linked context both depend on a `customer_id` existing to attach to.
- **Decision:** Milestone order is M1 (identity) → M2 (ownership records) → M3 (checkout + dashboard) → M4 (coupons) → M5 (support) → M6 (notifications/email reliability) → M7 (marketplace) → M8 (go-live review). See the Sprint Readiness Report for the full milestone assessment.
- **Alternatives considered:** Building coupons first as the smallest, fastest-to-ship piece (rejected — would require rework once identity lands, not merely extension).
- **Rationale:** Correct, straightforward dependency-ordering, independently re-derived by the ARB and unchanged at ratification.
- **Consequences:** None beyond the ordering itself.
- **Future considerations:** None.

### ADR-006: Account provisioning is purchase-triggered only; self-registration is explicitly out of scope

- **Status:** Accepted (new at ARB review, ratified here as a binding scope boundary).
- **Context:** The Blueprint's reasoning for skipping an independent email-verification loop is sound specifically because a successful payment is itself a strong identity signal (the customer proved control of the email via their bank/mobile-money provider's own confirmation flow). That reasoning does not extend to a hypothetical account created with no purchase behind it.
- **Decision:** Version 3.0.2 ships no "Sign Up" or self-registration surface anywhere. The only ways a `customers` row is ever created are (a) automatically, at first verified purchase, or (b) not at all. A "Sign In" affordance for an already-provisioned account is in scope; a "Sign Up" affordance is not.
- **Alternatives considered:** Building a general-purpose registration flow now, with its own verification loop, alongside purchase-triggered provisioning (rejected as solving a problem this project doesn't yet have — customers need accounts primarily to see purchases already made).
- **Rationale:** Keeps Milestone M1's security model fully justified by reasoning already established, and avoids silently shipping a weaker-than-intended verification story for a feature with no current demand.
- **Consequences:** Milestone M1's acceptance criteria must explicitly exclude a public registration endpoint/UI.
- **Future considerations:** A true self-registration feature, if ever prioritized, requires its own ADR and its own independent email-verification design — it may not simply reuse M1's provisioning logic as-is.

### ADR-007: Commerce-critical transactional email gets narrow-scope automated retry, superseding prior no-scheduled-infrastructure policy for that specific case

- **Status:** Accepted, with an explicitly narrowed scope (resolves the item the ARB left as "Deferred pending explicit re-decision").
- **Context:** `docs/monitoring-and-alerting.md` states plainly that "this project has zero Cloudflare Queues, Cron Triggers, or Durable Objects anywhere" and explicitly declines third-party observability tooling as disproportionate to this project's scale. `docs/backup-and-recovery.md` independently confirms the absence of automated email retry was a deliberate, documented decision — "not a bug." The original Blueprint's Milestone M6 proposed a general Cron-Trigger-driven retry sweep over all of `email_log` without citing or engaging with either document.
- **Decision — the previous decision, why it's being replaced, why the replacement is preferable, stated explicitly as required by this ratification's governing instructions:**
  - **Previous decision:** No automated retry for any failed email send, of any kind, relying on manual `email_log` monitoring and Resend's own dashboard. Documented and deliberate at the time it was made (Version 2.1-era), calibrated against a system where the highest-stakes email in production was a newsletter send.
  - **Why it's being replaced, narrowly:** Going Live means the highest-stakes email is no longer a newsletter — it's `purchase-receipt` and `secure-download`, sent once, immediately after a real customer pays real money. A failed send of one of these two specific templates is a materially different severity of failure than a failed newsletter send, and the original decision's own "proportionate to scale/stakes" reasoning, applied honestly to *this* specific case, points the other way.
  - **Why the replacement is preferable:** A single, narrowly-scoped Cloudflare Cron Trigger (this project's first, but its only one) that drains `email_log WHERE status = 'failed' AND template IN ('purchase-receipt', 'secure-download')` on a short interval (e.g. every 15 minutes, capped at a small number of retry attempts before marking `permanently_failed` and alerting) is a minimal, well-bounded piece of new infrastructure, not a general-purpose queue system. It leaves the original decision's reasoning fully intact for every other email type (newsletters, welcome, notifications) — those remain manually monitored, exactly as `docs/monitoring-and-alerting.md` and `docs/backup-and-recovery.md` already document.
  - **Explicit non-decision:** This ADR does **not** approve a general retry mechanism for all of `email_log`, does **not** approve introducing a third-party observability/APM tool, and does **not** reopen the "proportionate to scale" philosophy for anything other than the two named commerce-critical templates.
- **Alternatives considered:** (a) Ship M6 exactly as originally specified (all-templates retry) — rejected, disproportionate and not what the actual risk (money-adjacent email specifically) calls for. (b) Do nothing, keep relying on manual monitoring indefinitely — rejected, the severity argument above is judged sufficient to warrant the narrow exception. (c) The narrow scope adopted here.
- **Consequences:** `docs/monitoring-and-alerting.md` and `docs/backup-and-recovery.md` must be updated at Milestone M6's implementation time to reflect this narrow exception precisely — they should not be edited now, since no code exists yet to describe (a documentation-consistency action item carried in the Amendment Register, not executed in this documentation-only ratification sprint).
- **Future considerations:** If real operational experience shows the 15-minute/small-retry-count parameters are wrong, adjust them — that's an implementation-tuning detail, not a re-litigation of this ADR. If a future milestone identifies a *third* email type that's genuinely commerce-critical, that requires its own explicit addition to this ADR's named-template list, not an assumed extension.

### ADR-008: Receipts carry an itemized tax breakdown structure; population is pending confirmation of VAT-registration status

- **Status:** Accepted at the schema/architecture level. **Open** at the data level, pending a factual business input this document cannot supply.
- **Context:** Ghana's indirect tax structure is multi-layered (standard VAT, NHIL, GETFund Levy, and other levies apply compounding, not as a single flat rate, for a VAT-registered business). The original Blueprint's `receipts` entity modeled a single `tax_pesewas` field, which cannot represent an itemized, compliant breakdown if this business is VAT-registered.
- **Decision:** `receipts` carries a `tax_breakdown` field (JSON: an array of `{ label, rate_percent, amount_pesewas }` entries) in addition to the existing `subtotal_pesewas`/`total_pesewas`. `tax_pesewas` (a simple sum, retained for quick display/reporting) is derived from `tax_breakdown`, not the other way around.
- **Alternatives considered:** Keep the single `tax_pesewas` field and address tax itemization only if/when it becomes a proven compliance problem (rejected — the cost of adding the structure now, before any receipt has been issued under the ratified schema, is far lower than retrofitting it onto live receipt data later).
- **Rationale:** The schema addition is cheap and reversible-if-unneeded (an empty or single-entry `tax_breakdown` array is a valid degenerate case for a non-VAT-registered business); the absence of the structure would be expensive to fix retroactively.
- **Consequences:** Milestone M2 must include this field from the start. The actual computation logic populating it depends on confirming this business's VAT-registration status — an explicit prerequisite for M2, tracked in the Amendment Register and Sprint Readiness Report, not something this architecture can resolve on its own.
- **Future considerations:** If the business is not VAT-registered, `tax_breakdown` may simply stay an empty array indefinitely — the structure costs nothing to leave unused.

### ADR-009: `order_items.quantity` represents distinct license-seat cardinality

- **Status:** Accepted.
- **Context:** The original Blueprint left ambiguous whether `quantity > 1` means one shared license usable by multiple people, or multiple distinct license grants.
- **Decision:** `order_items.quantity = N` means fulfilment generates exactly `N` distinct `licenses` rows (and, correspondingly, `N` independent `deliveries` entitlements) for that line item — each seat is a fully independent grant, each individually revocable, each with its own `license_key`. A single order can therefore produce multiple licenses for the same product.
- **Alternatives considered:** One shared license record with a `seats` count field and shared download entitlement (rejected — this would make partial revocation of a single seat, a realistic institutional-refund scenario, impossible without redesigning the entitlement model; independent grants cost nothing extra to model now).
- **Rationale:** Independent grants compose cleanly with everything already designed (a seat is just an ordinary `licenses`/`deliveries` pair) and require zero special-case logic elsewhere in the system.
- **Consequences:** Fulfilment logic for `quantity > 1` must loop, not branch into a separate code path.
- **Future considerations:** Distributing individual seats to individual recipient emails (vs. all seats going to the purchaser) is a real institutional-purchasing feature, explicitly deferred — this ADR only resolves the *data model's* cardinality, not the distribution UX.

### ADR-010: Chargeback handling mirrors the refund entitlement-revocation pattern

- **Status:** Accepted.
- **Context:** A Paystack chargeback (customer's bank reverses payment) is a distinct event from a voluntary refund, and was entirely unaddressed in the original Blueprint.
- **Decision:** A chargeback-class webhook event triggers the exact same revocation operation specified in ADR-003 (set `licenses.revoked_at`, set `deliveries.status = 'revoked'`), with `refund_requests`-equivalent record-keeping distinguishing `reason = 'chargeback'` from `reason = 'customer_requested'` for reporting purposes.
- **Alternatives considered:** Treating chargebacks as an entirely separate table/workflow (rejected — the revocation mechanics are identical; only the trigger and the record-keeping distinction differ).
- **Rationale:** Reuses an already-specified mechanism rather than inventing a parallel one.
- **Consequences:** Webhook handling (`routes/webhooks.ts`, unchanged file, extended logic) must recognize the chargeback-class event type from Paystack in addition to `charge.success`.
- **Future considerations:** A repeated-chargeback customer is a fraud signal worth surfacing to `product_moderation_log`-adjacent tooling eventually — explicitly deferred, consistent with this project's existing, deliberate fraud-tooling deferral (`docs/v3-database-design.md`).

### ADR-011: The `platform_users` rename requires an explicit, reviewed migration plan as a Milestone M7 entry condition

- **Status:** Accepted.
- **Context:** `ALTER TABLE admin_users RENAME TO platform_users` (per `docs/v3-database-design.md`) touches the identity table every admin-auth code path depends on, with unusually wide foreign-key blast radius across the schema.
- **Decision:** Milestone M7 may not begin implementation until a specific, reviewed migration/rollback plan for this single step exists (e.g., a maintenance-window requirement, or a verified-safe staged approach) — not merely the schema diff already designed in `docs/v3-database-design.md`.
- **Alternatives considered:** Treat the rename as routine, no different from any other additive migration (rejected — the blast radius genuinely is different from this project's typical additive-migration pattern, and deserves proportionate care).
- **Rationale:** The cost of a written plan is small; the cost of an unreviewed failure mode in the identity table underlying all admin/staff authentication is high.
- **Consequences:** M7 planning must produce this artifact before implementation, not during it.
- **Future considerations:** None.

### ADR-012: Ghana's Data Protection Act, 2012 (Act 843) is the current governing compliance framework; other frameworks (GDPR, etc.) are future-readiness considerations only

- **Status:** Accepted.
- **Context:** The original Blueprint's data-retention reasoning cited "GDPR-adjacent... right-to-be-forgotten readiness" — imprecise for a Ghana-domiciled platform serving (at present) Ghanaian customers.
- **Decision:** All compliance-facing architecture and documentation must cite the Data Protection Act, 2012 (Act 843), enforced by Ghana's Data Protection Commission, as the current, actually-applicable legal framework. GDPR and any other jurisdiction's framework may be referenced only as a *future-readiness* consideration (i.e., "this design does not preclude X" or "this pattern already satisfies GDPR-equivalent requirement Y"), never presented as a current obligation.
- **Alternatives considered:** Continue citing GDPR loosely as a general best-practice shorthand (rejected — imprecise legal citation is a real credibility risk with an actual regulator or auditor, independent of whether the underlying design happens to be compliant with both).
- **Rationale:** Correctness of legal citation matters independently of whether the design itself needs to change — in this case, the panel found the underlying soft-delete/retention design likely satisfies either framework's substance, so this is a citation correction, not a redesign.
- **Consequences:** See the ratified Blueprint's Data Governance & Compliance section for the full, corrected treatment.
- **Future considerations:** If the platform ever serves EU (or other jurisdictions') customers directly, a genuine GDPR (or equivalent) compliance review becomes a real, current requirement at that point — not before.

### ADR-013: The purchase confirmation page distinguishes view access (by reference alone) from action access (session or single-use token required)

- **Status:** Accepted.
- **Context:** The original Blueprint described confirmation-page access as "no login needed, valid as long as the browser session/URL is fresh" — not a real, specified mechanism, and one that conflated two different access levels.
- **Decision:** Viewing a confirmation page's status/receipt content remains accessible by `purchaseReference` alone (unchanged from today's live behavior, and consistent with standard, expected deep-linking UX for a bookmarkable/shareable receipt-status page). Any *action* taken from that page beyond viewing — re-issuing a download token, initiating account/password setup, changing any data — requires either an authenticated `customer_sessions` session or a fresh, single-use action token minted specifically for that action, never the bare `purchaseReference` alone.
- **Alternatives considered:** Requiring authentication for the entire page, including viewing (rejected — breaks the low-friction, no-account-required guarantee ADR-002/ADR-003 depend on). Leaving the page fully action-capable by reference alone, as originally (under)specified (rejected — a `purchaseReference` in a forwarded email, shared browser history, or leaked referrer is a real, if narrow, exposure for anything beyond viewing).
- **Rationale:** Preserves the deep-linking UX benefit while closing the specific exposure the ARB identified.
- **Consequences:** Milestone M2/M3 implementation must mint a distinct, short-lived action token for confirmation-page actions rather than reusing `purchaseReference` as an implicit bearer credential.
- **Future considerations:** None beyond the specification itself.
