# Version 3.1 - Sprint M3A - M3 Database Impact Assessment

Planning only. No migration was created. No schema change was applied to any environment.

---

## Governing question: does M3 require any schema change?

**Mostly no.** Every M3 screen's data need is already satisfiable from tables that exist today (`purchase_sessions`, `order_items`, `licenses`, `receipts`, `deliveries`, `customer_sessions`, `customers`). This section walks through each API Gap Analysis item and confirms the underlying data already exists, with exactly **one small, optional, additive column** identified as worth considering, not required.

---

## Gap 1 & 2 (assets + download usage/limit/expiry on purchase responses): no schema change

`deliveries.max_downloads`, `deliveries.downloads_used`, `deliveries.access_expires_at`, and `deliveries.status` all already exist (live since before M1). The only work required is a **new query/service-layer call**, not a new column - `fulfilmentService.ts`'s existing asset-resolution logic already reads these exact fields for the guest confirmation page; M3 needs the same logic invoked from a customer-authenticated context, not a new data source.

## Gap 3 (list/revoke own sessions): no schema change

`customer_sessions` already has every field the proposed `GET /api/customer/sessions` needs to display (`token` - never returned to the client, only used internally for the "is this my current session" comparison; `created_at`; `last_seen_at`; `expires_at`; `revoked_at`; `user_agent`; `ip_created`). The proposed `POST /api/customer/sessions/:sessionId/revoke` needs only an id-scoped variant of the `UPDATE customer_sessions SET revoked_at = ...` statement `revokeSession()` already performs by token - a new service function, not a new column or table.

## Gap 4 (change password): no schema change

`customers.password_hash` already exists and is exactly what a change-password endpoint reads and rewrites. No new column is needed for the *mechanism* itself.

---

## The one column worth considering (optional, not required for M3's launch)

**`customers.password_updated_at`** - the ratified Blueprint's own Account Security page description lists "password-last-changed date" as displayed information. `customers` today has no dedicated column for this; only the generic `updated_at` (which reflects *any* write to the row, not specifically a password change, so it cannot be trusted to mean "password last changed" once other fields on the row are updated for unrelated reasons - e.g., a future profile edit would also bump `updated_at` and falsely imply a recent password change).

**Recommendation: add it, but treat it as a nice-to-have, not a blocker.** Two options, in order of preference:

1. **Add `customers.password_updated_at TEXT` (nullable)**, set whenever `POST /api/customer/auth/set-password` or the newly-proposed `POST /api/customer/auth/change-password` succeeds. This is a single, additive, nullable column - the same low-risk shape every prior migration in this project has used - and directly answers the Account Security page's own stated requirement precisely, rather than approximately.
2. **If schema-change avoidance is prioritized for M3 specifically:** ship M3's Account Security page without this one data point in its first release (show "password set" as a boolean fact derived from `password_hash IS NOT NULL`, without a specific date), and add the column in a small, later follow-up once real usage shows whether the exact date is actually valued by customers. This defers a trivial, low-risk migration rather than avoiding a real one.

**This review does not mandate a choice** - it is a genuinely optional trade-off between "one more tiny, additive migration now" and "a very slightly less complete Account Security page at launch," and either is defensible. If chosen, the migration would be the *only* schema change M3 needs, and would be the next sequential migration number after `0019` at implementation time (confirm the exact number against the real repository state when M3B begins, per this project's own established discipline - never assumed in a planning-only pass).

---

## What M3 explicitly does NOT need

- No new table. Every M3 screen is served by data already modeled across `purchase_sessions`/`order_items`/`licenses`/`receipts`/`deliveries`/`customer_sessions`/`customers`.
- No change to any existing table's constraints, indexes, or CHECK clauses.
- No change to `products`, `payment_transactions`, `download_tokens`, `receipt_download_tokens`, `audit_logs`, or any admin-side table.
- No VAT/tax-related schema change - that question remains exactly where M2 left it (see the Risk Assessment's VAT Readiness section), untouched by M3's own scope.

---

## Migration plan, if the optional column is adopted

```sql
-- 0020_customer_password_metadata.sql (number to be confirmed at implementation time)
ALTER TABLE customers ADD COLUMN password_updated_at TEXT;
```

One statement, purely additive, nullable, no default required (NULL correctly represents "never set/changed," which is already a valid, meaningful state for a guest-checkout customer who never set a password at all). No backfill needed or possible for existing rows (the actual historical date is not known and should not be guessed) - existing customers simply show no date until their next password set/change, an honest gap, not a defect.

**Rollback:** trivial - `ALTER TABLE customers DROP COLUMN password_updated_at` if ever needed, with no dependent table or code path outside the one new Account Security display field.

---

## Compliance verdict

**Pass, with one optional, low-risk, fully-additive column identified and left as an implementation-time decision, not a planning-time blocker.** No structural schema change, no new table, and no modification to any existing constraint is required for Milestone M3.
