# Version 3.2 - Sprint M4D - Documentation Review

Confirms whether M4C's documentation matches the actual delivered architecture, APIs, database, testing, and known limitations - and whether the mandatory-review document set this sprint's own brief named actually exists under the paths given.

---

## Finding 1: Every M4C implementation-phase deliverable exists, but under different filenames than this sprint's own "Mandatory Review" list specifies

This sprint's brief names seven implementation-phase documents to review:

```
docs/v3.2-m4-implementation-report.md
docs/v3.2-coupon-architecture-report.md
docs/v3.2-reviews-architecture-report.md
docs/v3.2-database-changes.md
docs/v3.2-api-changes.md
docs/v3.2-test-results.md
docs/v3.2-known-limitations.md
```

**None of these seven exact filenames exist.** The actual, equivalent documents are all present, complete in content, and were reviewed by this Board in full - but each carries an `m4c-` infix the brief's list does not use:

```
docs/v3.2-m4c-implementation-report.md
docs/v3.2-m4c-coupon-architecture-report.md
docs/v3.2-m4c-reviews-architecture-report.md
docs/v3.2-m4c-database-changes.md
docs/v3.2-m4c-api-changes.md
docs/v3.2-m4c-test-results.md
docs/v3.2-m4c-known-limitations.md
```

This is consistent with (and arguably a more precise application of) this project's own established naming convention - every other milestone's implementation-phase docs are milestone-lettered (`v3.1-m3-implementation-report.md`, `v3.0.2-m2-database-changes.md`), and M4C's docs correctly follow that pattern. **This Board judges the naming itself correct**; the mismatch is between this review sprint's own document list and the actual, correctly-named files. Recorded here as a documentation-accuracy finding regardless of which side is "right," since a future reader following this review's own file list verbatim would get 404s. **Non-blocking.**

## Finding 2: Missing rollback-strategy documentation (established project convention, not followed here)

M2's own migration (`0019_ownership_layer.sql`) explicitly points to its planning document's "rollback strategy section" as the documented plan for reversing that migration if ever needed. **Migration `0020_reviews_and_coupons.sql` and its companion `v3.2-m4c-database-changes.md` contain no equivalent rollback-strategy content at all** - confirmed by direct grep, zero matches for "rollback" in either file. Given the migration is purely additive (3 new tables, 2 new nullable/defaulted columns) a rollback would be straightforward to write (`DROP TABLE`s in reverse-dependency order; `ALTER TABLE ... DROP COLUMN` for the two `purchase_sessions` additions), but nobody has written it down. **Non-blocking for M4 acceptance; should be closed before M4E Closeout completes**, to match this project's own established documentation standard.

## Finding 3: The Customer Journey Validation's specifically-required disclosure is missing from Known Limitations

`v3.2-m4b-customer-journey-validation.md` explicitly required: "Reviews will launch with no automated collection mechanism, relying on organic/manual traffic to the review form until M5 ships the trigger... stated explicitly as a known, accepted limitation of M4's own scope." `v3.2-m4c-known-limitations.md` does not contain this disclosure in any form - confirmed by direct grep for "sparse," "empty state," "collection," and "trigger" across the file, zero relevant matches. See the Amendment Compliance Report's Amendment 3 section for the fuller context. **Non-blocking; should be added to Known Limitations before M4E Closeout.**

## Finding 4: Test-result figures in the M4C documents were independently re-verified and found accurate

This Board did not trust the "212/212 passing," "77 new tests," "40 unit + 37 integration" figures as claimed - each was independently re-derived by re-running the actual suite in isolated groupings (`npx vitest run tests/unit`, `npx vitest run tests/integration`, per-file counts for all seven new files individually) and cross-totaled. **All figures in `v3.2-m4c-test-results.md` and `v3.2-m4c-implementation-report.md` match this Board's own independent count exactly.** No discrepancy found here - called out specifically because it is exactly the kind of claim a rigorous review should not accept at face value, and in this instance it held up.

## Finding 5: The Coupon and Reviews Architecture Reports accurately describe the actual code

Spot-checked against the live implementation, not merely read on their own terms: the Coupon Architecture Report's description of the two-phase redemption design, the "always record even on a lost race" behavior, and the immutability-after-creation design were all independently confirmed against `couponService.ts`'s actual code (see Security Review and Functional Review for the specific evidence). The Reviews Architecture Report's description of the purchase-gating mechanism and the client/server rendering split were likewise confirmed accurate against `reviewService.ts` and `routes/books.ts`. **No inaccuracy found in either architecture report.**

## Finding 6: `receipts.discount_pesewas` provenance is correctly and honestly documented

Worth calling out as a documentation-quality strength, not merely a neutral finding: `v3.2-m4c-database-changes.md` correctly identifies that `receipts.discount_pesewas` was *not* added by M4C's own migration but was already reserved, unused, by M2's migration 0019 (`-- always 0 in M2 — no coupon system exists yet`). This Board independently confirmed this via direct grep across every migration file and found the documentation's account accurate down to the specific migration number. This is the kind of detail a less careful pass would get wrong (or simply claim as new work), and it was not.

---

## Overall Documentation Verdict

**No inaccuracy found in the substantive technical content of any M4C document reviewed.** All findings in this review are completeness gaps (a missing rollback section, a missing required disclosure) or a filename/path mismatch between this review's own brief and the actual, correctly-convention-following files - not incorrect claims. **No Blocking finding.**
