# Version 5.0 — Milestone 2.2 Architecture Update

Companion to the Milestone 2 and 2.1 engineering reports — this document only covers what Milestone 2.2 added or changed. The underlying architecture (planning phase → Cloudflare Queue → consumer batches, Vectorize for vectors, D1 for everything else) is **unchanged**; this milestone deliberately worked inside it.

## 1. New Module: `services/knowledge/ranking.ts`

Sits between Vectorize's raw match results and `searchService.ts`'s response — a pure-function scoring layer with no I/O of its own (no D1, no fetch, no bindings). Two exports drive the whole pipeline:

- `computeRankingSignals(query, vectorSimilarity, title, chunkText, sourceType) → { vectorSimilarity, titleBoost, keywordBoost, sourceBoost, finalScore }`
- `scoreToConfidence(finalScore) → 'high' | 'medium' | 'low'`

Being a pure module with no side effects, it's fully unit-testable in isolation (`ranking.test.ts`) separately from the D1/Vectorize integration tests in `searchService.test.ts`.

## 2. `searchService.ts` — Data Flow Update

```
query
  → embedText() [AI Gateway, unchanged]
  → KNOWLEDGE_INDEX.query() [Vectorize, unchanged — still topK = limit × 4, returnMetadata: 'none']
  → D1 join [knowledge_chunks + knowledge_documents, unchanged]
  → filter [visibility / status / data_classification, unchanged]
  → NEW: computeRankingSignals() per candidate
  → sort by finalScore (was: raw cosine score)
  → NEW: scoreToConfidence(finalScore) (was: scoreToConfidence(rawScore))
  → slice to limit
  → NEW: log top_document_id alongside existing search_log fields
```

The only behavior change to the retrieval pipeline itself is *what a result is sorted and confidence-bucketed by* — raw cosine, replaced by the blended score. Everything upstream (embedding, Vectorize query, D1 join, governance filters) is byte-for-byte the same code path Milestone 2 built and Milestone 2.1 hardened.

## 3. New Admin Service: `services/admin/knowledgeSearchAnalyticsService.ts`

A read-only aggregation layer over `knowledge_search_log` — no new write path, no new source of truth. Mirrors the existing `knowledgeBaseAdminService.ts` pattern (one service per admin dashboard section, thin route layer in `routes/admin/knowledgeBase.ts`).

## 4. Schema Changes — Migration `0038_knowledge_base_quality.sql`

| Table | Change | Backs |
|---|---|---|
| `knowledge_documents` | + `embedding_model`, `embedding_version`, `embedded_at`, `embedding_refreshed_at` | Task 5 |
| `knowledge_search_log` | + `top_document_id` (FK → `knowledge_documents.id`) | Task 4 (most-retrieved-documents) |
| *(new)* `knowledge_indexing_dead_letters` | full new table | Task 7 |

All additive; no column removed or repurposed; rollback is a documented, safe `DROP`/`ALTER ... DROP COLUMN` sequence (see the migration file's own header).

## 5. Dead-Letter Handling — Reuses, Does Not Extend, the Queue Topology

Milestone 2.1 established: one Cloudflare Queue (`robayer-knowledge-index-queue`), one producer binding, one consumer (`max_batch_size: 5`, `max_concurrency: 2`, `max_retries: 3`). **This is still true after Milestone 2.2.** Dead-letter tracking is a D1 table plus a `try/catch` in the existing `queue()` handler — no second queue, no second consumer, no new binding. See the Engineering Report §8 for why the first draft (a second queue) was reconsidered and replaced before deployment.

## 6. What Deliberately Did Not Change

- Vectorize index (`robayer-knowledge-base`, 1536 dimensions, cosine) — same index, same binding.
- The planning/consumer split from Milestone 2.1 — untouched.
- The AI Gateway embedding path (`embedText()`, `knowledge.embed` feature) — untouched; ranking and confidence are entirely post-retrieval concerns.
- `documentSources.ts` — no new document types indexed, no new crawl targets. (The Resources retrieval gap's most durable fix — indexing the `/resources/` catalog page itself — would touch this file, and was explicitly deferred pending the cheaper topK-oversampling experiment; see Known Limitations.)
