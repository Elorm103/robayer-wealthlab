# Version 5.0 Milestone 1.2 — AI Governance & Safety

**Governance Report**

## Founder Principle (permanent), and how this milestone enforces it structurally

> "No future AI product may ever communicate directly with OpenAI or any future provider. Everything must pass through the AI Gateway."

This was already true architecturally as of Milestone 1 (no module besides `services/ai/providerRegistry.ts` imports a provider file). Milestone 1.2 makes the Gateway itself the enforcement point for governance, not just a routing convenience:

- A feature cannot get an AI response without declaring a `classification` — the Gateway refuses before routing is even resolved.
- A feature cannot get an AI response whose classification isn't approved for the candidate provider — `services/ai/providerPolicy.ts` checks this per candidate, centrally, before any network call.
- A feature cannot spend money without a budget ceiling applying — omitting `maxCostUsdMicros` no longer means "uncapped," it means "inherits the platform default."
- A feature's prompt/response cannot be stored without passing through masking first, and the retention policy governing whether it's stored at all (and for how long) is centrally configured, not decided per-feature.

This is the concrete meaning of "the Gateway becomes the permanent foundation of every future AI capability" — not a policy document, but code every future feature (Knowledge Base, Customer AI, Admin AI, Investment Assistant, Fraud Detection, Recommendation Engine, Analytics AI) must pass through to get anything from a provider at all.

## Data Classification Engine (Task 3)

Six classifications, defined in `services/ai/providerPolicy.ts`: `PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `FINANCIAL`, `PERSONAL`, `HIGHLY_SENSITIVE`. Every `callAi()` request must declare exactly one; an unrecognized value is refused immediately.

**Important distinction, worth restating plainly:** this is a *different* concept from the pre-existing `ai_usage_log.data_classification` column (`PRODUCTION`/`INTERNAL`/`DEVELOPMENT`/`UNKNOWN`), which is the Version 4.9 platform-wide "is this real traffic or internal testing" convention, unchanged and still serving its original purpose. The new column is named `sensitivity_classification` specifically to avoid this confusion. Today's one real feature (`internal.gateway-diagnostic`) is classified `INTERNAL` under the new scheme — an internal operational health check, not customer or business data.

## Provider Policy Engine (Task 4)

`services/ai/providerPolicy.ts`'s `PROVIDER_POLICY` table maps each of the six classifications to an allow-list of approved providers. Today, every classification allows only `openai` — because that is the only provider this project has ever integrated and reviewed, not because each classification's risk profile with OpenAI has been individually assessed against a real data-processing agreement. This is disclosed honestly rather than presented as a completed compliance exercise: **the mechanism is real and enforced (verified by test); the actual policy content is a placeholder pending a genuine second-provider decision.**

Before a second provider (e.g. Anthropic) is wired into `routingConfig.ts`, this table needs a real decision, feature by feature and classification by classification, about which providers may see which kind of data — see the Security Report's §2 and §7, and Known Limitations.

Deliberately kept as reviewed, committed code rather than an admin-editable `site_settings` value — the same posture this project already applies to RBAC role lists and the routing table itself. A compromised admin session cannot silently loosen data-handling policy through the UI; changing it requires a code change, review, and deploy.

## Preventive Cost Enforcement (Task 1) — the five layers, and what changed from Milestone 1.1

| Layer | Milestone 1.1 | Milestone 1.2 |
|---|---|---|
| Per-request cap | Post-call only | **Preventive** — estimated before the provider is contacted |
| Daily budget | Warning-only, never blocked | **Preventive, blocks** |
| Monthly budget | Warning-only, never blocked | **Preventive, blocks** |
| Provider (lifetime) budget | Did not exist | **New, preventive, blocks** |
| Platform (lifetime) budget | Did not exist | **New, preventive, blocks** |

This is a deliberate reversal of Milestone 1.1's explicit "warning-only" decision for daily/monthly budgets, made because this milestone's brief explicitly asked for it ("Reject BEFORE contacting the provider if limits would be exceeded"). It is documented here as an intentional, founder-directed behavior change, not a silent contradiction of the earlier decision.

**Default dollar figures** (per-request $0.001, daily $1.00, monthly $20.00, per-provider lifetime $50.00, platform lifetime $100.00 — `services/ai/aiGatewayConfig.ts`) are engineering-judgment placeholders, conservative for a platform whose only real traffic today is a handful of diagnostic-test clicks. They are not founder-approved business figures and should be reviewed/adjusted via the Settings page before any real customer-facing AI feature ships.

## Mandatory Default Budgets (Task 2)

`services/ai/aiGatewayConfig.ts`'s defaults apply automatically the moment a `site_settings` key has never been explicitly configured — there is no "forgot to set a budget" state a developer can accidentally leave a feature in. `maxCostUsdMicros` remains an optional per-call override for a feature that genuinely needs a tighter (or, deliberately, looser) cap than the platform default; omitting it is safe by construction, never unsafe by omission.

## Prompt Retention Policy (Task 5)

Configured centrally (`ai_gateway_retention_storage_mode` / `ai_gateway_retention_days` in `site_settings`), five storage modes (`never`, `metadata_only`, `encrypted_prompt`, `encrypted_response`, `encrypted_both`) and five retention periods (30/90/180/365 days, or forever). Default: `metadata_only` / 90 days — no prompt/response text is ever persisted until an admin deliberately opts in, and even then only encrypted. Scheduled cleanup (the existing Cron Trigger) nulls out the sensitive text columns past their eligibility date, keeping the numeric/audit row forever — "nothing should require manual deletion" is satisfied without ever destroying cost/usage history.

## Sensitive Data Protection (Task 6)

`services/ai/sensitiveDataMasking.ts` runs unconditionally on every call's prompt/response, regardless of retention mode — so "how many prompts contained something that looked like a secret" (the dashboard's Sensitive Prompt Count) is a real signal even for calls whose text is never stored. See the Security Report §1/§6 for the honest "best-effort, not a guarantee" caveat on regex-based detection.

## Governance Dashboard & Audit (Tasks 7-8)

Every field the brief listed is now real and backed by a genuine query, not a placeholder — see the Engineering Report's frontend section and `services/admin/aiUsageService.ts`'s `getAiGovernanceSummary()`. Every `ai_usage_log` row now carries the full decision trail (`provider_decision`, `budget_decision`, `retention_decision`, `masking_applied`, plus versioning via `gateway_version`/`policy_version`) and is searchable through the existing AI Usage Log filters.
