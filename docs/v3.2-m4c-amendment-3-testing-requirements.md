# Version 3.2 - Sprint M4C - Amendment 3: Expanded Testing Requirements

**Required by:** M4B Technical Debt Assessment and Recommendations - admin-panel test coverage for the two new admin surfaces (review moderation, coupon management) is a **hard requirement** of this milestone's Testing Strategy, not a recommendation to retrofit later. This is the third consecutive milestone where an untested admin surface has been named a risk (M2, M3 both had this pattern found by their own acceptance reviews); this milestone commits to closing it from the first implementation pass.

## Mandatory Test Coverage (tracked here, delivered in Phase 7)

### Reviews
- Unit: `reviewService.ts` - submission (purchase-gated), edit (existing review updated, not duplicated), moderation (approve/reject), aggregate rating computation.
- Integration: `POST /api/customer/reviews` (submit, including rejection when no matching verified purchase exists - the core abuse-prevention mechanism), `GET /api/products/:slug/reviews` (public display, approved-only), `GET /api/admin/reviews` + `PATCH /api/admin/reviews/:id` (**new - first-ever test coverage for an admin review/moderation-shaped endpoint in this project**).
- Security: cross-customer ownership (a customer cannot submit a review referencing another customer's purchase_session_id), duplicate-review rejection (UNIQUE constraint honored, second attempt updates rather than errors).

### Coupons
- Unit: `couponService.ts` - validation (active/expired/product-restricted/redemption-limit checks), discount computation (percentage and fixed, including a percentage-over-100 rejection), the atomic redemption-count increment (including the race-loss path).
- Integration: `POST /api/coupons/validate` (discount preview), checkout with a valid coupon (amount correctly discounted, locked, and verified), checkout with an invalid/expired/exhausted coupon (rejected before payment), `GET/POST/PATCH /api/admin/coupons` (**new - first-ever test coverage for admin coupon management**).
- Security/race: a true-concurrency test (`Promise.all`, not sequential calls - this project's own established discipline since the M2D closeout's own concurrency-test precedent) proving a limited-redemption coupon cannot be over-redeemed beyond the documented, accepted edge case in the Amendment 2 security review; a `first_purchase_only` coupon used by a returning customer is detected and logged, not silently ignored.
- Regression: the full existing checkout/webhook test suite must continue passing unmodified with no coupon present (default `couponCode` absent = identical behavior to pre-M4 checkout, proving the change is genuinely additive).

### Checkout Regression (explicit, given this touches the payment-amount-locking path)

- Existing `tests/integration/checkout.test.ts` and `tests/integration/webhook.test.ts` must pass unmodified.
- New test: checkout with no coupon produces byte-identical `amount_pesewas` to pre-M4 behavior (discount_pesewas = 0, coupon_id = NULL).
- New test: the webhook's existing amount-mismatch high-severity rejection still fires correctly when a discounted amount is tampered with post-lock (proving the existing verification logic extends correctly to the discounted case without modification).
