# Version 3.3 Sprint M5D: Customer Reconciliation Validation Report

Independently validates `services/customer/reconciliationService.ts`, `routes/customer/reconciliation.ts`, and `/checkout/claim-purchase/` through live scenarios, not documentation review alone.

---

## Ownership Verification

**Verified live.** Seeded a "victim" customer (id 7) with an already-claimed verified purchase (`customer_id = 7`). Called `POST /api/customer/reconcile-purchases` with the victim's email from a fresh IP, simulating an attacker who knows only the victim's email address. Result: `customer_id` on the victim's purchase remained `7`, unchanged — the already-claimed row was correctly excluded by the `customer_id IS NULL` gate. **Pass.**

## Duplicate Prevention (Sequential)

**Verified live.** Reconciling the same email a second time, sequentially, after the first reconciliation completed, produces zero further linking and zero further audit log entries — confirmed both via the M5C unit test suite (re-run independently, passing) and via a fresh live HTTP call.

## Duplicate Prevention (Genuine Concurrency) — Non-Blocking Finding

**Not previously tested by the M5C suite; tested here for the first time.** The M5C test suite's own "duplicate prevention" test calls `reconcilePurchases()` twice sequentially (`await`ing the first call before starting the second). This Board instead called it twice via `Promise.all` — genuine concurrency, simulating a double-click or a client retry — against a single seeded orphaned purchase.

**Result:** the customer row itself stays correctly singular (`findOrCreateCustomer()`'s own race-safe UNIQUE-constraint recovery works as designed — confirmed, one customer row). However, **both concurrent calls proceed past the `customer_id IS NULL` read before either write lands**, so both write an `audit_logs` row and both call `issuePasswordToken()`, resulting in **2 audit log entries and 2 duplicate password-setup emails sent to the same customer for the same reconciliation event.** Reproduced directly (test since removed, results captured in this review's own working notes): `audit=2 tokens=2 emails=2`.

**Impact assessment:** no data corruption (the purchase-to-customer linkage itself is correct and singular), no unauthorized access, no financial impact. The customer experience impact is real but minor: two identical "set your password" emails instead of one, and a doubled (but harmless, non-misleading) audit trail. **Classified Non-blocking** — genuinely low-severity, and the realistic trigger (a near-simultaneous double submission of the same claim-purchase form) is narrow, unlike the review-reminder Cron Trigger finding's much more routine trigger condition (see the Review Reminder Validation Report, which found the same root-cause class of issue with materially higher real-world likelihood and a Blocking classification as a result).

**Recommendation:** a straightforward fix exists (e.g., an atomic claim step — gate the entire read-link-notify sequence behind a single atomic UPDATE whose row-count result determines whether to proceed to email, rather than a separate read-then-write) and should be applied in a near-term follow-up, but does not block this milestone's acceptance.

## Replay Protection

The password-setup token issued by reconciliation reuses `authService.issuePasswordToken()`/`setPassword()`'s existing single-use, atomically-consumed token mechanism, already proven correct by this project's own pre-existing concurrent-redemption test (`tests/unit/authService.test.ts`, re-run and confirmed passing in this review). No new replay surface is introduced by reconciliation itself.

## Audit Logging

**Verified.** Every real reconciliation event writes an `audit_logs` row (`actor_type = 'customer'`, `action = 'customer.purchases_reconciled'`, metadata including the reconciled purchase-session IDs), confirmed both via unit test and via direct D1 query after a live HTTP call. No reconciliation event happens silently.

## Historical Purchase Recovery — Verified Against Real Production Baseline

Independently re-queried real production D1 (read-only, `wrangler d1 execute --remote`) rather than trusting M5A/M5B's cited figures: confirmed **17 verified purchases, 15 with `customer_id IS NULL`, 2 customers, 0 reconciliation audit events** — every figure matches M5A's and M5B's own citations exactly, and confirms migration `0021` has genuinely not been applied to production (latest applied migration on remote is `0020_reviews_and_coupons.sql`), meaning this feature has never actually run against the real orphaned-purchase backlog it exists to fix. This is expected and correct given the "do not deploy" instruction for this sprint, not a finding.

## Invalid Ownership / Misuse Attempts

Attempted directly against the live route: a SQL-injection-shaped email (`' OR '1'='1`), a wrong-type email (a number), a missing `email` field, and a non-JSON body. Every attempt returned the identical generic `{success:true,{requested:true}}` response with no crash, no 500, and no malformed row created in `customers`. Rate limiting was verified to genuinely engage (checked via side-effect — whether the purchase actually got linked — rather than the response body, since the no-enumeration design makes a rate-limited response look identical to a normal one).

---

## Verdict

**Sound, with one genuine, low-severity, non-blocking concurrency finding.** Ownership validation, no-enumeration, rate limiting, and audit logging all independently confirmed correct. Recommend the concurrency fix as near-term follow-up work, not a blocker to this milestone's acceptance.
