# Version 3.3 Sprint M5A: Architecture Assessment

Reviews backend architecture, frontend architecture, APIs, database, security, scalability, and performance, using the `workers-best-practices` skill's rules as the evaluative framework (configuration, request and response handling, architecture, observability, code patterns, security), applied through direct inspection of the current codebase.

---

## Backend Architecture

A Cloudflare Worker with D1 (relational storage), R2 (digital assets and generated PDFs), and KV (rate limiting), following a consistent routes-are-thin, services-hold-logic pattern across every milestone reviewed. Route registration is a single, explicit array in `worker/index.ts`, checked and found complete and collision-free at Milestone M4's own release. No service binding, no Durable Object, and no Queue exists yet; none has been needed, since every background-adjacent task so far (newsletter campaign sends) has fit within `ctx.waitUntil()` against a durable, D1-backed recipient roster rather than requiring separate infrastructure. This is a deliberate, documented choice, not an omission.

## Frontend Architecture

Static HTML and vanilla JavaScript, no framework, no build step, served through GitHub Pages with the Worker intercepting specific route prefixes (`/api/*`, `/books/*`, `/resources/*`, `/blog/*`, `/free-guide/*`) at the edge. This architecture has scaled cleanly through four feature milestones without needing a framework migration, and this review found no evidence it is now a constraint: component-per-concern JavaScript files (one per page or shared behavior) remain small, readable, and independently testable through browser verification.

## APIs

Consistent `{success, data}` and `{success: false, error}` envelope across every endpoint reviewed, a shared `ApiErrorCode` union enforced at compile time (`tsc --noEmit` fails if a new error code is added to the union but not mapped to an HTTP status), and consistent role-gating middleware chains (`requireAuth`, `requireRole`, `requireCsrf`, rate limiting) reused identically across every admin and customer route. No API design inconsistency found.

## Database

20 migrations, all additive, zero destructive change across the platform's entire history. The one real data-integrity finding from this review (15 of 17 verified purchases lack a `customer_id`) is a historical artifact of when Milestone M1 shipped relative to the platform's pre-existing purchase history, not a schema design flaw; the schema itself correctly allows a nullable `customer_id` precisely because guest checkout is, and remains, a supported path.

## Security

Independently reviewed twice already at Milestone M3 and Milestone M4 (session management, CSRF, rate limiting, coupon-specific abuse scenarios including a true-concurrency race-condition test), with no exploitable vulnerability found in either review. Session tokens, CSRF secrets, and license keys all confirmed to use the Web Crypto API, not `Math.random()`. This review found no new security concern in the current architecture.

## Scalability

The current traffic and transaction volume (17 lifetime purchases, one active product) is far below any limit this architecture would meaningfully strain against. Cloudflare Workers and D1 both scale well past this platform's realistic near-term volume without architectural change. The one forward-looking scalability note: client-side product search and filtering (`content-filters.js`) loads the full catalog into the browser and filters it there, which is entirely appropriate at 2 products and would need revisiting only if the catalog grows into the tens of products, a scale this platform is not near today.

## Performance

No performance regression found across any milestone's own closeout testing. Static asset delivery through GitHub Pages and edge-routed dynamic content through the Worker together keep response times low; this was not independently re-measured in this planning sprint (no code changed to re-measure against), but no evidence in production logs or prior milestone reports suggests a performance problem exists.

---

## Bottlenecks Identified

None found at current scale. The nearest future bottleneck, client-side catalog filtering, is a two-or-three-product-catalogs-away concern, not a current one.

## Future Risks

- **Dependency version drift** (TypeScript, `@cloudflare/workers-types`, `wrangler`, all currently one or more versions behind latest, see `v3.3-technical-debt-assessment.md`). Low urgency today, worth a routine refresh cycle.
- **The orphaned-customer data gap will only grow more awkward to reconcile the longer it is left**, since new guest purchases (if guest checkout continues to be offered without an easy claim path) will keep adding to the backlog rather than shrinking it.
- **No visitor analytics remains the platform's largest blind spot** for any future architectural or product decision that depends on understanding real usage patterns rather than lagging proxies like purchase-session counts.

## Scaling Concerns

None found that are actionable at this platform's current volume. Revisit client-side catalog filtering and any future need for a Durable Object or Queue only if and when transaction volume or catalog size grows an order of magnitude past today's figures.

## Architectural Improvements Recommended

- Add visitor analytics (Cloudflare Web Analytics is the architecturally-native choice, requiring no new backend surface, no new data pipeline, and no departure from this platform's existing all-Cloudflare stack).
- Add a scheduled (Cloudflare Cron Trigger) job for the post-purchase review-request email named in `v3.3-customer-journey-review.md`, the platform's first genuine use case meeting this project's own stated bar ("no new Cron Trigger without a specific, narrow, named reason").

No other architectural change is recommended by this review.
