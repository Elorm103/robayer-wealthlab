## Sprint M5D's Blocking Findings, Restated

Sprint M5D identified one Blocking finding (B1), reproduced in two distinct ways: (a) a single failed review-reminder send permanently and silently suppressed all future reminders for that purchase; (b) genuinely concurrent Cron Trigger invocations sent duplicate reminder emails. A related, lower-severity, Non-blocking finding (N4) affected reconciliation's own concurrency. Both are addressed by Sprint M5D.1.

## Verification Method: Temporarily Revert, Prove Failure, Restore, Prove Fix

Rather than trusting Sprint M5D.1's own regression-test report, this Board did the following directly:

1. Backed up the current (remediated) `reviewReminderService.ts` and `reconciliationService.ts`.
2. Temporarily overwrote both files with their exact pre-Sprint-M5D.1 content (reconstructed from this Board's own knowledge of the prior implementation).
3. Ran the 6 new Sprint M5D.1 regression tests against this reverted code.
4. Restored the remediated files, confirmed byte-for-byte identical to the pre-revert state via `diff`.
5. Re-ran the same tests against the restored, remediated code.

### Result Against the Reverted (Pre-Remediation) Code: 5 of 6 New Tests Failed

```
FAIL  M5D.1: genuinely concurrent scheduled runs send exactly one reminder... — expected 2 to be 1
FAIL  M5D.1: a transient (non-permanent) send failure remains eligible...    — expected 'failed', got undefined
FAIL  M5D.1: a persistently-failing send stops retrying after MAX_SEND_...  — expected 1, got 0
FAIL  M5D.1: an immediately-permanent (4xx) send failure is marked...       — expected 'permanently_failed', got undefined
FAIL  M5D.1: genuinely concurrent reconciliation calls... exactly one...    — expected 1, got 2
```

(The 6th new test, "repeated sequential execution after a genuine success," passed even against the reverted code — correctly, since that specific scenario was never broken; only genuine concurrency and failure-handling were.)

This is direct, reproducible proof that Sprint M5D.1's regression tests are not tautological — they fail against the exact code Sprint M5D found Blocking, and this Board generated that failure independently, not by reading Sprint M5D.1's own claim of having done so.

### Result Against the Restored (Remediated) Code: All Tests Pass

After restoring the fixed files (confirmed identical via `diff` to the pre-revert state), the same test run: **26/26 passing** in both affected files.

## Finding B1(a) — Failed Send Permanently Suppressing Future Reminders: Resolved, Verified

The remediated `findDueReminders()` now distinguishes `review_reminder_attempts.status` values, re-including `'failed'` rows as eligible. Verified via the restored test suite's "transient (non-permanent) send failure remains eligible on a later run and succeeds once the outage clears" test, and independently re-confirmed live (see the Concurrency Verification Report) that a failed attempt is correctly classified and does not permanently vanish.

## Finding B1(b) — Concurrent Duplicate Sends: Resolved, Verified Under Stress

The remediated `claimReminderAttempt()`'s atomic `INSERT ... ON CONFLICT ... WHERE` correctly serializes concurrent claims. Verified beyond Sprint M5D.1's own 2-way test: this Board fired **5 genuinely concurrent** `/__scheduled` HTTP requests against a real running Worker (`wrangler dev --test-scheduled`) targeting a single due purchase, and confirmed via direct D1 inspection that `review_reminder_attempts.attempt_count = 1` — exactly one of the five invocations ever claimed it.

## Finding N4 — Reconciliation Concurrency: Resolved, Verified Under Stress

Similarly stress-tested beyond Sprint M5D's own 2-way reproduction: 5 genuinely concurrent `POST /api/customer/reconcile-purchases` requests for the same email against a real running Worker produced exactly 1 audit log entry and 1 password-setup email — confirmed by direct D1 query, not inferred.

## Can the Fix Regress Under the Scenarios Sprint M5D Identified?

No regression path found. The fix's correctness rests on D1/SQLite's own write serialization (a platform guarantee, not an application-level assumption this project controls, and therefore not something this remediation could have gotten subtly wrong in a way that only manifests occasionally) combined with an explicit `meta.changes` check — a binary, deterministic signal, not a heuristic or a timing-sensitive one. The one genuine near-miss this Board confirms was already caught and fixed **within** Sprint M5D.1 itself (the `datetime('now')` vs `.toISOString()` comparison bug, which briefly reintroduced exactly this class of regression before being caught by the same test suite) — see the Regression Verification Report for how this Board independently confirmed that fix too.
