# Version 3.3 Milestone M5C: Database Changes

## Migration 0021: `0021_activation_and_review_reminders.sql`

The only schema change this sprint makes. Applied to local D1 (`wrangler d1 execute --local`); not yet applied to remote/production D1, per this sprint's own instruction not to deploy.

```sql
ALTER TABLE customer_profiles ADD COLUMN review_reminder_opt_out INTEGER NOT NULL DEFAULT 0 CHECK (review_reminder_opt_out IN (0, 1));
ALTER TABLE customer_profiles ADD COLUMN review_reminder_opt_out_token TEXT;
```

Both columns are additive, nullable/defaulted — zero impact on any existing row's meaning, zero `DROP`, zero column removal. `database/schema.sql`'s `customer_profiles` block and its own "current as of migration" header were updated to match.

### Why reconciliation (Phase 2) needed no schema change

`purchase_sessions.customer_id` is already nullable and already supports being set after row creation — that is exactly what the M1 webhook auto-provisioning flow already does for every purchase since M1. Reconciliation applies the identical `UPDATE` pattern to older, pre-M1 rows. `customers`, `customer_profiles`, and `audit_logs` (whose `actor_type` CHECK constraint already includes `'customer'`) are all reused entirely unchanged.

### Why review reminders (Phase 5) needed exactly these two columns

An opt-out mechanism needs somewhere to record "don't send this customer any more review-request reminders." The existing `unsubscribe_tokens` table (used by the newsletter unsubscribe flow) is hard-scoped via a NOT NULL foreign key to `newsletter_subscribers`, a different entity — it cannot be reused generically for a customer-level preference. Two new, parallel, minimal columns on `customer_profiles` were added instead:

- `review_reminder_opt_out` — the actual preference flag, defaulting to 0 (still receiving reminders) for every existing row.
- `review_reminder_opt_out_token` — generated lazily, the first time a reminder is ever sent to that customer (`reviewReminderService.ts`'s `getOrCreateOptOutToken()`), not pre-populated for every existing row. A single, long-lived, non-expiring value per customer, not single-use — the opt-out action is idempotent and low-stakes by design (a forwarded or reused link can, at worst, opt someone out of a reminder email again; it grants no access to anything). This matches `unsubscribeService.ts`'s own "always succeeds, never errors" philosophy while remaining a structurally separate mechanism from `unsubscribe_tokens`.

### Rollback

`ALTER TABLE customer_profiles DROP COLUMN review_reminder_opt_out; ALTER TABLE customer_profiles DROP COLUMN review_reminder_opt_out_token;` — safe at any time; no other table references either column and no later migration builds on top of this one.

## Data reused, not modified

No other table's schema changed. This sprint's features read and write existing tables' existing columns:

- `purchase_sessions` (customer_id linking, verified_at/created_at for analytics)
- `customers` / `customer_profiles` (via the existing `findOrCreateCustomer()`)
- `customer_sessions` (`last_seen_at`, already-existing dashboard-usage signal)
- `audit_logs` (`actor_type = 'customer'` and `'system'`, both already valid per the existing CHECK constraint)
- `email_log` (`entity_type`/`entity_id`, used to detect an already-sent review reminder — no new column)
- `coupon_redemptions`, `product_reviews` (read-only, for the new analytics metrics)
- `customer_password_tokens` (a third `template` value routed through the existing `issuePasswordToken()`, no schema change)
