# Version 5.0 Milestone 1.2 — AI Governance & Safety

**Operations Report**

## What an admin needs to do after this deploys

1. **Review the default budget figures** on the Settings page's AI Gateway card (per-request cap, daily/monthly/platform budgets, per-provider budgets) — the shipped defaults are engineering placeholders (see the Governance Report), not business decisions. Adjust them to real numbers before any customer-facing AI feature goes live.
2. **Decide the real retention policy.** Default is `metadata_only` / 90 days (no prompt/response text ever stored). If prompt/response inspection is wanted for debugging or QA, switch to an `encrypted_*` mode — which requires step 3 first.
3. **Set `AI_PROMPT_ENCRYPTION_KEY`** (optional — only needed for encrypted retention modes) via:
   ```bash
   node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
   wrangler secret put AI_PROMPT_ENCRYPTION_KEY
   ```
   Until this is set, an `encrypted_*` retention mode silently and safely falls back to `metadata_only` (never plaintext) — see `retentionDecision` on any affected row, which states this explicitly.

## New scheduled job

The existing single Cron Trigger (`0 6 * * *`, daily) now also runs `services/ai/retentionCleanupService.ts`'s cleanup — no new trigger, no new schedule to configure. Its outcome is recorded as a `cron.heartbeat` audit event (`entityType: 'ai_gateway_retention_cleanup'`), same as the two existing scheduled jobs, and the running total is visible on the Settings dashboard ("Retention cleanup last ran" / "Total purged").

## New dashboard surfaces

- Settings page: "AI Gateway — Governance Dashboard" card — budget status badge, policy status, retention status, governance summary, classification/provider distribution charts, per-provider budget editor.
- AI Usage page: classification column + filter, and a "Governance" section in the row-detail drawer.

## Performance impact

- `callAi()` gained, per call: 3 parallel config/spend queries up front (budget config, retention config, spend snapshot — all cached/computed once per invocation, not per candidate), plus a per-provider lifetime-spend lookup cached within the call if multiple candidates share a provider. At today's single-candidate routing table, this is one extra round-trip of small, indexed queries — not measurable against the dominant cost (the actual OpenAI API call itself, hundreds of milliseconds).
- `getAiGovernanceSummary()` (the Settings dashboard) runs 8 queries in parallel, all scoped to a 30-day window except the lifetime purge count — same acceptable-at-current-volume caveat already noted in the Milestone 1.1 report for the lifetime cost aggregate.
- The scheduled cleanup job is a single `COUNT` + a single conditional `UPDATE`, run once daily — negligible.

## Cost implications

- **No new recurring provider spend.** Per the same reasoning as Milestone 1.1 (health monitoring stays derived from real call history, no synthetic ping), this milestone adds zero new AI API calls.
- **Real behavior change:** budgets now block. If the founder's real usage ever approaches the default $1.00/day or $20.00/month figures, calls will start being preventively refused rather than merely warned about. This is the intended effect of Task 1, but is worth knowing before it happens unexpectedly — see item 1 above.
