# Version 3.0.2 - Milestone M2 API Reference

Orders, Receipts & Customer Library. Covers the five new
customer-authenticated endpoints, the two new guest reference-scoped
receipt endpoints, the one new admin endpoint, and the one extended
existing endpoint. All responses use the project's standard envelope:
`{ success: true, data: {...} }` or `{ success: false, error: { code,
message } }`.

## New: Customer Library routes (`/api/customer/*`)

All five routes are thin HTTP wrappers over
`services/customer/purchaseHistoryService.ts` (and
`services/orders/receiptPdfService.ts` for the download route) - no
route touches D1 directly. Every route requires `requireCustomerAuth`
(the M1 `customer_session` cookie) - this is the Customer Library's data
layer only; no dashboard page consumes it yet (M3 scope). Every response
carries `Cache-Control: no-store` (financial/purchase data). Read routes
are rate-limited at 60/15min/IP; the receipt-download route at
20/15min/IP.

### `GET /api/customer/purchases`

**Auth**: `customer_session` cookie.

**Query params**: `page` (default 1), `limit` (default 20, max 50).

**Success (200)**:
```json
{
  "purchases": [
    {
      "purchaseReference": "RWL-2026-600001",
      "productTitle": "Starting to Invest with GH₵100",
      "amountDisplay": "GH₵39.00",
      "status": "ready",
      "createdAt": "2026-07-20T10:00:00Z",
      "receiptNumber": "RWL-RCT-2026-000001"
    }
  ],
  "total": 1,
  "page": 1,
  "limit": 20
}
```
`status` is one of `processing` | `ready` | `unavailable` | `refunded`
(mapped from the internal `purchase_sessions.status`, never the raw
value). A customer with zero purchases gets `{ purchases: [], total: 0,
page: 1, limit: 20 }`, not an error.

**Errors**: `NOT_AUTHENTICATED` (401); `VALIDATION_ERROR` (400) for a
malformed `page`/`limit`; `RATE_LIMITED` (429).

### `GET /api/customer/purchases/:reference`

**Auth**: `customer_session` cookie.

**Success (200)**: the same shape as one entry of the list above.

**Errors**: `NOT_FOUND` (404) - returned identically whether the
reference doesn't exist at all or belongs to a different customer
(never a distinct "forbidden" signal - see
`purchaseHistoryService.ts`'s own header comment); `NOT_AUTHENTICATED`
(401).

### `GET /api/customer/receipts`

**Auth**: `customer_session` cookie.

**Success (200)**:
```json
{
  "receipts": [
    {
      "receiptNumber": "RWL-RCT-2026-000001",
      "purchaseReference": "RWL-2026-600001",
      "productTitle": "Starting to Invest with GH₵100",
      "issuedAt": "2026-07-20T10:05:00Z",
      "totalDisplay": "GH₵39.00"
    }
  ]
}
```

**Errors**: `NOT_AUTHENTICATED` (401).

### `GET /api/customer/receipts/:receiptNumber/download`

**Auth**: `customer_session` cookie.

**Success (200)**: streams the PDF directly - `Content-Type:
application/pdf`, `Content-Disposition: attachment;
filename="{receiptNumber}.pdf"`. Self-healing: if the PDF was never
generated (or generation previously failed), it is generated on demand
via `getOrCreateReceiptPdf()` before streaming.

**Errors**:
- `RECEIPT_NOT_FOUND` (404) - the receipt number doesn't exist, or
  belongs to a different customer (same non-distinguishing discipline as
  the purchase-by-reference endpoint above).
- `ASSET_UNAVAILABLE` (503) - the receipt is owned by this customer but
  PDF generation/retrieval genuinely failed at request time (transient
  R2/pdf-lib failure) - safe to retry.
- `NOT_AUTHENTICATED` (401).

### `GET /api/customer/licenses`

**Auth**: `customer_session` cookie.

**Success (200)**:
```json
{
  "licenses": [
    {
      "licenseKey": "a1b2c3...",
      "productTitle": "Starting to Invest with GH₵100",
      "licenseType": "personal",
      "issuedAt": "2026-07-20T10:05:00Z",
      "status": "active"
    }
  ]
}
```
`status` is `active` | `revoked`, derived from `licenses.revoked_at`
being null or set - never a separately-stored value.

**Errors**: `NOT_AUTHENTICATED` (401).

## New: Guest reference-scoped receipt download

Preserves ADR-003's "no account ever required" guarantee for a
purchase's receipt, not just its asset download - mirrors the existing
`POST /api/purchases/:reference/downloads` → `GET
/api/download/:token` mint/redeem pair exactly, applied to receipts.

### `POST /api/purchases/:reference/receipt-download`

**Auth**: none (reference-scoped, matching the existing download-mint
endpoint).

**Rate limit**: 20/min/IP.

**Success (200)**: `{ downloadUrl: "/api/download-receipt/{token}",
expiresAt: "2026-07-20T10:20:00Z" }`.

**Errors**:
- `PURCHASE_NOT_FOUND` (404) - the reference is malformed or unknown.
- `RECEIPT_NOT_FOUND` (404) - the purchase exists but no receipt has
  been issued for it yet.
- `RATE_LIMITED` (429).

### `GET /api/download-receipt/:token`

**Auth**: none - the single-use token itself is the credential.

**Rate limit**: applies per the existing download-redeem calibration.

**Success (200)**: streams the PDF, `Content-Type: application/pdf`.
The token is marked used atomically on redemption.

**Errors**: `RECEIPT_NOT_FOUND` (404) - token missing, unknown,
expired, or already used (deliberately generic, matching the existing
asset-download-token redeem endpoint's anti-enumeration posture);
`ASSET_UNAVAILABLE` (503) - transient generation/storage failure.

## New: Admin refund action

### `POST /api/admin/orders/:reference/refund`

Internal, admin-triggered revocation (ADR-003). Added to the existing
`routes/admin/orders.ts` module alongside the pre-existing
resend-receipt/resend-download actions, not a new module.

**Auth**: admin session cookie, `EDITOR_ROLES` (`super_admin` \|
`editor`) - a `support`-role admin is rejected. **CSRF**: required
(`X-CSRF-Token` header matching the session's CSRF secret).

**Success (200)**: `{ refunded: true }`. Effects, all in one atomic D1
batch via `revokePurchase()`: `licenses.revoked_at` set for every
license on the order; `deliveries.status` set to `'revoked'`;
`purchase_sessions.status` set to `'refunded'`; an `audit_logs` row
written with action `order.refunded`, actor = the calling admin, and the
affected license/delivery ids in its metadata.

**Errors**:
- `NOT_FOUND` (404) - the reference is malformed or unknown.
- `VALIDATION_ERROR` (400) - the order has already been refunded
  (idempotent rejection, not a 500), or the order is not in a
  refundable (`verified`) state. **Note (added at M2D closeout):**
  both rejection reasons share this one HTTP code - they are
  distinguished only by the response's `message` text
  ("This order has already been refunded." vs. "Only a verified order
  can be refunded."), never by a separate error code. This also covers
  the case where two refund requests for the same order arrive
  genuinely simultaneously: exactly one succeeds, and the other
  receives this same already-refunded response, not a 500 - see
  `v3.0.2-m2-closeout-report.md` for the concurrency fix this
  guarantee depends on.
- `FORBIDDEN` (403) - authenticated but wrong role, or missing/invalid
  CSRF token.
- `NOT_AUTHENTICATED` (401) - no valid admin session.
- `RATE_LIMITED` (429) - shares the module's existing write-action rate
  limit.

**Verified end-to-end**: a download-permission request against a
revoked entitlement (`POST /api/purchases/:reference/downloads`) is
denied with `DOWNLOAD_NOT_AVAILABLE` immediately after a successful
refund - exercised by a real integration test, not just at the
database-write level.

## Extended: `GET /api/purchases/:reference`

Existing, unauthenticated, reference-scoped confirmation-page endpoint
(ADR-013 tier 1). Additive, non-breaking: the response now also
includes `receiptNumber: string | null` alongside the existing
`purchaseReference`, `productTitle`, `amountDisplay`, and `assets`
fields - `null` until the order-artifacts pass has completed (or if it
failed and hasn't yet self-healed on retry). `assets` continues to be
populated only when `status === 'ready'`, and is deliberately still
empty for `status === 'refunded'` even though `receiptNumber` may be
present - a refunded order keeps its historical receipt visible, but
never regains a download entitlement.

## New error code

`RECEIPT_NOT_FOUND` (404) - added to `types/api-contracts.ts`'s
`ApiErrorCode` union and `utils/responses.ts`'s `ERROR_STATUS` map.
Used wherever a receipt-scoped lookup (by receipt number, by ownership,
or by download token) fails, distinct from the pre-existing
`PURCHASE_NOT_FOUND`/`NOT_FOUND` codes used for purchase-scoped lookups.

## Order-artifact creation flow (informational, not a new endpoint)

For completeness - what happens automatically inside the existing `POST
/api/webhooks/paystack` handler once M2's code is wired in, none of
which is directly callable by a client:

1. Paystack's `charge.success` webhook verifies as it already did in
   M1 (signature check, then a server-side re-verify against Paystack's
   `/transaction/verify/{reference}`).
2. `findOrCreateCustomer()` runs (unchanged from M1).
3. **New in M2**: `createOrderArtifacts()` runs - creates one
   `order_items` row, `quantity` independent `licenses` rows (ADR-009),
   and one `receipts` row (with `receipt_number` set via the
   nullable-then-UPDATE pattern), then attempts PDF generation and R2
   storage. Never throws back to the caller - a failure here is logged
   and self-heals on the next receipt-download request, exactly the way
   M1's own webhook handler already never lets a non-critical side
   effect block the payment-success response.
4. `fulfilPurchase()` runs (unchanged from M1) - creates the download
   `deliveries` entitlement.
5. If the customer was newly created, the welcome email sends
   (unchanged from M1).
