# Version 3.1 - Milestone M3 Implementation Report

**Milestone:** M3 - Checkout Auto-Provisioning & Dashboard MVP
**Sprint:** M3B (Implementation)
**Status:** Complete (code); not yet deployed to production, not yet accepted.
**Scope discipline:** Implemented exactly the scope approved during M3A's architecture review. No VAT logic, coupons, promotions, marketplace, multi-vendor support, wishlist, notifications, analytics, affiliate features, admin redesign, new payment providers, or framework migration was introduced.

---

## Executive Summary

M3 closes the gap M2's own Known Limitations explicitly named: "No customer dashboard pages... the APIs exist and are tested, ready for M3 to consume." M3B builds that dashboard - five pages (My Library, Purchase History, Receipts, Licenses, Account Security) plus the small set of additive backend endpoints M3A's API Gap Analysis identified as missing (session list/revoke, change-password) and one non-breaking data extension (per-purchase asset/delivery info on the existing purchase-history service).

Every new page follows the same shell pattern already proven by `admin/`: a pure auth/CSRF library (`dashboard-auth.js`, mirroring `admin-auth.js`) plus a separate shell script that wires up the UI (`dashboard-shell.js`, mirroring `admin-shell.js`) - not a new pattern invented for this milestone. Every new backend function reuses an existing service module rather than introducing a parallel one; the two genuinely new authorization shapes M3 introduces (revoking a specific session by id, changing a password) were each checked against the closest existing precedent (`services/admin/sessionService.ts`) before being implemented, and in both cases the existing precedent's simpler design was chosen over this project's own earlier M3A planning-doc language where the two disagreed. Both deviations are called out in the code comments and in this report's "Deviations from M3A" section below.

Deliverables: 0 migrations (no schema change), 3 backend services extended, 1 new backend route module, 3 new API endpoints (plus 1 new error code, `CANNOT_REVOKE_CURRENT_SESSION`, added at M3C), 1 additive field on an existing service, 5 new frontend pages, 7 new frontend components/scripts, 1 extended CSS file (additive-only, one dark-mode token bug introduced and fixed during this sprint's own verification pass - see below), 2 small existing-file updates. Testing (final, as of M3D closeout): 135/135 passing (106 carried unchanged from M1/M2, 22 new at M3B, 3 added at M3C, 4 added at M3D). `npx tsc --noEmit` clean.

## Features Implemented

### Checkout Completion Experience
- `checkout/callback/index.html` - one sentence added to the existing post-purchase password-note paragraph, pointing a returning customer who already set a password to `/checkout/sign-in/`. No other change: the success/pending/failed/error states, loading state, and redirect behaviour on this page were all already M1/M2 scope and are unchanged.

### Automatic Customer Provisioning
- Unchanged from M1: welcome email, password-setup link, first-login, session creation are all M1's existing `authService.ts`/webhook-integration code, reused as-is per the "no duplicated auth code" instruction. M3B's contribution here is purely the destination: a real dashboard now exists at `/dashboard/` for `js/components/sign-in-form.js` to redirect a signed-in customer to (previously `/?signed-in=1`, a bare homepage query flag with nowhere real to land).
- **Open-redirect fix applied proactively**: `sign-in-form.js` now accepts an optional `?redirect=` param (set by `dashboard-auth.js` when it bounces an unauthenticated visitor off a specific `/dashboard/*` page) and validates it with `sanitizeRedirectPath()` - only a literal `/dashboard/`-prefixed path is ever used, never a scheme or `//`. This mirrors `admin-auth.js`'s own `sanitizeNextPath()`, built the same way from the start rather than introducing the same class of bug (CWE-601) fresh.

### Dashboard MVP
- `partials/dashboard-nav.html` + `js/components/dashboard-auth.js` + `js/components/dashboard-shell.js` - the shared shell every dashboard page includes. `dashboard-auth.js` is a pure library (`customerFetch`, `requireSession`, `logout`, `getCsrfToken`); `dashboard-shell.js` does the actual DOM wiring (email display, active-nav-link marking, logout binding) on `partials:loaded`, then dispatches a `dashboard:ready` custom event each page's own script listens for.
- Welcome/account display, logout: in the nav partial, present on every dashboard page.

### Customer Library UI
- `dashboard/index.html` + `js/components/library-list.js` - cards (`.library-row`) with title, status badge (`ready`/`processing`/`refunded`/`unavailable`, each mapped to an existing badge variant), download button (mint-then-redirect against the existing M1/M2 download-token flow), receipt link, purchase date. Empty, loading, and error states all present.

### Purchase History
- `dashboard/purchases/index.html` + `js/components/purchase-history-list.js` - same underlying data as My Library, presented as a transaction list (date, monospace purchase reference, amount, status badge). No search was added: M3A's roadmap listed search as conditional on approval, and no such approval is on record, so it was left out rather than assumed.

### Receipt Management
- `dashboard/receipts/index.html` + `js/components/receipts-list.js` - lists every receipt via the existing `GET /api/customer/receipts`, with a direct download link to the existing (M2) `GET /api/customer/receipts/:receiptNumber/download` endpoint. No new receipt-generation or storage code was written; this page is a UI in front of M2's existing, tested PDF pipeline.

### Account Settings
- `dashboard/security/index.html` + `js/components/account-security.js` - read-only profile (email), change-password form, and an active-sessions list with per-session "Sign out" (revoke) actions. Structural mirror of `admin-account.js`, including its `formatDate()` mixed-timestamp-format fix (see "Notable Fixes Reused Proactively" below). One deliberate difference from the admin equivalent: revoking a session here requires an explicit `window.confirm()` step first, per AR-009 (ratified in `v3.1-m3-ux-strategy.md` Section 7) - the admin page predates that ratification and was not retrofitted, since this milestone's scope is the customer dashboard only.

### API Enhancements
Three new endpoints, all additive, all under the existing `requireCustomerAuth` + `requireCustomerCsrf` middleware chain:
- `GET /api/customer/sessions` - list the caller's own active sessions.
- `POST /api/customer/sessions/:sessionId/revoke` - revoke a specific session by id.
- `POST /api/customer/auth/change-password` - change password; revokes every *other* active session as a side effect.

Plus one non-breaking data extension: `resolveAssetsWithDeliveryInfo()` (new, in `fulfilmentService.ts`) is consumed by `purchaseHistoryService.ts` to add an `assets` array to `listCustomerPurchases()`/`getCustomerPurchase()`'s existing response shape. The pre-existing, guest-facing `getFulfilmentStatus()` and its own narrower `assets` field are untouched - this was a deliberate choice to avoid coupling two different consumers (guest fulfilment page vs. customer dashboard) to one shared contract that would need to serve both audiences' different needs.

See [`v3.1-m3-api-reference.md`](v3.1-m3-api-reference.md) for full request/response detail.

## Database Changes

**None.** No migration was needed - every M3 feature is served by data that already existed (`customer_sessions`, `deliveries`, `product_files`/`media_assets`) via new query logic, not new storage. This matches M3A's own Database Impact Assessment's conclusion.

## Security Measures

- **CSRF**: every new mutating endpoint (`sessions/:id/revoke`, `change-password`) is behind the existing `requireCustomerCsrf` double-submit-cookie check, unchanged from M1.
- **Session-ownership / IDOR**: `revokeSessionById(env, customerId, sessionId)` filters by both `customerId` and `sessionId` - the one new authorization shape M3 introduces, since every other M1/M2 customer endpoint filters by `customerId` alone. Verified by a dedicated test asserting a customer cannot revoke another customer's session (returns the same not-found-shaped result either way, not a distinct "forbidden" signal, matching this project's existing `NOT_FOUND` convention for cross-customer access attempts).
- **Session self-revocation guard (added at M3C, the Acceptance Review)**: the original M3B implementation relied only on the dashboard UI never rendering a revoke control for the session flagged `isCurrent`, with no server-side guard - a live API call during the M3C review confirmed a customer could revoke their own current session directly, immediately invalidating the cookie making the request, violating the M3A Security Review's explicit "must never allow" requirement. Fixed in `routes/customer/sessions.ts`: the route now rejects the attempt with `CANNOT_REVOKE_CURRENT_SESSION` (400) before calling the service layer. See `v3.1-m3-api-reference.md` for the error code and `dashboardM3.test.ts` for the regression test.
- **Rate limiting**: `change-password` at 10/15min; sessions list/revoke inherit the existing customer-endpoint rate-limit conventions.
- **Timing-safe password verification**: `changePassword()` reuses the existing `DUMMY_PASSWORD_HASH` constant-time-comparison pattern already established in `authService.ts`'s login path - no new verification logic was written.
- **Open-redirect (CWE-601)**: `sign-in-form.js`'s new `?redirect=` handling only ever accepts a literal `/dashboard/`-prefixed path (see above).
- **Destructive-action confirmation (AR-009)**: session revoke requires `window.confirm()`; verified functionally, not just as present markup - both the cancel path (zero network calls, list unchanged) and the confirm path (real API call, list refreshes) were exercised in browser verification.
- **Download authorization**: unchanged - My Library's download button reuses the existing M1/M2 mint-then-redirect single-use token flow verbatim; no new download code path was introduced.

**One real defect was found and fixed during browser verification, not merely a passive check**: the dashboard nav's active-page indicator (`.dashboard-nav__links a[aria-current="page"]`) was styled with `var(--color-growth-green)` directly. That token is not dark-mode-aware - `tokens.css`'s own `[data-theme="dark"]` block documents exactly this failure mode for text usage of this color (2.9:1 measured contrast, under the 4.5:1 AA minimum) and defines `--color-accent` as the dark-mode-safe alternative (8.4:1). The fix (`css/components.css`) swaps to `var(--color-accent)`, the same token every other accent-colored interactive text on this site already uses. Confirmed via computed style after the fix: `rgb(83, 198, 121)` (`#53C679`, the documented dark-mode value) rendering correctly under `[data-theme="dark"]`.

## Known Limitations

- **No purchase search on the dashboard.** M3A's roadmap listed this as conditional on approval; no such approval exists, so it was left out rather than assumed. Purchase History and My Library both work correctly for the realistic near-term purchase-count range without it.
- **Session device summarization is coarse** (browser + OS only, via user-agent string matching) - a direct mirror of `admin-account.js`'s own existing approach, not a new limitation introduced by this milestone. No fingerprinting library was added, consistent with this project's stated privacy posture.
- **The one dark-mode CSS defect described above was caught and fixed within this same sprint** via browser verification before documentation was written - included here for completeness, not because it remains open.
- **`resolveAssetsWithDeliveryInfo()` is customer-dashboard-only.** It was deliberately not merged into the pre-existing guest-facing `getFulfilmentStatus()`/its `assets` field, to avoid coupling two different consumers to one shared contract. If a future milestone needs the same delivery-status detail on the guest fulfilment page, that is a small, additive follow-up, not a redesign.
- **No customer-facing UI change was made to the checkout page's password-setup flow itself** beyond the one added sentence - the actual welcome email and password-setup token flow are M1's, unchanged, per the "reuse existing backend logic" instruction.
