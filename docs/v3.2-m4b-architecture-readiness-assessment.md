# Version 3.2 - Sprint M4B - Architecture Readiness Assessment

Independently determines whether M4 (Reviews + Coupons) can be implemented using the current architecture, and whether it remains genuinely additive. This is the document where this Board's independent code inspection produced its most significant, concrete finding - reported here in full, with evidence.

---

## Product Reviews - Confirmed Additive, No Architectural Change Required

**Required API additions:** `POST /api/customer/reviews` (submit, purchase-gated), `GET /api/products/:slug/reviews` (public display), `GET /api/admin/reviews` + `PATCH /api/admin/reviews/:id` (moderation) - all following the existing route-file-per-concern pattern verified present in `backend/routes/`.

**Required database changes:** one new table, `product_reviews`. Verified against the actual `consultation_requests` schema (`backend/database/schema.sql:238-257`): structurally similar (id, status enum, timestamps, an assignee/moderator FK) but not identical - `product_reviews` additionally needs `customer_id`, `product_id`, and `purchase_session_id` foreign keys (all three tables already exist and are stable), plus a `rating` integer column. No dependency on any table that doesn't exist today.

**Required frontend changes:** one new component (review display + submission form), following the exact pattern `js/components/dashboard/*.js` already established across three milestones. Confirmed no framework or build-step change needed.

**Security implications:** purchase-gating (a review submission must reference a `purchase_session_id` owned by the submitting customer) mirrors the exact ownership-check pattern already proven in `services/customer/purchaseHistoryService.ts`. No new security primitive needed.

**Confirmed: remains fully additive.** This Board found no issue with M4A's characterization of Reviews.

## Coupon Engine - Additive in Principle, But M4A's Cited Design Cannot Be Implemented As-Is

This is the Board's central finding for this review.

**M4A's claim** (`v3.2-m4-scope-recommendation.md`, `v3.2-m4-feature-prioritization-matrix.md`): the coupon schema is "already fully designed... ready to implement as-is, no new design work needed," citing `docs/v3-database-design.md`.

**Independent verification performed:**

```
$ grep -n "platform_users" backend/database/schema.sql
```
Returns zero `CREATE TABLE platform_users` matches - every result is a comment referencing the *future*, unbuilt rename. The live schema's admin/creator identity table is, and remains, `admin_users`.

```sql
-- docs/v3-database-design.md, the schema M4A cites as ready-to-implement:
CREATE TABLE coupons (
  ...
  creator_id  INTEGER REFERENCES platform_users(id), -- NULL when scope = 'platform'
  ...
  scope       TEXT NOT NULL CHECK (scope IN ('platform', 'creator')),
  ...
  created_by  INTEGER NOT NULL REFERENCES platform_users(id),
  ...
  CHECK (scope = 'platform' OR creator_id IS NOT NULL)
);
```

This table cannot be created against the current schema - `platform_users` does not exist, and per ADR-011 (independently re-confirmed via `v3.0.2-architecture-decision-register.md`: "the platform_users rename requires an explicit, reviewed migration plan as a Milestone M7 entry condition... Status: Accepted... one ADR marked 'Requires Replanning'"), no timeline exists for when it will. Beyond the missing FK target, the schema's entire shape (`scope`, `creator_id`, the CHECK constraint requiring a creator for non-platform coupons) was designed for the V3.1/V3.2 multi-creator marketplace this platform does not yet have (confirmed via `v3-roadmap.md`'s own version-gating: creator-scoped features are gated to "V3.1 (10 creators)" and later).

**What this means:** M4's coupon feature needs a **new, deliberately simplified schema** - a platform-wide-only `coupons` table (drop `scope`, drop `creator_id`, `created_by` referencing the current `admin_users`) that can be extended later (adding `creator_id` back, this time against a real `platform_users` table) if and when M7's marketplace work actually lands. This is consistent with, not a departure from, this project's own established practice of building the minimum needed now and extending later (the exact discipline that produced `products.creator_id` as a lone scaffolding column in migration `0017`, rather than the full marketplace schema, back at V3.0).

**Required API additions (corrected):** checkout must accept an optional `couponCode` field (a new client input - the existing `checkout.ts` route explicitly documents that it "never accepts price, currency, or title from the client," which remains true; a coupon *code* is not a price, and the discount amount is still computed server-side, consistent with that discipline). `commerceService.ts`'s `createCheckoutSession()` must validate the code, compute the discount, and lock the *discounted* amount into `purchase_sessions.amount_pesewas` - the same field the webhook's high-severity mismatch check already guards. `POST /api/admin/coupons` CRUD, following the existing admin route pattern.

**Required database changes (corrected):** a new, simplified `coupons` table (platform-scope only) and `coupon_redemptions` (structurally as designed in `v3-database-design.md`, minus the creator-scope fields), plus `purchase_sessions.coupon_id`/`discount_pesewas` columns (these two specifically are fine to take from the existing design unchanged - they don't reference `platform_users`).

**Required frontend changes:** a coupon-code input at checkout, an admin coupon-management page - both follow existing, proven patterns.

**Security implications - the one genuinely elevated-attention item:** any change to `commerceService.ts`'s amount-computation logic touches the code this project's own prior security reviews have consistently called "the single most safety-critical boundary in the system." This Board does **not** consider this disqualifying - the existing webhook verification pattern (locked expected amount, strict equality check, high-severity logging on mismatch) is exactly the right mechanism to extend, not replace. But M4C's own Security Review must explicitly walk through: (a) the discount is computed and locked at checkout-creation time, never recomputed later; (b) the webhook verifies against the discounted, locked amount; (c) a coupon cannot be applied, changed, or removed after checkout-session creation without invalidating the session. This is a normal, expected depth of security review for a change to this specific code path - not evidence the feature shouldn't proceed.

**Confirmed: remains additive at the database/API/frontend level once a corrected schema is used.** M4A's specific "no new design work needed" claim is not confirmed - real, if small, design work remains.

---

## Overall Architecture Verdict

**M4 can be implemented using the current architecture, with one correction to how it gets there.** No framework change, no redesign, no new infrastructure category is needed for either feature - this Board's independent review confirms M4A's top-level Architecture Review conclusion. The correction is narrower and more specific than "the architecture doesn't support this": it is that one specific artifact M4A pointed to as ready-made (the coupon schema) is not actually usable in its cited form, and a corrected version must be produced before implementation begins - normal, expected planning work, not a reason to reconsider M4's scope.
