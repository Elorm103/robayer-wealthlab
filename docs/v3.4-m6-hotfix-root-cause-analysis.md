# Version 3.4 Milestone M6 Acceptance Failure: Root Cause Analysis Report

## Summary

The overlap shown in both attached screenshots (light mode and dark mode) has one single, deterministic root cause: a missing CSS override for the `hidden` attribute on `.book-card__cover-placeholder-text`. It is not a caching issue, not a first-paint timing issue, not duplicate DOM, not a Safari-specific rendering quirk, and not a separate dark-mode color defect. It is a plain CSS specificity bug that reproduces on every load, in every browser, whenever the featured product has an uploaded cover image, which production currently does.

## The mechanism, precisely

1. `js/components/product-loader.js`'s `initFeatureBanners()` correctly detects that the featured product has a real uploaded cover image and runs `placeholderEl.hidden = true`, which sets the HTML `hidden` attribute on `.book-card__cover-placeholder-text`.
2. The browser's own default stylesheet contains `[hidden] { display: none }`. This is normally what makes the `hidden` attribute work.
3. `css/components.css` sets `.book-card__cover-placeholder-text { display: flex; ... }` directly, in the site's own author stylesheet. Per the CSS cascade, an author stylesheet rule always wins over the user-agent default stylesheet, regardless of selector specificity. Setting `display` on an element via any class selector silently defeats the native `hidden` attribute, unless the stylesheet also explicitly re-declares `display: none` for the `[hidden]` state.
4. The result: `placeholder.hidden` reads `true` (the JavaScript did exactly what it was supposed to), but `getComputedStyle(placeholder).display` still reads `flex`. The element renders anyway.
5. Because it is not removed from layout, `.book-card__cover-placeholder-text` (a `height: 100%` flex column containing the eyebrow, title, and subtitle placeholder spans) occupies its own block of normal document flow directly after the real cover image, rather than being hidden. This pushes it into the same vertical space the hero's own eyebrow/title/subtitle block occupies immediately after it in the DOM.

## This exact bug pattern already exists, and was already fixed, three other places in the same file

`css/components.css` contains three prior instances of this identical problem, each with its own code comment documenting it:

- `.btn[hidden] { display: none; }` (line 65), commented: "The `[hidden]` attribute alone loses to the `display:inline-flex` rule above (author stylesheet always beats the UA stylesheet, regardless of specificity)."
- `.field__error[hidden] { display: none; }` (line 569)
- `.alert[hidden] { display: none; }` (line 609)

`.book-card__cover-placeholder-text` is the one place this already-established, already-documented fix pattern was not applied. This was not a new defect introduced by any recent change; it has existed since the typographic placeholder was added (see the rule's own comment referencing `docs/flagship-cover-design-brief.md`), and was never caught because no prior audit (including this milestone's own Responsive Design Audit, before this acceptance review) checked the actual rendered `display` value of an element toggled via the `hidden` property; every prior check read the CSS selector names and assumed the intended behavior held, rather than measuring it.

## Proof, not speculation

Measured directly against the live production DOM (`https://robayerwealthlab.com`, not localhost) via `getBoundingClientRect()` on the actual rendered elements, before any fix:

| Element | Top | Bottom |
|---|---|---|
| `.book-card__cover--hero` (the real cover image box) | 169 | 436 |
| `.book-card__cover-placeholder-text` (should have been hidden) | 436 | 702 |
| `.book-card__cover-placeholder-title` ("Small Cedis, Big Wealth") | 505 | 560 |
| `.book-card__cover-placeholder-subtitle` ("How Ordinary Ghanaians...") | 568 | 660 |
| `.hero__eyebrow` ("FINANCIAL EDUCATION FOR GHANA") | 553 | 574 |
| `.hero__title` ("Financial education built for everyday Ghanaians.") | 590 | 705 |

The placeholder subtitle (568 to 660) overlaps the hero title (590 to 705) by 70 pixels. This is exactly what both screenshots show: the placeholder's subtitle text running directly through the hero's large headline.

Confirmed live, on the production page, that `placeholder.hidden` was `true` while `getComputedStyle(placeholder).display` was `flex`, directly proving the mechanism above rather than inferring it from reading CSS alone.

## Confirmed as a permanent, steady-state defect, not a first-paint artifact

The measurement above was taken well after page load, with no scroll, no interaction, no re-check needed for settling: `hidden="true"` and `display: flex` do not change relative to each other over time, since nothing in the codebase re-evaluates or corrects this after the initial script run. There is no font-loading, JavaScript-timing, or duplicate-DOM explanation to rule out, because the two conflicting facts (the attribute is set; the CSS ignores it) are both static and permanent once `initFeatureBanners()` has run once.

## Why the dark mode screenshot looks different but has the identical cause

The placeholder's own text colors (`.book-card__cover-placeholder-eyebrow`/`-title`/`-subtitle`) are intentionally hardcoded dark navy, not theme tokens, because they are designed to sit on the fixed gold placeholder background (`--color-sika-gold`), which does not change between light and dark mode. That is correct when the placeholder is genuinely showing (no real cover uploaded). The dark mode screenshot's "poor contrast, mixed light and dark theme colors" is not a separate, independent dark-mode defect: it is this same wrongly-still-visible placeholder text, in its fixed dark-navy color, now sitting on top of the page's dark navy background instead of the gold placeholder box, which is why it reads as low-contrast and "mixed." Confirmed directly: with the fix applied, in dark mode, the placeholder correctly computes to `display: none`, and the hero's own title/subtitle colors resolve to `rgb(255,255,255)` and `rgb(168,172,179)` respectively (both proper theme tokens, both legible against the `rgb(16,22,31)` dark background), which is the complete, correct dark-mode rendering.

## Why WebKit-specific testing was not performed, and why it does not change the conclusion

No Playwright or standalone WebKit browser is available as a tool in this environment; only a Chromium-based Browser pane and the user's own Chrome are available. This is disclosed rather than worked around with a claim that cannot be substantiated. It does not weaken the root cause finding: the mechanism identified is a plain CSS cascade rule (author stylesheet beats user-agent stylesheet for equal-or-lower-specificity declarations), which is standard behavior defined by the CSS specification itself, not an engine-specific quirk. There is no plausible reason WebKit would apply the `[hidden]` attribute differently than Blink here; both browsers implement the same cascade rules for this exact case, and the existing, already-shipped `.btn[hidden]`/`.field__error[hidden]`/`.alert[hidden]` fixes in this same codebase exist precisely because this is a universal, not browser-specific, behavior.

## Fix

Added, following the exact existing convention:

```css
.book-card__cover-placeholder-text[hidden] {
  display: none;
}
```

Verified directly against the live production DOM by injecting this exact rule (no `!important`, matching the existing `.btn[hidden]` pattern) via a temporary client-side `<style>` tag: `getComputedStyle(placeholder).display` changed from `flex` to `none` immediately, with no other layout change required, and the hero title/subtitle positions were confirmed unchanged (590 and 721 respectively, matching their pre-fix positions), since they were never themselves misplaced, only obscured by the placeholder rendering on top of them. This client-side injection was for verification only and was not left in place; it does not persist and made no permanent change to production.

Also verified the fix does not affect the case where the placeholder is genuinely meant to show (no real cover image assigned, the normal/default state, reproduced on the local dev environment): with no `hidden` attribute present, `display` still correctly resolves to `flex`, unchanged.
