## What M3 is, precisely

Per the ratified Blueprint's Deliverable 11: **"Checkout Auto-Provisioning + Dashboard MVP."** Two halves:

1. **Checkout auto-provisioning UI** - the customer-facing pieces of the guest-checkout-to-account flow that M1 built the backend for but did not fully surface: the confirmation page's optional password-set prompt (already partially live in `checkout/callback/index.html`, currently a static, unconditional note per its own header comment - "the copy is worded to stay true either way"), and the sign-in/forgot-password/set-password pages (already live, built in M1, currently redirecting to the homepage on success because "M1 ships no dashboard to land on yet" - `js/components/sign-in-form.js`'s own comment, now directly actionable by M3).
2. **Dashboard MVP** - the eight pages the ratified Blueprint's Deliverable 5 specifies: My Library, Purchase History, Receipts, Licenses, Downloads, Account Security, Support, Notifications, Profile. **Per the ratified roadmap's own sequencing, only the first six are M3 scope** - Support (M5), Notifications (M6), and full Profile editing beyond what's needed for Account Security are explicitly later milestones. This review scopes M3 to: My Library, Purchase History, Receipts, Licenses, Downloads, Account Security.

## ADR compliance map for M3

| ADR | Requirement | M3 classification |
|---|---|---|
| ADR-002 | Guest-first checkout, zero fields on Robayer's own checkout page | **Unaffected.** M3 adds no checkout-time field - it is entirely post-purchase UI. |
| ADR-003 | Email-link access preserved permanently; revocation synced | **Mandatory, inherited.** Every dashboard download action must use the same entitlement/revocation-aware endpoints M1/M2 already built (`POST /api/purchases/:reference/downloads`, gated on `deliveries.status != 'revoked'`) - M3 must not introduce a second, weaker download path. |
| ADR-006 | Purchase-triggered-only provisioning; no self-registration surface | **Mandatory, inherited.** The dashboard's sign-in page is exactly M1's existing, unchanged `checkout/sign-in/`. M3 adds no "Sign Up" affordance anywhere. |
| ADR-009 | `order_items.quantity = N` -> N independent licenses/deliveries | **Read-only consumer.** The Library/Downloads pages must render N distinct license/delivery rows correctly for a future multi-seat purchase, not assume `quantity = 1`. No real product exercises this today (per the M2 Acceptance Report), but the UI must not hard-code a single-seat assumption. |
| ADR-013 | Confirmation-page view-vs-action split (reference alone for viewing; session or single-use token for any action) | **Mandatory, inherited and extended.** The dashboard itself is entirely session-gated (every dashboard page requires `requireCustomerAuth`); every download/receipt action from within it mints a fresh, single-use token exactly as the existing guest paths already do - the dashboard is not a second, parallel access mechanism, it is the same mechanism with a session already established. |
| AR-009 (-> Blueprint Deliverable 5) | Ratified empty-state and destructive-action-confirmation specification | **Mandatory, core M3 deliverable.** See the M3 UX Strategy document for the full specification this review inherits unchanged from the ratified Blueprint. |

No ADR requires amendment. No new ADR is needed for M3.

## Frontend architecture already in place (verified by direct inspection, not assumed)

- **No JS framework.** Vanilla JS components, one file per concern (`js/components/*.js`), each self-initializing on `DOMContentLoaded` and a custom `partials:loaded` event (for content injected via `data-include`, see `js/includes.js`).
- **Progressive enhancement, state-driven via `data-*` hooks.** `checkout/callback/index.html` + `fulfilment-status.js` is the exact, proven precedent: static HTML ships an honest no-JS/loading fallback, JS then shows exactly one of several `[data-*]`-tagged sections at a time (`hidden` attribute toggling), never a client-side router or virtual DOM.
- **A real, mature, WCAG-verified design system.** `css/tokens.css` (264 lines) defines every color/type/spacing value as a token with documented contrast ratios; `css/base.css`/`layout.css`/`components.css`/`utilities.css` provide the component vocabulary (`.btn`, `.alert`, `.card`, `.grid`, `.stack`, etc.) every existing page already uses.
- **Same-origin API access, no CORS/credentials complexity.** Per `wrangler.jsonc`'s own routing comments (Version 2.0 Same-Origin Migration), `/api/*` is served from the same origin as the static site - every `fetch()` call in every existing component (`sign-in-form.js`, `fulfilment-status.js`) already omits any `credentials`/CORS handling entirely, because none is needed. M3's dashboard pages inherit this for free.
- **A single, proven mint-then-navigate download pattern.** `fulfilment-status.js`'s `requestDownload()` - POST to mint a fresh single-use token, then `window.location.href` to the redeem URL, never a fetch+blob - is the exact pattern every M3 download action (asset downloads, receipt downloads) must reuse unchanged.
- **A live, honest gap already flagged in the code itself.** `sign-in-form.js`'s own header comment states its post-login redirect target (`/?signed-in=1`) is a placeholder specifically because "M1 ships no dashboard to land on yet... that's Milestone M3." This is a small, real, already-identified frontend change M3 must make (Section "Immediate small changes" below), not a new discovery.

## Immediate small changes M3 must make to existing (not new) files

1. **`js/components/sign-in-form.js`** - redirect target after successful login should become the new dashboard's My Library page (e.g. `/dashboard/` or `/account/`, exact path per the Frontend Architecture Plan), replacing the current homepage redirect.
2. **`checkout/callback/index.html`'s password-set note** - once the dashboard exists, this static copy can be tightened to point at it directly ("come back and see this purchase anytime" can link to `/dashboard/sign-in/` or the dashboard itself once a session exists) - a copy change, not a structural one.
3. **No change needed** to `fulfilment-status.js`, `set-password-form.js`, or `forgot-password-form.js` - all three continue to serve their existing, still-valid purpose unchanged.
