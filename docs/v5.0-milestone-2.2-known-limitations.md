# Version 5.0 — Milestone 2.2 Known Limitations

Honest, in order of what matters most for anyone building on this next.

## 1. The Resources retrieval gap — RESOLVED

~~The "What resources are available?" query did not surface the platform's actual resource item.~~ **Fixed and verified with real production data.** Diagnosed in two stages: (1) widening Vectorize's oversampling (`topK` 20 → 80, covering 89% of the entire corpus) still didn't surface it — proof this was not a ranking-weight problem, since a reranker can only reorder candidates it receives, and the resource item never entered the candidate pool at all; (2) the actual fix — indexing the `/resources/` catalog page itself as a first-class `static_page` document (`documentSources.ts` previously excluded any `/resources/` URL on the incorrect assumption that individual resource items covered it) — was implemented, deployed, and confirmed via a real incremental reindex and a live re-query. The catalog page now returns as the top result at 0.722 (high confidence). See the Production Verification Report for the full before/after.

This entry is kept (rather than deleted) as a record of the diagnosis process — the general lesson (reranking cannot rescue a document Vectorize never returns; check candidate-pool membership before assuming a ranking-weight fix will help) remains valid for any future retrieval gap.

## 2. Two frontend fixes — RESOLVED (were blocked, now deployed and confirmed)

~~Search Diagnostics' widened candidate pool and the Search Analytics auto-refresh fix were merged but not deployed~~ due to an external GitHub Actions/Pages outage (see the Deployment Guide for the full, evidence-based diagnosis — this project's own workflow was never at fault). Once GitHub's status page showed full recovery, both fixes deployed successfully and were confirmed live by direct verification (not assumed from the Actions UI alone) and by real subsequent Search Diagnostics use — Total Searches and Most Retrieved Documents both updated live, in real time, across every query run afterward.

## 3. Confidence thresholds are a first pass, not a final calibration

`high ≥ 0.6` / `medium ≥ 0.45` are grounded in real evidence (35 scored results across 7 queries — see the Confidence Calibration Report) but remain a small sample. They correctly classified every named target in production re-verification, which is meaningful validation, not proof of permanence. Revisit once Search Analytics' low-confidence trend has accumulated a larger, more diverse real query history.

## 4. Reranking is lexical, not semantic

Title/keyword boosting matches literal (normalized) word overlap — it has no concept of synonyms, paraphrase, or intent beyond simple singular/plural normalization. A query that means the same thing as a document's content but shares no literal vocabulary gets no boost at all (this is part of why the Resources gap isn't fixable by boosting alone — the resource's actual title and description don't contain the word "resources"). This is the accepted trade-off for staying inside "no external rerank API, reuse the existing architecture."

## 5. No dead-letter queue in the traditional sense

Task 7 deliberately reuses the existing indexing queue (via each message's `attempts` field) rather than provisioning a second Cloudflare Queue with native DLQ support — see the Engineering Report §8 for why. The trade-off: Cloudflare's own DLQ mechanism (with its own retry/inspection tooling) is bypassed in favor of a custom D1 table and manual retry action. This is adequate at today's genuinely rare failure volume (document-level failures never reach this path at all) but would need reconsideration if infrastructure-level failures ever became common enough to need Cloudflare's own tooling.

## 6. Content-change re-index infrastructure is unused

`enqueueContentChangeReindex()` exists, is tested, and is ready — but no CMS save route (blog, resource, product, settings) calls it. Every reindex today is still admin-triggered (manual incremental or full rebuild). This is exactly as scoped ("prepared but not exposed"), not an oversight, but it means content edits do not automatically become searchable until someone runs a reindex.

## 7. Embedding version tracking has zero historical data

Every one of the 38 currently-indexed documents shows "Not yet embedded" for the new tracking fields, since they were all indexed before this milestone's migration existed. The feature is real and correctly wired for the future, but provides no value until documents actually go through it — which happens on their next reindex, whenever that occurs.

## 8. Search Analytics is explicitly not a full analytics suite

No custom date-range filtering, no export, no per-admin breakdown, no correlation with actual customer outcomes (since Customer AI doesn't exist yet — every logged search today is admin/diagnostic traffic, not real user traffic). It answers "what has search behavior looked like so far," not "how well is search actually serving users," which is a materially different — and more important — question Customer AI's eventual usage will need its own answer to.

## 9. Corpus-specific score calibration does not generalize automatically

The 0.6/0.45 thresholds and the boost weights were tuned against *this specific* 38-document, single-site corpus. If the Knowledge Base's content mix changes substantially (many more documents, a different content style, a different embedding model), these numbers should be re-derived from fresh evidence rather than assumed to still hold — exactly the same caveat Milestone 2's own original 0.75/0.5 thresholds needed and didn't get until this milestone.
