# Version 3.4 Milestone M6 Acceptance Failure: Dark Mode Audit Report

## Finding

The dark mode defect shown in the attached screenshot is not a separate, independent dark-mode bug. It is the identical root cause documented in the Root Cause Analysis Report (the `.book-card__cover-placeholder-text[hidden]` CSS specificity bug), observed under `<html data-theme="dark">` instead of light mode. No second, unrelated dark-mode issue was found in the hero once this one is accounted for.

## Why it looks like a dark mode color problem

`.book-card__cover-placeholder-eyebrow`, `-title`, and `-subtitle` use intentionally hardcoded dark navy colors (`rgba(22, 35, 61, 0.65)`, `var(--color-navy, #16233d)`, `rgba(22, 35, 61, 0.75)`), not theme tokens. This is correct by design when the placeholder is genuinely showing: it sits on top of the fixed gold placeholder background (`--color-sika-gold`), which does not change between light and dark mode, so text on it should not change either. When the same wrongly-still-visible placeholder renders instead on top of the page's dark navy body background (because it was never actually hidden, per the Root Cause Analysis Report), dark navy text on a dark navy background is exactly what produces "poor contrast, low readability, mixed light and dark theme colors": it is light-mode-appropriate text landing on a dark-mode background it was never meant to sit on, not a hardcoded-color defect in the hero's own dark mode support.

## Verified directly: the hero's own dark mode support has no hardcoded-color defect

Checked `css/components.css`'s actual rules for `.hero__title`, `.hero__eyebrow`, and `.hero__subtitle`: neither `.hero__title` nor `.hero__eyebrow` sets its own color at all (both inherit from shared heading/eyebrow rules that already use theme tokens), and `.hero__subtitle` explicitly uses `color: var(--color-text-secondary)`, a proper theme token. Measured live on production with `data-theme="dark"` set and the placeholder-hiding fix applied: `.hero__title` computes to `rgb(255, 255, 255)`, `.hero__subtitle` computes to `rgb(168, 172, 179)`, both against a `rgb(16, 22, 31)` body background. Both are light text on a dark background with a large, clearly sufficient visual contrast margin. No hardcoded color was found in the hero's own text rules; every color involved in the hero itself resolves through the theme token system.

## Scope of what was and was not audited here

This report addresses the specific dark mode defect shown in the attached screenshot, which is fully explained above. It is not a full repeat of a site-wide color audit across cards, buttons, links, navigation, footer, forms, inputs, tables, dialogs, dropdowns, admin, customer pages, checkout, or emails, since the evidence in front of this review (the screenshots) does not show a defect in any of those areas, and fabricating an audit of areas with no reported symptom would not be honest work. If a broader, standing dark mode token audit across those areas is wanted independent of this specific defect, that is a separate, reasonable follow-up request, not something this acceptance review's evidence calls for on its own.
