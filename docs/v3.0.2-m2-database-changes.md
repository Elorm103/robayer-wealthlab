# Version 3.0.2 - Milestone M2 Database Changes

Orders, Receipts & Customer Library. One migration, additive only: no
existing column, table, row, or index is altered or dropped.

This document reflects what was actually implemented, confirming
`docs/v3.0.2-m2-database-planning-report.md`'s plan was followed, and
recording the one deviation from that plan (the `receipts.receipt_number`
nullability fix) discovered during implementation.

## Migration

`backend/database/migrations/0019_ownership_layer.sql`. Applied to the
local D1 instance (`wrangler d1 execute robayer-wealthlab-db --local
--file=./database/migrations/0019_ownership_layer.sql`) and verified
there throughout development and testing. **Not yet applied to
production D1** - this is a code-complete, not yet deployed, milestone.

## New tables

### `order_items`

Line items per purchase - enables bundles and multi-seat orders
(ADR-009), even though every product in this catalog is single-item
today. `product_title`/`unit_price_pesewas` are snapshotted at creation
time, the same discipline `purchase_sessions.product_title`/
`amount_pesewas` already established from M1 - a later product-content
edit never rewrites purchase history.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `purchase_session_id` | INTEGER NOT NULL REFERENCES `purchase_sessions(id)` | |
| `product_id` | TEXT NOT NULL | matches `purchase_sessions.product_id`'s own convention |
| `product_title` | TEXT NOT NULL | snapshotted at creation |
| `unit_price_pesewas` | INTEGER NOT NULL CHECK `>= 0` | |
| `quantity` | INTEGER NOT NULL DEFAULT 1 CHECK `>= 1` | ADR-009: N seats generates N independent `licenses` rows |
| `asset_id` | TEXT | nullable, matches `deliveries.asset_id`'s convention |

Indexes: `idx_order_items_session`, `idx_order_items_product`.

### `licenses`

Customer-facing, printable proof of ownership - deliberately separate
from `deliveries` (access control). The license key is never a bearer
credential for access (ADR-003); access stays gated by
`deliveries`/download tokens, unchanged from M1.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `purchase_session_id` | INTEGER NOT NULL REFERENCES `purchase_sessions(id)` | |
| `product_id` | TEXT NOT NULL | |
| `customer_id` | INTEGER REFERENCES `customers(id)` | nullable - mirrors `purchase_sessions.customer_id`'s own nullability reasoning (the rare no-confirmed-email path) |
| `license_key` | TEXT NOT NULL UNIQUE | 256-bit, `crypto.getRandomValues`-based hex |
| `license_type` | TEXT NOT NULL DEFAULT `'personal'` | CHECK `IN ('personal')` - deliberately narrow; commercial/educational types are an explicit M2A scope exclusion, to be widened in a later migration when they actually ship |
| `terms_version` | TEXT | copied from `purchase_sessions.license_version` at issuance - no new consent capture |
| `issued_at` | TEXT NOT NULL DEFAULT `datetime('now')` | |
| `revoked_at` | TEXT | set only by `services/orders/revocationService.ts`'s `revokePurchase()`, always alongside the matching `deliveries.status = 'revoked'` update in the same D1 batch (ADR-003) |

Indexes: `idx_licenses_customer`, `idx_licenses_purchase_session`.

### `receipts`

Persisted, regenerable proof of payment. One receipt per verified
`purchase_sessions` row (not per `order_items` row) - a multi-item order
gets one receipt with multiple `line_items` entries, matching how a real
invoice works.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `receipt_number` | TEXT UNIQUE | **nullable** - see "Deviation from plan" below |
| `purchase_session_id` | INTEGER NOT NULL REFERENCES `purchase_sessions(id)` | |
| `customer_id` | INTEGER REFERENCES `customers(id)` | nullable, same reasoning as `licenses.customer_id` |
| `issued_at` | TEXT NOT NULL DEFAULT `datetime('now')` | |
| `line_items` | TEXT NOT NULL | JSON array, one entry per `order_items` row - a denormalized snapshot, not a live join |
| `subtotal_pesewas` | INTEGER NOT NULL CHECK `>= 0` | |
| `discount_pesewas` | INTEGER NOT NULL DEFAULT 0 CHECK `>= 0` | always 0 in M2 - no coupon system exists yet |
| `tax_breakdown` | TEXT NOT NULL DEFAULT `'[]'` | JSON array of `{label, rate_percent, amount_pesewas}` (ADR-008) - empty array is the honest default for a non-VAT-registered business |
| `tax_pesewas` | INTEGER NOT NULL DEFAULT 0 CHECK `>= 0` | derived sum of `tax_breakdown`, computed and stored at issuance |
| `total_pesewas` | INTEGER NOT NULL CHECK `>= 0` | must equal the corresponding `purchase_sessions.amount_pesewas` - enforced at the application layer only, since SQLite cannot cross-reference another table in a CHECK constraint |
| `tax_behavior` | TEXT NOT NULL | copied from `products.tax_behavior` at issuance (`'inclusive'` \| `'exclusive'` \| `'exempt'`) |
| `currency` | TEXT NOT NULL DEFAULT `'GHS'` | future multi-currency readiness; no multi-currency logic ships in M2 |
| `pdf_storage_key` | TEXT | R2 object key (`receipts/{receiptNumber}.pdf`), NULL until generation completes |

Indexes: `idx_receipts_customer`, `idx_receipts_purchase_session`.

**Deviation from plan**: `v3.0.2-m2-database-planning-report.md`
originally specified `receipt_number TEXT NOT NULL UNIQUE`. During
implementation, the insert-then-derive-from-own-id pattern (identical to
`purchase_sessions.purchase_reference`'s own proven approach) required a
placeholder value between the row's INSERT and the follow-up UPDATE that
sets the real number. An empty-string placeholder would collide under
the UNIQUE constraint on concurrent inserts, since two `''` values are
duplicates under SQLite - a real bug caught and fixed before any test
ran, not in production. The column was changed to nullable
(`TEXT UNIQUE`, no `NOT NULL`) and the code binds `NULL` instead, which
SQLite's UNIQUE constraint never treats as a collision, exactly
mirroring `purchase_sessions.purchase_reference`'s own documented
pattern. Verified safe by a dedicated concurrent-insert unit test in
`tests/unit/orderService.test.ts`.

### `receipt_download_tokens`

Single-use, short-lived token for the guest, reference-scoped
receipt-download action (ADR-013 tier 2: viewing a confirmation page by
reference alone is fine; downloading a file is an action and needs its
own single-use token). A separate table from the existing
`download_tokens`, deliberately: `download_tokens.delivery_id` is
`NOT NULL REFERENCES deliveries(id)`, so widening it to also
(optionally) point at a receipt would mean either weakening that live,
security-critical constraint, or adding a second nullable `receipt_id`
column with an "exactly one of these two must be set" rule SQLite cannot
enforce declaratively. A small sibling table costs nothing and touches
nothing already live - the same reasoning migration 0018 already applied
when it built `customer_password_tokens` as a sibling of
`password_reset_tokens` rather than generalizing one table to serve both
purposes.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `token` | TEXT NOT NULL UNIQUE | 256-bit, `crypto.getRandomValues`-based hex |
| `receipt_id` | INTEGER NOT NULL REFERENCES `receipts(id)` | |
| `expires_at` | TEXT NOT NULL | short TTL, mirrors `download_tokens.expires_at` |
| `used_at` | TEXT | set atomically on redemption; a used token can never be redeemed again |
| `created_at` | TEXT NOT NULL DEFAULT `datetime('now')` | |

Index: `idx_receipt_download_tokens_receipt`.

## Extended tables

**None.** Unlike M1 (which extended `purchase_sessions` with six
consent/customer columns), M2 required no `ALTER TABLE` at all - every
new fact (order line items, license grants, receipt data, receipt
download tokens) fit cleanly into new tables referencing
`purchase_sessions`/`customers`, which M1 already put in place.

`fulfilmentService.ts`'s `FulfilmentStatus` return type gained a
`receiptNumber: string | null` field, but this is a TypeScript-level
addition to an in-memory response shape, not a database schema change -
it is populated by a `SELECT` against the new `receipts` table, no
existing table was touched.

## What was deliberately NOT added in M2

Per the Product Owner's Architecture Decision Approval and the M2A
readiness review, out of scope for this milestone:

- `refund_requests` (or any customer-facing refund workflow table) -
  refund is admin-triggered only in M2; a customer refund request/portal/
  approval/policy table is explicitly deferred, not modeled here even as
  an inert placeholder.
- `coupon_redemptions`, `notification_queue`, `support_requests` (later
  milestones, unchanged from M1's own exclusion list).
- `license_type` values beyond `'personal'` (Licensing Enhancements -
  explicitly excluded from M2; the CHECK constraint is intentionally
  narrow rather than pre-widened).
- Any `platform_users` rename or `customer_id` bridge (M7).
- A `deliveries` schema change for genuine per-seat (quantity-aware)
  entitlements - `licenses` is fully seat-aware (ADR-009's N-row loop);
  `deliveries` remains single-per-asset via its existing
  `UNIQUE(purchase_session_id, asset_id)` constraint from M1. This is a
  documented known limitation (see the Implementation Report), not an
  oversight - no real product needs multi-seat downloads yet.

## Rollback strategy

All changes are purely additive (4 new tables, 0 altered tables, 9 new
indexes) - nothing existing was modified. Two options, in order of
preference:

1. **Forward-fix (preferred)**: since nothing was altered or dropped, a
   bad deploy of application code that reads/writes these new tables can
   be rolled back independently of the schema - the schema change itself
   is inert until application code exercises it, identical to M1's own
   rollback posture.
2. **Down-migration**, if the schema itself must be reverted:
   ```sql
   DROP INDEX IF EXISTS idx_receipt_download_tokens_receipt;
   DROP TABLE IF EXISTS receipt_download_tokens;
   DROP INDEX IF EXISTS idx_receipts_purchase_session;
   DROP INDEX IF EXISTS idx_receipts_customer;
   DROP TABLE IF EXISTS receipts;
   DROP INDEX IF EXISTS idx_licenses_purchase_session;
   DROP INDEX IF EXISTS idx_licenses_customer;
   DROP TABLE IF EXISTS licenses;
   DROP INDEX IF EXISTS idx_order_items_product;
   DROP INDEX IF EXISTS idx_order_items_session;
   DROP TABLE IF EXISTS order_items;
   ```
   This would also require reverting the application code in the same
   deploy (`commerceService.ts`'s `createOrderArtifacts()` call,
   `revocationService.ts`, the admin refund route, and all five Customer
   Library endpoints depend on these tables existing) - there is no
   scenario where rolling back the schema alone, with M2 application code
   still deployed, is safe.

`backend/database/schema.sql` (the cumulative reference doc) has been
updated to reflect migration 0019 as the current baseline, with
`receipt_number` corrected to nullable per the deviation noted above.
