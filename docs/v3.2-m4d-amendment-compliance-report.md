## Amendment 1 - Coupon Schema Correction

**Requirement:** `coupons`/`coupon_redemptions` reference `admin_users`, not the nonexistent `platform_users`; no `scope`/`creator_id` marketplace concepts.

**Independent verification performed:**
```
$ grep -rn "platform_users" database/schema.sql database/migrations/0020_reviews_and_coupons.sql services/couponService.ts routes/admin/coupons.ts
```
Every match is a comment referencing the historical, superseded design or the still-unplanned M7 rename - zero live `REFERENCES platform_users` or `CREATE TABLE platform_users`. Direct schema inspection confirms `coupons.created_by INTEGER NOT NULL REFERENCES admin_users(id)` (`database/schema.sql:1088`). No `scope` column, no `creator_id` column, no `CHECK (scope = 'platform' OR creator_id IS NOT NULL)` constraint anywhere in the live schema.

**Verdict: Confirmed. Fully compliant.**

## Amendment 2 - Coupon Security Review (Payment-Amount-Locking as Primary Focus)

**Requirement (M4B, verbatim):** "M4C's Security Review must treat the payment-amount-locking/webhook-verification change as its primary focus area, not an incidental item."

**Independent verification performed:**
- `docs/v3.2-m4c-amendment-2-coupon-security-review.md`'s own structure was checked: its second section (immediately after the design principle) is "Where the Discount Is Computed and Locked," and its Race Conditions section is explicitly subtitled "(the primary finding of this review)" - matching M4B's requirement in substance, not merely in the document's framing.
- This Board independently re-derived and checked, against the live code, the three specific properties `v3.2-m4b-architecture-readiness-assessment.md` required the review to walk through:
  - **(a) Discount computed and locked at checkout-creation time, never recomputed later.** Confirmed: `commerceService.ts`'s webhook handler passes `session.discountPesewas` (the value read back from the `purchase_sessions` row, set once at creation) into `redeemCoupon()` - never a fresh call to `computeDiscountPesewas()`.
  - **(b) The webhook verifies against the discounted, locked amount.** Confirmed: `verifyResult.amountPesewas !== session.amountPesewas` (line 433) compares against `session.amountPesewas`, which already holds the post-discount value from checkout-creation time - no coupon-specific branch was added to this check, because none is needed; the existing high-severity mismatch guard covers the discounted case automatically.
  - **(c) A coupon cannot be applied, changed, or removed after checkout-session creation without invalidating the session.** Confirmed by exhaustive grep of every `UPDATE purchase_sessions` statement in the codebase (`commerceService.ts`, `revocationService.ts`): none touches `coupon_id`, `discount_pesewas`, or `amount_pesewas` after the row's initial insert. Only `status`, `purchase_reference`, `checkout_url`, `provider_reference`, and `customer_id` are ever updated post-creation.
- `tests/integration/couponRaceConditions.test.ts` was independently re-run (`npx vitest run tests/integration/couponRaceConditions.test.ts`) rather than trusted from the implementation's own report - passes, and the assertions genuinely exercise the claimed property (two real, `Promise.all`-concurrent, signed HTTP webhook deliveries against a `max_redemptions = 1` coupon; both verify, `redemptions_count` never exceeds `1`, both redemptions are recorded).
- This Board additionally attempted its own adversarial checks not explicitly named in the amendment (see the companion Security Review deliverable for full detail): XSS via a `<script>` payload in a review body (server-rendered and client-rendered paths both confirmed safe), SQL-injection-shaped dynamic WHERE-clause construction in `couponService.ts`/`reviewService.ts` (confirmed structurally safe - only hardcoded condition fragments are interpolated, all values remain parameterized).

**Verdict: Confirmed. Fully compliant, and independently re-verified at the code level, not merely accepted from the amendment-resolution document's own narrative.**

## Amendment 3 (M4B's #3) - Reviews' Empty/Sparse Launch State UX Design

**Requirement (M4B, verbatim, from the Product Strategy Review this amendment cites):** "the Board recommends this be stated explicitly as a design requirement in M4A's own successor planning (M4C's technical planning), not left implicit."

**Independent verification performed:** The actual behavior is correct and matches M4B's own stated expectation - `routes/books.ts` renders "No reviews yet — be the first to share what you thought." for a product with zero approved reviews, honest, non-manufactured-urgency copy consistent with this project's established AR-009 discipline. Browser-verified directly by this Board (see UX & Accessibility Review) against a freshly-seeded zero-review test product.

**However:** no dedicated UX planning artifact for this decision exists anywhere in the M4C documentation set - unlike Amendments 1 and 2, which each have their own named resolution document. `v3.2-m4c-known-limitations.md` also does not carry forward the specific, related disclosure the Customer Journey Validation separately required: "Reviews will launch with no automated collection mechanism... should be stated explicitly as a known, accepted limitation of M4's own scope" (M4B, `v3.2-m4b-customer-journey-validation.md`).

**Verdict: Behaviorally compliant, documentation-non-compliant.** The correct outcome shipped, but the traceable design reasoning M4B asked for was never written down, and a specifically-required disclosure is missing from Known Limitations. **Non-blocking** - the underlying UX is correct and this is a documentation-completeness gap, not a functional or architectural defect - but it should not be silently absorbed into Closeout without being named. See the Documentation Review and Recommendations deliverables.

## Amendment 4 (M4B's #4) - Admin-Panel Test Coverage

**Requirement:** admin-panel test coverage for review moderation and coupon management is "a hard requirement of M4C's own Testing Strategy, not merely recommended."

**Independent verification performed:** `tests/integration/adminReviews.test.ts` (8 tests) and `tests/integration/adminCoupons.test.ts` (12 tests) both independently re-run and confirmed passing. Coverage inspected line-by-line, not merely counted: both files exercise role-gating (every-role read access vs. `EDITOR_ROLES`-only mutation), CSRF enforcement, not-found handling, and - for coupons specifically - a dedicated test confirming immutable fields (`code`, `discountType`, `discountValue`) cannot be smuggled into a `PATCH` request and take effect. This is meaningful coverage, not superficial route-exists smoke testing.

**Verdict: Confirmed. Fully compliant, and the coverage is substantively adequate, not merely present.**
