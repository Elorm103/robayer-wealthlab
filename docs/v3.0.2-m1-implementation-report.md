## Executive Summary

M1 adds a durable customer identity to Robayer WealthLab without
disturbing the site's zero-friction guest checkout. A buyer still
clicks Buy Now and pays - no form, no forced account creation. After a
genuinely payment-verified purchase, the system automatically
provisions (or reuses) a `customers` record, invites the buyer by
email to set a password, and from then on that buyer can sign in to a
real, durable account. Consent to the Terms of Service and License
Agreement is captured as part of the purchase action itself (not a
form field), with a separate, clearly optional marketing checkbox.

The one place M1's literal functional requirements conflicted with the
already-ratified architecture - collecting name/phone/country and
consent via typed checkout-form fields versus ADR-002's ratified
zero-form checkout - was surfaced to the user before any code was
written, per the sprint's own governance gate. The user chose to keep
the ratified zero-form checkout and treat consent-capture as an
additive gap-fill instead of reopening ADR-002. That decision is
recorded in full in the Architecture Compliance Matrix below.

Deliverables: 1 migration (5 new tables, 6 new columns on
`purchase_sessions`), 5 new backend services, 5 new API endpoints, 3
new frontend pages, 1 new legal document, 43 automated tests (17 unit
+ 26 integration, all passing), and this documentation set.

  new `orders` table. Followed: M1 extends `purchase_sessions` rather
  than introducing a parallel orders concept.
- **ADR-002** - Guest-first checkout with automatic, optional account
  provisioning after payment. Followed, with the one documented
  deviation resolution below.
- **ADR-004** - `customers` and `platform_users` remain permanently
  separate identities. Followed: `customers` is a wholly separate
  table from `admin_users`; no shared login surface.
- **ADR-006** - Account provisioning is purchase-triggered only;
  self-registration is explicitly out of scope. Followed exactly: no
  registration endpoint exists anywhere in this scope; the only
  `customers` INSERT is the find-or-create call inside the payment
  webhook handler.

ADR-003 (email-based access alongside accounts), ADR-005 (sequencing
customer-identity before coupons/promotions), and ADR-007 through
ADR-013 govern later milestones or adjacent concerns and are noted
here only for completeness - none required action in M1.

### Which amendments are relevant

None. No amendment to the ratified architecture was required or made.
The one gap the Blueprint's schema had not anticipated (ToS/License/
marketing consent capture) was resolved as an additive database
gap-fill, not an architectural amendment - see the deviation

### Implementation constraints identified

- Zero-form checkout (ADR-002) - no typed fields may be added to
  Robayer's own checkout page.
- Purchase-triggered-only provisioning (ADR-006) - no self-registration
  surface, in any form.
- `customers`/`platform_users` separation (ADR-004) - no shared table,
  no shared login endpoint.
- Reuse proven security patterns (Blueprint's Security Architecture) -
  customer session/CSRF/password-token mechanics must mirror the
  existing, already-hardened admin auth implementation rather than
  invent new ones.

### Deviation surfaced and resolved before implementation

The sprint brief's own functional requirements (collect full name,
phone, country, and ToS/License acceptance via checkout-form fields)
directly conflicted with ADR-002's ratified zero-form checkout
(Paystack collects email at payment; no fields on Robayer's own
checkout page). Per the sprint's explicit "stop and ask" governance
gate, this was surfaced to the user with three options before any code
was written. **The user selected: follow the ratified architecture
as-is.** Concretely:

- No form was added to the checkout page.
- Terms of Service and License Agreement acceptance is captured as a
  non-blocking consent statement next to the Buy Now button - clicking
  Buy Now *is* the acceptance act, with no extra click required.
- A separate, genuinely optional, unchecked-by-default marketing
  consent checkbox sits next to it.
- Full name, phone number, and country collection is explicitly
  deferred to a future post-payment profile-completion flow (M3), not
  built in M1.

This required no new ADR (fully consistent with ADR-002 as ratified)
and no reopening of governance - only an additive database gap-fill
(five new columns on `purchase_sessions`; see the Database Changes
report) to actually store the consent record. **No further
architectural deviation was required for the remainder of M1.**

## Features Implemented

- **Guest checkout with consent capture**: `POST /api/checkout/sessions`
  now requires `termsAccepted`/`licenseAccepted` (both strictly
  `true`) and accepts an optional `marketingOptIn`. Server-stamps the
  current terms/license version (`v1.0`) - never client-supplied,
  matching the existing price/title checkout-time-locking discipline.
- **Payment-verified account provisioning**: on genuine payment
  success, `findOrCreateCustomer()` creates a new `customers` row or
  reuses an existing one matched by normalized (lower-cased, trimmed)
  email - no duplicate identities, even across repeat purchases.
- **Password-setup and reset flow**: one shared mechanism
  (`customer_password_tokens`, single-use, 30-minute expiry) serves
  both the initial post-purchase invitation and any later self-service
  reset.
- **Customer session management**: login, logout, session check,
  12-hour sessions, double-submit CSRF, direct mirror of the existing
  admin session implementation.
- **Legal**: new License Agreement page; Terms of Use updated to
  describe the real, live, optional account system (previously said
  "no accounts exist yet").
- **Frontend**: consent statement + marketing checkbox on the book
  detail page; sign-in, forgot-password, and set-password pages.

## Security Measures

- **Never trust client-side validation alone**: `termsAccepted`/
  `licenseAccepted` are re-validated server-side with strict `=== true`
  checks in `commerceService.createCheckoutSession()`, independent of
  the route-layer validation.
- **CSRF protection**: double-submit pattern (`customer_csrf` cookie +
  `X-Customer-CSRF-Token` header), required on logout - the only
  customer-auth endpoint that mutates state on behalf of an
  authenticated session. Verified end-to-end: logout without the
  header returns `FORBIDDEN`; with it, succeeds.
- **Rate limiting**: login 5/15min/IP, forgot-password 3/15min/IP,
  set-password 10/15min/IP - all per-IP, matching the calibration
  already used for admin auth.
- **Timing-safe login**: a constant dummy password-hash comparison
  (mirroring admin auth's `DUMMY_PASSWORD_HASH` pattern) keeps
  unknown-email and wrong-password responses equally fast.
- **No enumeration**: forgot-password always returns an identical
  generic response regardless of whether the email exists (verified
  by an automated test asserting byte-for-byte identical response
  bodies) - including when rate-limited.
- **Secure token generation**: session tokens, CSRF secrets, and
  password-setup tokens are all 256-bit, `crypto.getRandomValues`-based.
- **Server-side payment verification**: no `purchase_sessions` row can
  reach `verified` without a genuine, independently-checked call to
  Paystack's `/transaction/verify` endpoint - the webhook payload's own
  embedded fields are never trusted for the pass/fail decision.
- **Webhook signature verification**: HMAC-SHA512 over the raw body,
  unchanged from the existing implementation, exercised by dedicated
  invalid-signature and tampered-amount tests.
- **Input sanitization / injection safety**: verified with dedicated
  negative tests - SQL-injection-shaped and XSS-shaped input are
  safely handled as inert, parameterized values; malformed JSON and
  oversized input are rejected cleanly, never a 500.
- **Idempotent webhook handling**: redelivering an identical webhook
  produces no duplicate transaction or entitlement row.
- **Secrets never logged**: password hashes, session tokens, and CSRF
  secrets are never written to application logs.

## Risks

- **Consent-record legal defensibility**: `terms_accepted_at`/
  `license_accepted_at` are stamped from the click-to-purchase action
  itself rather than an explicit separate "I agree" click. This is the
  approach the user explicitly chose (preserving ADR-002's zero-form
  checkout) and is disclosed as such in the on-page consent statement
  wording, but it is a materially different legal posture from a
  dedicated checkbox - worth a compliance/legal review before scaling
  transaction volume significantly.
- **No account-lockout on customer login**: repeated failed login
  attempts are only slowed by the general per-IP rate limit (5/15min),
  not tracked per-account. See Technical Debt below.

## Technical Debt

- **No `failed_login_attempts`/`locked_until` on `customers`**: the
  ratified schema has no such columns, and none were added - adding
  them would have been an unrequested architectural addition beyond
  M1's scope. Per-IP rate limiting is the only current brute-force
  mitigation for customer login. Flagged here rather than silently
  built; recommended for a future security-hardening milestone.
- **`content/products/*.json` vs. live D1** (pre-existing, not
  introduced by M1, but touched by this work): `worker/env.ts` still
  carries a stale comment implying products are read from
  `content/products/*.json`; `productCatalogService.ts` actually reads
  live from D1. Noted for a future documentation-cleanup pass.

## Known Limitations

- **Test-tooling environment quirk (not a product bug)**: this
  sandbox's `@cloudflare/vitest-pool-workers` test-worker process
  cannot use undici's `MockAgent` (the package's own documented
  `fetchMock` mechanism) - constructing even a bare `MockAgent` with no
  configuration crashes the test worker outright, confirmed in
  isolation. It also cannot reach a real local HTTP server bound to
  `127.0.0.1` - workerd's default outbound network policy only permits
  publicly-routable addresses ("in order to prevent SSRF attacks"),
  silently denying loopback connections even in local dev, with no
  flag exposed through this package's config surface to relax it. The
  working alternative - and the one actually used - is Miniflare's
  `outboundService` option: a plain JS function that intercepts every
  outbound `fetch()` the worker-under-test makes, before workerd's
  network layer is ever involved. Because that function runs in a
  separate host-side process from the test files themselves (which
  execute inside the simulated Worker), configuring per-test mock
  behavior required routing configuration through D1 itself (a
  `test_mock_responses` table, test-infrastructure only - see
  `backend/tests/outboundMock.ts`'s header comment for the full
  diagnostic trail) rather than simple shared JS state. This is purely
  a test-infrastructure detail; it has no effect on production
  behavior, since `PAYSTACK_BASE_URL`/Resend's URL are the real
  provider URLs in every non-test environment.
- **Consent-record legal posture** - see Risks above.
- **No dashboard exists yet**: successful sign-in currently redirects
  to `/?signed-in=1` (a query-string flag with no UI treatment yet) -
  there is nowhere for a signed-in customer to actually go. This is
  expected and intentional for M1 (a customer dashboard is out of this
  milestone's scope) but worth calling out explicitly since it's the
  most visible "unfinished-feeling" edge of this milestone from an end
  user's perspective.
