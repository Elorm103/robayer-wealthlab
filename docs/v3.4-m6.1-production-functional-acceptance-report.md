# Version 3.4 M6.1: Production Functional Acceptance Report

## Method

Every workflow in this report was exercised against the live production domain (`https://robayerwealthlab.com`), not localhost, using the real customer-facing pages and API endpoints, with outcomes confirmed against actual D1 database state and actual email delivery records rather than inferred from reading code. Where a workflow required a real customer or order to exercise meaningfully, a minimal, clearly-marked test record was created directly in production D1, exercised through the real API, and removed afterward. No live Paystack payment was executed, per the explicit instruction; checkout initialization was verified up to and including a real Paystack checkout URL being issued, and the resulting pending session was then removed rather than completed.

## Summary of what was executed

- Full customer authentication lifecycle: forgot-password, email delivery, token generation, set-password, single-use token rejection, login, session check, CSRF-protected logout, post-logout session invalidation.
- General contact form and consultation form: submission, validation, database record, acknowledgement email, rate limiting.
- Newsletter: new subscription, duplicate subscription (idempotent, no duplicate row or duplicate email), invalid email rejection, unsubscribe token confirmation, subscriber count.
- CMS publishing immediacy: a real product price change and a real SEO meta description change, each confirmed live on the public API and the actual rendered page within seconds, with no deploy, then reverted.
- Commerce: books listing and book detail pages render correctly; checkout session creation returns a genuine Paystack checkout URL; an existing real order's receipt PDF and its customer-facing download endpoint were exercised end to end.
- Email authentication: SPF, DKIM, and DMARC DNS records for the actual sending path were checked directly against DNS, not assumed.
- Infrastructure: Worker, D1, R2, admin authentication gating, and the Cron schedule were each confirmed live.

## Corrections made during this review, stated plainly

Two things I initially reported as problems during this review turned out, on closer inspection, not to be:

1. I first concluded a production receipt's PDF was missing from R2 storage. This was caused by my own testing mistake: I queried R2 without the `--remote` flag, which checks a local, empty simulation rather than the actual production bucket. Once queried correctly, the PDF was present. I had already reset the receipt's stored key and triggered a real regeneration before catching this, which is harmless (it produced a second, equally valid PDF) but was an unnecessary action based on a false alarm. This is disclosed rather than left uncorrected.
2. I initially flagged the domain's SPF record as not authorizing Resend's sending infrastructure. Checking only the apex domain's SPF record was incomplete: Resend's actual sending path uses a subdomain (`send.robayerwealthlab.com`), which carries its own correct SPF record (`include:amazonses.com`), and a DKIM record is correctly present at the standard `resend._domainkey` selector. The full picture is that email authentication is correctly configured, not misconfigured.

Both corrections are included because a report that quietly drops an earlier wrong claim without saying so is not trustworthy. Both are detailed further in the Email Delivery Verification Report and Infrastructure Verification Report.

## What could not be tested as originally scoped, and why

- **Customer registration and activation** as standalone, pre-purchase steps do not exist in this codebase. There is no registration form. A customer record is created only when a purchase completes (Paystack's hosted checkout collects the email), and "activation" is the customer using an emailed set-password link for the first time. This was verified by reading `backend/routes/customer/auth.ts`'s own route list (login, logout, session, forgot-password, set-password, change-password; no register/activate endpoint exists) and confirmed structurally correct, not a gap to fix.
- **Dedicated Media and Partnerships contact channels** do not exist as separate features. There is one general contact form (`POST /api/contact`) and one consultation form (`POST /api/consultation`); no code path, page, or database table distinguishes a "media inquiry" or "partnership inquiry" from a general one. This is reported honestly rather than tested against something that is not there.
- **Customer library access and review eligibility** could not be tested against a genuinely new, real customer, because no customer in production has ever completed checkout with a real (non-placeholder) email address; every "successful" transaction in production D1 used Paystack's test-mode flow with a synthetic `checkout+<reference>@robayerwealthlab.com` address. The customer-facing download and receipt mechanisms were still verified end to end using this existing test data.
- **Exhaustive, every-screen coverage of the Admin Panel** (every filter, every pagination edge case, every settings field) was not attempted individually; the underlying mechanisms proven this session (immediate D1-to-API-to-page publishing, authentication gating, the specific fixes made in M6 and M6's acceptance review) cover the parts of the admin panel most likely to have broken.
