# Version 3.2 - Sprint M4B - Feature Prioritization Audit

Independently re-scores every candidate feature against M4A's Prioritization Matrix. Where this Board agrees, it says so briefly. Where it challenges a score, it explains why and shows the evidence.

## Items Where This Board Agrees Without Reservation

Product reviews, Customer notifications, Email automation, Newsletter platform (folded into Email automation), Customer profiles, Search improvements, Recommendation engine, Admin/Sales analytics, Multi-currency support, Affiliate/referral system, Product bundles, Video lessons, Learning progress tracking, Digital certificates, Instructor portal, AI-assisted learning tools. For each of these, this Board's own independent read of the codebase and the cited planning documents confirms M4A's business-value, effort, and risk characterization is accurate. No changes recommended.

## Items This Board Challenges

### Coupon Engine - effort and risk understated

**M4A's score:** Business Value High, Effort S, Risk Low-Medium, "zero open design questions."

**Board finding, independently verified:** two claims in M4A's characterization do not hold up under direct code/schema inspection:

1. **"Already fully schema-designed... ready to implement as-is" is incorrect.** `docs/v3-database-design.md`'s `coupons` table (`creator_id INTEGER REFERENCES platform_users(id)`, `created_by INTEGER NOT NULL REFERENCES platform_users(id)`, `scope TEXT CHECK (scope IN ('platform', 'creator'))`) references a table, `platform_users`, that **does not exist in the current production schema** - confirmed directly (`grep -n "platform_users" backend/database/schema.sql` returns zero table-definition matches; every current FK still points to `admin_users`). This design was written for the V3.0/V3.1 multi-creator marketplace vision and depends on ADR-011's `platform_users` rename, which is itself explicitly gated as "Requires Replanning" and has no scheduled timeline. **The cited coupon schema cannot be implemented as written today.** A new, simpler, single-seller-scoped `coupons` table (no `scope`, no `creator_id`, `created_by` referencing `admin_users`) needs to be designed - small, real work M4A characterized as unnecessary.
2. **The effort estimate does not account for where a coupon discount must be applied.** `commerceService.ts` computes `amountPesewas` once, at checkout-session creation, directly from the product catalog price, and *locks* it into `purchase_sessions.amount_pesewas`. The webhook handler then performs a strict equality check (`verifyResult.amountPesewas !== session.amountPesewas`) against this locked value, flagged in the code's own comments as a "high-severity" mismatch category - this is the single most safety-critical calculation in the entire system. Implementing coupons means this calculation must correctly incorporate the discount *before* the amount is locked, and the webhook's verification must check against the discounted amount, not the catalog price. This is well-precedented, safe, and buildable - but it is not a trivial, isolated addition; it modifies the one code path every prior security review in this project's history has treated with the most caution.

**Revised score: Business Value High (unchanged); Effort S-M; Risk Low-Medium (unchanged, but the specific risk should be named explicitly - "modifies the payment-amount-locking calculation" - not left implicit).**

**This does not change the recommendation to include Coupons in M4** - both findings are corrections to a design/effort estimate, not evidence the feature is a poor fit for M4. They do mean M4's successor technical-planning sprint cannot simply "implement the existing design" as M4A's Scope Recommendation instructs - it must first produce a new, simplified schema.

### Product Reviews - one unaddressed launch-state risk

**M4A's score:** Business Value High, Effort S, Risk Low. This Board agrees with the score but flags a gap: given only 2 real customers and 17 verified purchases exist in production today (independently confirmed, see Product Strategy Review), Reviews will launch with almost no content. M4A's own Business Opportunity Report calls Reviews "the single highest-leverage, lowest-cost item" without addressing that its leverage depends on people actually leaving reviews, which nothing in M4's own scope drives (the review-request trigger is M5). **Not a reason to change the score or the milestone** - but M4C's own UX work should explicitly design the empty/sparse state, not treat it as an afterthought.

### Wishlist - dependency correctly identified, but the ADR-006 tension deserves more weight

M4A correctly flags that Wishlist is "structurally in tension with ADR-006." This Board agrees with the flag but notes M4A's Roadmap treats this as a simple "resolve or defer" switch in M5A planning. Given ADR-006 was a *ratified, ARB-reviewed* decision ("purchase-triggered provisioning only... explicitly excludes self-registration"), any resolution that involves even a lightweight account-adjacent mechanism for Wishlist should itself go through the same governance weight ADR-006 originally received, not be resolved informally inside a single milestone's own planning sprint. **Recommendation: if Wishlist requires any exception to ADR-006, it should produce its own amendment proposal, reviewed with the same rigor as the M4/M5 re-sequencing this package already calls for** - not a lighter-weight decision just because it's smaller in scope.

## Items Not on the Original List - Board Additions

- **VAT readiness** was already correctly identified in M4A as "not an engineering decision," and this Board's own read of `computeTaxBreakdown()` and `ADR-008` confirms that characterization exactly. No change.
- **A specific coupon-schema correction task**, named above, should be added to the tracked work either as an M4A-successor deliverable or as the first item of M4C - this Board treats it as a Required Amendment (see Recommendations), not a new candidate feature in its own right.
