# Version 3.3 Sprint M5A: Technical Debt Assessment

Independently reviewed against the actual codebase, using the `workers-best-practices` skill's checklist (configuration, request and response handling, architecture, observability, code patterns, security) rather than a general impression.

---

## Findings, by Category

### Code Quality (Clean)

- Zero `TODO`, `FIXME`, or `HACK` markers found in any production service, route, or worker file (confirmed by direct grep across `services/`, `routes/`, `worker/`).
- Zero unsafe `as any` casts found in any production file (only in test files, where `env as any` is the established, acceptable pattern for satisfying the test-mock environment type; this is the same pattern used throughout the M4 test suite).
- Zero module-level mutable `let` or `var` state found in `worker/index.ts` or any service file, meaning the cross-request data-leak anti-pattern the `workers-best-practices` skill specifically warns against is not present.
- No `Math.random()` found in any security-sensitive code path (session tokens, license keys, CSRF secrets all confirmed to use the Web Crypto API, not a predictable pseudo-random source).

### Configuration

- `compatibility_date` is `2026-07-06`, 20 days old at the time of this review, not stale, but worth a routine refresh the next time any Worker code changes, per the skill's own "update periodically" guidance.
- `nodejs_compat` is deliberately not enabled, with an explicit comment in `wrangler.jsonc` explaining nothing in this codebase needs a Node.js shim yet. This is a documented decision, not an oversight.
- `observability` is already configured (structured logging, sampling), matching the skill's own recommended baseline.

### Dependencies

`npm outdated` shows three packages behind their latest release: `@cloudflare/workers-types` (one major version behind), `typescript` (behind by two major versions, 5.9.3 versus 7.0.2 latest), and `wrangler` (one minor version behind, 4.107.0 versus 4.114.0). None of these represent an active security advisory or a breaking-change risk found in this review; all three are routine version-currency debt, not urgent.

### Test Coverage

221 tests, all passing at the close of Version 3.2. Coverage of the payment-integrity path (checkout, webhook, receipts) is genuinely strong, including a true-concurrency race-condition test and a full end-to-end financial-pipeline test added at Milestone M4's own closeout. The one honestly-disclosed gap from Milestone M4's own governance history: authenticated admin-UI-level browser testing (as opposed to API-level testing, which is thorough) requires new local-development tooling (a password-hash bootstrap flow) that does not exist yet. This is a real, tracked, low-severity gap, not a new finding of this review.

### Data Integrity (New Finding, This Review)

**Fifteen of seventeen verified purchases (88 percent) have no `customer_id`.** This is not a bug: it is a historical artifact of Milestone M1 (Customer Identity and Guest Checkout) having been added to an already-live checkout system, confirmed by directly comparing purchase timestamps against the customer-provisioning code's own deployment. Every verified purchase created after Milestone M1 shipped correctly receives a `customer_id`. The debt is not in the code; it is in the data: a real, unresolved backlog of legitimate paying customers with no account-linked identity. See `v3.3-customer-journey-review.md` and `v3.3-feature-inventory.md` for the recommended reconciliation mechanism.

### Migrations

20 migrations applied across the platform's history, all additive, zero rollback ever executed in practice. A documented rollback strategy now exists for the most recent migration (Milestone M4's own closeout), matching the precedent Milestone M2 first established. This is a mature, low-risk pattern worth continuing, not changing.

---

## Overall Verdict

**Technical debt is low for a platform of this age and scope.** The one genuine debt item with real business consequence (the orphaned guest-purchase data) is a data-reconciliation problem, not a code-quality problem, and is already reflected as a leading candidate in `v3.3-feature-inventory.md` and `v3.3-m5-recommended-scope.md`. Dependency-version currency is the only routine housekeeping item this review recommends scheduling, at low priority, alongside whatever Version 3.3 scope is approved.
