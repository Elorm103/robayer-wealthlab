# Version 3.2 - Sprint M4B - Technical Debt Assessment

Re-classifies every item on M4A's consolidated Technical Debt Register by timing relative to M4 specifically, per this sprint's own required framework (Must complete before M4 / Can be completed during M4 / Can safely wait until M5+).

---

## Must Complete Before M4 (i.e., before M4C implementation begins)

| Item | Why it must come first |
|---|---|
| **Corrected coupon schema design** (new finding, this review - see Architecture Readiness Assessment) | M4A's own cited coupon schema cannot be implemented against the current database. Implementation cannot begin against a schema that doesn't work. This is now the single gating item for M4. |

**Nothing else on the register rises to this level.** This Board specifically checked whether the VAT question or the `platform_users` migration plan should be added here and confirms M4A's own reasoning holds: neither blocks Coupons or Reviews from being built (VAT because the tax-display interaction is genuinely trivial while `computeTaxBreakdown()` returns an empty array regardless; `platform_users` because the corrected coupon schema above deliberately avoids depending on it).

## Can Be Completed During M4

| Item | Why M4 is the right time |
|---|---|
| **Admin-panel test coverage, for the specific new admin surfaces M4 introduces** (review moderation, coupon management) | M4A already recommends this; this Board concurs and elevates it from "recommended" to "should be treated as a hard requirement of M4C's own Testing Strategy," given this exact pattern (an untested new admin surface) has now produced a genuine acceptance-review finding in 2 of 2 milestones that shipped one. |
| **No reusable script for production test-data cleanup** | M4's own production verification (M4E-equivalent) will need to seed and clean up verification data a fourth time. Building the reusable script during M4 pays for itself immediately, exactly as M4A's own Technical Debt Review already recommended. |

## Can Safely Wait Until M5 or Later

Every other item on M4A's register: `deliveries` seat-awareness (no multi-seat product exists), `createOrderArtifacts()` atomicity (same reason), session device-summarization coarseness (cosmetic), `resolveAssetsWithDeliveryInfo()` scope (deliberate), `customers.password_updated_at` (deliberately deferred), load/performance testing baseline (no near-term traffic-increase driver from M4 itself), Licenses page `aria-live` gap (sitewide, unrelated to M4), KV rate-limiter design (no current trigger), the full Low-priority list (rounding-drift bundle math, `audit_logs.entity_id` audit, newsletter Queue migration, backup-export gaps, PBKDF2 ceiling, last-super-admin guard, `wrangler dev` environment cosmetic issue) - this Board independently confirms none of these interact with Reviews or Coupons in any way that would change if resolved before versus after M4.

## Escalation Items (not "debt" in the code sense, but tracked here per M4A's own framework)

- **VAT-registration business question**: this Board independently confirms M4A's framing - a Product Owner decision, not an engineering task, correctly not gating M4. Given this is now the seventh consecutive planning pass to carry this item forward (M1, M2A, M2B, M2C/M2D, M3A, M4A, and now M4B), this Board adds its own explicit recommendation: **if this question is still unresolved by the time M4 ships, the M4D-equivalent closeout should refuse to treat "still pending" as an acceptable steady state and should require a written explanation from the Product Owner of what is blocking a decision** - a step beyond "escalate again," since escalating alone has visibly not worked six times running.
- **`platform_users` migration/rollback plan (ADR-011)**: correctly independent of M4; this Board found no reason to change M4A's "start planning it in parallel" recommendation.

One new Must-Fix item was found by this review (the coupon schema correction) - everything else on M4A's own register was independently re-confirmed correctly classified as non-blocking for M4.
