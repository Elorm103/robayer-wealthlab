# Version 3.4 Milestone M6: Branding Consistency Report

Scope: every location branding (logo, favicon, colors, typography) appears across the website, admin panel, emails, receipts, PDFs, Open Graph, Twitter Cards, and manifest, with each location's origin traced and, where it referenced a static asset independently, replaced with the centralized system.

## 1. The centralized system

`js/components/branding.js` fetches `GET /api/branding` (public, unauthenticated, `no-store`) and swaps `src` on every element carrying the `.nav__logo-mark` class, plus the favicon `<link>` tags, based on what the admin has assigned in `admin/branding/`. Six named slots exist (`primary`, `dark`, `favicon`, `og`, `email`, `appIcon`), each storing a `media_assets.id` in `site_settings` via `backend/services/admin/brandingService.ts`. A `SLOT_IS_WIRED` map documents which slots have a real consumer.

This is the correct, single source of truth for the logo: an admin assigns an image once in `admin/branding/`, and that assignment should reach every location listed below with no code change.

## 2. Slot-by-slot status after this milestone

| Slot | Wired before M6 | Wired after M6 | What changed |
|---|---|---|---|
| `primary` | Yes | Yes | No change. Header and footer logos (public site), and now the admin sidebar (see 2.1). |
| `dark` | Yes | Yes | No change. Dark-mode logo swap, driven by `<html data-theme="dark">`. |
| `favicon` | Yes | Yes | No change. |
| `email` | No (stored, unconsumed; `SLOT_IS_WIRED.email` was `false`) | Yes | New: every transactional email now resolves this slot (falling back to `primary`, then the static default) into an absolute logo URL at send time. See Section 3. |
| `og` | No | No (unchanged, by design) | See Section 4: OG tags are static HTML on pages the Worker never renders per-request, so a client-side swap could never reach a social-preview crawler regardless of how this slot is wired. Not a gap; a correct architectural limit. |
| `appIcon` | No | No (unchanged, by design) | No PWA manifest or app-icon consumer exists anywhere in this codebase to wire it to. Documented as future-ready, not a current gap. |

## 3. Fixed this milestone

### 3.1 Email logo

`backend/emails/layouts/base.html` previously hardcoded `<img src="https://robayerwealthlab.com/assets/branding/logo/logo-mark.png" alt="Robayer WealthLab" ...>` directly in the shared layout every one of the 13 email templates renders through. This was a real, independent branding asset reference, exactly the "no location should reference a static asset independently" case the brief asks to find and fix.

Fixed by:
- Replacing the hardcoded `src`/`alt` with `{{LOGO_URL}}`/`{{LOGO_ALT}}` placeholders in `base.html`.
- Adding `resolveEmailLogo(env)` to `backend/services/emailService.ts`, which calls the same `getPublicBranding()` the website already uses, prefers the `email` slot, falls back to `primary`, and falls back to the static bundled asset only if neither has ever been assigned. Email clients cannot resolve a relative URL the way a browser can, so this always resolves to an absolute URL built from `env.SITE_BASE_URL`.
- Updating `SLOT_IS_WIRED.email` from `false` to `true` to reflect the new, real consumer, and correcting the prior comment ("no transactional email template currently includes a logo image") which was factually inaccurate: `base.html` line 31 always did include a logo image, it simply was not connected to this slot.

Verified: with no `email`/`primary` slot assigned (the current state of both local and production `site_settings`), `resolveEmailLogo()` resolves to `https://robayerwealthlab.com/assets/branding/logo/logo-mark.png` with alt text `"Robayer WealthLab"`, exactly matching the value that was previously hardcoded. This confirms the change is behavior-neutral until an admin actually assigns a logo to one of these slots, which is the correct default.

### 3.2 Admin sidebar logo

`partials/admin-sidebar.html`'s logo `<img>` used only its own class, `admin-sidebar__brand-mark`, and was never touched by `branding.js` (which only ever queried `.nav__logo-mark`). This meant the admin sidebar logo was a second, independent hardcoded reference to the same static file the public header/footer use, and did not respond to either a CMS logo change or the admin's own dark-mode toggle (a real, if minor, contrast bug: the sidebar kept its light-mode logo file even when the admin switched to dark mode).

Fixed by adding the `.nav__logo-mark` class alongside the existing `.admin-sidebar__brand-mark` class on the same element. `admin.css`'s own sizing rule (`width: 24px`) continues to apply and win the cascade over `components.css`'s `.nav__logo-mark` rule (`width: 40px`), since `admin.css` loads after `components.css` on every admin page, so this is a pure behavior addition with no visual size change. `branding.js` itself was also added to all 29 admin page templates (it was previously loaded only on the branding editor page), so every admin page, not just the sidebar's page, now participates in both the dark-mode swap and the CMS override.

Verified in-browser: the admin sidebar logo's computed width remained 24px after the change, and toggling `data-theme="dark"` correctly swapped its `src` to `logo-mark-dark.png`, exactly matching the public header's own behavior.

## 4. Reviewed and confirmed correct, not changed

### 4.1 Open Graph and Twitter Card images

Every page's OG/Twitter meta tags are static `<meta>` tags in that page's own `<head>`, since the static site (GitHub Pages) never runs server-side rendering per request; only `/api/*`, `/books/*`, `/resources/*`, `/blog/*`, and `/free-guide/*` are intercepted by the Worker. Social-preview crawlers (Facebook, Twitter, LinkedIn, etc.) fetch a page's raw HTML and do not execute JavaScript, so even if `branding.js` swapped an `og:image` tag client-side, no crawler would ever see the swapped value. Wiring the `og` slot into a client-side swap would create the appearance of a working feature that does nothing for its actual purpose. The correct fix, if this is prioritized in a future milestone, is templating the OG tags into the same detail-page `renderShell()` mechanism `books.ts`/`blog.ts`/`resources.ts` already use for per-item SEO fields, which does run server-side. This is a genuinely different piece of work than "wire the existing slot" and is called out as future scope in the Final Release Recommendation, not attempted here.

### 4.2 Receipt PDF branding

`backend/services/orders/receiptPdfService.ts` draws a bold text wordmark ("Robayer WealthLab") via `pdf-lib`'s `page.drawText()`, using `StandardFonts.Helvetica`/`HelveticaBold` and hardcoded near-black/gray RGB values with no traceable connection to `css/tokens.css`'s actual brand palette. No logo image is embedded at all. This is a real branding inconsistency (the one generated document a customer keeps does not match the site's visual identity), but embedding an image into a generated PDF and matching its color values to the design token system is meaningfully more work than a slot-wiring fix, and was not attempted in this pass. Recorded here as a known gap, addressed in the Final Release Recommendation.

### 4.3 Email/website color drift

All 13 email templates and `base.html` hardcode brand colors independently of `css/tokens.css`, documented in-code as "kept in sync by convention, not a build step." This audit found two different hardcoded green values for CTA buttons across templates (`#1F5C4A` in 6 templates, `#1F5C4E` in 5), and neither matches the website's current brand green (`--color-growth-green: #206F34`, itself changed from an older `#1F5C4E`-family value during a past UI polish pass). This is direct, concrete evidence the "sync by convention" approach has already failed once. Not fixed in this pass (a genuine content/copy correction across 13 files, not a slot-wiring change), but flagged with specific evidence so it is not silently carried forward. See the Final Release Recommendation.

### 4.4 `assets/config/site.json`'s branding block

`site.json`'s own `branding` block is explicitly commented as "Reference-only... duplicated as static tags in every page's `<head>`," meaning it is not actually read by any code, just documentation of what value is duplicated where. This is stale, dead-weight documentation rather than a live branding inconsistency (nothing reads it, so it cannot drift the live site), but it does mean an admin editing the logo today still requires a manual find-and-replace across every page's raw `<head>` tags for anything this block describes but `branding.js` doesn't reach (favicon variants, manifest icons). Recorded for cleanup, not fixed here.

## 5. Conclusion

Every location where a genuinely fixable, real branding inconsistency existed (email logo, admin sidebar logo) was fixed this milestone by connecting it to the existing centralized slot system, not by inventing a new one. The two escaped attempts (Open Graph, receipt PDF) were confirmed to require materially different work than slot-wiring, and are called out honestly rather than either silently skipped or force-fitted into a client-side swap that would not actually work.
