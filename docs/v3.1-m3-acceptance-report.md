# Version 3.1 - Milestone M3 Acceptance Report

**Sprint M3C - Independent Milestone Acceptance Review (MAR)**
**Milestone:** M3 - Checkout Auto-Provisioning & Dashboard MVP
**Review type:** Independent Milestone Acceptance Review Board (MARB) - Principal QA Engineer, Principal Frontend Architect, Principal Backend Architect, Security Reviewer, UX Reviewer, Accessibility Reviewer, Product Owner Representative, Release Readiness Manager, Technical Documentation Reviewer.
**Reviewer posture:** This review did not treat the M3B Implementation Report's own claims as verified fact. All nine M3A planning documents and all six M3B implementation documents were read in full; the actual production code (services, routes, tests, frontend components, CSS) was read directly; the full test suite and TypeScript type check were re-run independently; a real, freshly-seeded customer was driven through every dashboard flow in a live browser session (login, all five pages, download mint, change-password, session list/revoke, keyboard-only navigation, tablet/mobile viewports, dark mode) rather than trusting the M3B report's own browser-verification narrative; and a live, direct API call was made specifically to test the one security requirement the M3A Security Review flagged as needing its own dedicated verification.

**One genuine defect was found and fixed during this review** (Section 5, Section 11 Item 1) - see the Final Decision for how this affects acceptance.

## 1. Executive Summary

Milestone M3 ships the customer dashboard M2's own Implementation Report explicitly deferred ("no customer dashboard pages... the APIs exist and are tested, ready for M3 to consume"): five pages (My Library, Purchase History, Receipts, Licenses, Account Security) plus three new backend endpoints and one additive field, exactly the scope M3A's planning sprint approved. No VAT logic, coupons, marketplace, or framework migration was introduced. No schema change was made, matching the Database Impact Assessment's own conclusion.

**Independently confirmed:** 131/131 tests passing (19 test files, re-run twice by this review — once before and once after this review's own fix), `npx tsc --noEmit` clean both times. Every ADR M3 is bound by (ADR-002, ADR-003, ADR-006, ADR-009, ADR-013) and AR-009's ratified confirmation-gate requirement are satisfied in the actual code and in live browser interaction, not merely asserted in documentation.

**This review found one genuine, live-confirmed security-requirement violation**: the M3A Security Review's Session handling section states the session-revoke endpoint "must never allow revoking the current session through this specific control" — the initial M3B implementation enforced this only in the dashboard UI (no revoke button rendered for the current session), with no server-side guard. A direct API call by this review confirmed a customer's own current session could be revoked via `POST /api/customer/sessions/:sessionId/revoke`, immediately invalidating the very cookie making the request. **This review fixed the gap** (`routes/customer/sessions.ts`, a four-line guard), added three regression tests (the self-revoke rejection, plus the two negative/adversarial tests the M3A Testing Strategy had explicitly required and M3B had not written), updated the two affected documentation files, and independently re-verified the fix live against the running `wrangler dev` backend before and after. The suite grew from 128 to 131 tests, all passing.

Beyond that fixed defect, this review found: one stale code comment referencing filenames from the original Frontend Architecture Plan that were superseded during implementation (fixed); one UX-Strategy-required UI verification step (keyboard-only navigation) that M3B's own browser verification had skipped, independently performed by this review and found to pass; and one documentation completeness gap (the Database Impact Assessment's optional `password_updated_at` column was correctly deferred but the deferral was never explicitly logged in Known Limitations). None of these rises to a blocking defect.

**Final decision: Option B - Milestone M3 Accepted with Minor Observations.** See Section 14.

## 5. Security Review

- **Authentication**: every dashboard page requires `requireCustomerAuth` via `requireSession()`; live-confirmed redirect-before-render behavior for an unauthenticated visitor.
- **CSRF**: both new mutating endpoints (`sessions/:id/revoke`, `change-password`) require the double-submit `X-Customer-CSRF-Token` header; confirmed by reading `requireCustomerCsrf()` call sites and by the re-run integration tests (`FORBIDDEN` without the header).
- **Ownership/IDOR — the one new authorization shape M3 introduces**: `revokeSessionById()` filters by both `customerId` and `sessionId`; a cross-customer revoke attempt returns the same `NOT_FOUND` a nonexistent session would, confirmed both by the pre-existing dedicated test and by this review's own reading of the query (`WHERE id = ? AND customer_id = ? AND revoked_at IS NULL`).
- **Session self-revocation — genuine defect found and fixed.** The M3A Security Review states this route "must never allow revoking the current session through this specific control... should either exclude the current session from the revocable list in the response, or explicitly reject an attempt to revoke it via this route." The initial M3B implementation deliberately chose neither option, instead relying only on the dashboard UI never rendering a revoke control next to the session flagged `isCurrent` — a client-side-only enforcement of a server-side security requirement. **This review confirmed the gap live**: authenticated as a real customer via `curl`, called `POST /api/customer/sessions/{own-current-session-id}/revoke` directly (bypassing the UI entirely, as any customer with browser devtools or a script could) — the call succeeded (`{"revoked":true}`), and the immediate next request using the same session cookie was rejected as unauthenticated. Severity is low (self-inflicted lockout only; the ownership check already prevents any cross-customer exposure — no other customer's session can ever be affected), but it is a direct, confirmed violation of an explicit "must never allow" planning requirement, not a hypothetical one. **Fixed during this review**: `routes/customer/sessions.ts`'s `handleRevokeCustomerSession` now rejects with `CANNOT_REVOKE_CURRENT_SESSION` (400) when `sessionId === auth.auth.sessionId`, before calling the service layer. Re-verified live after the fix: the same self-revoke call now correctly fails, the session remains valid, and revoking a genuinely different session still succeeds normally (no regression). Three new tests were added (`dashboardM3.test.ts`) and the full 131-test suite passes.
- **Password change security**: re-read `changePassword()` — timing-safe `DUMMY_PASSWORD_HASH` comparison runs on every path (including a hypothetically-missing customer row), new-password strength validated via the existing shared policy, every *other* session revoked on success while the acting session is deliberately preserved — confirmed both by code reading and by the re-run integration test asserting the acting session survives.
- **Negative/adversarial test coverage — gap found and closed.** The M3A Testing Strategy explicitly required two specific adversarial tests that `dashboardM3.test.ts` did not contain: "malformed/oversized `:sessionId` path parameter" and "SQL-injection-shaped values in the `change-password` request body." Both were added by this review. The malformed-`:sessionId` test confirmed the existing `parseInt`/`Number.isInteger` guard correctly rejects non-numeric, oversized, and injection-shaped path values. The SQL-injection test confirmed the `customers` table survives a `'; DROP TABLE customers; --`-shaped `newPassword` value unharmed (parameterized binding, not string concatenation) — the request itself is correctly rejected as `INVALID_CREDENTIALS` well before that value would ever reach a write.
- **Download authorization**: unchanged, reused mint-then-redirect flow; no new download code path was introduced anywhere in M3.
- **Rate limiting**: confirmed present on all three new/extended endpoints via direct code reading (`change-password` 10/15min, sessions read 60/15min, sessions write 20/15min) — no dedicated rate-limit *test* exists for these three endpoints specifically (M2's own Acceptance Report flagged the identical gap for M2's endpoints and classified it non-blocking under the same reasoning: the protection is verified sound by code inspection even where the test coverage is thin); consistent, non-blocking (Section 9/11 Item 4).

**Verdict: Pass, after this review's own fix.** One genuine, confirmed security-requirement violation was found and corrected within this review, with regression coverage added. No other exploitable issue was found.
