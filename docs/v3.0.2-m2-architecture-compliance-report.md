## ADR map

| ADR | Requirement | Classification for M2 |
|---|---|---|
| ADR-001 | `purchase_sessions` remains the order-of-record; no new `orders` table. Naming resolution deferred to M7. | **Mandatory.** `order_items`, `licenses`, `receipts` all reference `purchase_sessions.id`, never a new orders table. |
| ADR-002 | Guest-first checkout, zero fields on Robayer's own page. | **Mandatory (inherited, unaffected).** M2 adds no checkout-time field. Receipts/licenses are generated post-payment, from data already captured. |
| ADR-003 | Email-link download access preserved permanently; license/entitlement revocation must be synchronized (`licenses.revoked_at` and `deliveries.status = 'revoked'` in one operation) whenever either is set. | **Mandatory, core to M2.** This is the central data-integrity guarantee the `licenses` table exists to make real. See the scope-boundary note below on how much of the *triggering* mechanism (refund workflow) ships in M2 versus later. |
| ADR-004 | `customers`/`platform_users` stay separate. | **Not applicable to M2** - no new identity concept is introduced. |
| ADR-006 | Purchase-triggered-only provisioning, no self-registration. | **Mandatory (inherited, unaffected).** M2 introduces no new account-creation path. Every new customer-facing endpoint requires an existing session (M1's `requireCustomerAuth`), never creates one. |
| ADR-008 | `receipts.tax_breakdown` (JSON array of `{label, rate_percent, amount_pesewas}`), in addition to `subtotal_pesewas`/`total_pesewas`. `tax_pesewas` is a derived sum, not a separately entered value. Population of the array is gated on confirming this business's VAT-registration status - a business fact, not an engineering decision. | **Mandatory at the schema level. Conditionally mandatory at the computation level** - see Risks. The schema field must exist and be populated (even if with a single degenerate entry, or an empty array, for a non-VAT-registered business) from the start; the *tax-computation logic* specifically should not be finalized against a guess. |
| ADR-009 | `order_items.quantity = N` generates N independent `licenses` rows and N independent `deliveries` entitlements - never one shared license with a seat count. | **Mandatory.** Governs the fulfilment-loop design in the API Planning Report. Every current product in this catalog has `quantity = 1` in practice (no bundle/multi-seat product exists yet), so this requirement is architecturally required but not yet exercised by real inventory - worth a dedicated test with a synthetic `quantity = 2` case rather than only relying on production data to prove it. |
| ADR-010 | Chargeback handling mirrors the refund revocation pattern; explicitly scoped to Milestone M8. | **Deferred, correctly out of M2.** No chargeback-class webhook handling should be added in M2. |
| ADR-013 | Confirmation-page view/action access split - viewing by `purchaseReference` alone; any *action* requires session or a fresh single-use action token. | **Mandatory.** Directly governs how the existing `/checkout/callback/` page's "Download" action and any new receipt-download action must be authorized. The current M1 download-token minting already follows this pattern for the entitlement path; M2 must apply the identical discipline to receipt/license access, not invent a weaker one. |

## Scope-boundary finding requiring a decision before M2B begins

The ratified Blueprint's own M2 success criteria (Deliverable 11) state: *"a test refund correctly sets both `licenses.revoked_at` and `deliveries.status = 'revoked'` in one operation, and a subsequent download-token request for that entitlement is correctly denied."* ADR-003's own consequences line is explicit: *"The refund-processing and chargeback-processing code paths (Milestone M2 for the mechanism, M8 for chargebacks specifically) must both write to two tables in one logical operation."*

This sprint's own scope instruction, however, lists only Orders, Order Management, Customer Purchase History, Customer Library, Receipts, and Customer Purchase APIs as included, and does not name refunds, and separately excludes "Licensing Enhancements."

**Recommended resolution, to be confirmed before M2B implementation begins:**

- **Mandatory for M2:** the revocation-sync *service function* itself (small, fully specified by ADR-003, and the only way to prove the `licenses`/`deliveries` design is real rather than theoretical) plus a minimal way to trigger it - reasonably scoped as an admin-side action under "Order Management" (e.g. a revoke action on an existing/extended admin purchase-detail view), not a customer-facing flow.
- **Deferred:** the full `refund_requests` table (reason tracking, customer-initiated requests, admin approval workflow) and any customer-facing "request a refund" UI. This is not named in this sprint's scope list, is naturally adjacent to Milestone M5 (Support Ticketing, which already handles order-aware customer requests), and its absence does not block M2's own named deliverables (Orders, Receipts, Customer Library data).

This keeps M2 tightly scoped to what was asked, while still satisfying the one ratified success criterion that is otherwise unreachable without it. It is not a blocker - it is a decision the Product Owner role should explicitly confirm at the start of M2B, since it slightly narrows what "the mechanism" in ADR-003's M2 assignment means in practice.

## Compliance verdict

**Pass.** No architectural deviation is required. The one item above is a scope-boundary clarification, not a conflict with the ratified architecture - the recommended resolution keeps every ADR requirement satisfied while respecting this sprint's explicit exclusion list.
