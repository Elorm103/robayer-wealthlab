# Version 4.2.1 — Hero Cover Flicker: Instrumentation & Real Root Cause

## Summary

Version 4.2 Part 1.1's fix (decoupling the cover from the scroll-reveal fade) was correct and remains in place, but it did not touch the actual bottleneck. This investigation instrumented the live page instead of theorizing further, and found the real cause: a global security-header rule in the backend was silently stripping the cover image's caching header on every response, forcing a full multi-second-to-multi-ten-second re-download of the ~1.9MB cover file on **every single page view**, not just hard refreshes. Fixed server-side, verified live with a direct before/after measurement.

## 1. Instrumentation built (Phases 1–4)

Added a temporary, diagnostic-only script (`js/debug/hero-instrumentation.js`, loaded first, before any other script) that logged, with `performance.now()` timestamps, every event the brief asked for:

- Lifecycle: script execution, `readystatechange`, `DOMContentLoaded`, `window.load`
- Paint timing: `first-paint`, `first-contentful-paint`, and every Largest Contentful Paint candidate (via `PerformanceObserver`)
- Resource timing for `/api/products` and every `/api/media/file/*` request (`startTime`, `responseStart`, `responseEnd`, `duration`)
- A `MutationObserver` on `.hero__visual`, `.hero__visual-link`, `.book-card__cover-image`, `.book-card__cover-placeholder`, `.book-card__cover-placeholder-text`, `.hero__content`, `.hero__text` — logging every `class`/`style`/`hidden`/`src` change with before/after snapshots (opacity, transform, display, visibility)
- A separate, observation-only `IntersectionObserver` per element (never interferes with the real one)
- `requestAnimationFrame` timing
- Duplicate-element checks: total `<img>` count, images inside the hero/banners, and counts of `[data-feature-banner]` / `[data-feature-placeholder]` / `[data-feature-cover-img]`

**Phase 4 result — no duplicates found.** Exactly 2 real `[data-feature-banner]` elements (Hero, Featured eBook), exactly 2 `[data-feature-cover-img]` images, exactly 1 `[data-feature-placeholder]` (only the Hero has a text placeholder). The live HTML's apparent "4 banner" grep hits were HTML comments mentioning the attribute names, not real duplicates.

**Phase 5 result — no second script touches the hero.** Grepped the entire project for `hero__visual`, `book-card__cover-image`, `hero__visual-link`, `feature-banner`, `data-feature-banner` in every `.js` file: only `js/components/product-loader.js` manipulates these elements (`js/components/library-list.js` touches the same *class names* but only on the unrelated Customer Library page). `initFeatureBanners()`'s `data-bound` guard is set synchronously, before any async work, so the dual `partials:loaded`/`DOMContentLoaded` bindings cannot double-process the same banner.

## 2. What the instrumentation actually showed (Phase 3, Phase 6)

Local mechanism check (mocked API, real viewport) confirmed the Part 1.1 architecture is sound: `.hero__visual` stays at `opacity: 1` throughout, `.hero__text` still fades in correctly, and the mutation sequence on the Hero's own image element is clean — one `src` mutation, one `hidden` mutation, no repeats.

Deployed the instrumentation to production and captured a real hard-refresh trace. The critical lines:

```
resource timing: .../5f1ea15a-...png   startTime 1917.70  responseEnd 12167.40  duration 10249.70
resource timing: .../966b7ae9-...png   startTime 1920.90  responseEnd 12428.20  duration 10507.30
```

Both cover images took **over 10 seconds** to fully download — an order of magnitude slower than every other resource on the page (`/api/products` took 855ms in the same trace). `responseStart` (time to first byte) was reasonably fast (~1–1.3s); the remaining ~9 seconds was spent receiving the rest of the bytes on every load, with no variance explained by anything in the JS/CSS layer — this pointed straight at the network/caching layer, not at rendering.

## 3. Root cause

`curl`-ing the live image directly showed the real problem:

```
Cache-Control: no-store, no-cache, must-revalidate
```

`backend/routes/media.ts` (line 80) explicitly sets `Cache-Control: public, max-age=31536000, immutable` on every real, content-addressed media file — correct, and exactly what Part 1's investigation found in the code. But `backend/worker/index.ts` (line 603) passes **every** response through `withSecurityHeaders()`, and `backend/middleware/securityHeaders.ts` (line 117, before this fix) unconditionally overwrote `Cache-Control` with `no-store, no-cache, must-revalidate` on any response whose `Content-Type` wasn't `text/html` — which includes every served image. The media route's own header was being silently stomped on every single response, site-wide, for every uploaded image, not just the hero cover.

**Why this is the real cause, not a "frame" or timing-race problem:** with no caching anywhere (browser or edge), every page view forced a full, real, multi-second network transfer of a ~1.9MB PNG. No CSS or JS change — a "flicker" fix — can hide a genuinely slow, uncached network fetch; the placeholder has to stay up until the bytes actually arrive, every time, forever. This is also why the symptom read as inconsistent ("flicker," "sometimes half-rendered," "sometimes late") rather than a fixed delay — the exact wait length varied with real network/connection conditions on each individual page load, since nothing was ever being reused from a previous visit.

## 4. Why Part 1 and Part 1.1 did not solve it

Both were real, correctly-diagnosed, correctly-fixed bugs — Part 1 fixed premature image reveal before `decode()`; Part 1.1 fixed the scroll-reveal container racing the image's own reveal. Neither investigation checked the **actual wire-level response header** the image was served with; Part 1's report trusted `routes/media.ts`'s code directly (which does set the header correctly) without confirming what reached the browser after the security-headers middleware ran afterward. That gap is exactly what this instrumentation pass was built to close by observing real behavior instead of re-reading intent.

## 5. The permanent fix

One conditional, in `backend/middleware/securityHeaders.ts`:

```ts
const existingCacheControl = response.headers.get('Cache-Control');
const routeOptedIntoPublicCaching = existingCacheControl?.startsWith('public,') ?? false;
if (!isHtmlResponse(response) && !routeOptedIntoPublicCaching) {
  headers['Cache-Control'] = 'no-store, no-cache, must-revalidate';
  headers['Pragma'] = 'no-cache';
}
```

The global no-store default still applies to every JSON/admin/sensitive response exactly as before (none of those set their own `Cache-Control`, so they're unaffected). The only change: a route that has already explicitly opted into public caching (currently only `routes/media.ts`) keeps its own header instead of having it overwritten. No CSS, no JS, no animation, no delay, no hack — a one-line exception in the one place that was incorrectly blanket-overriding a deliberate, already-correct header.

Covered by a new regression test, `backend/tests/integration/mediaCacheHeaders.test.ts`: asserts a real media file keeps `public, max-age=31536000, immutable`, and a genuinely-missing file still gets the safe `no-store` default. Verified this test fails without the fix and passes with it.

- `scripts/bump-asset-versions.mjs`: re-run, 0 stale references.

```
0ms      HTML begins parsing
~60ms    DOMContentLoaded — scroll-reveal & product-loader both bind
~350ms   /api/products responds (fast, uncached but small — not the bottleneck)
~440ms   Hero <img>.src assigned — image download begins
~440ms   ┆
   ↓     ┆  10+ SECONDS — no caching anywhere (the real bug): browser
         ┆  and edge both re-fetch the full ~1.9MB file from scratch,
         ┆  every load, because Cache-Control was being overwritten
         ┆  to no-store on every response
~10,700ms  Image fully downloaded, decode() resolves

```

```
0ms      HTML begins parsing
~60ms    DOMContentLoaded
~350ms   /api/products responds
~435ms   Hero <img>.src assigned — served instantly from browser cache

~435ms   decode() resolves essentially immediately
~435ms   hidden=false — cover appears with the rest of the page, no visible wait
```

## Scope discipline

No animation, transition, CSS, or JS reveal logic was touched in this pass — the Part 1.1 fix (moving `data-reveal` off `.hero__visual`) remains exactly as shipped. The only change is the one-line exception in the security-headers middleware described above, plus removing the now-unneeded diagnostic script.
