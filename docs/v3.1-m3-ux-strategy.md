| Priority | Category | Impact | M3 application |

| 2 | Touch & Interaction | Critical | Every action button (Download, View Receipt, Log out other sessions) is a real button, minimum 44x44px, never icon-only without a label - matches the existing site's own `.btn`/`.btn--accent` convention. |

## 2. Design system: reuse, do not reinvent

**Governing rule, inherited unchanged from the ratified M2A UX Plan:** no new visual system for the dashboard. Confirmed by direct inspection of `css/tokens.css` (264 lines, WCAG contrast ratios already documented and verified) and every existing page's use of `.card`, `.btn`, `.alert`, `.grid`, `.stack`, `.section` component classes.

| Token category | Values already available | M3 usage |
|---|---|---|
| Color roles | `--color-growth-green` (primary), `--color-sika-gold` (accent), `--color-success`/`--color-warning`/`--color-error`/`--color-info` (+ tints) | Status badges (Section 5) use the semantic roles directly - `ready`=success, `processing`=info, `refunded`=warning, never a raw hex. |
| Typography | Newsreader (headings), Space Grotesk, Work Sans (body), IBM Plex Mono (technical/reference strings) | Purchase references and receipt numbers render in the existing mono face, matching how `checkout/callback/index.html` already sets `data-fulfilment-reference`. |
| Backgrounds | `--color-bg` (white default), `--color-bg-alt` (warm-paper, alternating sections) | Dashboard pages use `.section`/`.bg-sand` exactly as the rest of the site already does for alternating content blocks. |

**No new color, font, or spacing token is proposed.** Any perceived gap (e.g., a dashboard-specific "card" treatment) should first be checked against the existing `.card` component before a new class is considered.

## 3. Information architecture and navigation

A single, flat, six-item navigation is proposed for the authenticated dashboard area, matching Priority 9's "predictable, not overloaded" guidance and the ratified Blueprint's own six-page M3 scope:

```
My Library  |  Purchase History  |  Receipts  |  Licenses  |  Downloads  |  Account Security
```

- **Entry point:** My Library - matches the ratified Blueprint's own description ("entry point, every product owned").
- **No nested navigation, no hamburger-hidden secondary menu on desktop** - six flat items fit comfortably in a single header row at all breakpoints down to tablet; on mobile, collapse to a standard disclosure menu (not a bottom tab bar - this is not a mobile-app-shaped product, and the existing site has no bottom-nav precedent to extend).
- **Deep-linkable, per Priority 9's own "no broken back behavior, real deep links" requirement:** every dashboard page has a real, bookmarkable URL (e.g. `/dashboard/library/`, `/dashboard/receipts/`), not a single-page-app hash route - consistent with the whole site's existing multi-page-HTML architecture (see Frontend Architecture Plan).
- **Distinct from the existing, unauthenticated confirmation page.** `checkout/callback/index.html` (view-by-reference, ADR-013 tier 1) remains unchanged and separate from the dashboard (session-gated, ADR-013 tier 2/full-Library access) - a customer arriving at the dashboard without a session is redirected to `checkout/sign-in/`, never shown a stripped-down or degraded dashboard.

## 4. Page-by-page UX specification

### My Library

- One row/card per **purchase** (not per line item), consistent with `receipts.line_items` being one JSON array per purchase session (a multi-item order shows as one row with an expandable line-item list - a future-proofing detail, since no bundle product exists yet).
- Each row surfaces, without a click: product title, purchase date, amount paid, a status badge (text + color, never color alone - Priority 10's own rule applied even outside a literal chart), and two direct actions: **Download** and **View Receipt**.
- Desktop: card-like rows with generous spacing, not a dense data-grid - this is a handful of purchases per customer at realistic volume, not an admin-scale table.
- Mobile: the same rows stack to a vertical card list; every action renders as a full-width, labeled button, never an icon-only control (Priority 2).

### Purchase History

- A chronological, transaction-facts-first view (date, reference, amount, status) - the "did I actually pay for this, and when" mental model, distinct from the Library's "what do I own" mental model. Both read from the same underlying data; the distinction is presentational only (see API Gap Analysis - no second endpoint is needed).

### Receipts

- List view: receipt number, issue date, total, one-click PDF download - hits the existing, already-tested `GET /api/customer/receipts/:receiptNumber/download` directly (no mint-then-redeem step needed for the authenticated path, unlike the guest flow).
- Loading feedback required on the download button itself during the request (Priority 3/8) - a brief inline spinner, not a full-page loading state, since this is a small, fast, single-resource fetch, mirroring `fulfilment-status.js`'s own `requestDownload()` button-state pattern (`disabled` + changed label while in flight).

### Licenses

- List view: license key (monospace, truncated with a copy-to-clipboard affordance), product, type, issue date, status (`active`/`revoked` - text, not color alone). A "View/print certificate" action is a nice-to-have, not required for M3's own MVP scope (the ratified Blueprint lists it as a Library page action; M3's minimum viable version can defer the print-formatted certificate view to a fast-follow if timeline pressure requires trimming, since the underlying data is already fully exposed via the API either way).

### Downloads

- Distinct from Purchase History: "how many times have I downloaded this, and when," sourced from `deliveries.downloads_used`/`last_download_at` (already-live fields, no new schema - see Database Impact Assessment). Per the ratified UX Plan's own conclusion, this is better shown as a secondary line under each Library row ("Downloaded 2 times, last on [date]") than as a fully separate page, given this data volume - M3 should implement it this way rather than building a seventh standalone page for a single line of text.

### Account Security

- Displayed: email (from the session), password-last-changed context (see Database Impact Assessment for the one small gap here), active sessions.
- Actions: change password, log out other sessions - **both require an explicit confirmation step before executing**, per AR-009's own ratified requirement, never a direct one-click action. This is the one page in M3's scope with a genuinely destructive action, and it must not be treated as equivalent in risk to a Library download button.

## 5. Empty states (mandatory, per AR-009 and Priority-table guidance)

| Page | Empty-state copy direction |
|---|---|
| My Library | "Nothing here yet. Browse our guides to get started." with a direct link to `/books/` - the exact language AR-009 itself specifies, never a blank card or empty table. |
| Purchase History | Same empty state as Library (same underlying zero-purchase condition). |
| Receipts / Licenses | "No receipts/licenses yet - they'll appear here as soon as you make a purchase." |
| Downloads | Folded into the Library row (Section 4) - no standalone empty state needed. |

**Data-contract requirement this depends on:** every list endpoint must return a clean, empty array (`{success: true, data: {purchases: [], total: 0}}` and equivalents) for a zero-purchase customer, never an error - already true of every M2 endpoint today, confirmed by the M2 test suite's own dedicated empty-state tests. No API change needed for this requirement.

## 6. Loading states

Matching `fulfilment-status.js`'s own proven pattern (Priority 3/7): show an honest, non-decorative loading indicator while the initial page data fetches, then render exactly one of {populated list, empty state, error state} - never a layout shift between the loading skeleton and the final content's actual dimensions (Priority 3's CLS guidance). No skeleton-screen shimmer animation is required; a simple, static "Loading your library..." message is consistent with this site's own established low-motion, honest-copy design philosophy and avoids introducing a new animation pattern for a sub-second fetch.

---

## 7. Confirmation dialogs (AR-009, Priority 8)

Required for exactly two M3 actions, both on Account Security:

1. **Change password** - a real "Are you sure" step is not required for the change itself (submitting a new password is the confirmation), but the *effect* (all other sessions are revoked) must be stated clearly before submission, not discovered after.
2. **Log out other sessions** - requires an explicit confirmation step before executing, per AR-009's own ratified requirement for exactly this action.

No other M3 action (viewing a receipt, downloading a file) is destructive or irreversible, and none should be gated behind a confirmation dialog - over-confirming a safe, reversible action (viewing/downloading) would itself be a UX anti-pattern (unnecessary friction on a low-risk action).

---

## 8. Accessibility

- Every status badge carries text, never color alone (already stated above, repeated here as the standing rule).
- Every action button keyboard-reachable with a visible focus ring - matching the site's own already-audited, pre-existing focus-state treatment (per the retrospective's own confirmation that no accessibility regression exists anywhere in M1/M2's surface).
- Skip-link present on every new page (`checkout/callback/index.html`'s own `<a href="#main-content" class="skip-link">` is the exact, direct precedent to copy).
- `aria-live`/`role="alert"` on any inline error message, matching `sign-in-form.js`'s existing `showServerError()` pattern.

---

## 9. Mobile responsiveness

No new breakpoint strategy needed - `css/tokens.css`'s own documented breakpoints (mobile 0-767px, tablet 768-1199px, desktop 1200px+) already govern every existing page and should govern the dashboard identically. Card-based layouts (Library, Receipts, Licenses) reflow naturally from desktop rows to mobile stacked cards using the existing `.grid`/`.stack` utility classes - no bespoke mobile layout code should be needed.

---

## 10. Brand consistency

Full compliance expected and required: navy/green/gold brand system unchanged, Newsreader/Space Grotesk/Work Sans/IBM Plex Mono typography unchanged, the site's own "honest, low-pressure, never-manufactured-urgency" copy philosophy applied to every dashboard string (e.g., a "Downloaded 2 times" line states a fact, never "Only 2 downloads left!" urgency framing that isn't how this system's download policy actually works for most products).

---

## 11. Performance expectations

- Dashboard pages are read-mostly, low-data-volume (a handful of rows per customer) - no pagination-performance concern at realistic scale, though the existing `GET /api/customer/purchases` pagination (already built, already tested) should be used as-is rather than fetching an unbounded list client-side.
- No image assets beyond what already exists (product cover thumbnails, if shown on Library rows, reuse the exact same asset pipeline the product catalog pages already use - no new image-serving path).
- No CLS risk given the loading-state discipline in Section 6.
