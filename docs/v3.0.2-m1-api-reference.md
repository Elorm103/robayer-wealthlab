# Version 3.0.2 - Milestone M1 API Reference

Customer Identity & Guest Checkout. Covers the one changed endpoint
(`POST /api/checkout/sessions`) and the five new customer-auth
endpoints. All responses use the project's standard envelope:
`{ success: true, data: {...} }` or `{ success: false, error: { code,
message } }`.

## Changed: `POST /api/checkout/sessions`

Unchanged URL and unchanged request shape's core (`productId`), with
three new fields added by M1.

**Request body**

```json
{
  "productId": "starting-to-invest-with-gh100",
  "termsAccepted": true,
  "licenseAccepted": true,
  "marketingOptIn": false
}
```

| Field | Required | Notes |
|---|---|---|
| `productId` | yes | unchanged - the product slug |
| `termsAccepted` | yes | must be the literal boolean `true`; anything else (including the string `"true"`, `false`, or omission) is rejected. This is not a form field - the frontend always sends `true` here because clicking Buy Now *is* the acceptance act (see `js/components/buy-button.js`) |
| `licenseAccepted` | yes | same validation as `termsAccepted` |
| `marketingOptIn` | no | any non-`true` value (including omission) is treated as opted-out; only `true` opts in |

**New error code**: `CONSENT_REQUIRED` (400) - returned when
`termsAccepted` or `licenseAccepted` is not strictly `true`.

**Success response** is unchanged in shape
(`{ purchaseReference, checkoutUrl }`); the consent fields are stamped
server-side onto the `purchase_sessions` row (`terms_accepted_at`,
`terms_version`, `license_accepted_at`, `license_version`,
`marketing_opt_in`) and are not echoed back in the response body.

Rate limit: unchanged, 10/min/IP.

## New: Customer auth routes (`/api/customer/auth/*`)

All five routes are thin HTTP wrappers over
`services/customer/authService.ts` - no route touches D1 directly.
There is **no registration endpoint**: the only way a `customers` row
is created is the purchase-triggered find-or-create in the webhook
handler (ADR-006).

### `POST /api/customer/auth/login`

**Request**: `{ "email": string, "password": string }`

**Success (200)**: sets two cookies (`customer_session` - HttpOnly,
Secure, SameSite=Lax, 12h; `customer_csrf` - Secure, SameSite=Lax, not
HttpOnly so the frontend can read it and echo it back as a header) and
returns `{ customerId, email, expiresAt }`.

**Errors**:
- `INVALID_CREDENTIALS` (401) - wrong password, unknown email, *or* an
  account that has never set a password (`password_not_set` reason) -
  the response message distinguishes the "no password set yet" case
  for the user, but the HTTP status/code is identical either way; a
  timing-safe dummy hash comparison (mirroring
  `services/admin/authService.ts`'s `DUMMY_PASSWORD_HASH` pattern)
  keeps unknown-email and wrong-password responses equally fast, so
  timing cannot be used to enumerate accounts.
- `RATE_LIMITED` (429) - 5 attempts / 15 min / IP.

### `POST /api/customer/auth/logout`

**Auth**: requires a valid `customer_session` cookie **and** the
`X-Customer-CSRF-Token` header matching the session's CSRF secret
(double-submit pattern - see `middleware/customerCsrf.ts`).

**Success (200)**: revokes the session server-side, clears both
cookies, returns `{ loggedOut: true }`.

**Errors**: `NOT_AUTHENTICATED` (401) if no valid session;
`FORBIDDEN` (403) if the CSRF header is missing or wrong.

### `GET /api/customer/auth/session`

**Auth**: requires a valid `customer_session` cookie. No CSRF header
needed (safe/read-only).

**Success (200)**: `{ customerId, email }`.

**Errors**: `NOT_AUTHENTICATED` (401).

### `POST /api/customer/auth/forgot-password`

**Request**: `{ "email": string }`

**Success (200)**: **always** `{ requested: true }`, whether or not
the email belongs to a real account (no-enumeration discipline,
matching admin's forgot-password behavior) - including when the
request is itself rate-limited, so a client can never distinguish
"you got rate-limited" from "we sent an email" from "no such account."
Internally, if the email matches a real customer, a
`customer_password_tokens` row is minted and a
`customer-password-reset` email is sent via `issuePasswordToken()`.

Rate limit: 3/15min/IP (an unauthenticated endpoint that sends real
email to a real inbox is itself a spam/harassment vector even without
any credential risk).

### `POST /api/customer/auth/set-password`

Serves **both** the initial post-purchase password-setup flow and any
later self-service password reset - same endpoint, same mechanism,
different originating email.

**Request**: `{ "token": string, "newPassword": string }`

**Success (200)**: `{ passwordSet: true }`. Atomically: validates the
token (exists, unused, unexpired), validates password strength,
hashes and stores it, marks the token used, and revokes every existing
session for that customer (a password change invalidates all prior
logins).

**Errors**:
- `INVALID_TOKEN` (400) - token missing, unknown, expired, or already
  used. Deliberately generic (doesn't distinguish "expired" from
  "already used" from "never existed") - same anti-enumeration
  posture as the login endpoint.
- `VALIDATION_ERROR` (400) - password fails strength policy (reuses
  `utils/passwordPolicy.ts`, the same policy admin passwords use); body
  includes a `fields` array with the specific violated rule(s).
- `RATE_LIMITED` (429) - 10/15min/IP.

## Guest checkout → account provisioning flow (informational, not a new endpoint)

For completeness - the full sequence this milestone implements, none
of which is directly callable by a client except the two endpoints
above:

1. `POST /api/checkout/sessions` - creates a `purchase_sessions` row,
   `status='pending'`, with consent stamped.
2. Customer completes payment on Paystack's hosted page.
3. Paystack calls `POST /api/webhooks/paystack` (existing endpoint,
   unchanged URL/shape - signature-verified via
   `x-paystack-signature`, HMAC-SHA512 over the raw body using
   `PAYSTACK_SECRET_KEY`).
4. `commerceService.handlePaymentWebhook()` re-verifies the payment
   server-side against Paystack's `/transaction/verify/{reference}`
   (the webhook payload's own embedded fields are never trusted for
   the pass/fail decision - only used to know *which* reference to
   verify).
5. On genuine success: `findOrCreateCustomer()` runs (new customer, or
   reuse of an existing one matched by normalized email); the
   `purchase_sessions` row is updated with `customer_id`; a download
   entitlement/delivery is created (`fulfilmentService.ts`, unchanged
   from prior versions); if the customer was newly created, a
   `customer-welcome` email is sent with a password-setup link
   (`issuePasswordToken()`); if the customer already existed, no
   welcome email is sent (only the standard purchase-receipt/
   secure-download emails).
6. Customer clicks the link → lands on `/checkout/set-password/` →
   `POST /api/customer/auth/set-password` → account usable.
