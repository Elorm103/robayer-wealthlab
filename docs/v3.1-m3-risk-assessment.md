## VAT Readiness (dedicated review, per this sprint's explicit instruction)

**Status: unchanged from Milestone M2. Still an open business question, not a technical one.**

### Assumptions

- The business is currently assumed **not VAT-registered**, per the M2A Product Owner decision already in force - this assumption is not re-litigated or re-decided by M3, only inherited.
- `receipts.tax_breakdown` will continue to be an honest, empty JSON array for every receipt M3 displays, exactly as it is today.
- No M3 screen computes, infers, or guesses a tax figure anywhere - Receipts page rendering is a direct, literal display of whatever `tax_breakdown`/`tax_pesewas`/`total_pesewas` the API already returns, nothing more.

### Risks

- The business question has now been carried, unresolved, across **five** consecutive planning/review passes counting this one (M1 planning, M2A planning, M2B implementation, M2C/M2D review, and now M3A). This is a process risk, not a technical one, and this planning sprint explicitly repeats the Version 3.0.2 Retrospective's own recommendation: escalate with a real deadline, rather than carrying it forward silently an sixth time.
- If the business confirms VAT registration at any point *during* M3's implementation, the Receipts page's display logic does not need to change - the `tax_breakdown` array's shape already accommodates a real, populated breakdown (per ADR-008's own "the structure costs nothing to leave unused" reasoning) - only the *computation* (a backend concern, not M3's own UI) would need to change, and separately.

### Implementation impact

**None, for M3's own scope.** M3 is a pure consumer of whatever `tax_breakdown` already exists on a receipt; it introduces no new tax-related risk and requires no new decision to proceed. The Receipts page's display should be built generically enough to render zero, one, or several `tax_breakdown` entries correctly (since the array's cardinality is not fixed at zero forever, only *today*), which is a small, cheap UI-robustness requirement, not a blocked dependency.

---

## Overall risk posture

No risk identified above is severe enough to block starting M3. The two risks worth resolving *before* M3's implementation begins, specifically because they are cheap to resolve now and more expensive to discover mid-build, are: confirming the browser-automation tooling question early (Testing Strategy), and making the one new authorization shape (session-id-scoped revoke) an explicit, named test requirement from the start rather than an assumed extension of the existing pattern.
