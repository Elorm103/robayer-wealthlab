## Browser Verification (Manual)

Automated tests exercise the HTTP/service layer; the following was verified manually against a local `wrangler dev` instance (port 8787) proxied through the static-site dev server (port 5500), using a locally-seeded test product and test coupon (both created and removed via direct D1 `execute` calls, scoped to local dev only, never touching production):

- **Product page reviews section**: renders the "No reviews yet" empty state and a working "Sign in to write a review" link (correctly pointing at `/checkout/sign-in/?redirect=...`) for a signed-out visitor. No console errors.
- **Coupon entry on the product page**: the coupon-code field and "Apply" button render correctly in the hero. Submitting an unknown code round-trips through `POST /api/coupons/validate` and displays "We couldn't find that coupon code." Submitting a real, freshly-created 10%-off coupon against a GH₵100.00 test product correctly displays "Coupon applied: -GH₵10.00. New total: GH₵90.00." - confirming the full client-to-server-to-client discount computation path works end to end against real HTTP responses, not mocked data.
- **Admin login redirect**: `/admin/reviews/` and `/admin/coupons/` both correctly redirect an unauthenticated visitor to the admin sign-in page (confirming `admin-shell.js`'s session guard fires correctly ahead of the new page-specific scripts), with zero console errors during the redirect.

Full authenticated admin-page verification (moderating a real review, creating/deactivating a real coupon through the admin UI) was not performed in this sprint, since it required either hand-crafting a valid PBKDF2 password hash or extending the local-dev seed process beyond this sprint's scope - the equivalent logic is fully covered by `adminReviews.test.ts`/`adminCoupons.test.ts`'s real-HTTP integration tests instead, which exercise the identical route handlers these pages call.
