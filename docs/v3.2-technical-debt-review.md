# Version 3.2 - Sprint M4A - Technical Debt Review

Consolidates every technical debt item on record across `v2.1-technical-debt-register.md`, the V3.0.2 Retrospective's own Technical Debt Register, and every M1/M2/M3 Known Limitations document, into one classified register. Nothing below is newly discovered by this review except where explicitly marked "New" - this is a consolidation and reclassification pass, not a fresh audit.

Classification is by **urgency to address relative to Version 3.2 planning**, not by original severity label.

---

## Critical

**None.** No item on record today blocks correct operation, risks data loss, or represents an open security vulnerability. This is worth stating plainly: the platform is not carrying hidden risk that would make starting M4 unsafe.

## Intentional Debt (correctly deferred, not a gap to "fix")

Per the ratified Blueprint and this project's own explicit scope discipline at every milestone: tax computation logic (pending the VAT question above); coupons/promotions (ratified M4 candidate, not yet built); support ticketing (ratified M5); notification system (ratified M6, narrow-scope only); `purchase_sessions`→`orders` rename (ratified M7, ADR-001); marketplace/creator/affiliate features (ratified M7, "explicitly not required for the current single-catalog business to launch"); chargeback handling (ratified M8, ADR-010). None of these are debt in the sense of an oversight - each was deliberately sequenced by the ratified roadmap and remains correctly unbuilt until its own milestone.

---

## What This Means for M4

No High or Critical item on this register blocks starting M4. The two items worth actively resolving *in parallel with* M4 (VAT escalation, `platform_users` migration planning) require no engineering time from whichever team builds M4's actual features - they are a Product Owner decision and a solo architecture-planning task, respectively. The one item this review recommends folding directly into M4's own scope, whatever M4 turns out to be, is closing the admin-panel test-coverage gap for the specific surface M4 touches - a repeat of the exact "don't let a self-imposed Testing Strategy bullet go unchecked" lesson this project has already learned twice (M2's and M3's own acceptance reviews both found test-coverage gaps that should have been caught internally first).
