# Version 3.2 - Sprint M4D - Recommendations

Consolidated, prioritized recommendations for Sprint M4E (Closeout & Production Readiness), derived from every deliverable in this review. Ordered by priority, not by which deliverable they came from.

---

## Must Close Before M4E Completes

1. **Add automated test coverage for the discount→receipt→PDF pipeline.** Extend `tests/unit/orderService.test.ts` with a case passing a nonzero `discountPesewas` into `createOrderArtifacts()`, asserting `subtotalPesewas`/`receipts.discount_pesewas`/`receipts.total_pesewas` are all correct. Add a direct unit test for `renderReceiptPdf()` asserting the discount line is present when `discountPesewas > 0` and absent when `0`. This is the single most important open item from this review - financial-record-generation code, in a file with a real, prior bug (the M2C MAR closeout rounding-drift fix) in this exact area.
2. **Add a rollback-strategy section to `v3.2-m4c-database-changes.md`**, matching the M2 precedent (`v3.0.2-m2-database-planning-report.md`'s own rollback section, referenced from migration 0019's header comment).
3. **Add the Customer Journey Validation's required disclosure to `v3.2-m4c-known-limitations.md`**: Reviews launches with no automated post-purchase collection trigger until M5's own trigger ships - stated explicitly, as M4B required, not left implicit.

## Should Close Before M4E Completes

4. Add a short UX-design rationale note (even a paragraph) documenting the Reviews empty/sparse-launch-state decision as its own traceable artifact, closing the Amendment 3 (M4B's #3) documentation gap directly rather than only via the Known Limitations disclosure above.
5. Extend `checkFirstPurchaseOnlyViolation` test coverage to cover the actual violation-detected case, not only the no-violation cases.
6. Reconcile the M4C document filenames against any future review sprint's own "Mandatory Review" list - either rename to match, or (this Board's actual recommendation) explicitly ratify the `m4c`-infixed convention in a short note so a future reviewer isn't left guessing which side is correct.

## Track for a Future Milestone (Not M4E's Responsibility)

7. Build a reusable local-dev admin-account bootstrap/seed utility (a real gap this review and the implementation both hit independently) - would benefit every future milestone's own admin-UI browser verification, not just M4's.
8. Add a numeric text equivalent to `admin-reviews.js`'s star-rating column for screen-reader clarity (minor, admin-only, non-blocking).
9. Independently re-verify light-mode contrast and the tablet (768×1024) viewport for the new Reviews/Coupons UI with working tooling, closing the verification-method gap this review's own UX & Accessibility Review disclosed honestly rather than glossing over.
10. Everything already correctly tracked in `v3.2-m4c-known-limitations.md` (admin product-dropdown scaling, no bulk admin actions, no dedicated "My Reviews" dashboard page) remains correctly deferred - no change recommended to that document's existing scope-boundary items.

## Process Recommendation

M4B's own required-amendments list should be treated as the authoritative amendment count for any milestone with a multi-sprint governance chain (M4A → M4B → M4C → M4D, in this milestone's case) - this review found that M4C's own brief silently dropped one of M4B's four amendments (the UX sparse-state design requirement) when restating its own Phase 1 checklist as "Amendment 1/2/3." No harm resulted here (the underlying behavior shipped correctly regardless), but a future milestone should not rely on each sprint's own restatement of a prior sprint's requirements - it should re-read the prior sprint's own primary document directly, the same discipline this Board applied in writing this review.

---

## Summary

Nothing in this list blocks M4's acceptance. Every item is closeable within M4E's own stated scope ("Closeout & Production Readiness") without new feature work, new architecture, or new scope - exactly the kind of finding a Closeout sprint exists to absorb.
