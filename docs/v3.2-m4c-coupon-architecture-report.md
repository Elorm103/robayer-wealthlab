## Purpose

This report documents the coupon engine's architecture as actually built, for anyone extending or reviewing it later. It restates the two decisions that shape everything else - platform-wide-only scope, and two-phase redemption - and traces how a coupon code moves through the system from a visitor's keystroke to a locked, audited discount.

## Scope Decision: Platform-Wide Coupons Only

M4B's Amendment 1 required removing the original design's `scope`/`creator_id` columns, which existed to distinguish a "platform" coupon from a "creator" coupon in a multi-seller marketplace this codebase does not have and has no near-term plan to build (see `docs/v3-marketplace-governance.md`'s own open questions, still unresolved as of this sprint). The corrected schema has no scope concept at all: every coupon is created by an admin (`created_by REFERENCES admin_users(id)`) and is either platform-wide (`product_id IS NULL`) or scoped to exactly one product (`product_id` set). There is no path to a creator-owned coupon, because there is no creator role in this codebase's authorization model. If a marketplace is ever built, this table will need a real redesign at that time, not a bolted-on flag - the same reasoning M4B's own review applied.

## The Discount Computation

`computeDiscountPesewas(discountType, discountValue, amountPesewas)` is the one function that ever turns a coupon into a pesewa amount, and it is pure - no D1 access, easy to unit-test exhaustively (see `couponService.test.ts`). Two rules, both defensive:

- **Percentage**: `Math.round((amountPesewas * discountValue) / 100)`, capped at `amountPesewas` - a 100%-off coupon discounts the full price, never more.
- **Fixed**: `discountValue` directly, capped at `amountPesewas` - a GH₵50-off coupon on a GH₵39 product discounts GH₵39, never produces a negative charge.

This function is called from exactly two places: `validateCoupon()` (preview) and, again, independently, inside `createCheckoutSession()` at the moment the amount is actually locked. The client never supplies a discount amount at any point - only a `couponCode` string. This is not a new invariant; it is `routes/checkout.ts`'s pre-existing "never accept price, currency, or title from the client" rule, extended to cover the one new input surface M4 adds.

## The Two-Phase Redemption Design

This is the sprint's central architectural decision, and the one Amendment 2 specifically required a security review to justify before it was built. The problem: a coupon with `max_redemptions = N` is the first resource in this codebase's history where two customers can legitimately race for the same limited thing, with real money already in flight by the time the race matters.

**Phase 1 - `validateCoupon()`, non-mutating.** Called twice: once by the public discount-preview endpoint (before checkout even starts, purely to show the visitor "-GH₵5.00" before they commit), and once inside `createCheckoutSession()`, immediately before the discounted amount is locked into `purchase_sessions`. Both calls check `redemptions_count < max_redemptions` as a soft, best-effort gate - it can be stale by the time payment actually happens, and that staleness is accepted, not treated as a bug.

**Phase 2 - `redeemCoupon()`, called exactly once, only after payment is confirmed.** From `commerceService.ts`'s `handlePaymentWebhook()`, immediately after `verifySessionAtomic()` has already succeeded - never before, never speculatively. It does two things:

1. An atomic, conditional `UPDATE coupons SET redemptions_count = redemptions_count + 1 WHERE id = ? AND (max_redemptions IS NULL OR redemptions_count < max_redemptions)`. Whether this update actually changes a row (`result.meta.changes === 1`) is the *only* authoritative answer to "did this redemption count against the limit" - D1's own atomicity is what makes this race-safe, not application-level locking.
2. An unconditional `INSERT INTO coupon_redemptions` - always executed, regardless of whether step 1's increment won or lost.

Why always record the redemption even when the limit was already reached? Because **the payment already happened.** This service follows the same discipline `commerceService.ts` already established everywhere else in this codebase: once money has genuinely moved, nothing downstream is allowed to pretend it didn't, or to reverse it, because of a bookkeeping race that has nothing to do with whether the charge was real. The customer who "lost" the race still paid the discounted price they were shown; taking that away from them after the fact would be a worse outcome than a coupon being redeemed 101 times instead of 100. The loser is recorded via a `logger.error('coupon.redemption_limit_race', ...)` call - a real anomaly worth an admin's attention, not a silent no-op, but never a blocked or reversed sale.

`tests/integration/couponRaceConditions.test.ts` verifies this exact scenario with true HTTP concurrency (`Promise.all`, two real webhook deliveries, not sequential awaits): both payments verify successfully, `redemptions_count` never exceeds `max_redemptions`, and both redemptions are still recorded in `coupon_redemptions`.

## `first_purchase_only`: Best-Effort by Necessity

A `first_purchase_only` coupon cannot be enforced *before* payment in this codebase's guest-checkout architecture, because the customer's real identity (their email) is not known until Paystack's webhook confirms it - `createCheckoutSession()` runs before any customer record necessarily exists. `checkFirstPurchaseOnlyViolation()` therefore runs *after* customer provisioning, inside the webhook handler, and only ever logs (`coupon.first_purchase_only_violated`) if the now-resolved customer turns out to have a prior verified purchase. It never blocks or reverses the sale already in progress. This mirrors the ARB's own prior, explicit acceptance of this exact risk category from the original V3.0 checkout architecture review - not a new gap this sprint introduced.

## Data Flow: A Coupon-Discounted Purchase, End to End

1. Visitor types a code into `#purchase-coupon-code` on the product page and clicks Apply. `buy-button.js` calls `POST /api/coupons/validate` (public, rate-limited, non-mutating) and shows the computed discount.
2. Visitor clicks Buy. `buy-button.js` sends the same code (previewed or not - an un-previewed code is never dropped) as `couponCode` in the `POST /api/checkout/sessions` body.
3. `createCheckoutSession()` calls `validateCoupon()` again, independently. If valid, `discountPesewas` is subtracted from the catalog price and the resulting `amountPesewas` - the actual amount that will be charged - is what gets locked into `purchase_sessions` (along with `coupon_id` and `discount_pesewas`) and what Paystack is told to charge.
4. Customer pays. Paystack's webhook fires. `verifySessionAtomic()` confirms the payment and cross-checks the verified amount against the locked `amount_pesewas` - the same safety-critical check this codebase already applies to every purchase, unaffected by whether a coupon was involved.
5. `redeemCoupon()` runs (Phase 2, above), then `checkFirstPurchaseOnlyViolation()` if applicable.
6. `createOrderArtifacts()` builds the receipt: `subtotal_pesewas` recovers the original, pre-discount price (`amountPesewas + discountPesewas`); `discount_pesewas` is stored as its own column; `tax_pesewas`/`total_pesewas` are computed from the actual, already-discounted `amountPesewas`, exactly as before M4. The downloadable PDF receipt renders a "Discount: -X" line whenever `discountPesewas > 0`.

## Immutability After Creation

`updateCoupon()`'s input type only ever accepts `status`, `maxRedemptions`, and `expiresAt` - code, discount type, discount value, and product scope are not part of the type at all, not merely validated-and-rejected. This is deliberate: a coupon code may already have been shown to a customer by the time an admin wants to change something about it, and silently changing what "SAVE10" means after the fact would be confusing at best and exploitable at worst (an admin could otherwise redefine an already-distributed code's discount value after seeing who used it). Deactivating and creating a new coupon is the correct path for a genuine correction.
