# Version 3.4 Milestone M6: Production Publishing Verification Report

Scope: prove, for every editable content type, that the path Admin to Database to Production Website to Customer happens in real time, with no git commit, Cloudflare deployment, Worker redeployment, manual cache clearing, or service restart. Where a dependency remains, it is documented and justified rather than hidden, per the brief's explicit instruction.

## 1. Caching discipline that makes immediacy possible

Every D1-backed public read route (`backend/routes/books.ts`, `blog.ts`, `resources.ts`, `branding.ts`, and this milestone's new `hero.ts`) sets `Cache-Control: no-store` on its response. This is a deliberate, previously-established policy, not new to this milestone: `books.ts`'s own header comment (lines 75-87) documents it as a fix found during an earlier adversarial review, specifically so an admin editing a price or publishing a product has no caching-related delay before it is visible. This is contrasted, correctly, against `routes/media.ts`'s deliberate opposite choice (`public, max-age=31536000, immutable`) for UUID-keyed media files, which genuinely never change once uploaded (a new upload gets a new key, it never overwrites an old one). The two policies are each correct for what they serve; neither is a bug.

## 2. Direct verification performed this milestone

Rather than relying on reading the caching headers alone, this milestone performed a live, empirical test of the exact "Admin to Database to Production Website to Customer" path for the new `hero_content` field, using a local instance of the same D1 schema and Worker code that runs in production:

1. Inserted a `hero_content` row directly into the local D1 instance via `wrangler d1 execute --local`, simulating an admin save (this is exactly the write `PATCH /api/admin/settings` performs, minus the HTTP/auth layer, which was already exercised for every other `site_settings` key in prior milestones).
2. Reloaded the homepage in a live browser preview with no server restart, no cache clear, and no redeploy between steps 1 and 2.
3. Confirmed the new headline, subheading, eyebrow, and both CTA buttons' text and `href` attributes reflected the new database value immediately.
4. Deleted the test row afterward to restore the default state.

This is direct, empirical proof for this specific field, not an inference from the caching header alone. The same underlying mechanism (`GET /api/hero`, `no-store`, client-side fetch on `partials:loaded`) is what every other D1-backed public field already uses, so this test also stands as confirmation of the general mechanism, already relied upon for products, blog posts, resources, and branding slots in prior milestones.

## 4. Where a real dependency on deployment remains, and why

### 4.1 The static site itself (GitHub Pages)

The HTML, CSS, and JavaScript files that make up the site (every page's markup, every `<script>` tag, every CSS rule) are served from GitHub Pages, confirmed live via `curl -sI https://robayerwealthlab.com/` returning GitHub's own `x-github-request-id` response header and a `Cache-Control: max-age=600` (a 10-minute edge cache). Any change to the actual HTML/CSS/JS (for example, this milestone's hero markup restructuring, or the new `data-content` attributes) requires a real deploy: a git push to the branch GitHub Pages builds from.

This is a correct, justified architectural boundary, not an oversight: GitHub Pages has no server-side execution, so it cannot read `site_settings` at request time the way the Worker's D1-backed routes can. This is exactly why this milestone's hero content fix works the way it does: the markup ships once (via deploy), and that markup's own client-side JavaScript then fetches the live D1 value on every page load. The content is immediate; the container that fetches it is not, and cannot be, without a fundamentally different hosting architecture (moving the static site itself behind the Worker, which is a materially larger architectural change than this milestone's scope, and not recommended purely to shave 10 minutes off a rare markup change).

### 4.2 Email template body copy

The 13 email templates are bundled into the Worker at build time (`wrangler.jsonc`'s `[[rules]] type = "Text"`, since Workers have no runtime filesystem to read `backend/emails/*.html` from). Changing an email's wording requires editing the file and deploying the Worker. This is a genuine, currently-real dependency, not eliminated this milestone. Eliminating it would require a template-editor admin UI storing template bodies in D1 instead of the filesystem, which is a materially larger feature than a slot-wiring fix and is recommended as future scope (see the Final Release Recommendation), not attempted here.

### 4.3 Navigation and footer structure

As detailed in the CMS Architecture Audit Report, no admin mechanism exists at all for the nav menu or footer link structure; both are static HTML. This is not a caching-related delay to eliminate; it is a missing feature. Recorded here for completeness, cross-referenced to the architecture and inventory reports rather than duplicated in full.

## 5. Conclusion

For every content type that already has an admin-editing mechanism, the publishing path was confirmed immediate, either by direct empirical test (hero content, this milestone) or by the pre-existing `no-store` discipline already covering products, blog, resources, and branding. The two remaining deployment dependencies (the static site container itself, and email template body copy) are structural, correctly justified, and explicitly documented rather than hidden, matching the brief's explicit instruction to eliminate the dependency where practical and document it honestly where not.
