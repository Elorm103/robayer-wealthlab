# Version 3.3 Sprint M5D.1: Review Reminder Concurrency Design

Documents the corrected architecture for `services/customer/reviewReminderService.ts`, replacing the design Sprint M5D found to be Blocking.

---

## Problem Recap

Cloudflare Cron Triggers are documented as at-least-once delivery, for every plan tier. Sprint M5D reproduced two concrete failures in the original (Milestone M5C) design, which relied solely on a `NOT EXISTS` check against `email_log`:

1. A single failed send (any status other than a clean success) still wrote an `email_log` row, which permanently satisfied the "already attempted" check — the purchase was never retried, and the customer never received the reminder, silently.
2. Two genuinely concurrent `scheduled()` invocations both read "eligible" before either had written anything, and both sent — a duplicate email.

## Corrected Architecture

A new table, `review_reminder_attempts` (migration `0022`), is the single source of truth for "has this purchase been reminded, is it currently being attempted, or has it permanently failed" — replacing `email_log` in that role. `email_log` itself is unchanged and still receives a row for every send attempt (for its own, unrelated audit/diagnostics purposes — e.g. `settingsService.ts`'s per-template send/fail/skip counts), but it is no longer what `reviewReminderService.ts` reads to decide eligibility.

### Why a dedicated table, not a change to `email_log`

`email_log` is generic and multi-purpose: the same `(entity_type, entity_id, template)` triple legitimately recurs for other templates today (a customer-initiated receipt resend reuses the same `purchase_session_id` under `'purchase-receipt'`). Adding a uniqueness constraint there to solve this one template's problem would risk breaking that unrelated, already-working feature. A narrow, purpose-built table carries no such risk and makes the state machine (`claimed` → `sent` | `failed` | `permanently_failed`) explicit rather than inferred.

### State Machine

```
                 ┌─────────────┐
   (no row) ────►│   claimed   │
                 └──────┬──────┘
                        │
          ┌─────────────┼──────────────┐
          ▼             ▼              ▼
     ┌────────┐   ┌───────────┐  ┌──────────────────┐
     │  sent  │   │  failed   │  │ permanently_failed│
     │(terminal)  │(retry-able)│  │   (terminal)      │
     └────────┘   └─────┬─────┘  └──────────────────┘
                        │
                        │ next scheduled run,
                        │ if not yet at MAX_SEND_ATTEMPTS
                        ▼
                 ┌─────────────┐
                 │   claimed   │  (attempt_count + 1)
                 └─────────────┘
```

`claimed` is also reachable FROM `failed` (a genuine retry) and, in the narrow case of an invocation crashing mid-attempt without ever settling the row, from a stale `claimed` row older than `CLAIM_STALE_MINUTES` (10 minutes — comfortably longer than any single Worker invocation's own CPU/wall-time budget).

### The Atomic Claim

```sql
INSERT INTO review_reminder_attempts (purchase_session_id, status, attempt_count, claimed_at)
VALUES (?, 'claimed', 1, ?)
ON CONFLICT(purchase_session_id) DO UPDATE SET
  status = 'claimed',
  attempt_count = review_reminder_attempts.attempt_count + 1,
  claimed_at = ?,
  completed_at = NULL
WHERE review_reminder_attempts.status = 'failed'
   OR (review_reminder_attempts.status = 'claimed' AND review_reminder_attempts.claimed_at <= ?)
```

D1 (like the SQLite it is built on) serializes writes to the same row. Of two concurrent invocations attempting this statement for the same `purchase_session_id`, only one can ever see `meta.changes === 1` — the other sees `0` and moves on without sending. This is the same atomic-UPDATE-then-check-`meta.changes` idiom already used throughout this codebase (`authService.ts`'s `setPassword()`, `sessionService.ts`'s `revokeSession()`, `unsubscribeService.ts`'s `consumeTokenAtomic()`), applied here for the first time to a multi-row batch scenario.

### Settling an Attempt

After `sendEmail()` returns, the claim is settled based on its own existing `permanentFailure` signal — no new failure-classification logic was invented; the existing distinction (a 4xx-rejected recipient is permanent, anything else retryable) is reused directly:

- `result.sent === true` → `status = 'sent'` (terminal).
- `result.sent === false` and (`result.permanentFailure` or the attempt count has reached `MAX_SEND_ATTEMPTS = 3`) → `status = 'permanently_failed'` (terminal), and a new `customer.review_reminder_failed` audit log entry is written — closing the audit-visibility gap Sprint M5D also found (a failed send previously left zero trace anywhere).
- Otherwise → `status = 'failed'` (retry-eligible on a later scheduled run).

### A Real Bug Found and Fixed During This Same Remediation

The first implementation of this design used SQL's own `datetime('now')` for `claimed_at`, compared against a JS-computed `.toISOString()` staleness cutoff. Direct testing (`datetime('now') < '2026-07-26T00:00:00.000Z'` evaluating `true` even when chronologically later that same day) proved this comparison was silently broken: SQLite's `datetime('now')` produces `"YYYY-MM-DD HH:MM:SS"` (a space, no milliseconds, no `Z`), while `new Date().toISOString()` produces `"YYYY-MM-DDTHH:MM:SS.sssZ"` — and because `' '` (0x20) sorts before `'T'` (0x54), a same-day SQL-formatted timestamp always compares as "earlier" than a JS-ISO one, regardless of actual time. This meant every `'claimed'` row was always treated as stale, and the very race this design exists to prevent still occurred. Fixed by computing `claimed_at`/`completed_at` in JS and binding them as parameters throughout, matching `sessionService.ts`'s own established, correct convention (never mix SQL-generated and JS-generated timestamps on either side of a comparison). See `docs/v3.3-m5d1-retry-idempotency-strategy.md` for why this matters more broadly than just this one fix.

## Verification

- Independently reproduced live via `wrangler dev --test-scheduled`: two genuinely concurrent HTTP-level scheduled-trigger requests against a single due purchase resulted in exactly one `review_reminder_attempts` row with `attempt_count = 1` — not two.
- 5 new permanent regression tests (`tests/unit/reviewReminderService.test.ts`) cover genuine concurrency, transient-failure retry-and-recovery, the `MAX_SEND_ATTEMPTS` cap, immediate permanent-failure classification, and repeated sequential execution after a success. See `docs/v3.3-m5d1-regression-test-report.md`.
