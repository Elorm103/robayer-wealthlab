## Review of New Tests

## Gap Found in New Test Coverage

**None of the 37 new tests exercise genuine concurrent (`Promise.all`) invocation of either `reconcilePurchases()` or `sendDueReviewReminders()`.** The existing `reconciliationService.test.ts`'s own "duplicate prevention" test and `reviewReminderService.test.ts`'s own "one reminder per purchase" test both call the function under test twice **sequentially**, `await`ing the first call's completion before starting the second — a materially different, and materially easier, scenario than genuine concurrency. This project's own pre-existing `identityService.test.ts` already established the correct pattern for testing this class of risk (`Promise.all([findOrCreateCustomer(...), findOrCreateCustomer(...)])`, explicitly labeled "genuine concurrent double insert"), but that pattern was not applied to either new concurrency-sensitive function in M5C. This Board applied it directly (via a temporary, since-deleted verification test) and it is what surfaced both the Blocking review-reminder finding and the Non-blocking reconciliation finding documented elsewhere in this package.

**Recommendation:** add a genuine `Promise.all`-based concurrency test for both functions to the permanent suite, following the existing `identityService.test.ts` precedent, once the underlying idempotency fix (Review Reminder Validation Report) is applied — a regression test that would have caught this before this milestone's review, and should prevent its reintroduction.

## Review of Bugs Fixed During M5C

Two genuine bugs were found and fixed during M5C's own implementation, disclosed in its Test Results doc. This Board independently re-verified both:

1. **Repeat-purchase same-second tiebreak.** Confirmed the root cause is real (`datetime('now')` has one-second resolution; two same-second purchases previously tied and neither counted as a repeat). Confirmed the fix (`id` as a tiebreaker) is correct — this Board independently re-derived the same result via a hand-seeded, exact-duplicate-timestamp scenario against the live endpoint (see the Analytics Validation Report), not merely by re-reading the unit test that originally caught it. **Fix confirmed correct.**
2. **Test-file cleanup ordering.** A test-infrastructure-only defect (a `beforeEach` deleting `customers` before clearing FK-referencing child rows from an earlier `describe` block). Confirmed the fix (adding the missing cleanup statements) is correct and the full suite passes cleanly. **Fix confirmed correct**, and correctly scoped as a test-only fix with no product-code implication.

## Verdict

**The existing test suite is genuine, well-targeted, and its own claims (258/258, tsc clean) independently reproduce exactly.** The one material gap is the absence of genuine-concurrency testing for the two functions where it matters most, which is precisely where this review's own additional (temporary, now-removed) testing found this package's Blocking and Non-blocking findings. This gap should be closed permanently, not just noted, before this feature's Cron Trigger is enabled in production.
