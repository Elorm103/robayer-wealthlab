# Version 3.2 - Sprint M4B - Architecture Approval Report

**Independent Architecture & Product Review Board** - Chief Solutions Architect, Chief Product Officer, Principal Software Architect, Principal Frontend Engineer, Principal Backend Engineer, UX Architect, Security Architect, QA Lead, Business Strategy Lead, Release Governance Chair.

**Reviewer posture:** This review did not treat the M4A planning package's own conclusions as correct because they were produced. All eleven M4A documents were read in full. The actual production codebase was independently inspected (route files, `worker/index.ts`'s route table, `backend/database/schema.sql`, `commerceService.ts`'s amount-computation logic, the referenced `v3-database-design.md` coupon schema, the current test suite). Actual production data was independently queried, read-only, to verify two specific empirical claims M4A made without citing evidence (support-request volume, real-customer/purchase counts).

---

## Executive Summary

M4A recommended M4 = Product Reviews + Coupon Engine, deferring the course-platform cluster behind a cheap evidence-gathering step in M6, and recommended re-sequencing M5 (Retention & Engagement pulled ahead of the ratified Support Ticketing slot). This Board's independent review **confirms the overall recommendation is sound and, in two places, independently verifies it more strongly than M4A itself demonstrated**: production data confirms near-zero support-request volume (justifying the M5 re-sequencing) and zero course-demand signal of any kind (justifying the course-platform deferral), neither of which M4A cited with actual data.

**This Board also found one genuine, concrete defect in the M4A package**: the coupon schema M4A cites as "already fully designed... ready to implement as-is, no new design work needed" (`docs/v3-database-design.md`) references a database table, `platform_users`, that does not exist in the current production schema and is gated behind an unplanned future migration (ADR-011). This schema cannot be implemented as written. A new, simplified, platform-scope-only coupon schema must be designed before implementation - real but small, contained work, not a reason to change M4's feature selection. This finding also revealed that M4A understated the engineering risk of Coupons: implementing it requires modifying `commerceService.ts`'s payment-amount-locking calculation, the code path this project's own security reviews have consistently identified as the single most safety-critical boundary in the system.

Every other claim in the M4A package - the Architecture Review's route/schema/frontend feasibility analysis, the Prioritization Matrix's scoring of the other 20 candidate features, the Customer Journey Analysis, the Technical Debt Register consolidation - was independently checked and confirmed accurate.

**Final decision: Option B - M4 Scope Approved with Required Amendments.** See Section 14.

## Summary of Required Amendments (Blocking for M4C start, not for this approval)

1. **Produce a corrected, simplified `coupons`/`coupon_redemptions` schema** (platform-scope only, no `creator_id`/`scope`, referencing `admin_users`) before implementation begins - see Architecture Readiness Assessment for the exact correction.
2. **M4C's Security Review must treat the payment-amount-locking/webhook-verification change as its primary focus area**, not an incidental item - see Risk Review.
3. **M4C's UX planning must explicitly design Reviews' empty/sparse launch state** (near-zero real customers/purchases today means near-zero reviews at launch) - see Product Strategy Review and Customer Journey Validation.
4. **Admin-panel test coverage for the two new admin surfaces (review moderation, coupon management) is a hard requirement of M4C's own Testing Strategy**, not merely recommended - see Technical Debt Assessment.

## Non-Blocking Observations

- Wishlist's ADR-006 tension deserves the same governance weight as ADR-006 itself received, if it proceeds in M5 - a process recommendation, not a blocker for M4.
- M4A's own documents (`v3.2-m4-scope-recommendation.md`, `v3.2-m4-feature-prioritization-matrix.md`) should be corrected to remove the "no new design work needed" / "zero open design questions" language for Coupons, so a future reader isn't misled by the uncorrected original claim.
- The VAT-registration question has now been carried across seven consecutive planning passes; this Board adds a stronger recommendation than "escalate again" - see Technical Debt Assessment.

## Final Decision

## Option B: M4 Scope Approved with Required Amendments

**No Blocking finding prevents approving M4's overall scope** (Reviews + Coupons, deferring the course-platform cluster, re-sequencing M5 ahead of Support Ticketing). Every Required Amendment listed above is a correction to implementation-level detail, not a change to *what* M4 should build - the feature selection, the prioritization logic, and the roadmap sequencing all survive independent, evidence-based challenge intact, and in two places (M5's justification, the course-platform deferral) this Board's own data collection makes the case *stronger* than the original planning package presented it.

**Is the project ready to proceed to Sprint M4C - Reviews & Coupons Implementation?**

**Not directly to full implementation - one short, focused technical correction should come first.** This Board recommends M4C begin with (or be immediately preceded by) a brief technical-planning step that produces: the corrected coupon schema, and an explicit note in M4C's own Security Review scoping that the payment-amount-locking change is the milestone's primary risk-review focus. This is consistent with how this project has always operated - M1, M2, and M3 each had a dedicated detailed-planning pass before implementation began, and M4A (the strategic-level roadmap this Board just reviewed) was explicitly strategic, not implementation-detail-level, by its own design. Once that short correction is produced (small enough to fold into M4C's own opening work, not a reason for a separate lettered sprint), **implementation may proceed.**

Every non-blocking observation above should be tracked and addressed during M4C/M4D, not before M4C begins.
