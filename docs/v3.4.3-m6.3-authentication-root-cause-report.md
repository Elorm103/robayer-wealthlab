# Version 3.4.3 M6.3: Authentication Root Cause Report

## Summary

Customers could never sign in, and reviews could never be submitted, because no real customer account ever received a working password. This was not a bug in the authentication code itself. Every authentication function (login, forgot password, set password, session issuance) worked correctly whenever it was given real data. The defect was one step upstream: the checkout flow never captured a real customer email, so the password setup email that every account depends on was always sent to an address no human could read.

## Trace: purchase to password to sign-in

```
Purchase (RWL-2026-000046, live Paystack mobile money payment)
  -> Customer auto-provisioned (customers.id = 9)
  -> customer_password_tokens row created at the same instant (id 9,
     token issued, 30 minute expiry)
  -> "customer-welcome" email queued, rendered, sent to Resend,
     accepted, logged as "sent" -- to checkout+rwl-2026-000046@robayerwealthlab.com
  -> Real customer never receives this email (they do not control that
     inbox)
  -> Real customer never redeems the token
  -> customers.password_hash stays NULL indefinitely
  -> Sign-in impossible (no password exists to check)
  -> Review submission impossible (requireCustomerAuth fails before
     the review-ownership check is ever reached)
```

Every link in this chain was independently verified against production data and production code:

- `customers` row 9: `password_hash: null` at time of investigation, confirming no password had ever been set.
- `customer_password_tokens` row 9: created at `2026-07-31 18:26:32`, the exact same second as the purchase, `used_at: null`, confirming the token was issued but never redeemed.
- `backend/services/customer/authService.ts`'s `issuePasswordToken()`: correctly builds the setup URL and sends the email; no defect found here.
- `backend/routes/customer/reviews.ts`'s `handleSubmitReview()`: calls `requireCustomerAuth()` first, before any ownership or eligibility check; a customer with no session can never reach the purchase-ownership logic. No defect found here either.

## Root cause

`services/payments/paystackProvider.ts` generated a synthetic placeholder email (`checkout+<purchaseReference>@robayerwealthlab.com`) and sent it to Paystack's `/transaction/initialize` call, on the documented assumption that Paystack's own hosted checkout page would prompt the buyer for their real email during payment. `verifyPayment()` then read back whatever email Paystack's `/transaction/verify` response reported and trusted it as the confirmed customer email.

That assumption held for card payments, where Paystack's hosted page does let the buyer enter or edit an email. It does not hold for the `mobile_money` channel. The real, live production purchase traced in this investigation was paid via MTN Mobile Money; Paystack's own transaction record for that charge (`payment_transactions.gateway_response`) shows `"customer":{"email":"checkout+rwl-2026-000046@robayerwealthlab.com", "phone": null, ...}` -- the placeholder, unchanged, because Paystack's mobile money flow never asked the buyer for an email at all. `verifyPayment()` therefore always echoed the placeholder straight back, and `commerceService.ts` correctly (and unavoidably) stored that placeholder as the "confirmed" customer email.

A check of every verified purchase in production confirmed this was not an isolated incident: 18 of 18 verified purchase sessions carried the exact synthetic placeholder pattern. No real customer email had ever been captured for any completed purchase.

## Fix

The real email is now collected on the site's own checkout form, the one channel-independent point every payment method passes through, before Paystack is ever contacted:

- `js/components/buy-button.js` now reads a required `#purchase-email` field and sends it as `email` in the checkout request. Basic format validation runs client-side as a fast fail; the server never trusts this.
- `routes/checkout.ts` validates the field with the existing shared `isValidEmail()` helper and rejects the request with `VALIDATION_ERROR` if missing or malformed.
- `services/commerceService.ts` re-validates server-side (defense in depth, matching the existing terms/license consent pattern), stores the real email on the `purchase_sessions` row immediately at checkout creation (not only after verification), and passes it to the payment provider.
- `services/payments/paystackProvider.ts` sends this real email to Paystack instead of a placeholder. The existing security posture is unchanged: `verifyPayment()`'s provider-confirmed email is still preferred whenever the provider offers a different one (e.g. a card payment where the buyer edits it on Paystack's page); the site-collected email is only ever the floor a channel with no such prompt falls back to.
- `verifySessionAtomic()`'s UPDATE now uses `customer_email = COALESCE(?, customer_email)` instead of an unconditional overwrite, so a null/absent provider-side email can never erase the real email already on file from checkout time.

This is a repair of the checkout architecture's own assumption, not a workaround layered on top of it. `ADR-002`'s "zero-form checkout" is not fully preserved: one required field was added. The alternative (continuing to have zero reachable customers for the market's dominant payment channel) was assessed as the greater defect.

## Live verification performed

- Confirmed the fix rejects a checkout request with no email or a malformed email (`VALIDATION_ERROR`, live `curl` against production).
- Confirmed a checkout request with a real email now stores that email immediately in `purchase_sessions.customer_email` at creation time (verified against the live database).
- Corrected the real, already-existing customer record (id 9) to use a real, monitored email, then exercised the full chain: forgot password, real reset token retrieved from the database (not fabricated), password set via the real `/api/customer/auth/set-password` endpoint, and sign-in via the real `/api/customer/auth/login` endpoint. All three succeeded and were confirmed against production responses.
- Confirmed the customer session issued by sign-in was then accepted by `POST /api/customer/reviews`, and a review was successfully created (`reviewId: 2`) for the product this customer actually purchased.

## Residual risk

Every verified purchase made before this fix (18 sessions) still has a synthetic placeholder email on file and no real customer will ever be reachable for those specific historical purchases unless they use "Recover purchase" with their real email (now that reconciliation works end to end -- see the Email Delivery Root Cause Report). This is a data-completeness gap for past orders, not an ongoing defect; no code change can retroactively invent an email that was never collected.
