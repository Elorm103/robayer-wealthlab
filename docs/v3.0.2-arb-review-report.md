# Robayer WealthLab — Version 3.0.2 Architecture Review Board (ARB) Report

**Subject of review:** [`docs/v3.0.2-commerce-architecture-blueprint.md`](v3.0.2-commerce-architecture-blueprint.md) ("the Blueprint")
**Review type:** Independent panel review — Principal Solutions Architect, Principal Software Engineer, Enterprise Architect, Product Manager, Security Architect, UX Architect, Database Architect, DevOps Architect, QA Lead, Technical Risk Manager.
**Status:** Design-only review. No code was written, no repository files outside `docs/` were touched, no commits were made.
**Independence note:** This review does not treat the Blueprint's prior reasoning as a starting presumption of correctness. Every finding below was re-verified against the live codebase and, where relevant, against operational documentation the Blueprint itself did not fully engage with (`docs/monitoring-and-alerting.md`, `docs/backup-and-recovery.md`) — several of this report's most material findings come directly from that re-verification, not from re-reading the Blueprint's own words back to it.

## Phase 1 — Executive Summary

**Overall architecture:** The Blueprint proposes a customer-identity and ownership layer (`customers`, `order_items`, `licenses`, `receipts`, `notification_queue`, `support_requests`) grafted onto an already-live, already-strong transaction spine (`purchase_sessions` → `payment_transactions` → `deliveries` → `download_tokens`), sequenced across eight milestones.

**Core philosophy:** Reuse proven patterns (admin session/auth machinery, snapshot-at-transaction-time discipline, thin-routes/services separation) rather than invent parallel ones; guest-first checkout with automatic, optional account provisioning after payment.

**Major strengths:** The panel concurs with the Blueprint's own assessment that the underlying transaction engine (idempotent webhooks, locked checkout-time pricing, single-use download tokens, paid-content isolation from the public media API) is genuinely production-grade — this was independently re-verified against the live schema and route code, not accepted on the Blueprint's word. The decision to extend proven admin-auth patterns to customers rather than build a second, parallel auth system is sound engineering judgment. The five-table new-entity design is coherent and, on the whole, well-normalized.

**Principal risks:** Three findings materially change the panel's confidence relative to the Blueprint's own self-assessment:

1. **The Blueprint's M6 milestone proposes introducing this project's first-ever Cloudflare Cron Trigger for automated email retry — without engaging with the fact that this project has *twice* deliberately declined to build exactly this** (`docs/monitoring-and-alerting.md`: "the originally planned... Cron Trigger... was never built... this project has zero Cloudflare Queues, Cron Triggers, or Durable Objects anywhere"; `docs/backup-and-recovery.md`: "no automated retry... this is a deliberate, documented trade-off... not a bug"). This is not a minor oversight — it is a live architectural tension between two documents that must be resolved before Sprint 2, not silently carried forward.
2. **The `purchase_sessions`-as-order-record decision, re-examined independently, shows real strain** once every future column from both this Blueprint and `docs/v3-database-design.md` is added to one table — a genuine "god table" risk the Blueprint did not weigh against the alternative it dismissed.
3. **Several Phase 8 items the Blueprint gestures at thinly** (account recovery without email access, multi-email identity, chargeback handling, license-revocation-on-refund synchronization) need to move from "acknowledged" to "specified" before implementation, not necessarily before Sprint 2, but before Live Mode.

**Long-term suitability:** With the above addressed, the panel judges this architecture genuinely suitable as a multi-year foundation — the marketplace-compatibility mapping in the Blueprint's Deliverable 9 holds up under scrutiny (see Phase 3), and no finding in this review requires reopening the core five-table design.

**Recommendation: Approve with Required Amendments.** Not Ready-as-written, not Not-Ready — the foundational shape is correct and the gaps found are specific, bounded, and addressable within the Blueprint's own milestone structure without a redesign. See Phase 12 for the full, prioritized amendment list.

## Phase 3 — Deep Technical Review of the Five Foundational Decisions

### Decision 1: Extend `purchase_sessions` instead of introducing a new `orders` table

**Why it was made:** A prior `orders` table existed in this codebase's history and was removed in migration 0008 as genuinely unused dead weight; `purchase_sessions` already functions as the order record in every service that touches it today.

**Benefits:** Avoids reintroducing exactly the ambiguity ("which table is the real order — `orders` or `purchase_sessions`?") that a prior team already resolved once. Zero migration of existing rows. Every existing service/query continues to work unchanged.

**Drawbacks — re-examined independently, and this is where the panel diverges from the Blueprint's confidence level:** `purchase_sessions` is now the accumulation point for: its own original ~15 columns, this Blueprint's `customer_id`, and — via `docs/v3-database-design.md`, which this Blueprint explicitly endorses composing with — `creator_id`, `affiliate_product_link_id`, `coupon_id`, `discount_pesewas`, `platform_commission_pesewas`, `creator_earnings_pesewas`, `affiliate_commission_pesewas`. That is a table doing pre-payment checkout-flow duty (`status='pending'`, `expires_at`) *and* permanent-financial-record duty *and* marketplace-commission-ledger duty, all at once. This is a real "god table" pattern, and the panel does not believe the Blueprint weighed this cost seriously against the alternative it dismissed.

**Alternative considered:** A genuinely separate `orders` table, created *only* at the moment `purchase_sessions.status` transitions to `verified` — `purchase_sessions` stays a purely transient, prunable, pre-payment-flow table (arguably even eligible for a retention policy that periodically archives old `pending`/`failed`/`expired` rows, which is presently impossible given the same table is also the permanent order record), and `orders` becomes the clean, permanent, ever-growing financial-and-marketplace record everything else (`order_items`, `licenses`, `receipts`) references.

**Panel determination: modify, don't reverse.** The migration-cost argument against reintroducing a second table is real and the panel does not recommend physically splitting the table in Sprint 2 — that would be a meaningfully larger, riskier piece of work than the gap it closes, given the current table's genuine adequacy for present scale. **But the naming and conceptual framing should change now, cheaply, while it's still just documentation:** every future reference to "the order" in code and docs should be understood as "the row in `purchase_sessions` after `status='verified'`," and the panel recommends the table be renamed in a future, low-urgency migration once the marketplace columns from `docs/v3-database-design.md` actually land (Milestone M7) — at that point, with real new columns being added anyway, is the natural, low-incremental-cost moment to also rename the table to reflect what it has become. Flagging this now, rather than after M7 ships, is what a review board is for.

### Decision 2: Guest checkout with automatic account creation after successful payment

**Why it was made:** Every additional pre-payment field measurably reduces conversion; Paystack's hosted page already collects a provider-confirmed email better than a custom form could.

**Benefits:** The panel strongly agrees with this decision and found no defensible alternative in its independent review. This is the single strongest decision in the entire Blueprint.

**Drawbacks:** None found at the checkout-flow level itself. The drawback surfaced by this review is not in the decision but in an underspecified consequence of it — see Phase 5's finding on immediate post-purchase access.

**Alternative considered:** Forced pre-payment registration (rejected by both the Blueprint and this panel — the conversion-cost evidence is not close), and a middle option of an *optional* "create account first" link before checkout (already accommodated by the Blueprint's design without needing to be built specially — a customer who logs in first simply already has a `customer_id` by the time they check out, no special-case code needed).

**Panel determination: unchanged.** This decision should stand exactly as specified.

### Decision 3: Maintain email-based purchase access while introducing customer accounts

**Why it was made:** The existing email-link download flow must never be broken for a customer who never sets a password — a stated, explicit non-negotiable in the Blueprint.

**Benefits:** Correct, and correctly prioritized — a regression here would be a genuine, serious harm to real paying customers, and the panel treats "never breaks the existing link" as a hard acceptance criterion for every milestone that touches this path, not merely a preference.

**Drawbacks:** None in the decision itself. A related gap the panel did surface: the Blueprint does not specify what happens to the email-link path if a `licenses` row is later `revoked_at` (refund) — does the old email link keep working? It should not, and the Blueprint doesn't say so explicitly. See Phase 4/8.

**Alternative considered:** Deprecating the email-link path once an account exists (rejected — correctly, in the panel's judgment; this would strand exactly the low-friction customers this platform is trying hardest not to alienate).

**Panel determination: unchanged, with one addition** — explicitly specify that download-token issuance must check `deliveries.status != 'revoked'` (already a valid value in the live schema's `CHECK` constraint) regardless of which path (email link or dashboard) requested it, and that a refund must set this. This is a one-line addition to the Blueprint's own existing entitlement model, not a new mechanism.

### Decision 4: Keep `customers` separate from `platform_users`

**Why it was made:** A hard schema boundary against privilege escalation, versus a single "users" table with a role flag that would require every authorization check to correctly filter out the customer role.

**Benefits:** The panel strongly agrees. This is a well-reasoned, defensible security boundary and the correct call for a platform that will eventually have creators, affiliates, and staff all needing meaningfully different capabilities than a customer.

**Drawbacks:** The one real cost — a customer who *later* becomes a creator or affiliate (explicitly anticipated by `docs/v3-database-design.md`'s own `user_roles` table, itself designed for exactly "an account that holds multiple roles") needs a defined bridging story: does that person end up with two separate rows (one in `customers`, one in `platform_users`) that must both exist and somehow be linked, or does becoming a creator involve a distinct "upgrade" flow? The Blueprint doesn't address this composition point, and neither did `docs/v3-database-design.md`, since it was written before `customers` existed as a concept at all.

**Alternative considered:** A single unified identity table with a `user_roles`-style capability system from day one (rejected by the panel too — this would have required designing the full marketplace identity model now, disproportionate to a Version 3.0.2 sprint whose actual gap is customer-side).

**Panel determination: unchanged, with an explicit open question flagged for M7 (Marketplace Schema Activation), not for Sprint 2** — when `platform_users`/`user_roles` is actually implemented, that milestone must specify the customer-becomes-creator bridging mechanism (most likely: a `platform_users` row referencing `customer_id`, linking the two identities without merging them) before it ships, not as an afterthought.

### Decision 5: Sequence customer identity before coupons, promotions, and support

**Why it was made:** Every one of those features needs a customer or order to attach to; building them first would mean rebuilding them once identity exists.

**Benefits:** Correct sequencing logic, and the panel independently re-derived the same dependency graph — M4 (coupons) genuinely does depend on M1 for `first_purchase_only` logic to mean anything, and M5 (support) genuinely benefits from `customer_id`-linked tickets from day one rather than retrofitting the link later.

**Drawbacks:** None found — this is straightforward, correct dependency-ordering, not a contestable design choice.

**Alternative considered:** Building coupons first, since it's the smallest, most self-contained piece and could ship fastest (rejected — correctly; "fastest to ship" is not the same as "right to ship first," and the panel agrees a coupon system built against a customer-less checkout would need real rework, not just extension, once identity lands).

**Panel determination: unchanged.**

## Phase 7 — Operational Review

This is where the review's most material finding lives.

**Finding — Maintainability/Deployment/Migration complexity:** The Blueprint's new tables follow this project's own established migration conventions correctly (additive, `CHECK`-constrained, snapshot-discipline) — re-verified against the live schema's own conventions. No concern here.

**Finding — the `platform_users` rename (M7), inherited from `docs/v3-database-design.md`:** `ALTER TABLE admin_users RENAME TO platform_users` touches the identity table every single admin-auth code path in production depends on. SQLite table renames are cheap at the storage layer, but this is still a single migration with unusually wide blast radius (every `admin_users(id)` foreign key reference across `products`, `blog_posts`, `resources`, `consultation_requests`, `contact_messages`, `email_log`-adjacent tables, `site_settings`, and the admin-auth system itself, all confirmed present in the live schema). Neither the original blueprint document nor `docs/v3-database-design.md` proposes a specific migration/rollback strategy for this one step specifically (e.g., a maintenance-window requirement, a staged dual-read period, or a same-deploy code+migration coupling requirement).

**Finding — the observability/retry contradiction (the review's single most material finding):** `docs/monitoring-and-alerting.md` states plainly: "this project has zero Cloudflare Queues, Cron Triggers, or Durable Objects anywhere" and explicitly declines third-party observability tooling as disproportionate to this project's real scale. `docs/backup-and-recovery.md` independently confirms the *absence* of email-retry automation was a **deliberate, previously-documented decision**, not an oversight ("not a bug"). The Blueprint's M6 milestone proposes reversing that decision — introducing the project's first-ever Cron Trigger — without citing either document or engaging with the reasoning behind the original decision at all.

This does not mean M6 is wrong. A failed *purchase-receipt or download-ready* email is a materially higher-stakes failure than a failed newsletter send (the case the original "proportionate to scale" reasoning was likely calibrated against) — a real argument exists that commerce-critical transactional email deserves automation that marketing email doesn't, and Live Mode (real money) changes the proportionality calculation the original documents were written under. But that argument needs to be made explicitly, on the record, superseding the prior documented decision deliberately — not silently contradicted by a milestone that doesn't acknowledge the prior decision exists.

**Finding — no error-tracking/APM tool integrated (Sentry or equivalent).** Consistent with `docs/monitoring-and-alerting.md`'s explicit, reasoned position that this is disproportionate at current scale. The panel does not recommend introducing one now, but notes that "thousands of customers" (the Blueprint's own stated target) is exactly the scale threshold at which that calculus should be revisited — not a Sprint 2 item, but worth a named trigger condition ("revisit if/when X") rather than an indefinite deferral.

**Upgrade strategy / future maintenance costs:** The panel finds no elevated concern beyond what's already noted above — the additive-migration discipline this codebase already practices keeps ongoing maintenance cost proportionate.

## Phase 10 — Architecture Decision Records

### ADR-001: Extend `purchase_sessions` rather than introduce a new `orders` table (with a scheduled rename)

- **Status:** Accepted, with a scheduled follow-up.
- **Context:** A prior `orders` table existed and was removed as dead weight in migration 0008; `purchase_sessions` already functions as this project's order record.
- **Alternatives considered:** (a) A genuinely separate `orders` table created only at verification, leaving `purchase_sessions` as a purely transient pre-payment table. (b) Status quo, unmodified.
- **Rationale:** The migration cost and conceptual-clarity cost of reintroducing a second table outweighs the naming imprecision of keeping one — but only if the naming imprecision is acknowledged and scheduled to be resolved, not left permanent.
- **Consequences:** `purchase_sessions` will continue accumulating fields from both this document and `docs/v3-database-design.md`. A rename to reflect its true role is scheduled for Milestone M7, when new columns are being added anyway.
- **Future implications:** If, by M7, the table has grown to the point that even a rename feels insufficient (i.e., query performance or genuine conceptual confusion has become a real operational problem, not just a naming one), this ADR should be revisited and the physical-split alternative reconsidered at that time, informed by real usage data this review cannot yet have.

### ADR-002: Guest checkout with automatic, optional account creation after payment

- **Status:** Accepted, unchanged.
- **Context:** Conversion-rate evidence strongly favors minimal pre-payment friction; Paystack's hosted checkout already provides a stronger identity signal (provider-confirmed email) than a custom pre-payment form could.
- **Alternatives considered:** Forced pre-payment registration (rejected — conversion cost); optional pre-payment sign-in (accommodated without special-casing).
- **Rationale:** See Phase 3, Decision 2 in full.
- **Consequences:** Account creation is a system-triggered side effect, never a customer-initiated registration flow, for the initial launch scope (see ADR-005 below on the self-registration boundary).
- **Future implications:** If a genuine self-registration ("sign up before buying") feature is ever prioritized, it must ship with its own independent email-verification design — see ADR-005.

### ADR-003: `customers` and `platform_users` remain permanently separate identity tables

- **Status:** Accepted, unchanged.
- **Context:** A single unified "users" table with a role flag would require every future authorization check to correctly exclude the customer role — a structural privilege-escalation risk.
- **Alternatives considered:** Unified identity table with role-based access from day one (rejected — disproportionate scope for this sprint; the actual marketplace identity model isn't needed yet).
- **Rationale:** See Phase 3, Decision 4 in full.
- **Consequences:** A future customer-becomes-creator/affiliate transition needs an explicit bridging design.
- **Future implications:** This bridging design must be specified as an entry condition for Milestone M7, not discovered mid-implementation.

### ADR-004: License revocation must synchronize with `deliveries` entitlement status

- **Status:** New (added by this review, not present in the original Blueprint).
- **Context:** The Blueprint separates `licenses` (document) from `deliveries` (permission) for good reason, but never specifies what happens to the permission when the document is revoked.
- **Alternatives considered:** Leaving `deliveries` untouched on refund and relying on manual admin intervention (rejected — too easy to forget, real financial-control risk, see Risk R3).
- **Rationale:** A refund is not complete, from a security standpoint, until access is actually revoked, not merely until the license document says "revoked."
- **Consequences:** The refund-processing code path (wherever it's implemented in Sprint 2/M2) must update both `licenses.revoked_at` and the corresponding `deliveries.status` in the same operation.
- **Future implications:** None beyond the fix itself — this is a small, contained addition to an already-well-designed pair of tables.

### ADR-005: Purchase-triggered account creation only — no self-registration in this scope

- **Status:** New (added by this review).
- **Context:** The Blueprint's email-verification reasoning is sound specifically because a successful payment is a strong identity signal; that reasoning does not extend to a hypothetical account created without a purchase.
- **Alternatives considered:** Building a general-purpose "Sign Up" flow now, with its own verification loop, alongside purchase-triggered provisioning (rejected as out of scope for this sprint's actual gap — customers already need an account primarily to see purchases they've made).
- **Rationale:** Keeps M1's security model simple and fully justified by the reasoning already in the Blueprint; avoids silently shipping a weaker-than-intended verification story for a feature nobody asked for yet.
- **Consequences:** No "Sign Up" call-to-action should be built or exposed anywhere in Sprint 2 — only "Set a password" for an already-provisioned (post-purchase) account, and "Sign in" for one that already has a password.
- **Future implications:** A true self-registration feature, if ever prioritized, is a distinct future ADR with its own email-verification design.

### ADR-006: Automated email-retry (M6) requires an explicit override of prior documented policy

- **Status:** New (added by this review) — proposed as **Deferred pending explicit re-decision**, not yet Accepted.
- **Context:** `docs/monitoring-and-alerting.md` and `docs/backup-and-recovery.md` both explicitly, deliberately documented "no automated retry, proportionate to this project's scale" as a considered decision, not an oversight.
- **Alternatives considered:** (a) Proceed with M6 as originally specified, silently superseding the prior decision. (b) Do not build automated retry; rely on manual `email_log` monitoring indefinitely, as today. (c) Build a narrower, scoped automation — e.g., retry only commerce-critical templates (`purchase-receipt`, `secure-download`), not all email — via a mechanism proportionate to that narrower scope, which may or may not require a full Cron Trigger.
- **Rationale for not simply accepting M6 as-written:** A decision this consequential (this project's first-ever scheduled background job) deserves an explicit, on-the-record justification for overriding prior documented reasoning, not an implicit one buried in a milestone description.
- **Consequences:** Sprint 2 planning must resolve this ADR to Accepted (with a stated scope and justification) or Rejected (in favor of continuing the documented manual-monitoring approach) before M6 work begins.
- **Future implications:** Whichever way this resolves should update `docs/monitoring-and-alerting.md` and `docs/backup-and-recovery.md` directly, so those documents stay the accurate operational source of truth rather than drifting out of sync with what M6 actually ships.

## Phase 12 — Executive Recommendation

**Approve with Required Amendments.**

The panel's independent re-verification confirms the Blueprint's foundational judgment is sound: the existing transaction spine is genuinely strong, the five foundational decisions each survive rigorous, independent scrutiny (with one — the `purchase_sessions` naming question — modified rather than reversed), and the marketplace-compatibility mapping holds up capability-by-capability. This is not a document that needs to be sent back for redesign; the shape is right.

It is also not a document ready to be approved exactly as written. This review surfaced one genuinely material finding the original Blueprint missed entirely — a live contradiction between its own M6 milestone and two pieces of this project's existing, deliberate operational policy — plus a set of smaller but real gaps (license/entitlement revocation sync, Ghana-specific tax structure, chargeback handling, empty-state/destructive-action UX specifics, and a scope boundary around self-registration) that are each individually small but collectively too numerous to wave through as "fine, implement and see."

### Amendments, prioritized

**Critical — must be completed before Sprint 2 begins:**
1. Resolve ADR-006 (email-retry automation) explicitly — accept with justification, reject in favor of the status quo, or scope narrower — and update `docs/monitoring-and-alerting.md`/`docs/backup-and-recovery.md` to match whatever is decided.
2. Specify license-revocation-on-refund synchronization with `deliveries` (ADR-004) as part of M2's design, before any code is written for it.

**High — should be completed during Sprint 2:**
3. Scope M1 explicitly to purchase-triggered account provisioning only, with no self-registration surface (ADR-005).
4. Specify the confirmation-page view-vs-action access model (Phase 5/R10).
5. Require an explicit migration/rollback plan for the `platform_users` rename before M7 begins, not after (R7).
6. Resolve `order_items.quantity` cardinality in documentation before M2 ships (R5).

**Medium — complete before live Paystack activation:**
7. Confirm this business's VAT-registration status and add `tax_breakdown` to `receipts` if needed (R4).
8. Add chargeback-webhook handling (R8).
9. Specify dashboard empty states and destructive-action confirmations before M3 ships (Phase 5).
10. Correct the GDPR citation to Ghana's Data Protection Act, 2012 (Act 843) throughout.

**Low — future enhancement, no launch dependency:**
11. Schedule the `purchase_sessions` → renamed-order-table conceptual rename at M7 (ADR-001).
12. Specify the customer-becomes-creator identity-bridging design before M7's marketplace work begins (Decision 4).
13. Design granular per-type notification preferences (Phase 8) — a V3.1+ item.
14. Revisit third-party observability tooling once real customer volume approaches a scale where `docs/monitoring-and-alerting.md`'s current "proportionate to scale" judgment should be re-tested (no fixed trigger date — a usage-scale trigger).

With these amendments incorporated into the Sprint 2 plan — the Critical and High items specifically resolved *before* implementation begins, not discovered during it — this panel has no reservation recommending the architecture as Robayer WealthLab's foundation for the years ahead. The underlying engineering discipline evident throughout the live codebase (idempotency, snapshot consistency, proven-pattern reuse, honest documentation of what is and isn't built) is exactly what makes this panel confident these are closeable gaps, not signs of a deeper problem.
