# Version 5.0 — Milestone 2.2 Operational Runbook

For admins and engineers operating the Knowledge Base day to day. Covers the admin dashboard at `/admin/knowledge-base/` as it stands after Milestone 2.2.

## 1. Reading the Dashboard

### Index Health
Green "Healthy" requires: the most recent indexing run completed successfully AND zero documents currently `failed`. If either isn't true, it shows the specific reason (last run failed / documents failed / no run has ever completed).

### Search Diagnostics
Type any query, click Search (or press Enter). Each result now shows:
```
<confidence> final score <N> · <source type> · <title>
vector similarity <N> · title boost +<N> · keyword boost +<N> · source boost +<N> · final <N> → <confidence>
<chunk text preview>
```
Use this to debug *why* something ranked where it did — if `source boost` is `+0.000` on every result for a query you'd expect to trigger it, the expected document likely isn't even in Vectorize's candidate pool (see §4, "Diagnosing a missing result").

### Search Analytics
Aggregated from real `knowledge_search_log` history — not a live/real-time stream, refreshed on page load and after every Search Diagnostics query you personally run. Confidence distribution and the 14-day low-confidence trend are the two most useful signals for deciding whether the thresholds in `ranking.ts` need revisiting — if "low" is a large and growing share of real traffic, that's the trigger to recalibrate again, the same way this milestone's own thresholds were derived.

### Embedding Versions
Shows `embedding_model`, `embedding_version`, first-embedded and last-refreshed timestamps per document. A document showing **"Not yet embedded"** simply predates this tracking (indexed before Milestone 2.2) or Milestone 2.2's migration — it is not evidence of a problem. These fields populate on that document's next reindex, whenever that happens naturally (content change) or is triggered manually (Full Rebuild).

### Dead Letters
Documents whose indexing message exhausted every retry on the queue. Empty is the expected, healthy state — a real Vectorize/D1 hiccup is rare by design (see the Engineering Report §8 for why). If something appears here, the "Retry" action re-enqueues the exact same message onto the same queue; check the `reason` column first if the same document keeps reappearing, since a persistent failure (not a transient one) won't be fixed by retrying alone.

## 2. Routine Operations

### Running an incremental reindex
Use after any content change (new blog post, edited resource, etc.) that you know happened outside of an automatic trigger (Task 6's content-change infrastructure is built but not yet wired to any CMS save action — see Known Limitations). Only documents whose content hash changed are re-processed; everything else is skipped.

### Running a full rebuild
Use after: an embedding model change, a chunking-strategy change (a deliberate `embedding_version` bump), or if you suspect drift between D1 and Vectorize. Re-processes every document regardless of whether its content changed. Takes noticeably longer — the last real full rebuild (38 documents) took ~73 seconds across 8 queue-consumer invocations.

### Interpreting a stuck "Running" status
If a run shows `status: running` for longer than a few minutes with no progress, check `documents_resolved` vs `documents_enqueued` directly in `knowledge_indexing_runs` (via `wrangler d1 execute ... --remote`). If resolved is stuck below enqueued and no new consumer invocations are appearing in `wrangler tail`, the queue may be backed up or a consumer invocation may have hit an unrecoverable error before dead-letter tracking could record it — this was the exact failure mode Milestone 2.1 encountered before the queue redesign; it should not recur under the current architecture, but if it does, `wrangler tail` during a fresh trigger is the fastest way to see exactly where it stalls (this is how every Milestone 2.1 incident was actually diagnosed, not guessed).

## 3. Interpreting Confidence Scores

Current thresholds (Milestone 2.2): **high ≥ 0.6, medium ≥ 0.45, low < 0.45**, applied to the *final* (post-reranking) score, not raw vector similarity. These are a first, evidence-grounded pass (see the Confidence Calibration Report) — not guaranteed permanent. If Customer AI or any future caller starts surfacing confidence directly to end users, revisit this document and the Search Analytics low-confidence trend before assuming the current cutoffs are still correct at whatever scale that feature reaches.

## 4. Diagnosing a Missing or Poorly-Ranked Result

1. Run the query in Search Diagnostics, expand the score breakdown for the top few results.
2. If the expected document doesn't appear at all: it's either not indexed (check the Documents table/filter by status), or it's not making Vectorize's candidate pool for this query (raw semantic similarity too low relative to what's already in the top-K) — reranking cannot fix this; it needs either a deeper candidate pool (see the Resources gap experiment in the Deployment Guide) or the content needs richer/different wording to embed closer to how users actually phrase the question.
3. If it appears but ranks low: check its `title boost`/`keyword boost`/`source boost` values. All zero means neither the title nor the chunk text nor the source-type trigger words overlap the query — a legitimate ranking outcome for a genuinely different topic.
4. Cross-check against `knowledge_search_log` (`top_document_id`, `top_score`) for whether this is a one-off phrasing issue or a recurring pattern (via Search Analytics' "most common searches").

## 5. What Requires a Code Change vs. What Doesn't

**No code change needed** — adjustable via the admin UI or a routine reindex:
- Any individual document's content (edit the source, run an incremental reindex).
- Investigating a specific query's ranking (Search Diagnostics already shows the full breakdown).

**Requires a code/config change** (and, per this project's standing convention, founder confirmation before deploying):
- Confidence threshold values (`CONFIDENCE_HIGH_THRESHOLD`/`CONFIDENCE_MEDIUM_THRESHOLD` in `ranking.ts`).
- Boost weights (`TITLE_BOOST_WEIGHT`/`KEYWORD_BOOST_WEIGHT`/`SOURCE_BOOST_WEIGHT`) or the source-type trigger-word map.
- The Vectorize `topK` oversampling multiplier (currently `limit × 4` in `searchService.ts`, `limit × 20` — via `limit: 20` — for the admin diagnostics tool specifically).
- Wiring Task 6's content-change re-index infrastructure into any actual CMS save route.
- Adding a real dead-letter queue if Task 7's reused-queue approach ever proves insufficient at higher failure volume.
