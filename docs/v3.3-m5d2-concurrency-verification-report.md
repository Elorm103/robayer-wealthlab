# Version 3.3 Sprint M5D.2: Concurrency Verification Report

Independently verifies concurrent scheduled execution, retry behaviour, duplicate prevention, atomic processing, and transient email recovery — using realistic concurrent execution against a real running Worker wherever practical, not simulation alone.

---

## Concurrent Scheduled Execution

**Verified live, at higher concurrency than Sprint M5D.1's own testing.** Sprint M5D.1 verified 2 genuinely concurrent `/__scheduled` requests. This Board fired **5 simultaneous requests** (`curl ... & curl ... & ... & wait`, five backgrounded processes racing against a real `wrangler dev --test-scheduled` instance) against a single seeded, due purchase. Result: one invocation reported `{"eligible":1,"claimed":1,"sent":0}` (the real send failed on the placeholder Resend key, correctly classified `permanently_failed` since it was a 401/4xx); the other four reported `{"eligible":0,"claimed":0,"sent":0}`. Direct D1 inspection confirmed `review_reminder_attempts.attempt_count = 1` for the purchase — not 5, not 2, exactly 1.

## Retry Behaviour

Verified via the restored regression suite (see the Blocking Finding Verification Report for the revert/restore methodology): a transient (`'failed'`) outcome remains eligible on a subsequent run and succeeds once the simulated outage clears; a persistently-failing purchase retries up to `MAX_SEND_ATTEMPTS = 3` and then stops, marked `'permanently_failed'` with a real audit log entry; an immediately-permanent (4xx) failure is marked `'permanently_failed'` on its very first attempt without wasting retries on an address that will never accept the email. All three behaviors were independently confirmed to fail against the pre-remediation code and pass against the current code.

## Duplicate Prevention

Verified at two levels: automated (the restored regression suite's concurrent-execution tests) and live (the 5-way stress tests above, for both the review-reminder Cron Trigger and the reconciliation HTTP endpoint). In both live stress tests, exactly one side effect (one claim, one audit log entry, one email) resulted from five simultaneous attempts — not merely "fewer than five," but precisely one, confirmed by direct database query rather than by trusting the function's own return value alone.

## Atomic Processing

The atomicity itself rests on D1/SQLite's own write serialization, applied via two idioms this Board independently traced through the actual current source (not the report's description of it):

- **Review reminders:** `INSERT INTO review_reminder_attempts ... ON CONFLICT(purchase_session_id) DO UPDATE ... WHERE <retry-eligible>`, with `meta.changes` checked immediately after. Confirmed the `WHERE` clause's staleness comparison now uses JS-computed `.toISOString()` timestamps consistently on both sides (the claim's own `claimed_at` and the comparison cutoff) — this Board specifically re-checked this after Sprint M5D.1's own report disclosed that an earlier version of this exact fix used a mismatched format (SQL `datetime('now')` vs JS ISO) that silently defeated the staleness check. Independently confirmed via direct query that `datetime('now') < '<same-day>T00:00:00.000Z'` evaluates `true` in this project's actual D1 instance — the bug Sprint M5D.1 itself found and fixed was real, not overstated.
- **Reconciliation:** the pre-existing linking `UPDATE ... WHERE customer_id IS NULL`, now with its `meta.changes` result checked before any notification proceeds, and the actually-affected rows re-derived via a follow-up `SELECT` rather than assumed.

## Transient Email Recovery

Verified via the automated suite's use of `tests/outboundMock.ts`'s new `queueResendResponseStickyOverride()` (a persistent, non-auto-consumed Resend response override, needed because `emailService.ts`'s own `sendEmail()` retries once internally — a one-shot queued override only covers the first of those two internal attempts). This Board independently confirmed this test-infrastructure addition is sound: it mirrors the existing, pre-M5D.1 `queueVerifyResponse()`/`peekResponse()` precedent exactly, and every pre-existing test using the original one-shot `queueResendResponse()` was re-run and continues to pass unchanged (the sticky override is checked first in `outboundMock()` but is empty by default, so it is additive, not disruptive). Live, real-network transient-failure simulation was not additionally performed against `wrangler dev` (the local dev Resend key is a non-functional placeholder, so every real send attempt fails uniformly and cannot be made to fail-then-succeed without the same mocking the automated suite already provides) — this Board judges the automated verification sufficient and does not consider this a gap, since the mechanism under test (the eligibility query's status-based retry logic) is identical regardless of which layer triggers the failure.

## Verdict

**Every concurrency property Sprint M5D found lacking is now independently confirmed present**, verified at higher stress (5-way, not 2-way) than Sprint M5D.1's own testing, and confirmed via direct database state rather than function return values alone.
