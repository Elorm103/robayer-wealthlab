# Version 3.2 - Milestone M4C - Amendment Tracking Correction

**Written at M4E closeout**, resolving `v3.2-m4d-amendment-compliance-report.md`'s finding that M4C's own sprint brief tracked only three of M4B's four Required Amendments. This document is the authoritative reconciliation between M4B's original numbering and M4C's actual delivered work, so a future reader never has to guess which "Amendment 3" a given document means.

---

## What Happened

`v3.2-m4b-architecture-approval-report.md` (Section "Summary of Required Amendments") specified four required amendments, in this order:

1. Corrected coupon schema (`admin_users`, not `platform_users`)
2. Security review treating payment-amount-locking as the primary focus area
3. UX planning must explicitly design Reviews' empty/sparse launch state
4. Admin-panel test coverage for both new admin surfaces, as a hard requirement

M4C's own sprint brief restated this as "Amendment 1, 2, 3" - correctly capturing M4B's #1, #2, and #4, but never independently re-reading M4B's own primary document to confirm the count. M4B's #3 (the UX design requirement) was silently dropped from M4C's own tracking. The underlying UX behavior still shipped correctly (see `v3.2-m4c-reviews-sparse-launch-state-ux.md` for the design decision this document should have prompted from the start), but the requirement itself went untracked until M4D's independent review caught the discrepancy.

Renaming it to "amendment-4" was considered and rejected: it would require updating nine existing cross-references for a purely cosmetic gain, and this reconciliation table achieves the same traceability goal without touching a single working link. See `v3.2-m4d-recommendations.md`'s own recommendation #6, which this document implements.

## For Future Milestones

Do not rely on a sprint's own restatement of a prior sprint's requirements as the authoritative count. Re-read the prior sprint's own primary document (here, `v3.2-m4b-architecture-approval-report.md`'s "Summary of Required Amendments" section) directly before beginning implementation. This is the specific process gap M4D identified (`v3.2-m4d-recommendations.md`'s "Process Recommendation" section) and this document is the concrete evidence of why that discipline matters - a real requirement went untracked for two full sprints (M4C and the first pass of M4D's own review) before being caught.
