# Version 3.0.2 - Milestone M2 Acceptance Report

**Sprint M2C - Milestone Acceptance Review (MAR)**
**Milestone:** M2 - Orders, Receipts & Customer Library
**Review type:** Independent Milestone Acceptance Review Board (MARB) - Principal QA Engineer, Principal Solutions Architect, Security Reviewer, Product Owner Representative, UX Reviewer, Database Architect, Technical Documentation Reviewer, Release Readiness Manager.
**Reviewer posture:** This review does not treat the M2 Implementation Report's own claims as verified fact. Every claim below was checked independently: 12 governance/planning documents were read in full; the actual production code (services, routes, migration, schema, tests) was read directly; the full test suite and TypeScript type check were re-run independently by this review, not taken from the implementation report's numbers.

## 1. Executive Summary

Milestone M2 implements the Ownership Layer (`order_items`, `licenses`, `receipts`, `receipt_download_tokens`) the ratified Blueprint's Deliverable 3 specifies, wires it into the existing webhook-verified purchase flow, builds a real PDF receipt generator (`pdf-lib`, confirmed compatible with `workerd`), implements the ADR-003 revocation-synchronization mechanism with a minimal admin-triggered refund action, and ships the Customer Library's data-layer APIs (purchase history, receipts, licenses) - exactly the scope the Product Owner's Architecture Decision Approval authorized, no more.

**Independently confirmed:** 88/88 tests passing (16 test files, re-run once by this review), `npx tsc --noEmit` clean. Every ADR this milestone is bound by (ADR-001, ADR-002, ADR-003, ADR-006, ADR-008, ADR-009, ADR-013) is satisfied in the actual code, not merely asserted in documentation. The one named, literal success criterion from the ratified Blueprint's own M2 milestone definition - "a test refund correctly sets both `licenses.revoked_at` and `deliveries.status = 'revoked'` in one operation, and a subsequent download-token request for that entitlement is correctly denied" - is proven by a real, passing integration test (`tests/integration/adminRefund.test.ts`), not only by a unit test in isolation.

This review found no defect that changes correct behavior for any purchase, receipt, or refund exercised by the current implementation. It found two genuine test-coverage gaps against M2A's own Testing Strategy (negative/rate-limit tests for the new path parameters were specified but not written), one dormant rounding-edge-case in multi-seat receipts that no current product can trigger, and a handful of lower-severity observations, all detailed below with file/line references. None of these rises to a blocking defect.

**Final decision: Option B - Milestone M2 Accepted with Minor Observations.** See Section 14.

## 3. Functional Review

**Orders.** `createOrderArtifacts()` (`services/orders/orderService.ts`) is called exactly once per purchase, from `commerceService.ts:496`, only on the branch of `handlePaymentWebhook()` that survives the `verifySessionAtomic()` status-gated UPDATE (`WHERE status = 'pending'`) - confirmed by reading the surrounding code (`commerceService.ts:443-448`) that a redelivered webhook for an already-verified session returns early, before `createOrderArtifacts()` is ever reached. This means a webhook retry cannot create duplicate `order_items`/`licenses`/`receipts` rows. This was not asserted in any M2 test directly (the M1 `webhook.test.ts` idempotency test only asserts `payment_transactions`/`deliveries` counts, not the new M2 tables) - traced independently by this review via code reading, not by a test. See Section 11, Item 2.

**Receipts.** Numbering (`formatReceiptNumber`), the nullable-then-UPDATE pattern for `receipt_number`, and the `pdf-lib`-based PDF generation were all read directly and match their documented design. `getOrCreateReceiptPdf()` is genuinely idempotent (checks `pdf_storage_key` first) and self-healing (a failed generation leaves the row exactly as it was, retried on next request) - confirmed by reading `services/orders/receiptPdfService.ts:141-142` and `164`. No HTML fallback exists in the codebase (the spike passed, so it was never needed) - `docs/v3.0.2-m2-implementation-report.md`'s claim that the fallback wasn't needed is accurate.

**Receipt downloads.** Guest path (mint-then-redeem, `receipt_download_tokens`) and authenticated customer path (`GET /api/customer/receipts/:receiptNumber/download`, direct stream) both verified by reading the route/service code and by re-running `tests/integration/receiptDownload.test.ts` and `tests/integration/customerPurchases.test.ts` - both pass.

**Customer Library data layer.** `purchaseHistoryService.ts` filters every query by the session's own `customerId` server-side (never a client-supplied value) - read directly, confirmed for all five functions (`listCustomerPurchases`, `getCustomerPurchase`, `listCustomerReceipts`, `findOwnedReceiptId`, `listCustomerLicenses`). Empty-state contract (`{purchases: [], total: 0}` for a zero-purchase customer, never an error) matches the M2A UX Plan's explicit data-contract requirement, confirmed by `tests/integration/customerPurchases.test.ts`'s "returns a clean empty array" test.

**Verdict: Pass**, no functional defect found.

## 4. Refund & Revocation Review

Read `services/orders/revocationService.ts` and `services/admin/orderService.ts`'s `refundOrder()` line by line, and `routes/admin/orders.ts`'s `handleOrderRefund` for the full authorization chain.

- **Atomicity:** `env.DB.batch()` is used for the three-statement write (licenses, deliveries, purchase_sessions) - D1's closest primitive to a transaction. Confirmed this is the *only* place in the entire codebase that ever writes `licenses.revoked_at` (grepped for `revoked_at` across `backend/services/` and `backend/routes/` - one writer, `revocationService.ts:72`).
- **Idempotency:** A second call for an already-refunded purchase returns `{ok: false, reason: 'already_revoked'}` without a partial write, verified by `tests/unit/revocationService.test.ts`'s idempotency test and `tests/integration/adminRefund.test.ts`'s "is idempotent" test (also confirms the audit log is not double-written: `COUNT(*) = 1` after two refund attempts).
- **Edge cases attempted by this review, independently of the existing test suite:**
  - Revoking a `pending` (never-verified) purchase - correctly rejected with `not_verified`, tested (`revocationService.test.ts:84-93`).
  - Revoking a nonexistent reference - correctly rejected with `not_found`, tested.
  - A purchase with zero licenses/deliveries at time of revocation (e.g., `order.artifacts_missing` had previously occurred) - `revokePurchase()`'s two `SELECT ... WHERE ... != 'revoked'`/`IS NULL` queries would simply return empty result sets, and the subsequent `UPDATE` statements would affect zero rows without erroring - the function still succeeds and still transitions `purchase_sessions.status` to `'refunded'`. This exact scenario is **not directly tested** (no test seeds a verified purchase with zero licenses/deliveries and revokes it), but is safe by inspection: no statement in the batch depends on affecting a non-zero row count. Non-blocking.
  - Concurrent double-refund (two simultaneous refund requests for the same reference) - not tested with genuine concurrency (`Promise.all`), unlike the receipt-number generation path which does have a concurrency test. The status-gate (`session.status === 'refunded'` check before the batch) is a read-then-write pattern, not an atomic conditional UPDATE like `commerceService.ts`'s `verifySessionAtomic()` - in a genuine race, both requests could pass the initial read before either writes, resulting in the batch running twice (D1 `UPDATE ... WHERE revoked_at IS NULL` clauses would make the second run's writes a no-op in practice, so no double-revocation *damage* would occur, but the audit log would be written twice, contradicting the idempotency test's stated guarantee under true concurrency rather than sequential double-calls). **This is a real, if narrow, gap**: the idempotency test as written only proves sequential idempotency, not concurrent idempotency. See Section 11, Item 5.
- **Download revocation, verified end-to-end**: `tests/integration/adminRefund.test.ts`'s final test confirms a `POST /api/purchases/:reference/downloads` request after refund returns `DOWNLOAD_NOT_AVAILABLE` - re-run independently by this review, passes.
- **Audit logging:** `auditService.record()` called with `action: 'order.refunded'`, `actorId` the calling admin, `metadata` containing the affected license/delivery ids - confirmed present and correctly populated by reading `services/admin/orderService.ts:451-458`. `entityId` is passed as `null` rather than the purchase session's id - see Section 11, Item 6.

**Verdict: Pass with Observations** (Section 11, Items 5-6) - no defect in the delivered functionality; two hardening opportunities for a future pass.

## 5. Security Review

- **Authorization:** Every customer-authenticated M2 endpoint requires `requireCustomerAuth`, confirmed by reading all five handlers in `routes/customer/purchases.ts`. The one admin endpoint requires `requireAuth` + `requireRole(EDITOR_ROLES)` + `requireCsrf`, in that order, confirmed by reading `routes/admin/orders.ts:163-169` - a `support`-role admin is rejected (tested, `adminRefund.test.ts`), an unauthenticated request is rejected (tested), a missing-CSRF request is rejected (tested).
- **ID enumeration prevention:** `getCustomerPurchase()`/`findOwnedReceiptId()` return `null` identically whether a reference/receipt number doesn't exist or belongs to a different customer; the route layer converts both to the same `NOT_FOUND`/`RECEIPT_NOT_FOUND` response - confirmed by reading the code and by `tests/integration/customerPurchases.test.ts`'s explicit ownership-isolation tests (a different customer's reference returns `404`/`NOT_FOUND`, not a distinct signal).
- **Token handling:** `receipt_download_tokens` uses the same 256-bit `crypto.getRandomValues` generation as every other token in this codebase (`utils/orderToken.ts`), single-use enforced by an atomic conditional `UPDATE ... WHERE used_at IS NULL AND expires_at > ?` (not a read-then-write race), confirmed by reading `services/orders/receiptEntitlementService.ts:60-69` and matching `entitlementService.ts`'s proven pattern exactly.
- **Receipt privacy:** No new sensitive-data category introduced - receipts carry email/product/amount, the same class of data `purchase_sessions`/`email_log` already store.
- **Input validation:** Path parameters (`:reference`, `:receiptNumber`) are regex-gated (`REFERENCE_PATTERN`, `RECEIPT_NUMBER_PATTERN`) before any database query, confirmed by reading `routes/customer/purchases.ts:33-42` and `routes/purchases.ts`. **However**, unlike M1's `negative.test.ts`, no M2-specific test exercises a malformed or SQL-injection-shaped value against these new parameters to prove the gate holds under adversarial input - see Section 11, Item 7. The gate itself is sound by inspection (a `RegExp.test()` on a strictly-anchored pattern, followed by parameterized D1 queries throughout - no string concatenation was found anywhere in the new M2 service files), so this is a coverage gap, not a suspected vulnerability.
- **Rate limiting:** Present on the two endpoints most exposed to unauthenticated abuse (`POST /api/purchases/:reference/receipt-download` at 20/min, `GET /api/download-receipt/:token` at 20/min) and on the authenticated read/download endpoints (60/15min, 20/15min respectively) - confirmed by reading `routes/purchases.ts`, `routes/downloads.ts`, `routes/customer/purchases.ts`. No dedicated rate-limiting *test* exists for any M2 endpoint (`tests/integration/rateLimiting.test.ts` was grepped and contains zero M2-related assertions) - see Section 11, Item 7.
- **Admin-only endpoint isolation:** confirmed a customer session cannot reach the admin refund route (it requires `requireAuth`, the admin session middleware, which does not recognize a `customer_session` cookie - read `middleware/requireAuth.ts` to confirm it checks `admin_session` specifically, a structurally separate cookie namespace from `customer_session`).

**No exploitable vulnerability was found.** The two coverage gaps above (negative-input tests, rate-limit tests) do not indicate the underlying protections are absent - they are absent from the *test suite*, and the protections themselves were verified sound by direct code inspection.

## 7. Database Review

- **Migration correctness:** `database/migrations/0019_ownership_layer.sql` contains exactly four `CREATE TABLE` statements and their indexes - zero `ALTER TABLE`, zero `DROP` - confirmed by reading the full file. `schema.sql` (the cumulative reference doc) was independently diffed against the migration file's column-by-column definitions for all four tables (`order_items`, `licenses`, `receipts`, `receipt_download_tokens`) - **identical**, no drift found.
- **Constraints:** `licenses.license_type CHECK (license_type IN ('personal'))` correctly narrow (not pre-widened for `commercial`/`educational`, per the explicit M2 exclusion). `order_items.quantity CHECK (quantity >= 1)`, `unit_price_pesewas CHECK (>= 0)`, `receipts.*_pesewas CHECK (>= 0)` all present and match the planning report.
- **Indexes:** All nine planned indexes exist (`idx_order_items_session`, `idx_order_items_product`, `idx_licenses_customer`, `idx_licenses_purchase_session`, `idx_receipts_customer`, `idx_receipts_purchase_session`, `idx_receipt_download_tokens_receipt`, plus the two `UNIQUE` constraints on `license_key`/`receipt_number`/`token`). `GET /api/customer/purchases`'s `LEFT JOIN receipts` and `licenses`/`receipts` ownership queries are covered by `idx_receipts_customer`/`idx_licenses_customer` - no unindexed customer-scoped scan was found.
- **Relationships:** All four new tables are pure leaves off `purchase_sessions` (and, for three of them, `customers`) - no circular reference, matching the planning report's own stated design.
- **Nullable fields verified correct:** `licenses.customer_id`, `receipts.customer_id` nullable (matches the documented rare no-confirmed-email edge case). `receipts.receipt_number` nullable - **this was specifically checked for concurrency safety, per this review's explicit brief.** Read `tests/unit/orderService.test.ts`'s "never leaves receipt_number NULL after completion, and never collides under concurrent creation" test, which runs two `createOrderArtifacts()` calls via a genuine `Promise.all()` (not sequential awaits) against two different purchase sessions and asserts both receive distinct, non-null receipt numbers. This review independently re-ran this test in isolation (`npx vitest run tests/unit/orderService.test.ts`) - passes. The underlying mechanism (`INSERT` with `receipt_number = NULL`, then `UPDATE ... SET receipt_number = ? WHERE id = ?` using the row's own freshly-returned `last_row_id`) has no shared mutable state between concurrent callers - each call operates on its own row's id from its own `INSERT`'s return value, so there is no race window between two *different* purchases' receipt-number assignment. The design is sound and the fix (documented as a deviation from the original plan in `docs/v3.0.2-m2-database-changes.md`) is correctly implemented and correctly tested.
- **Rollback safety:** The down-migration in `docs/v3.0.2-m2-database-changes.md` was checked against the actual table/index names in the migration file - matches exactly, correct `DROP` order (reverse of creation, respecting FK direction, though none of these four tables are referenced by any other table so order is a readability concern only, not a correctness one).

**Verdict: Pass.** No database-integrity defect found. The specific concurrency question this review was asked to verify (`receipt_number` under concurrent inserts) is confirmed safe by both design analysis and a real, independently re-run test.

## 11. Outstanding Risks (numbered for cross-reference above)

1. **Rounding drift in multi-seat line items** (`services/orders/orderService.ts:63,87-93`): `unitPricePesewas = Math.round(amountPesewas / quantity)`, then `lineTotalPesewas = unitPricePesewas * quantity`. For an `amountPesewas` not evenly divisible by `quantity` (e.g. 10000 pesewas / 3 seats), `lineTotalPesewas` (9999) can differ from `subtotalPesewas`/`totalPesewas` (10000, set independently from the original charged amount) by up to `quantity - 1` pesewas. `totalPesewas` itself is always correct (it is never derived from the line items, by design - see the code's own comment at line 98-104), so this affects only the *displayed line-item breakdown's internal arithmetic*, not the actual charged/receipted total. The existing multi-quantity test (`orderService.test.ts:63-85`) uses 7800/2=3900, which divides evenly and does not expose this. **Non-blocking** - no current product has `quantity > 1`.
2. **Webhook-redelivery non-duplication for order artifacts is correct by code-path analysis, not directly tested.** Traced in Section 3. Recommend a small addition to `tests/integration/orders.test.ts` or `webhook.test.ts` asserting `order_items`/`licenses`/`receipts` row counts stay at 1 after a redelivered webhook, mirroring the existing `payment_transactions`/`deliveries` idempotency assertions.
3. **VAT flag operational risk:** `isVatRegistered()` and `computeTaxBreakdown()` are each individually correct and honest today (default `false`; empty array regardless). But if a future operator sets `site_settings.vat_registered = 'true'` (directly via `wrangler d1 execute`, since no admin UI exists for this flag) **before** the real tax-computation logic is implemented, every receipt issued from that point forward would silently continue showing an empty tax breakdown while the flag itself now asserts VAT-registered status - an internally inconsistent, potentially non-compliant receipt, not merely an incomplete one. The code comment at `taxService.ts:74-79` already anticipates this ("an unimplemented computation must never silently fabricate a number") but there is no runtime guard (e.g., a startup check or a loud log) that would catch an operator flipping the flag prematurely. **Recommend, before this flag is ever set in production:** either a code-level assertion that logs at `error` severity if `isVatRegistered()` returns `true` while `computeTaxBreakdown()`'s real logic is still the stub, or a runbook note in the eventual go-live checklist making this sequencing dependency explicit. Non-blocking for M2 acceptance (the flag is not set today, and the default is safe) but should be resolved before VAT registration is real.
4. **Admin endpoint path deviates from the M2A API Planning Report** (`POST /api/admin/orders/:reference/refund` vs. the planned `POST /api/admin/purchases/:reference/revoke`). Verified this is a reasonable, better choice, not an oversight: it reuses the pre-existing `routes/admin/orders.ts` module, which already had `ORDER_STATUSES` including `'refunded'` and an audit-action-string precedent (`'order.refunded'`) already present in the `audit_logs` schema's own header comment before M2 existed - confirmed by reading that file's git-blame-adjacent header comment. No functional gap results from this deviation.
5. **Concurrent (true `Promise.all`) double-refund is not tested**, unlike the receipt-number generation path, which explicitly has this class of test. Traced in Section 4 - no damage occurs in practice, but the audit-log-write-once guarantee is only proven under sequential calls, not genuine concurrency.
6. **`audit_logs.entity_id` is `NULL` for `order.refunded` events** (`services/admin/orderService.ts:456`), unlike the pattern other audit events in this codebase generally follow of populating `entity_id` with the affected row's id. The `reference` string is present in `metadata` instead, so the event is still findable, just not via the indexed `idx_audit_logs_entity` lookup path. Low-priority.
7. **Test-coverage gaps** against M2A's own Testing Strategy: no negative/adversarial test for any new M2 path parameter, no rate-limit test for any new M2 endpoint. Detailed in Section 9.

None of the seven items above describes incorrect behavior in the shipped code as far as this review's direct inspection could determine - each is either a dormant edge case with no current trigger, a test-coverage shortfall, or a minor operational/traceability nit.

This is not necessarily a deployment blocker - `wrangler deploy` bundles from whatever is present in the local `node_modules` at build time regardless of which `package.json` section a package is listed under, and M1's own deployment precedent ran `wrangler deploy` from a full local dev install (never a `--production`/`--omit=dev` install step). **Verdict: Ready for the same production deployment sequence M1 already proved** (migration, then Worker, then verification), once `pdf-lib`'s dependency classification is confirmed and the two test-coverage gaps are addressed or explicitly accepted as carried debt.
