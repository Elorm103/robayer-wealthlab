# Version 3.2 - Sprint M4C - Amendment 2: Coupon Security Review

**Required by:** M4B Architecture Approval Report - "M4C's Security Review must treat the payment-amount-locking/webhook-verification change as its primary focus area." Completed before any coupon implementation code was written, per the sprint's own "do not continue until all three amendments are resolved" instruction.

---

## Design Principle (inherited unchanged from the existing checkout architecture)

`routes/checkout.ts` already documents, and this review preserves without exception: **the client never supplies a price.** A coupon *code* is not a price - the discount amount is always computed server-side, from the coupon's own stored `discount_type`/`discount_value`, never trusted from the request body. This single principle resolves most of the threat categories below by construction.

## Where the Discount Is Computed and Locked

`commerceService.ts`'s `createCheckoutSession()` computes `amountPesewas` from the product catalog price (unchanged) and, if a valid coupon code was supplied, subtracts the server-computed discount **before** the amount is locked into `purchase_sessions.amount_pesewas` - the same column the webhook's existing high-severity mismatch check already guards (`verifyResult.amountPesewas !== session.amountPesewas`). **No change to the webhook verification logic itself is needed or made** - it continues to compare against whatever was locked at checkout time, which now correctly includes the discount. This is the minimum-necessary-change approach the M4B review's own Architecture Readiness Assessment recommended.

## Threat-by-Threat Review

### Price tampering

**Not possible.** The client sends only a `couponCode` string (added to the existing checkout request body, alongside the already-unchanged `productId`). The discount is looked up and computed entirely server-side from the `coupons` table. A tampered or fabricated coupon code simply fails validation (`COUPON_INVALID`); there is no field the client can set to directly influence the charged amount.

### Unauthorized application

Coupon codes are, by design, a semi-public promotional mechanism (like any e-commerce discount code) - no customer authentication or ownership check is required to *apply* one, only validity checks (active, not expired, within any product restriction, within redemption limits). This matches standard e-commerce UX and is not a security boundary this feature needs to introduce.

### Expired coupons

Checked at checkout-session creation time only (`status = 'active'`, `starts_at`/`expires_at` window) - the one point the discount is ever computed. Once locked into `purchase_sessions.amount_pesewas`, the amount is fixed regardless of what happens to the coupon afterward (an admin disabling or letting a coupon expire mid-checkout does not retroactively change an already-locked session) - this mirrors the existing, deliberate tolerance for "a legitimate price change mid-checkout" already documented in `commerceService.ts`'s own comments for product price generally.

### Replay

Each checkout attempt creates a new `purchase_sessions` row (unchanged, existing behavior) - there is no "replay" concept specific to coupons beyond what already exists for checkout sessions generally. A coupon code can be legitimately reused across many different checkout attempts by different customers (that is its intended purpose); what must not happen is the *same coupon exceeding its own redemption limit*, addressed below.

### Stacking

**Explicitly disallowed by schema construction**, not application logic alone: `coupon_redemptions.UNIQUE(purchase_session_id)` makes a second redemption row for the same purchase session impossible at the database layer. The checkout API accepts at most one `couponCode` per request (not an array) - there is no code path that could apply two coupons to one purchase.

### Race conditions - the redemption-limit race (the primary finding of this review)

**The core design decision**: redemption-count enforcement happens in two phases, deliberately.

1. **At checkout-session creation** (soft check): validate the coupon is active, not expired, and (if `max_redemptions` is set) `redemptions_count < max_redemptions` at that moment. This gives an honest, immediate "this coupon is no longer valid" response to a customer *before* they pay - good UX, not a security boundary.
2. **At payment verification** (hard, atomic check): only once Paystack has confirmed the payment (`verifySessionAtomic()` already succeeded) does this feature atomically increment the counter: `UPDATE coupons SET redemptions_count = redemptions_count + 1 WHERE id = ? AND (max_redemptions IS NULL OR redemptions_count < max_redemptions)`.

**The race this cannot close, and why that is the correct decision, not an oversight:** if two customers simultaneously complete checkout using the last remaining redemption of a limited coupon, both may pass the soft check at step 1 (each sees `redemptions_count < max_redemptions` at slightly different moments), both get charged the discounted amount by Paystack, and only one of the two atomic increments at step 2 succeeds. **This feature does not attempt to deny, reverse, or claw back the second customer's already-completed payment.** This is not a gap - it is the same "log, never undo a real payment" discipline this codebase applies everywhere else a post-payment inconsistency is possible (e.g., `commerceService.ts`'s own handling of a product becoming unpurchasable between checkout and payment). The failed atomic increment is logged (`coupon.redemption_limit_race`) for admin visibility; the purchase, receipt, and license are all created normally regardless. **Business impact is bounded**: at most one extra redemption beyond the stated limit, only in a genuine simultaneous-completion race, which requires two customers completing payment for the same limited coupon within the same narrow window - a low-probability, low-impact scenario this review judges acceptable, consistent with the ARB's own prior acceptance of the structurally similar `first_purchase_only` risk (see below).

### `first_purchase_only` enforcement - a known, accepted limitation, not a new one

**Cannot be strictly enforced pre-payment**, for a structural reason specific to this platform: ADR-002/ADR-006 mandate guest-first, zero-form checkout - the customer's email is not known until Paystack's own hosted page collects it, which happens *after* the discount has already been computed and the coupon already applied. This feature implements `first_purchase_only` as a **best-effort, detection-only check at webhook-verification time**: once `verifyResult.customerEmail` resolves a real identity, check whether that customer already has a prior verified purchase; if so and the coupon was `first_purchase_only`, log an anomaly (`coupon.first_purchase_only_violated`) for admin visibility. **The payment is never reversed or denied** - by the time this check runs, Paystack has already charged the discounted amount. This is not a new risk this review introduces: it is the exact "multi-account/repeat-customer coupon abuse" vector the original ARB review (cited throughout the M4A/M4B planning package) already explicitly reviewed and accepted as non-blocking. This implementation makes the acceptance concrete and auditable (a real log line) rather than merely theoretical.

### Coupon-tax interaction

Confirmed, per the M4A Risk Assessment's own finding, genuinely trivial today: `computeTaxBreakdown()` returns an empty array regardless of any input, so there is no real interaction to secure yet. `receipts.subtotal_pesewas` (recovered as `amount_pesewas + discount_pesewas`) and `receipts.discount_pesewas` (the coupon's actual discount) are both populated correctly and independently of tax logic. Flagged, per the M4A Risk Assessment's own recommendation, as a required re-check whenever real VAT computation is eventually implemented.

## Summary of Protections Implemented

| Threat | Protection |
|---|---|
| Price tampering | Discount always server-computed from stored coupon data; client sends only a code |
| Unauthorized application | Not a security boundary by design (public promotional codes) |
| Expired coupons | Checked once, at the one point the discount is computed; locked amount is immutable afterward |
| Replay | No coupon-specific replay surface beyond existing checkout-session semantics |
| Stacking | Database-enforced (`UNIQUE(purchase_session_id)` on `coupon_redemptions`) |
| Redemption-limit race | Two-phase check (soft pre-check + atomic post-payment increment); failure mode is log-only, payment never reversed - an accepted, bounded, low-probability edge case |
| `first_purchase_only` bypass | Best-effort, detection-only (cannot be enforced pre-payment in a guest-checkout system); matches the ARB's own prior acceptance of this exact risk category |

**Status: Resolved.** No blocking security finding. Implementation may proceed with the design documented above.
