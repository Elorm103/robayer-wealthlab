### Item 3: GitHub Pages re-confirmation for `/dashboard/*`

**Status: Resolved - verified live, not re-assumed.**

Per the M3A Risk Assessment's own explicit instruction ("re-confirm, don't re-assume"), this sprint ran the actual read-only checks against production rather than trusting M1's prior confirmation to still hold:

- `.nojekyll` confirmed present at the repository root - GitHub Pages will not run Jekyll processing, so no directory-naming or Liquid-templating risk exists for `dashboard/`.
- `dashboard/*`'s five pages (`dashboard/index.html`, `dashboard/purchases/index.html`, `dashboard/receipts/index.html`, `dashboard/licenses/index.html`, `dashboard/security/index.html`) confirmed to mirror the exact directory-plus-`index.html` structure `checkout/sign-in/index.html` and `checkout/callback/index.html` already use - the identical structure M1's own production deployment report proved works on GitHub Pages (polled until `200` was returned, per that report's own Section 5).
- `backend/wrangler.jsonc`'s `routes` array re-read directly: the Worker only intercepts `robayerwealthlab.com/api/*`, `/books/*`, `/resources/*`, `/blog/*`, and `/free-guide/*` at the Cloudflare edge. `/dashboard/*` is not in this list and therefore falls through untouched to GitHub Pages, exactly as the routing comment in that file states ("every other path on the zone remains untouched, served by GitHub Pages exactly as before").
- **Live-verified against the actual production domain** (read-only `curl`, no state changed): `https://robayerwealthlab.com/dashboard/` returns `404` (correct - not yet deployed) and `https://robayerwealthlab.com/checkout/sign-in/` returns `200` (confirms the routing/hosting mechanism itself is live and healthy for the identical directory pattern today, not merely as of M1's original deployment).

No assumption in the Risk Assessment was found to be incorrect. No corrective action was needed - this item closes as a confirmation, not a fix.

### Item 4: Dedicated rate-limit tests for M3 endpoints

**Status: Resolved.**

`backend/tests/integration/rateLimitingM3.test.ts` (new, 4 tests): the 61st request to `GET /api/customer/sessions` within the window is rejected (60/15min); the 21st request to `POST /api/customer/sessions/:sessionId/revoke` is rejected (20/15min); the 11th request to `POST /api/customer/auth/change-password` is rejected (10/15min); and one test confirms rate-limit buckets are isolated per endpoint (exhausting `change-password`'s limit does not affect `GET /api/customer/sessions` for the same IP). All four tests passed on the first run - the underlying rate-limit logic was already correctly wired at M3B, exactly as M3C's code-inspection-based verdict concluded; this sprint only closes the proof gap.

### Item 5: Licenses "Copied!" `aria-live` polish

**Status: Deliberately not addressed - documented, not fixed.**

The M3C Acceptance Report itself classified this as "opportunistic, non-blocking... sitewide scope" (its Section 9 Technical Debt Register explicitly notes it mirrors `admin-media.js`'s own pre-existing pattern, not an M3-introduced regression). Consistent with this sprint's "no new functionality beyond what resolving an observation required" instruction and with the precedent M2D's own closeout established (fixing only what an accepted item required, not opportunistically redesigning adjacent, out-of-scope code), this item was deliberately left open and logged in `v3.1-m3-known-limitations.md`'s new "Deliberately not addressed at M3D closeout" section, with the reasoning stated explicitly rather than silently dropped.
