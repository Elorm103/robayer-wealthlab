# Version 3.3 Sprint M5A: Recommended M5 Scope

**Milestone name: M5, Activation, Analytics, and Customer Reconciliation.**

Deliberately not named after a single flashy feature. Every item in this scope exists to activate value the platform has already built or to give future milestones real data to plan against, rather than to add new monetization surface area before the existing surface area is used.

---

## In Scope

### 1. Legacy Guest-Purchase Account Reconciliation

A "claim your purchase" flow: a person who bought a product as a guest before Milestone M1 shipped (15 of 17 verified purchases in production today) can, using the email address their purchase was made under, set a password and be linked to their own historical purchase or purchases. Reuses the existing password-setup token mechanism from Milestone M1 and the existing customer-identity schema; requires one additive migration step at most (a matching mechanism from `purchase_sessions.customer_email` to a newly-created or existing `customers` row), no destructive change to any existing table.

**Why this belongs in M5 and not later:** it is the single highest-impact, evidence-backed gap this planning cycle found, it uses architecture that already exists, and every month it remains unaddressed adds more orphaned purchases to the backlog it needs to reconcile.

### 2. Visitor and Marketing Analytics

Cloudflare Web Analytics (or an equivalent privacy-respecting, native option), added as a lightweight script tag with no backend change required. Gives every future planning cycle real conversion, funnel, and traffic-source data instead of the purchase-session-count proxy this very planning cycle had to rely on.

**Why this belongs in M5 and not later:** it is a prerequisite for correctly scoping conversion, acquisition, and campaign-targeting work in any milestone that follows it. Building M6 or M7 without it repeats the same measurement gap this project's own governance documents have already flagged twice.

### 3. Triggered Post-Purchase Review-Request Email

One scheduled (Cloudflare Cron Trigger) job, checking for verified purchases a short, fixed number of days old with no existing review, and sending one email inviting the customer to leave a review, linking to the product page's own review form.

**Why this belongs in M5 and not later:** it is the first genuinely justified use of a Cron Trigger this project has had (matching its own stated "no new Cron Trigger without a specific, narrow, named reason" bar), it directly closes a gap predicted in advance by this project's own Milestone M4B governance history, and it depends on item 1 above to reach the majority of eligible customers, making it a natural, connected addition to the same milestone rather than a separate one.

## Explicitly Not in Scope for M5

- **Platform Fee Engine.** See `v3.3-platform-fee-engine-assessment.md`. No marketplace exists for it to apply against.
- **Wishlist, gift purchases, loyalty, affiliate, course platform, personalized recommendations.** See `v3.3-feature-inventory.md` and `v3.3-prioritization-matrix.md` for the evidence behind deferring each.
- **Bundles, upsells, cross-sells, average-order-value work.** All require a second active product, which is a content and business timeline decision outside this milestone's engineering scope.
- **A promotional coupon and newsletter campaign.** Recommended, but as an immediate business action available today (both systems already exist), not as engineering scope for M5.

## Engineering Effort Estimate

Comparable to Milestone M3's own scope (a moderate, single-sprint-implementable milestone: modest schema extension, one new customer-facing flow, one scheduled job), not comparable to Milestone M4's larger two-feature scope. This review estimates M5 as a smaller, faster milestone than M4, appropriate given its purpose is activation and measurement rather than new feature construction.

## Security and Governance Note

The account-reconciliation flow touches customer identity and must go through the same review discipline every prior milestone has (an architecture and scope approval review before implementation, an independent acceptance review before closeout), given it involves linking a new account claim to a historical financial record (a real purchase), a class of change this project's own history treats with real caution.

---

## Verdict

**M5 scope is recommended as defined above.** It is small, evidence-backed, reuses existing architecture, and is scoped specifically to activate and measure what Version 3.2 already built, rather than to add new monetization surface area ahead of demonstrated need.
