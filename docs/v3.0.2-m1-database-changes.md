# Version 3.0.2 - Milestone M1 Database Changes

Customer Identity & Guest Checkout. One migration, additive only: no
existing column, table, row, or index is altered or dropped.

## Migration

`backend/database/migrations/0018_customer_identity.sql`. Applied to
the local D1 instance (`wrangler d1 migrations apply
robayer-wealthlab-db --local`) and verified there throughout
development and testing.

**Not yet applied to production D1 as of the M1 Acceptance Review
(2026-07-25).** `wrangler d1 migrations list robayer-wealthlab-db
--remote` confirms `0018_customer_identity.sql` is still pending
against the live database, and `wrangler deployments list` confirms
the currently-deployed Worker predates this milestone's code (last
deploy 2026-07-24T22:57, before this work began) - so production is
in a consistent, unaffected state (neither the schema nor the code
that depends on it has shipped), not a broken half-deployed one.
Applying `wrangler d1 migrations apply robayer-wealthlab-db --remote`
and deploying the updated Worker are required, explicitly-authorized
follow-up actions before this milestone is live - see the M1
Acceptance Report's Final Acceptance Decision.

## New tables

### `customers`

The customer-facing identity, deliberately kept separate from
`admin_users`/`platform_users` (ADR-004: customer and staff/creator
identities must never merge).

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `email` | TEXT NOT NULL UNIQUE | normalized lower-case/trimmed before insert |
| `password_hash` | TEXT | **nullable by design** - NULL until the customer sets a password; no password means no one, including an attacker who knows the email, can log in. This is what makes guest checkout possible with zero account-creation friction |
| `email_verified_at` | TEXT | stamped immediately at provisioning - a successful payment is itself the identity signal (ADR-006), never left NULL for a provisioned account |
| `status` | TEXT NOT NULL DEFAULT `'active'` | CHECK `IN ('active','suspended')` |
| `created_at` / `updated_at` | TEXT | |
| `deleted_at` | TEXT | soft delete, reserved for a future account-closure flow |

Indexes: `idx_customers_status`, `idx_customers_deleted_at`.

**The only INSERT into this table anywhere in the codebase** is
`findOrCreateCustomer()` in `services/customer/identityService.ts`,
called from `commerceService.handlePaymentWebhook()` after Paystack
verification succeeds. There is no public registration endpoint.

### `customer_profiles`

1:1 with `customers`, holding everything not authentication-critical,
kept in a separate table so profile growth never touches the
auth-sensitive one.

| Column | Type | Notes |
|---|---|---|
| `customer_id` | INTEGER PK REFERENCES `customers(id)` | |
| `display_name` | TEXT | not populated in M1 |
| `country` | TEXT | not populated in M1 - deferred to post-payment profile completion (M3) |
| `marketing_opt_in` | INTEGER NOT NULL DEFAULT 0 | seeded once, at provisioning, from `purchase_sessions.marketing_opt_in`; never re-seeded on a later purchase by the same customer |
| `preferred_topics` | TEXT | not populated in M1 |
| `avatar_media_id` | INTEGER REFERENCES `media_assets(id)` | not populated in M1 |
| `updated_at` | TEXT | |

A row is created (empty, all-NULL beyond `customer_id`) at the exact
moment the `customers` row is provisioned - never on a later purchase
by an existing customer.

### `customer_sessions`

Direct structural mirror of `admin_sessions` (migration
`0006_admin_auth_foundation.sql`) - same token/CSRF/expiry/revocation
shape, applied to a second audience rather than reinvented.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `token` | TEXT NOT NULL UNIQUE | 256-bit, `crypto.getRandomValues`-based hex |
| `customer_id` | INTEGER NOT NULL REFERENCES `customers(id)` | |
| `csrf_secret` | TEXT NOT NULL | per-session, backs the double-submit CSRF pattern |
| `ip_created` | TEXT | audit/anomaly context only - never an access decision |
| `user_agent` | TEXT | |
| `expires_at` | TEXT NOT NULL | absolute 12h lifetime |
| `revoked_at` | TEXT | set on logout; a revoked session is never valid again regardless of `expires_at` |
| `created_at` / `last_seen_at` | TEXT | |

Indexes: `idx_customer_sessions_customer`, `idx_customer_sessions_expires`.

### `customer_password_tokens`

Same shape and single-use/short-lived (30 min) discipline as
`password_reset_tokens` (migration `0013_identity_security.sql`). One
table serves **both** the initial post-purchase password-setup flow
(link from the welcome email) and any later self-service password
reset - the mechanism (mint a token, email a link, redeem once) is
identical; only the triggering email's copy differs.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `token` | TEXT NOT NULL UNIQUE | |
| `customer_id` | INTEGER NOT NULL REFERENCES `customers(id)` | |
| `expires_at` | TEXT NOT NULL | 30 minutes from issuance |
| `used_at` | TEXT | set atomically on redemption; a used token can never be redeemed again |
| `created_at` | TEXT | |

Index: `idx_customer_password_tokens_customer`.

## Extended table: `purchase_sessions`

| Column | Type | Notes |
|---|---|---|
| `customer_id` | INTEGER REFERENCES `customers(id)` | nullable - a `purchase_sessions` row exists (`status='pending'`) before the customer is provisioned; set only at verification, alongside the find-or-create step |
| `terms_accepted_at` | TEXT | stamped at checkout-session creation |
| `terms_version` | TEXT | server-stamped from `CURRENT_TERMS_VERSION` (`'v1.0'`) in `commerceService.ts`, never client-supplied |
| `license_accepted_at` | TEXT | stamped at checkout-session creation |
| `license_version` | TEXT | server-stamped from `CURRENT_LICENSE_VERSION` (`'v1.0'`) |
| `marketing_opt_in` | INTEGER NOT NULL DEFAULT 0 | genuinely optional, opt-out by default |

Index: `idx_purchase_sessions_customer`.

**Scope note on the consent columns**: these five columns are not in
the originally ratified Blueprint schema. They were added as an
additive gap-fill once M1's own functional requirements (capture ToS/
License/marketing consent) surfaced a real requirement the
architecture hadn't modeled - consistent with the architecture's own
snapshot-at-checkout-time discipline (price, title, and version are
already locked onto this same row the same way). This is not a
reversal of ADR-002 (no form on Robayer's own checkout page):
`terms_accepted_at`/`license_accepted_at` are stamped from the
click-to-purchase action itself, and `marketing_opt_in` from one
explicit, separate, unchecked-by-default checkbox next to the Buy
button - see `js/components/buy-button.js` and
`backend/routes/books.ts`.

## What was deliberately NOT added in M1

Per the ratified roadmap, out of scope for this milestone:

- `licenses`, `receipts`, `order_items` (Milestone M2)
- `notification_queue`, `support_requests` (M5/M6)
- Any `platform_users` rename or `customer_id` bridge (M7)
- Account-lockout columns on `customers` (`failed_login_attempts`,
  `locked_until`) - the ratified schema has none; see the
  Implementation Report's Known Limitations for why this is flagged
  rather than silently added.

## Rollback strategy

All six changes are purely additive (5 new tables, 6 new columns on an
existing table, 8 new indexes) - nothing existing was modified. Two
options, in order of preference:

1. **Forward-fix (preferred)**: since nothing was altered or dropped,
   a bad deploy of application code that reads/writes these new
   columns/tables can be rolled back independently of the schema -
   the schema change itself is inert until application code exercises
   it.
2. **Down-migration**, if the schema itself must be reverted:
   ```sql
   DROP INDEX IF EXISTS idx_purchase_sessions_customer;
   ALTER TABLE purchase_sessions DROP COLUMN marketing_opt_in;
   ALTER TABLE purchase_sessions DROP COLUMN license_version;
   ALTER TABLE purchase_sessions DROP COLUMN license_accepted_at;
   ALTER TABLE purchase_sessions DROP COLUMN terms_version;
   ALTER TABLE purchase_sessions DROP COLUMN terms_accepted_at;
   ALTER TABLE purchase_sessions DROP COLUMN customer_id;
   DROP TABLE IF EXISTS customer_password_tokens;
   DROP TABLE IF EXISTS customer_sessions;
   DROP TABLE IF EXISTS customer_profiles;
   DROP TABLE IF EXISTS customers;
   ```
   D1 (SQLite) supports `DROP COLUMN` on recent versions; verify
   against the target environment before running. This would also
   require reverting the application code in the same deploy (the
   customer auth routes, `commerceService.ts`'s consent validation and
   provisioning block, and `fulfilmentService.ts`'s welcome-email
   trigger all depend on these columns/tables existing) - there is no
   scenario where rolling back the schema alone, with the M1
   application code still deployed, is safe.

`backend/database/schema.sql` (the cumulative reference doc) has been
updated to reflect migration 0018 as the current baseline.
