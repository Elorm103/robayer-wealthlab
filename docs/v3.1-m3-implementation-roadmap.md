# Version 3.1 - Sprint M3A - M3 Implementation Roadmap

Planning only. Nothing in this document was executed. It exists so Sprint M3B can begin building with minimal open questions, mirroring the exact structure `v3.0.2-m2-implementation-roadmap.md` already established for M2.

---

## Security review, consolidated

Already covered in full in `v3.1-m3-security-review.md`. Summary: every new endpoint reuses an existing, proven authentication/authorization/CSRF pattern; the one genuinely new authorization shape (session-id-scoped, not customer-id-scoped) is explicitly named as needing its own dedicated test, not assumed safe by analogy.

---

## Pre-implementation action items (should be resolved at the start of M3B, not treated as open questions to discover mid-implementation)

1. **Decide on the optional `customers.password_updated_at` column** (Database Impact Assessment) - either add it now (a trivial, additive migration) or explicitly defer it and ship Account Security's password-status display without a specific date for M3's first release. Either is acceptable; the decision should be made once, deliberately, not left ambiguous during implementation.
2. **Confirm the browser-automation tooling question cheaply, on day one** (Testing Strategy) - navigate the existing Browser pane to any existing first-party page and confirm normal operation before assuming new tooling is required. This is expected to resolve in minutes, not to become a blocker.
3. **Escalate the VAT-registration business question one more time, with an explicit deadline**, in parallel with M3's own work, not blocking it (per the Version 3.0.2 Retrospective's own repeated recommendation, now carried across five consecutive planning passes) - M3's own scope is fully insulated from this question either way (Risk Assessment).
4. **Confirm the next migration number** by checking `backend/database/migrations/` directly at implementation time, only if action item 1 results in adding the optional column - not assumed in this planning pass.

None of these four is a reason to delay *starting* M3B - each has a clear owner and a clear, fast resolution path.

---

## Build order

1. **Backend first, small and additive** (API Gap Analysis): extend `GET /api/customer/purchases`/`:reference` with `assets`; add `GET /api/customer/sessions`, `POST /api/customer/sessions/:sessionId/revoke`, `POST /api/customer/auth/change-password`. Each is independently small and independently testable - build and test each one fully (including its own negative/cross-customer test) before moving to the next, not all four in one undifferentiated pass.
2. **The optional migration**, if action item 1 above chose to add it - before any code that would read/write the new column.
3. **Shared dashboard shell**: `dashboard-auth-guard.js`, `dashboard-nav.js`, `partials/dashboard-nav.html` - the one piece every subsequent page depends on, built and verified (redirect-on-401 behavior) before any individual page.
4. **My Library** (the dashboard's entry point) - the first real page, exercising the new `assets`-extended endpoint end-to-end, including its Download action reusing the existing mint-then-redirect flow unchanged.
5. **Purchase History, Receipts, Licenses** - each a smaller, presentational variant of the same list-page pattern My Library establishes; can proceed in any order or in parallel once the pattern is proven on Library.
6. **Account Security** - the one page with genuinely new backend surface (sessions, change-password) and the one page with real destructive-action confirmation requirements (AR-009) - built last, since it depends on the new endpoints from step 1 being fully proven first.
7. **Small existing-file changes**: `sign-in-form.js`'s post-login redirect target; `checkout/callback/index.html`'s optional copy tweak.
8. **Full test suite** (Testing Strategy), written alongside each step above, not batched at the end - matching this project's own proven practice throughout M1 and M2.
9. **Documentation**: an M3 Implementation Report, Database Changes doc (if the optional column was added), and API Reference update, following the exact template M1 and M2's own documentation already established.
10. **Independent Milestone Acceptance Review**, mirroring M1/M2's own MARB process exactly - this planning report is not a substitute for that independent review once M3B's code exists.

---

## What M3B must explicitly NOT do

Per this sprint's own scope instruction and the ratified roadmap: no checkout/payment flow changes, no coupons/promotions, no support ticketing, no notification center, no VAT/tax computation logic, no chargeback handling, no marketplace/creator/affiliate work, no `purchase_sessions` rename, no `platform_users` work. No new visual/design system - reuse `css/tokens.css` and existing component classes unchanged. No new JS framework, router, or build tooling.

---

## Dependencies and sequencing relative to other milestones

- M3 depends on M1 and M2 - both complete, both deployed, both independently verified in production.
- M3 has no dependency on M4 (Coupons), M5 (Support), M6 (Notifications), M7 (Marketplace), or M8 (Go-Live Review) - all can be planned or begun independently of M3's own timeline, per the ratified roadmap's own dependency graph.
- M5 (Support Ticketing) depends on M3 (needs the dashboard surface to host its own page) - M3 should be substantially complete before M5's own implementation begins, though M5's *planning* could start in parallel.
- The M7 migration-planning work (not implementation) identified as a standing item in the Version 3.0.2 Retrospective should continue in parallel with M3, at zero cost to M3's own schedule.

## Final Decision

## Milestone M3 Approved for Implementation

Every requirement M3 needs is either already fully specified by the ratified Version 3.0.2 architecture (Blueprint Deliverable 5, ADR-013's view/action split, AR-009's empty-state/confirmation specification) or has been resolved to a concrete, minimal, additive answer within this same planning sprint (the four API additions, the one optional column, the browser-automation question). No open architectural question remains - this is the same bar `v3.0.2-m2-architecture-compliance-report.md` set for M2's own approval, applied here and met.

**Justification:**

- **Architecture:** Pass, no deviation required (M3 Architecture Review).
- **API surface:** four small, additive endpoints identified, none requiring a redesign of anything M1/M2 already shipped; every existing endpoint M3 needs is already built, tested, and live in production (M3 API Gap Analysis).
- **Database:** no required schema change; one small, optional, fully-additive column identified and left as a deliberate, low-stakes implementation-time choice (M3 Database Impact Assessment).
- **Security:** no unresolved risk; the one genuinely new authorization shape is explicitly named for its own dedicated test rather than assumed safe (M3 Security Review).
- **UX:** fully specified against the existing, proven, WCAG-verified design system - no new visual language to invent or approve (M3 UX Strategy).
- **Testing:** a complete strategy exists, including a specific, evidence-based resolution to the one open tooling question this sprint was asked to review (M3 Testing Strategy) - the M2 browser-automation gap was found not to generalize to M3's own same-origin pages, pending one cheap, fast confirmation step at implementation start.
- **Risk:** nothing identified rises to a level that should delay starting implementation; the two items worth resolving early (browser-tooling confirmation, the optional-column decision) are both fast, low-stakes, and already have a clear resolution path (M3 Risk Assessment).

Approval is conditioned on the four pre-implementation action items above being resolved at the *start* of M3B, exactly as M2A's own approval was conditioned on its own four day-one action items - none of the four is a reason to delay *starting* M3B, each has a clear owner and a fast resolution path.
