# Version 3.1 - Milestone M3 Known Limitations

Sprint M3B, updated at Sprint M3D closeout. None of the items below are
defects discovered and left unfixed - each is either an intentional
scope boundary (per M3A's approved scope and this sprint's explicit
exclusions), a pre-existing characteristic inherited from M1/M2 and not
addressed because it was out of this milestone's named scope, or a
deliberate, pre-approved deferral logged here explicitly per the M3C
Acceptance Review's own recommendation (`v3.1-m3-acceptance-report.md`
Recommendation 1).

## Scope boundaries (intentional, per M3A approval)

- **No purchase search on the dashboard.** M3A's Implementation Roadmap
  listed search as conditional on separate approval; no such approval
  is on record for this sprint, so it was not built. Both My Library
  and Purchase History work correctly without it at the realistic
  near-term purchase-count range for a single customer.
- **No VAT logic, coupons, promotions, marketplace, multi-vendor
  support, wishlist, notifications, analytics, or affiliate features** -
  all explicitly excluded by the sprint instruction; none were touched.
- **No admin redesign, new payment providers, or framework migration** -
  explicitly excluded; the dashboard is static HTML with the same
  `data-include`/`partials:loaded` pattern as the rest of the site, no
  React/Vue/Svelte, no build step, no client-side router.
- **No `customers.password_updated_at` column, and Account Security's
  Profile section shows only email, no password-last-changed date.**
  `docs/v3.1-m3-database-impact-assessment.md` identified this as one
  optional, additive column and explicitly sanctioned shipping without
  it ("Option 2... defers a trivial, low-risk migration rather than
  avoiding a real one"). M3B took that option deliberately, but did not
  log the decision here at the time - the M3C Acceptance Review flagged
  the missing log entry (not the underlying engineering choice, which
  it confirmed was correct and pre-approved) as a documentation
  completeness gap; closed by this entry at M3D closeout. If a future
  milestone wants the exact date, the column and its write-on-set/
  write-on-change population are still exactly as scoped in the
  Database Impact Assessment - no new design work needed, just the
  originally-deferred migration.

## Inherited from M1/M2, not addressed (out of this milestone's scope)

- **Session device summarization is coarse** (browser + OS only, via
  user-agent string matching, no fingerprinting library) - a direct
  mirror of `admin-account.js`'s own pre-existing approach, not
  something this milestone introduced or was asked to improve.
- **`deliveries` remains single-per-asset, not quantity-aware** - an M2
  limitation, carried forward unchanged. The new `assets` field added
  in M3 surfaces exactly this existing shape (one delivery entitlement
  per asset, regardless of `order_items.quantity`); it does not change
  or work around it.
- **Tax computation logic is still not implemented** (M2's own
  documented limitation, `computeTaxBreakdown()` returns an empty
  array) - untouched by M3, since VAT logic was explicitly excluded
  from this milestone.

## Design decisions worth flagging (not limitations, but judgment calls)

- **`resolveAssetsWithDeliveryInfo()` is customer-dashboard-only** and
  was deliberately not merged into the pre-existing guest-facing
  `getFulfilmentStatus()`. If a future milestone needs the same
  delivery-status detail on the guest fulfilment page, that would be a
  small additive follow-up (a second consumer of the same underlying
  join query), not a redesign of either endpoint.
## Defects found and fixed across M3B/M3C/M3D (included for completeness)

- **Dark-mode contrast on the dashboard nav's active-page indicator**
  (found and fixed in M3B). Initially styled with a dark-mode-unsafe
  color token (`--color-growth-green` used directly for text, measuring
  2.9:1 contrast against the dark theme's background - under the 4.5:1
  AA minimum). Found via M3B's own dark-mode browser verification pass,
  before documentation was written, and fixed by switching to
  `--color-accent` (the dark-mode-aware token every other
  accent-colored interactive text on the site already uses, measuring
  8.4:1). Confirmed fixed via computed style read after the change. No
  open action item remains.
- **Session self-revocation had no server-side guard** (found and fixed
  in M3C). M3B's original design deliberately left `revokeSessionById()`
  itself without a current-session guard, matching
  `services/admin/sessionService.ts`'s existing precedent, and relied
  on the dashboard UI alone never rendering a revoke control for
  `isCurrent: true`. The M3C Acceptance Review tested this live with a
  direct API call (bypassing the UI entirely) and confirmed a customer
  could revoke their own current session, immediately invalidating the
  cookie making the request - a real violation of
  `docs/v3.1-m3-security-review.md`'s explicit "must never allow"
  requirement, not merely a stylistic difference from the admin
  precedent. **Fixed during M3C**: `routes/customer/sessions.ts` now
  rejects the attempt with `CANNOT_REVOKE_CURRENT_SESSION` (400) before
  calling the service layer; `revokeSessionById()` itself is unchanged
  (still has no guard of its own - the guard lives one layer up, at the
  route). See `docs/v3.1-m3-api-reference.md` for the documented error
  code and `backend/tests/integration/dashboardM3.test.ts` for the
  regression test. No open action item remains.
- **Two negative/adversarial tests the M3A Testing Strategy explicitly
  required were missing** (found and closed in M3C): malformed/oversized
  `:sessionId` path values, and SQL-injection-shaped `change-password`
  body values. Both added to `backend/tests/integration/dashboardM3.test.ts`.
- **No rate-limit test existed for any of M3's three new/extended
  endpoints** (flagged non-blocking by M3C, closed in M3D). All three
  endpoints already had the rate-limit logic itself correctly wired
  (verified by code reading during M3C); `backend/tests/integration/rateLimitingM3.test.ts`
  now proves it, mirroring `rateLimitingM2.test.ts`'s own pattern.

## Deliberately not addressed at M3D closeout

- **Licenses page's "Copied!" button-text feedback has no `aria-live`
  announcement.** Flagged by the M3C Acceptance Review as an
  opportunistic, non-blocking accessibility polish item. Not addressed
  at M3D closeout because it is a direct mirror of
  `admin-media.js`'s own pre-existing pattern - a sitewide gap, not an
  M3-introduced one, and out of this milestone's scope to redesign
  unilaterally. Left as a candidate for a future, sitewide
  accessibility pass rather than a one-off fix scoped to this page
  alone.
