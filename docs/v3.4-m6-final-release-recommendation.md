# Version 3.4 Milestone M6: Final Release Recommendation

## 1. What this milestone shipped

- Homepage hero headline, subheading, eyebrow, and both CTA buttons (text and destination) are now genuinely admin editable, backed by a new `hero_content` `site_settings` key, following the exact established pattern from Version 2.1 Phase 5. Verified live: a direct database write reflected on the homepage with no deploy, no cache clear, no restart.
- The featured book cover and its adjacent CTA now share one anchor element, so the cover is clickable to the same destination as the CTA, with no duplicate link and no reintroduction of the redundant-link accessibility defect a past review had specifically fixed.
- The branding CMS's `email` slot, previously stored but never consumed, now genuinely drives every transactional email's logo, with a same-value fallback so existing emails are visually unchanged until an admin explicitly assigns a logo.
- The admin sidebar logo, previously an independent hardcoded reference, now participates in the same centralized branding system (and the same dark-mode swap) the public site already had.
- Five concrete, evidenced responsive defects were fixed (admin table overflow, product-title overflow in the cover placeholder, footer grid breaking at tablet width, and touch-target sizing on five sparse admin controls), and two more (a deliberate nav breakpoint, three smaller bespoke breakpoints) were investigated and explicitly not changed, with the reasoning recorded rather than hidden.

## 3. Phase 6: email and generated asset findings not covered elsewhere

The Branding Consistency Report covers the email logo fix and the color-drift finding. Two further findings from this milestone's Phase 6 audit, not about branding specifically:

- **Dark mode**: none of the 13 email templates implement any `prefers-color-scheme` handling. Several mail clients (notably Apple Mail) apply their own automatic dark-mode color inversion to emails that do not opt out, which can produce unpredictable results against a template with a fixed navy header and fixed light body background (an auto-inverted navy header could turn a light color, fighting the white logo/text drawn on top of it). This was not fixed this milestone (it is a real design decision, not a quick fix) but is recorded as a genuine, previously unreported gap.
- **Accessibility**: the shared layout correctly uses `role="presentation"` on its layout tables (so screen readers do not announce them as data tables) and, after this milestone's logo fix, the logo image now always carries real alt text via `{{LOGO_ALT}}`. Text color contrast within the templates was not independently measured against WCAG thresholds in this pass; this is recorded as unverified rather than asserted as passing.

## 4. Phase 7: SEO findings not covered elsewhere

- **Why older snippets may still appear in Google Search despite production updates**: two independent, compounding reasons, both confirmed by direct inspection rather than assumption. First, `sitemap.xml` is a static, hand-maintained file whose own header comment states detail-page entries are omitted by design and must be added manually "as content goes live." Any product, blog post, or resource published through the CMS since the sitemap was last hand-edited is not in it at all, meaning Google may not have discovered that page's current content yet through the sitemap, independent of any caching. Second, even for pages Google has crawled, its own search-result snippet cache refreshes on its own schedule, not on this site's publish cadence, so a very recent content edit can take real time to appear in search results regardless of how quickly it appeared on the live site.
- **Confirm the current implementation is technically correct**: per-item SEO (product, blog, resource detail pages) is properly templated through a shared `renderShell()` function in each route file, backed by real, admin-editable D1 columns (`seo_title`, `seo_description`, `seo_canonical_url`) with sane fallbacks when a field is blank. Book structured data (JSON-LD) is generated from the same live product row, not a separate, driftable copy. This is technically correct and does not need remediation.
- **What is recommended, and why each recommendation genuinely helps indexing**: automate `sitemap.xml` generation from the D1 product/blog/resource tables via a new route (directly addresses the discovery-lag cause identified above, rather than leaving it as a manual step someone must remember); add a site-wide Organization schema and default social-image setting as a new `site_settings` key (per the CMS Architecture Audit Report's Section 3), replacing the currently-duplicated static tags with one source of truth, reducing drift risk without changing what is actually indexed today. No other SEO change is recommended: this audit specifically did not find evidence that any other change (for example, adding more keywords, or restructuring existing correct markup) would move the needle, and the brief's own instruction was to recommend only genuine improvements, not busywork.

## 5. What still separates Robayer WealthLab from a mature enterprise publishing platform

Reported in full, per the brief's explicit instruction not to hide remaining work:

1. **Navigation and footer management**: no admin mechanism exists at all. Both require a genuinely new schema decision (see the CMS Architecture Audit Report, Section 3), not a quick fix, and are the largest remaining gap in "the Admin Panel as single source of truth."
2. **Testimonials and FAQs**: neither has real backing content or a CMS mechanism. FAQs in particular are hand-duplicated across seven pages in two different formats (visible accordion and JSON-LD), a real drift risk today.
3. **Global SEO settings**: Organization schema, default social image, and similar site-wide values are static and duplicated per page, with no admin panel exposure at all.
4. **Email template body copy**: bundled at Worker build time, requiring a code deploy for any wording change. Building a template-editor admin UI is a materially larger feature than anything else in this milestone.
5. **Receipt PDF branding**: no embedded logo, unrelated hardcoded colors. The one generated document customers keep does not visually match the brand.
6. **Email/website color drift**: already measurably happened once (two different hardcoded greens across templates, neither matching the current website green). The "kept in sync by convention" approach has no enforcement and will drift again.
7. **Sitemap automation**: currently manual, a direct, confirmed contributor to indexing lag (Section 4 above).
8. **Three small bespoke CSS breakpoints** (admin Product Editor, Goal Planner, admin `.editor-field-row`) deviate from the documented system with no recorded justification, unlike the main nav's deliberate exception.
9. **Five icon-only admin controls** (modal/drawer close buttons, dense toolbar buttons) remain below the 44px touch-target floor; the sparse controls were fixed this milestone, but these denser layouts need their own individual check before a blind size increase.

## 6. Recommendation

Release Version 3.4 Milestone M6 as complete for its stated scope: completing the CMS architecture for the content types this milestone specifically targeted (hero section, branding centralization, the responsive defects found), not for every editable surface on the site. Every acceptance criterion is either fully met or partially met with the exact remaining gap named and justified, matching the brief's own instruction that a partial result must be disclosed, not hidden.

The nine items in Section 5 are real, and none were found to be quick fixes disguised as bigger ones on closer inspection; each genuinely needs its own scoped milestone (a navigation/footer schema, a testimonials/FAQ table, a template-editor UI, a sitemap-generation route). Recommend treating Section 5 as the seed of a Version 3.5 or M7 backlog, prioritized roughly in the order listed: navigation and footer management first (the largest gap against "single source of truth"), sitemap automation second (cheapest fix with a direct, confirmed indexing benefit), and the remaining items after, since none of them block production readiness on their own.
