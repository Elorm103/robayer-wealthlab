# Version 5.0 — Milestone 2 Engineering Report: Knowledge Base

**Status:** Implementation complete, tested, type-checked, zero regressions. **Not yet deployed to production** — Vectorize index creation, migration, and the first real indexing run are gated behind founder confirmation (see "What Is Not Yet Verified" below).

## 1. Objective

Build the permanent knowledge layer for Robayer WealthLab: a single trusted source of platform content that every future AI capability queries before falling back on model knowledge. This milestone builds the indexing and retrieval infrastructure only. Customer AI — the feature that would actually surface Knowledge Base answers to a customer — is explicitly out of scope, per the founder's instruction to "stop before Customer AI."

## 2. What Was Actually Indexable — A Correction to the Original Design Doc

The pre-Milestone-2 planning document (`v5.0-knowledge-base.md`) assumed most requested content categories were already database-backed, flagging FAQs and policies as "the one genuine gap." Direct inspection of the codebase (routes, `wrangler.jsonc`'s route table, the real `sitemap.xml`, and `content/SCHEMA.md`) found this was wrong for most categories:

| Requested category | Actual source |
|---|---|
| Blog | Real D1 table (`blog_posts`), Worker-rendered detail pages |
| Resources | Real D1 table (`resources`); no individual detail page — cited via the listing page anchor |
| Product descriptions | `products` table is transactional-only (price, status, SKU-like fields) — the real description content lives on the Worker-rendered `/books/{slug}/` page, not in D1 |
| Investment Centre, Policies, Services, Calculators, most top-level pages | Static HTML, zero database backing, served via GitHub Pages — **not** Worker routes |
| FAQs | No dedicated table; real FAQ content is embedded as `FAQPage` JSON-LD on static pages |
| Help pages | Do not exist anywhere on the platform |
| CMS content | One real settings row (`site_settings.hero_content`) |

This was surfaced to the founder directly rather than silently assumed, via two decisions:

1. **Vector storage**: Cloudflare Vectorize vs. embeddings-as-D1-rows. **Decision: Vectorize.**
2. **Static-page indexing mechanism**: since GitHub Pages content has no database record, the only honest way to index it is for the Worker to fetch the live public URLs, seeded from the site's own `sitemap.xml`. **Decision: crawl-based indexing is acceptable.**

Both decisions shaped the architecture described below.

## 3. Architecture

### 3.1 Reuse of Milestone 1 / 1.2

Per the brief's explicit instruction ("reuse the AI Gateway," "reuse the governance framework"), embeddings are never called directly against OpenAI. `services/ai/aiGateway.ts` gained a sibling function, `embedText()`, that runs through the **exact same governed pipeline** as `callAi()`: classification validation, provider-policy check, preventive budget enforcement (via a shared `checkBudget()`, refactored out of `callAi()` for this purpose), masking/retention via the existing `prepareStorageFields()`, and logging to the same `ai_usage_log` table. A new routing table entry, `'knowledge.embed'`, points at `text-embedding-3-small`. Every embedding call — whether from indexing or from a search query — is classified `PUBLIC`, since every source this milestone indexes is public-facing content.

This means the Founder Principle established in Milestone 1.2 — "No future AI product may ever communicate directly with OpenAI or any future provider" — holds without exception in the Knowledge Base.

### 3.2 New tables (migration `0036_knowledge_base.sql`)

Five tables, each with one job: `knowledge_documents` (the source-of-truth registry, doubles as the indexing queue via `status`), `knowledge_chunks` (retrievable text; the embedding itself lives in Vectorize, not D1), `knowledge_faqs` (Q&A pairs from JSON-LD, a distinct retrieval shape from generic chunks), `knowledge_indexing_runs` (run history, backs the dashboard), `knowledge_search_log` (one row per search, backs Search Diagnostics — the same "the log is the dashboard's data source" pattern as `ai_usage_log`).

`knowledge_documents.source_type` is already constrained to include values beyond what's indexed today — the schema anticipates the brief's "prepare but do not expose" list (customer documents, internal SOPs, engineering docs) without requiring a future migration for the column shape itself, only for new CHECK values and readers.

### 3.3 Pipeline

`documentSources.ts` → `chunking.ts` → `aiGateway.embedText()` → `KNOWLEDGE_INDEX.upsert()` → `knowledge_chunks`/`knowledge_faqs`, orchestrated by `indexingService.ts`.

- **Extraction**: `htmlExtraction.ts` uses Cloudflare's native `HTMLRewriter` to pull `<title>`, meta description, `<main>` text, and JSON-LD blocks from both live-fetched static pages and Worker-rendered product pages. FAQs are parsed from real `FAQPage` JSON-LD already present on the site — not re-derived from arbitrary HTML.
- **Chunking**: paragraph-boundary-aware, targets 300–500 tokens per chunk, with sentence-level splitting for any single paragraph that alone exceeds 600 tokens. Reuses the AI Gateway's own token estimator for consistency.
- **Staleness detection**: SHA-256 of the extracted text, compared against the stored `content_hash`. Incremental runs skip any document whose hash and status are unchanged; full rebuilds re-process everything (needed after an embedding-model change, since a new model invalidates every existing vector's comparability).
- **Versioning discipline**: matches the AI Gateway's own prompt-versioning precedent. A re-indexed document's old vectors are deleted from Vectorize only *after* the new ones are successfully written — there is never a window where a mid-reindex document has zero searchable content.
- **Background execution**: admin-triggered reindex/rebuild runs return `{started: true}` immediately and continue via `ctx.waitUntil()`, tracked in `knowledge_indexing_runs` and polled by the dashboard — the same fire-and-continue pattern this project's existing Cron Trigger already uses. There is no Cloudflare Queue here; the current indexable content volume comfortably fits one Worker invocation's wall-clock budget. A genuine Queue is the right next step if that volume grows by an order of magnitude.

### 3.4 Retrieval

`searchService.ts` embeds the query via the same governed `embedText()`, queries Vectorize for the nearest chunk vectors (over-fetched 4x to absorb post-filtering), and joins back to D1 for the actual text, title, and citation URL. **Vectorize only ever answers "which vectors are nearest" — D1 remains the single source of truth for `visibility`, `data_classification`, and `status` filtering.** This is a deliberate choice: Vectorize's own metadata-filter DSL was not relied upon for anything security- or correctness-sensitive.

Confidence bucketing (`high` ≥ 0.75, `medium` ≥ 0.5, `low` below) is an engineering-judgment placeholder, not a calibrated threshold — see Known Limitations.

### 3.5 Testing strategy for an unsimulatable binding

Miniflare has no local Vectorize simulation (confirmed via its own runtime warning: "Vectorize Index bindings do not support local development"). Rather than skip vector-dependent tests, `tests/knowledgeTestHelpers.ts` provides a real in-memory implementation with genuine cosine-similarity ranking, so ranking-sensitive assertions (confidence bucketing, top-score ordering) are still meaningful, not just "some result came back."

Outbound calls to the real site (`robayerwealthlab.com/sitemap.xml`, live page fetches) and to OpenAI's embeddings endpoint are routed through the project's existing `outboundMock.ts` mechanism, extended with a new hostname case — the same mechanism already used for Paystack, Resend, and OpenAI chat completions throughout this engagement. Without this, test runs would have fetched the real live site.

## 5. Two Bugs Found and Fixed During This Milestone's Own Test Development

Both were caught by tests written for this milestone, not discovered later:

1. **Version double-increment.** `processDocument()`'s final success-path update unconditionally ran `version = version + 1`, but a brand-new document's row is inserted with the schema's own `DEFAULT 1` — so a document's first-ever successful index produced `version = 2`, not `1`. Fixed by making the increment conditional on whether the document already existed before this run (`existingId !== null`), which `processDocument()` already receives as a parameter.
2. A test-only gap (not application logic): the "full rebuild" test passed a hardcoded, unseeded admin ID into a column with a foreign-key reference to `admin_users`, causing a constraint failure. Fixed by seeding a real admin row, matching the pattern already established in `aiGateway.test.ts`.

## 6. What Is Not Yet Verified

Per the brief's "verify with real content already on the platform" instruction, this section is deliberately honest about what has and has not happened:

- **No real content has been indexed yet.** The Vectorize index (`robayer-knowledge-base`) has not been created — `wrangler vectorize create` has not been run. This is intentional: per this project's standing convention across every prior milestone, infrastructure creation and deployment require founder confirmation first (Task #113).
- Everything described as "tested" above was tested against **synthetic seeded content** (test-inserted blog posts, mocked sitemap/page fetches) run through the fake in-memory Vectorize double — not the real platform's actual books, blog posts, or Investment Centre pages.
- Genuine end-to-end verification — running a real indexing pass against the live site, confirming what got indexed and what didn't, and confirming search actually retrieves real content with correct citation URLs — can only happen *after* the Vectorize index exists and migration `0036` is applied to remote D1. That work is scoped to Task #113 and will be documented separately once it happens, with real counts and real search results, not projected ones.

## 7. Known Limitations

- **Crawl-based staleness for static pages.** Static pages (Investment Centre, Policies, Services, most top-level pages) have no database change-tracking — re-indexing means re-running the crawl against the live sitemap, not an automatic push when content changes. A content editor updating a static page will not be reflected in search until the next indexing run.
- **Uncalibrated confidence thresholds.** The 0.75/0.5 high/medium/low cosine-similarity cutoffs in `searchService.ts` are engineering-judgment starting points, not calibrated against real query/result pairs — there is no real search traffic yet to calibrate against. Revisit once `knowledge_search_log` has accumulated genuine history.
- **No Cloudflare Queue.** Background indexing runs via `ctx.waitUntil()` within a single Worker invocation. This is adequate at today's content volume but has a real scale ceiling; a Queue-based redesign is the right next step if indexable content grows by an order of magnitude.
- **Embedding cost is ongoing, not one-time.** Every incremental/full-rebuild run re-embeds every changed (or, for a full rebuild, every) document's chunks through the AI Gateway, which is metered and budgeted like any other AI Gateway call — this is not a zero-marginal-cost operation, and repeated full rebuilds should be used deliberately (e.g. after an embedding-model change), not as a routine maintenance habit.
- **Resources have no individual citation page.** Since `/resources/` has no per-item detail route, resource search results cite the shared listing page with an anchor fragment (`#slug`), not a dedicated URL — a less precise citation than blog posts or products get.
- **`data_classification` on `knowledge_documents` is a content-lifecycle label (PRODUCTION/INTERNAL/DEVELOPMENT/UNKNOWN), not the same field as the AI Gateway's request-sensitivity classification** (PUBLIC/INTERNAL/CONFIDENTIAL/etc. from Milestone 1.2). Both use the word "classification" for a different axis — worth flagging so a future engineer doesn't conflate the two when extending either system.

## 8. Explicitly Out of Scope (By Design)

Per the founder's instruction, Customer AI — any feature that would let a customer actually query this Knowledge Base — is not part of this milestone. The `searchKnowledge()` function exists and is tested, but nothing in the current admin routes or frontend exposes it to a customer-facing surface. The admin Search Diagnostics tool is the only caller today, and it is `super_admin`-gated.
