# Version 5.0 — Recommendations for Milestone 3 (Customer AI)

Written from inside the Knowledge Base work, before any Customer AI code exists — these are observations about what Customer AI will actually be building on, not a design for Customer AI itself.

## 1. Resolve the Resources gap before Customer AI leans on it

If Customer AI is expected to answer "what do you offer / what resources do you have" style questions, do not assume the current Knowledge Base handles this well — it's confirmed, with evidence, not to. Either complete the topK-oversampling experiment (cheap, likely sufficient today given the resource library's small size) or index the `/resources/` catalog page as a first-class document (more durable as the library grows) before Customer AI ships anything that depends on resource discovery.

## 2. Do not surface raw confidence scores to customers without a UX decision first

The current high/medium/low buckets were calibrated for *admin diagnostic* use — deciding whether a retrieval result is trustworthy enough to act on. Whether and how to expose confidence to an end user (silently filter low-confidence results? show a "I'm not fully sure, but..." caveat? decline to answer below some threshold?) is a product decision Milestone 2.2 did not make and should not be assumed. The thresholds themselves may also need separate tuning for a "should I answer at all" decision versus a "should an admin trust this diagnostic result" decision — these are not necessarily the same question.

## 3. Treat the Knowledge Base's honesty guarantees as a floor, not a ceiling

Every answer the Knowledge Base can currently produce is a literal, D1-sourced chunk — there is no generation, no paraphrase, no synthesis. This means zero hallucination risk *within the Knowledge Base itself*, by construction. The moment Customer AI adds an LLM generation step on top of retrieved chunks (to phrase an answer conversationally, combine multiple chunks, etc.), that guarantee no longer automatically holds — it becomes Customer AI's own responsibility to ensure generated text stays grounded in what was actually retrieved, not just cite it as a source. Plan for this explicitly rather than assuming grounding is inherited for free.

## 4. Reuse `searchKnowledge()` directly — do not reimplement retrieval

Everything Customer AI needs from retrieval (visibility scoping, classification filtering, reranking, confidence) already exists in `services/knowledge/searchService.ts`. The only thing Milestone 2 explicitly deferred was exposing this to a customer-facing caller (`actorType: 'customer'` is already a valid, tested value in the request shape) — Customer AI's job is to call this function with the right actor context and rate-limiting, not to build a parallel retrieval path.

## 5. Search Analytics today is 100% admin/diagnostic traffic — plan for the shift

Every row currently in `knowledge_search_log` came from an admin testing the tool, not a real customer. Once Customer AI goes live, this same table will suddenly carry real usage patterns at a different volume and distribution than anything the current analytics or confidence calibration was validated against. Re-run the same evidence-based recalibration process this milestone used (real scored queries → derive thresholds), don't assume the numbers from a 7-query admin smoke test still hold at customer scale.

## 6. Decide on content-change re-indexing before it becomes a support problem

Today, editing a blog post or resource does not automatically update what's searchable — someone has to manually trigger a reindex. This is invisible to admins today (the site's obvious source of truth is the CMS edit, and nobody's asking the Knowledge Base a live question about it yet). It stops being invisible the moment Customer AI answers a question with stale content from before an edit. Task 6's infrastructure (`enqueueContentChangeReindex()`) is ready and tested — wiring it into the actual CMS save routes is a small, well-scoped piece of work worth doing *before* Customer AI ships, not after a customer notices a wrong answer.

## 7. The dead-letter design assumption may not hold at Customer AI's scale

Task 7's reused-queue dead-letter approach was justified specifically because document-level indexing failures are rare and self-healing (caught immediately, never retried). That reasoning doesn't automatically extend to whatever new failure modes a customer-facing query path introduces (e.g., rate limiting under real traffic, cost-budget rejections under real volume via the AI Gateway's own governance). Revisit whether the existing AI Gateway budget/retry/error-handling patterns (already built in Milestone 1.2) are sufficient for customer-facing query volume, or whether Customer AI needs its own failure-handling layer.

## 8. Keep the "index is the source of truth, not the model" principle explicit in Customer AI's own design

This has been the organizing principle of the entire Knowledge Base effort (Milestones 2 through 2.2) — every answer traces to an indexed chunk, nothing is invented. Whatever Customer AI's actual architecture turns out to be, this is worth stating as an explicit, testable design constraint from day one, not an implicit assumption that erodes as generation gets layered on top.
