# Version 3.2 - Sprint M4A - Architecture Review

Determines whether the existing architecture supports the candidate next milestones unchanged, and names the minimum necessary evolution where it does not. Governing principle, inherited unchanged from every prior architecture review in this project's history: **avoid redesign unless justified.**

---

## Frontend

**Current shape:** Zero-build, zero-framework static HTML + vanilla JS, GitHub Pages-hosted, same-origin Worker for `/api/*` plus server-rendered `/books/*`, `/blog/*`, `/resources/*`, `/free-guide/*`.

**Supports unchanged:** Reviews UI, coupon entry at checkout, notification center, search UI, wishlist UI - every one of these is a new page or a new component in the existing `js/components/*.js` pattern, no different in shape from what M3 already built for the dashboard. **No framework migration is justified by any near-term candidate feature.**

**Requires evolution for:** Video lessons (a real video player component and a genuinely new asset-delivery pattern - R2 does not natively stream/transcode video the way it serves static files today); a course "player" UI with progress state (more stateful than anything this frontend currently does, though still buildable in vanilla JS - this project's own precedent for stateful, multi-step UI, `js/components/admin/*`, shows the pattern scales without a framework, just with more component code).

## Backend

**Current shape:** ~110 routes across `backend/routes/{admin,customer,*}`, dispatched via `URLPattern` matching against a flat `ROUTES` array in `worker/index.ts`, no router dependency. Proven to scale from M1's handful of routes to today's ~110 without needing a router library - this pattern has no near-term ceiling.

**Supports unchanged:** Every near-term candidate feature (reviews, coupons, notifications, search improvements, sales analytics extension) fits the existing route-file-per-concern pattern exactly - `routes/reviews.ts` + `routes/admin/reviews.ts`, `routes/customer/coupons.ts` or similar, following the identical shape M2's/M3's own new route files already established.

**Requires evolution for:** A course/lesson content model (new service layer, genuinely new domain logic - "has the customer completed lesson 3 of 8" is not a shape any existing service handles); notifications at scale (the "customer notifications" candidate, if it means more than email, needs either a new `notification_queue` table with in-dashboard read/unread state - already named in the ratified Blueprint's M6 scope - or it's out of scope for now).

## API

**Current shape:** Consistent envelope (`{success, data}`/`{success:false, error}`), consistent auth middleware chain (`requireCustomerAuth`/`requireAuth` + CSRF + rate limiting), consistent no-enumeration ownership pattern. This consistency is a real asset - every new endpoint this project has added since M1 has been reviewable against an established, proven pattern rather than invented fresh each time.

**Supports unchanged:** Every near-term candidate feature. No API redesign is justified.

## Database

**Current shape:** 19 migrations, all additive (confirmed: zero `ALTER`/`DROP` beyond the one `0017` scaffolding migration's column additions), D1 as the single source of truth for all content (a deliberate, proven-out architectural choice per `v2-same-origin-architecture.md`'s own migration-strategy work).

**Supports unchanged:** Reviews (one new table, `product_reviews`, structurally identical in shape to the existing `consultation_requests`/`contact_messages` precedent this codebase already has two working, well-tested examples of); coupons (already fully designed in `v3-database-design.md` - `coupons`/`coupon_redemptions`, ready to implement as-is, no new design work needed); notifications (`notification_queue`, already named in the ratified Blueprint's M6 scope).

**Requires evolution for:** Courses/lessons/progress tracking (a genuinely new schema domain - lessons, modules, per-customer progress state, none of which resembles any existing table); a real multi-item cart (would touch `purchase_sessions`'s own one-product-per-session shape, a materially larger change than any other candidate on this list - not recommended without its own dedicated architecture review, consistent with how seriously this project has always treated changes to the order-of-record).

## Authentication

**Current shape:** Two fully separate identity systems (`customers` and `admin_users`/`platform_users`-to-be, per ADR-004's deliberate permanent separation), both mature, both independently security-reviewed at every milestone.

**Supports unchanged:** Every near-term candidate feature. No candidate feature requires a new identity system or a change to the customer/admin separation.

## Dashboard

**Current shape:** Five pages (My Library, Purchase History, Receipts, Licenses, Account Security), the `dashboard-auth.js`/`dashboard-shell.js` split proven across three milestones now (M3B built it, M3C found and fixed its one real gap, M3D/M3E/M3F re-verified it repeatedly in production).

**Supports unchanged:** A sixth page (e.g., "My Reviews," a wishlist page, a notification center) is a direct, proven extension of the existing pattern - add a page, add a nav link, add a component script, reuse `requireSession()`. No architectural change needed for any near-term candidate.

## Downloads

**Current shape:** Mint-then-redeem single-use tokens, mature, unchanged since M1, independently re-verified through M3E.

**Supports unchanged:** Every near-term candidate feature. No candidate feature touches this system.

**Would require evolution for:** Video lessons specifically - the existing download-token pattern assumes "deliver a file once, the customer now has it" (a completed download). Video lessons imply repeated, streamed access to the same asset, a different access model entirely. This is one of the clearest, most concrete pieces of evidence that video lessons are architecturally further away than any other candidate feature on the list.

## Security

**Current shape:** No open finding. Every new endpoint added since M2 has followed the same CSRF/ownership/rate-limit/no-enumeration pattern, independently verified at every milestone.

**Supports unchanged:** Every near-term candidate feature - the existing pattern is proven to extend cleanly (M3's three new endpoints all followed it without incident, aside from the one self-revocation gap M3C caught, which was itself a missed *application* of an existing pattern, not evidence the pattern itself doesn't scale).

## Deployment

**Current shape:** Two-component deploy (Worker + GitHub Pages static site), no schema-migration dependency unless a migration is actually needed, proven safe across four consecutive production deployments (M1, M2, M3, and this session's own M3E).

**Supports unchanged:** Every near-term candidate feature deploys through the identical, already-proven process.

## Performance

**Current shape:** No load/performance testing exists anywhere (a named gap, not new to this review). D1/Workers has comfortable headroom at current real traffic.

**Requires attention, independent of M4's feature choice:** Establish a performance baseline before any milestone that would meaningfully increase traffic (most likely a growth/marketing-focused effort, not a feature milestone per se). Not a blocker to starting M4.

## Accessibility

**Current shape:** WCAG-conscious throughout, independently verified at every milestone (M3's own review found and fixed one real contrast defect, and the review process itself is now proven to catch this class of issue reliably).

**Supports unchanged:** No candidate feature requires an accessibility-architecture change - only the same "verify contrast, keyboard nav, focus rings" discipline already applied consistently since M1.

## Documentation

**Current shape:** Extremely thorough per-milestone documentation (this project produces 15-20 documents per milestone, every one independently checked for accuracy at every review stage) - but also, per the ratified Blueprint's own Gap Analysis, carrying a real "documentation sprawl" problem (~180 files in `docs/` as of this review, many pre-dating the current governance discipline and never consolidated).

**Recommendation, independent of M4's feature choice:** The Blueprint's own Executive Recommendation #5 ("schedule the documentation consolidation... partially discharged by this ratification itself; broader consolidation remains open") is still open. Not urgent, not a blocker, but worth naming again since it has now gone unaddressed across the entire M1-M3 lifecycle.

## Testing

**Current shape:** 135/135 passing, `@cloudflare/vitest-pool-workers` (real Workers runtime, not mocked), excellent coverage of the commerce-critical path, zero coverage of the admin panel or newsletter campaigns (see Technical Debt Review).

**Supports unchanged:** The testing infrastructure itself needs no change for any candidate feature - the gap is coverage of existing untested surfaces, not a limitation of the test tooling.

---

## Summary: Does the Current Architecture Support the Next Milestones Unchanged?

**Yes, for every near-term candidate feature this review recommends prioritizing** (reviews, coupons, notifications, search/recommendation improvements, sales analytics extension, email automation on top of the existing campaign system). Each fits the proven route-file / D1-table / dashboard-page pattern this project has now validated across three consecutive milestones.

**No, for the course-platform cluster specifically** (course/lesson content model, video lessons, learning progress tracking, digital certificates, instructor portal). These require genuinely new architectural surfaces - a content-and-progress domain model, a video-delivery mechanism structurally different from the existing download-token pattern, and (for an instructor portal) a third identity/permission surface beyond the existing customer/admin separation. None of this is disqualifying - it is simply real, non-trivial architecture work that should get its own dedicated planning sprint (an "M(course)A" of its own, mirroring how this project has always planned before building) once the business case is proven, not designed speculatively now.

**Minimum necessary evolution recommended for M4 itself:** none beyond new, additive tables and route files following the existing pattern exactly. No redesign is justified.
