# Version 3.0.2 - Sprint M2A - M2 Testing Strategy

Planning only. No test file was written. This strategy describes what M2B should build, reusing M1's proven test infrastructure rather than building new tooling.

---

## Reused infrastructure (no new tooling decisions needed)

M1 already built and proved, across 49 passing tests: `@cloudflare/vitest-pool-workers` running against real D1/KV bindings inside real `workerd`, a migration-application `setupFiles` hook, `tests/helpers.ts`'s seed-and-cleanup pattern, and - critically for M2 - `tests/outboundMock.ts`'s `outboundService`-based interception of outbound `fetch()` calls (Paystack, Resend), which M2 needs zero changes to reuse, since M2 introduces no new outbound provider call of its own (PDF generation and R2 storage are both first-party, no external HTTP call involved). M2B should extend the existing `tests/` directory, not create a parallel one.

## Unit tests

- `formatReceiptNumber()` - format correctness, year-boundary behavior, mirroring `purchaseReference.test.ts`'s existing coverage pattern for its sibling function (if no such test file exists yet for `formatPurchaseReference`, add one for both at the same time, closing a pre-existing gap while adding the new function's own coverage).
- Revocation-sync service function - given a purchase session with N licenses/deliveries, asserts all N licenses get `revoked_at` set and all N deliveries get `status = 'revoked'` in what the test can observe as a single atomic unit (no partial state visible if the operation is interrupted - test this by asserting both tables' state together, not each in isolation).
- Tax-breakdown computation function - isolated unit tests for both the "no VAT" empty-array path and (once the business answer arrives) the real computation path; written now against the empty-array case so the function's contract is locked in before the real logic exists.
- Fulfilment-loop quantity handling - given `order_items.quantity = N`, asserts exactly N `licenses` rows and N `deliveries` rows are created, each with a distinct `license_key` - the direct unit-level proof of ADR-009 compliance, independent of any real product ever having `quantity > 1` in production.

## Integration tests

- Full webhook-to-receipt chain: a verified purchase produces exactly one `order_items` row, N `licenses` rows, one `receipts` row, with `receipts.total_pesewas` equal to `purchase_sessions.amount_pesewas` - the direct integration-level check for the financial-integrity risk named in the Risk Assessment.
- `GET /api/customer/purchases` - returns only the authenticated customer's own purchases, correctly paginated, correctly empty for a zero-purchase customer (the empty-state data-contract requirement from the Customer Library UX Plan).
- `GET /api/customer/purchases/:reference` - returns the purchase for its owner; returns `NOT_FOUND` (not a distinct "forbidden" code) for a reference belonging to a different customer - the direct test of the Security Review's ownership-enumeration requirement below.
- `GET /api/customer/receipts/:receiptNumber/download` - authenticated customer receives their own receipt file; a session for a different customer requesting the same `receiptNumber` is rejected.
- Guest reference-scoped receipt flow: `POST /api/purchases/:reference/receipt-download` mints a token, `GET /api/download-receipt/:token` redeems it exactly once, a second redemption attempt with the same token fails - mirroring `download_tokens`' already-tested single-use discipline exactly.
- Revocation end-to-end: a test "refund" (calling the admin revoke endpoint directly, not through a UI that doesn't exist yet) sets both tables' state, and a subsequent download-token mint attempt against the now-revoked entitlement is correctly denied - this is the literal, named success criterion from the ratified Blueprint's own M2 milestone definition, and must be represented by an actual test, not merely asserted in documentation.
- Multi-item/multi-quantity purchase (synthetic test data, since no real product has `quantity > 1` today) - produces the correct number of independent license/delivery rows and one receipt whose `line_items` array has the correct number of entries.

## Negative tests

- Malformed/oversized `:reference` and `:receiptNumber` path parameters rejected before any database query (mirroring M1's existing `negative.test.ts` pattern for session tokens).
- SQL-injection-shaped and XSS-shaped values in any new path parameter, confirmed safely parameterized (same pattern M1's negative suite already established for `productId`).
- Requesting a receipt/license for a purchase session that exists but never reached `verified` status (still `pending`/`failed`/`expired`) - confirmed no receipt/license/order_items row exists for it, and the API returns a clean not-found rather than a partial or malformed record.
- Requesting the revoke endpoint for a purchase with no licenses/deliveries yet (e.g. still pending) - confirmed it fails cleanly rather than creating malformed revoked-but-never-issued records.
- Double-revocation (calling the admin revoke endpoint twice for the same purchase) - confirmed idempotent, no error, no duplicate state change, matching this codebase's established idempotent-by-construction convention throughout M1.

## Security tests

- **Receipt/license ownership enumeration**: confirmed that querying another customer's purchase/receipt/license through any authenticated M2 endpoint returns the identical response shape and status code a genuinely nonexistent resource would - never a distinct "exists but not yours" signal. This is the same no-enumeration discipline M1's `authService.login()`/`forgotPassword()` already established, applied to a new resource type.
- **Guest download-token security**: the new `receipt_download_tokens` single-use/short-TTL/random-generation properties tested with the same rigor `download_tokens` already received in M1 - garbage token rejected cheaply, expired token rejected, used token rejected, real token succeeds exactly once.
- **Admin revoke endpoint authorization**: confirmed it requires the existing admin session + CSRF, and that a customer session (even a valid, authenticated one) cannot call it - a customer-authenticated request to an admin-only route must be rejected the same way any other admin route already rejects one.
- **Rate limiting**: extend the same test pattern M2 closeout (Sprint 2B) already established for the M1 customer-auth endpoints to any new endpoint that should carry a limit (most plausibly the guest `receipt-download` mint endpoint, to prevent trivial enumeration-by-brute-force of reference values even though the reference format itself is not sequential/easily guessable).

## Regression tests

- Full re-run of M1's existing 49 tests after every M2 change, with zero expected change in outcome - M2 must not touch `checkout.test.ts`, `webhook.test.ts`, `customerAuth.test.ts`, `negative.test.ts`, `rateLimiting.test.ts`'s own assertions, only extend the webhook flow they already exercise.
- The existing guest, no-account, email-link download path (a purchase where the customer never sets a password) confirmed completely unaffected by every M2 change - the single most important regression check, given ADR-003's "preserved permanently" guarantee is the architectural promise M2's own revocation feature must not accidentally break for a customer who was never revoked.
- `TypeScript` typecheck (`tsc --noEmit`) clean after every change, same standing bar M1 held throughout.

## Acceptance tests

Directly against the ratified Blueprint's own M2 success criteria (Deliverable 11), each mapped to a concrete, checkable test above:

1. "A test purchase produces a receipt whose totals match the charged amount" - covered by the webhook-to-receipt integration test.
2. "A `tax_breakdown` structure populated according to the now-confirmed VAT status" - covered by the tax-computation unit tests, with the real-computation-path test only completable once the business answer arrives (tracked as an explicit follow-up, not a silent gap).
3. "A license whose type/terms are correctly recorded" - covered by the fulfilment-loop unit and integration tests.
4. "A test refund correctly sets both `licenses.revoked_at` and `deliveries.status = 'revoked'` in one operation, and a subsequent download-token request for that entitlement is correctly denied" - covered by the revocation end-to-end integration test.

M2B should not be considered feature-complete until all four map to a passing test, not merely a manual verification - matching the discipline the M1 Milestone Acceptance Review already established as the bar for this project (independent verification, not self-reported completion).
