# Version 3.2 - Milestone M4 - Rollback Strategy

**Written at M4E closeout**, resolving `v3.2-m4d-documentation-review.md` (Finding 2) and `v3.2-m4d-production-readiness-assessment.md`'s identification that M4C's migration carried no rollback documentation, unlike the precedent M2's own migration (`0019_ownership_layer.sql`) established - that migration's header comment points to its planning document's own rollback section. This document is M4's equivalent, referenced from `database/migrations/0020_reviews_and_coupons.sql`.

---

## Database Rollback

Migration `0020_reviews_and_coupons.sql` is purely additive: three new tables (`product_reviews`, `coupons`, `coupon_redemptions`) and two new columns on `purchase_sessions` (`coupon_id`, `discount_pesewas`). No existing table, column, or row is altered or dropped - matching migration 0019's own "all changes are additive" precedent exactly.

**To reverse, in dependency order** (children before parents, matching the FK direction):

```sql
-- 1. Drop the child table first (references coupons and purchase_sessions)
DROP TABLE IF EXISTS coupon_redemptions;

-- 2. Drop product_reviews (references products, customers, purchase_sessions, admin_users)
DROP TABLE IF EXISTS product_reviews;

-- 3. Drop coupons (referenced BY purchase_sessions.coupon_id - must come after step 4)
--    and product_reviews/coupon_redemptions above, which reference it)

-- 4. Remove the two added columns from purchase_sessions - SQLite 3.35+
--    (D1's underlying engine) supports DROP COLUMN directly; run this
--    BEFORE dropping the coupons table, since coupon_id's FK would
--    otherwise reference a table that no longer exists (D1/SQLite does
--    not enforce FK existence retroactively, but this ordering avoids
--    ever having a dangling reference even transiently):
ALTER TABLE purchase_sessions DROP COLUMN discount_pesewas;
ALTER TABLE purchase_sessions DROP COLUMN coupon_id;

-- 5. Now safe to drop coupons itself
DROP TABLE IF EXISTS coupons;
```

**Data-loss implications, stated explicitly:** any coupon, redemption, or review data written after this migration was applied is permanently lost on rollback - there is no soft-delete or archival step. If real coupons or reviews have already been created in production by the time a rollback is ever considered, **do not run this rollback without first exporting the three tables' data** (`wrangler d1 export` or a manual `SELECT` dump) - this is a data-preservation decision for whoever executes the rollback to make deliberately, not an automatic step this document prescribes.

**`receipts.discount_pesewas` is explicitly NOT part of this rollback.** That column was added by M2's own migration 0019, not by M4's migration 0020 - rolling back M4 must never touch it. Every receipt row will simply have `discount_pesewas = 0` again post-rollback (the value M2 always wrote before M4 existed), which is correct, not a defect of the rollback.

## Worker (Application Code) Rollback

Standard `wrangler rollback` to the prior deployed Version, exactly as this project's own M2E/M2F deployment history already used - M4 introduces no new deployment mechanism, no Durable Object, no new binding that would make this behave any differently than it already does for every prior milestone.

**Ordering constraint, if a rollback is needed while both the M4 migration and M4 Worker code are live:** roll back the Worker code first, then the database. A Worker running M4's route handlers against a database that has already had the M4 tables dropped would fail loudly (missing-table errors) rather than corrupt data - the safer failure mode - but rolling back the Worker first avoids that failure mode entirely by removing the code paths that reference the M4 tables before those tables disappear.

## Deployment Rollback (Sequencing Discipline)

The same ordering discipline every prior schema-changing milestone in this project has already followed (e.g. M2E's own deployment sequence): **migrations apply before the dependent Worker code deploys, on the way in; Worker code rolls back before the migration reverses, on the way out.** This is not a new rule invented for M4 - it is the existing convention, restated here because M4's rollback specifically depends on getting this order right (an M4 Worker deployed against a pre-M4 database would fail on its very first coupon/review-touching request).

## Static Asset Rollback

M4 adds two new static admin pages (`admin/reviews/index.html`, `admin/coupons/index.html`) and three new/extended JS files (`js/components/product-reviews.js`, `js/components/admin/admin-reviews.js`, `js/components/admin/admin-coupons.js`) plus the extension to the pre-existing `js/components/buy-button.js`. These are served from the GitHub Pages static origin, not the Worker - reverting them is a normal `git revert` of the relevant commit(s) and a subsequent GitHub Pages redeploy, independent of the Worker/database rollback steps above. **`buy-button.js`'s M4 extension is additive and backward-compatible by construction** (`initCouponInput()`'s own early-return guard no-ops cleanly if the coupon markup isn't present - see the Production Readiness Assessment) - reverting the static assets alone, without also rolling back the Worker, does not break checkout; it only removes the coupon-entry UI, leaving standard checkout fully functional.

## Operational Rollback

No scheduled jobs, cron triggers, queues, or other operational infrastructure were introduced by M4 (confirmed via `wrangler.jsonc` inspection during the Production Readiness Assessment - `triggers.crons` remains empty). There is no operational state to reverse beyond the database and Worker code themselves - no queue backlog to drain, no in-flight scheduled job to cancel.

## Rollback Decision Guide

| Scenario | Action |
|---|---|
| A defect is found in the Worker code only (routes, services), database schema is fine | Worker rollback only (`wrangler rollback`) |
| A defect is found in the migration itself, before any real coupon/review data exists | Full rollback: Worker first, then database (steps above) - safe, no data-loss concern |
| A defect is found after real coupon/review data has accumulated | Export the three new tables first, then follow the full rollback sequence; consider whether a forward-fix is safer than a rollback once real user data is involved (matching this project's own general preference for forward fixes over rollbacks once user-facing state exists) |
| A defect is isolated to the frontend (a specific JS/HTML bug, API is fine) | Static asset revert only, no Worker or database change needed |
