# Version 3.5: Executive Dashboard Architecture Report

## Scope

Transformed `admin/index.html` from a six-card summary page into a full executive command centre, following the milestone brief's explicit instruction: "Do not redesign the admin panel. Instead, transform the Dashboard." No other admin page, no shared partial, and no existing endpoint was changed in a way that alters its own behavior. Every new capability is additive.

## What already existed and was reused, not rebuilt

Before writing any new code, the existing dashboard/analytics infrastructure was read in full:

- `services/admin/dashboardService.ts` (`GET /api/admin/dashboard/summary`) — kept exactly as-is; still used nowhere by the new page, but not removed, since other integrations may depend on it.
- `services/admin/analyticsService.ts` — the "no caching layer, real D1 aggregate" discipline and the current-vs-previous `KpiMetric` pattern were both carried forward into the new service rather than reinvented.
- `services/admin/settingsService.ts`'s `getSettingsStatus()` — already computed genuine Paystack/Resend/system diagnostics (secret-configured, last successful payment, per-template email stats, app version, deployment metadata, current migration). The new health panel calls this directly rather than re-deriving any of it.
- `js/components/admin/timeseries-chart.js` — the project's existing dependency-free inline-SVG line chart, extended (not replaced) with a `renderBarChart()` function for categorical data (payment channel breakdown), using the identical hand-rolled-SVG philosophy documented in that file's own header comment ("this platform's real data volume doesn't justify [a charting library] dependency").
- `.stat-card`, `.card`, `.table`, `.admin-table-wrap`, `.empty-state`, `.badge--success/warning/error`, `.grid--2/3/4` — every existing admin.css component class was reused unchanged. Only three genuinely new class families were added: `.health-grid`/`.health-item` (health panel), `.alert-list` (alerts), `.quick-actions`.

## A real, pre-existing gap found and fixed along the way

`services/admin/settingsService.ts`'s `appVersion` field reads `packageJson.version` — but `backend/package.json`'s version had never been bumped past `0.1.0`, despite this project having shipped through Version 3.4.3 across many milestones. This diagnostic has been silently wrong every time anyone looked at it. Fixed by bumping `package.json` to `3.5.0` and treating this as the same "bump on every release" discipline the project already applies to its cache-busting query strings.

A second, more consequential gap: "Last successful Cron execution" had no real signal to read at all. The Cron Trigger (`review-reminders`) only ever wrote data when it found something due to send — a quiet day with zero reminders due would look identical, from the outside, to the Cron never having fired. Fixed by adding an unconditional heartbeat write (`audit_logs`, `action: 'cron.heartbeat'`) at the end of every `scheduled()` invocation, success or failure, in `backend/worker/index.ts`.

## New backend surface

Six new endpoints, all under `/api/admin/dashboard/*`, all `requireAuth`-gated exactly like every existing admin analytics endpoint (open to all three roles — nothing here is mutable):

| Endpoint | Backs |
|---|---|
| `GET /health` | Phase 1 (Business Health panel) |
| `GET /executive-summary` | Phases 2, 7, 9, 10 (KPIs, revenue intelligence, publishing inventory, financial breakdown) |
| `GET /charts?from=&to=` | Phase 3 (sales analytics) |
| `GET /customer-insights?from=&to=` | Phases 4, 8 (customer analytics, experience metrics) |
| `GET /operational` | Phase 5 (recent activity feeds) |
| `GET /alerts` | Phase 6 (business alerts) |

Two new services back these: `systemHealthService.ts` (health checks only) and `executiveDashboardService.ts` (everything else). Kept as two files rather than one, matching the existing convention of separating health/diagnostics concerns (settingsService.ts) from business-metric concerns (analyticsService.ts).

## Design decisions worth recording

- **Health checks are real, live probes, not configuration flags.** Paystack and Resend connectivity are each verified with an actual, side-effect-free API call (Paystack's bank-list endpoint, Resend's domain-list endpoint) on every uncached check — not merely "is a secret key present." A key that is set but revoked is correctly reported as unhealthy.
- **60-second KV cache on health only.** Every other endpoint queries D1 directly and fresh on every load, matching this project's established "real row counts don't justify caching yet" position. Health is the one section making live outbound HTTP calls on every check, so it alone is cached, per the milestone's own Phase 13 performance instruction.
- **Alerts are asserted from real conditions only.** No alert type in the milestone brief that this service could not honestly compute from existing data was implemented — see the Operational Monitoring Report for the one item (a hardcoded "expected migration count") deliberately left out, and why.
- **One field the brief asked for was intentionally omitted**: "Top Referrers." This codebase stores no referrer field anywhere. Rather than approximate it from Paystack's `metadata.referrer` (present in only some transactions, not a structured or queryable column), the dashboard states plainly that this data does not exist, matching the existing Analytics page's own precedent for Cloudflare Web Analytics ("its dashboard has no API — these numbers can't be embedded here honestly").
- **Quick Actions omits "Export Customers" and "Backup Database."** Neither has a real, existing implementation anywhere in this codebase. Building a button that calls nothing, or hastily wiring a new export/backup feature not requested by any other part of this brief, would have introduced exactly the kind of placeholder this milestone explicitly forbids.
