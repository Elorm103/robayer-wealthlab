Deploying the migration without the Worker update is safe on its own (purely additive, and the currently-live M1 Worker code never references the new tables) - so if these two steps must be split across a maintenance window, applying the migration first and deploying the Worker second is the only safe order, never the reverse.

## 4. Rollback procedure

**Schema rollback (if needed after the migration is applied but before/without the Worker deploy):** Every change in migration `0019` is additive only - 4 new tables (`order_items`, `licenses`, `receipts`, `receipt_download_tokens`), 0 altered tables, 9 new indexes. No existing column, table, row, or constraint is altered or dropped. Because of this:

- **Preferred rollback path:** do nothing to the schema. An additive-only migration left in place causes no harm even if the Worker deploy is rolled back separately - the currently-live M1 Worker code simply never reads or writes the new tables. Rolling back the *Worker* to the pre-M2 version (`wrangler rollback` to the `d83bc5f3` deployment recorded in Section 3, or any deployment before it) is sufficient to fully undo M2's user-facing behavior without touching the database at all.
- **Full schema rollback (only if the new tables must be physically removed, e.g. for a compliance reason):**
  ```sql
  DROP TABLE IF EXISTS receipt_download_tokens;
  DROP TABLE IF EXISTS receipts;
  DROP TABLE IF EXISTS licenses;
  DROP TABLE IF EXISTS order_items;
  ```
  This must only be run after the Worker has already been rolled back to a pre-M2 version (running it while M2's Worker code is still live would break the order-artifact-creation step and every Customer Library/receipt-download endpoint immediately). Not tested against a live D1 instance in this sprint (per the "do not deploy" instruction). Given these four tables hold financial/audit records (`v3.0.2-commerce-architecture-blueprint.md`'s Data Governance section: "Financial records - Never deleted"), a full `DROP` should be treated as an exceptional, deliberately-authorized action, not a routine rollback step - the "leave it in place, roll back the Worker" path is the one actually expected to be used in practice, matching M1's own checklist's identical conclusion for its own tables.

**Rollback readiness verdict: Ready.** The additive-only schema design means the low-risk rollback path (Worker-only rollback, leave schema in place) requires no database action at all and is always available.

## 6. Deployment prerequisites

- [x] **Confirmed (read-only)**: the `STORAGE` R2 binding is present in `wrangler.jsonc`'s `r2_buckets` list - already live, reused unchanged from every prior digital-fulfilment feature. M2 stores generated receipt PDFs at `receipts/{receiptNumber}.pdf` in this same bucket; no new bucket is provisioned or required.
- [x] **Confirmed (read-only, run 2026-07-25)**: no `site_settings` row for `vat_registered` exists in production - `wrangler d1 execute robayer-wealthlab-db --remote --command "SELECT value FROM site_settings WHERE key = 'vat_registered'"` returned zero rows (`rows_read: 0`). **This is the one item this checklist treats as a hard pre-deployment gate, not a routine box to check**, and it is currently in its safe state. Per the M2C Acceptance Report and the M2 Implementation Report's Known Limitations: `computeTaxBreakdown()`'s real computation logic is not implemented; if `vat_registered` is ever set to `'true'` in production before that logic ships, every receipt issued from that point forward would claim VAT-registered status while still showing an empty tax breakdown - an internally inconsistent, potentially non-compliant receipt. **Re-run this exact query immediately before deploying** (not only at the time this checklist was written) - it costs nothing and this is the one condition on this checklist capable of producing a legally-relevant defect, not merely a functional one.
- [ ] Notify whoever monitors R2 storage/costs that a new object prefix (`receipts/`) will start appearing after this deploy - expected to be small (a few KB to low hundreds of KB per receipt, per the M2A Risk Assessment), not a meaningful cost concern at this project's realistic transaction volume, but worth knowing what the new prefix is for.

## 7. Verification checklist after deployment

To be run by the operator after both the migration and the Worker deploy complete. None of these were run against production during this sprint.

1. `wrangler d1 migrations list robayer-wealthlab-db --remote` returns "No migrations to apply" (confirms migration `0019` landed).
2. `GET /api/health` (or the site's existing health-check route) returns `200` (confirms the new Worker build - now including its first-ever runtime npm dependency, `pdf-lib` - started cleanly).
3. Perform one real, small-value test purchase through Paystack's actual Live or Test mode (whichever is configured) and confirm: the purchase completes, the webhook is received and verified, `order_items`/`licenses`/`receipts` rows are created (check via `wrangler d1 execute robayer-wealthlab-db --remote --command "SELECT id, receipt_number, total_pesewas FROM receipts ORDER BY id DESC LIMIT 1"`), and the receipt total matches the actual charged amount.
4. From that same test purchase's confirmation page (`GET /api/purchases/:reference`), confirm the response now includes a non-null `receiptNumber`.
5. Mint and redeem a guest receipt download for that same test purchase (`POST /api/purchases/:reference/receipt-download`, then `GET` the returned `downloadUrl`) and confirm a real PDF streams back (`Content-Type: application/pdf`, non-trivial `Content-Length`).
6. Log in as that purchase's customer (if a password was set) and confirm `GET /api/customer/purchases`, `GET /api/customer/receipts`, and `GET /api/customer/licenses` all return the new purchase.
7. As an admin (`super_admin` or `editor` role), call `POST /api/admin/orders/:reference/refund` against that same test purchase and confirm: the response is `{refunded: true}`, a subsequent `POST /api/purchases/:reference/downloads` request is denied with `DOWNLOAD_NOT_AVAILABLE`, and `wrangler d1 execute ... "SELECT action, entity_id FROM audit_logs WHERE action = 'order.refunded' ORDER BY id DESC LIMIT 1"` shows exactly one new row with a non-null `entity_id`.
8. Confirm the existing, unrelated M1 flows (guest checkout with no password ever set, the email-link download path, customer login/session) still work unchanged - M2 must not regress anything M1 already shipped.
9. Watch `wrangler tail` (or the dashboard's real-time logs) for the first few minutes after deploy for any unexpected error rate on `/api/webhooks/paystack` specifically, and for PDF-generation latency inside that path (`receipt.pdf_generated`/`receipt.pdf_generation_failed` log lines) - the one new runtime behavior the M2A Risk Assessment flagged as not fully provable in a test environment.
