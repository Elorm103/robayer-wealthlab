## Review-Reminder Idempotency (Corrected)

Sprint M5D reproduced two genuine defects in the original Milestone M5C implementation: a single failed send permanently suppressed all future reminders for that purchase, and genuinely concurrent Cron Trigger invocations (Cloudflare's own documented at-least-once delivery guarantee) sent duplicate emails. Both are fixed in Milestone M5D.1 via a dedicated atomic claim table (`review_reminder_attempts`, migration `0022`) — see `docs/v3.3-m5d1-retry-idempotency-strategy.md` for the full design. Remaining, honestly-disclosed limitations of the corrected design:

- **A purchase whose send fails 3 times (`MAX_SEND_ATTEMPTS`) stops retrying and is marked `permanently_failed`**, even if the underlying cause was ultimately transient (e.g., a multi-day Resend outage exceeding 3 scheduled runs). This is a deliberate bound, not an oversight — retrying an unbounded number of times against a persistently-failing recipient risks masking a genuinely bad email address behind infinite retries. A `permanently_failed` row now writes a real, findable `customer.review_reminder_failed` audit log entry (closing the audit-visibility gap Sprint M5D also found), so this is discoverable and correctable by a human, not silent.
- **The staleness window for recovering an abandoned claim (`CLAIM_STALE_MINUTES = 10`) is a fixed constant**, not configurable at runtime. Chosen to comfortably exceed any single Worker invocation's own CPU/wall-time budget; revisit only if this platform's own scheduled-job duration profile changes materially.

## New Limitation Introduced by This Sprint's Own Fix

**Reconciliation's concurrency fix does not use a dedicated claim table the way review reminders now do.** It instead checks `meta.changes` on the existing linking `UPDATE` and re-derives the actually-affected rows via a follow-up `SELECT`. This is correct for the realistic race this system can actually produce (two concurrent `reconcilePurchases()` calls for the identical email, which always resolve to an all-or-nothing outcome in practice, since no other code path links these specific rows). It is a narrower fix than the review-reminder one, appropriate to a narrower risk (see `docs/v3.3-m5d1-review-reminder-concurrency-design.md` for why the two features needed different-shaped fixes despite sharing a root-cause class).
