# Version 3.3 Sprint M5B: Architecture Readiness Assessment

Independently determines whether M5's recommended scope (account reconciliation, visitor analytics, triggered review-request email) can be implemented using the current architecture, reviewing backend, frontend, APIs, database, security, and scalability.

---

## Account Reconciliation: Readiness Confirmed, One Design Detail Identified

**Required backend work:** a new endpoint (or an extension of an existing password-setup-adjacent route) that, given an email address, checks for verified purchase sessions with that `customer_email` and no `customer_id`, creates a customer record if one does not already exist, issues a password-setup token (reusing `customer_password_tokens`, independently confirmed present and already keyed to a `customer_id`), and, once the password is set, links every matching historical `purchase_sessions` row to the new or existing customer.

**Design detail this Board identifies, not present in M5A's own documents:** the existing `customer_password_tokens` table is keyed to an already-existing `customer_id`; for a person with no customer row at all yet (the entire orphaned population), a customer row must be created first, before a token can be issued. M5A's own scope description anticipates this ("a matching mechanism...to a newly-created or existing customers row"), so this is a confirmation of technical feasibility, not a new gap, but it should be stated explicitly in whatever implementation-level design document M5C produces, so the two-step sequence (create-or-find customer, then issue token) is not assumed to be a single existing call.

**Required frontend work:** one new page or form (a "claim your purchase" entry point), reusing the existing password-setup page pattern already proven at Milestone M1.

**Database impact:** no destructive change. `purchase_sessions.customer_id` is already nullable and already supports being set after row creation (confirmed: this is exactly what Milestone M1's own auto-provisioning already does for post-M1 purchases); reconciliation is an application of the same update pattern to older rows, not a new schema capability.

**Verdict: fully implementable with the current architecture.** No new authentication primitive, no new database capability, no framework change.

## Visitor Analytics: Readiness Confirmed

Cloudflare Web Analytics (or an equivalent) requires a script tag addition to the static site's own page templates; no Worker code change, no new binding, no new backend surface. This Board confirms this is the architecturally simplest item in the entire recommended scope.

## Triggered Review-Request Email: Readiness Confirmed, With One Operational Note

Requires a new Cloudflare Cron Trigger entry in `wrangler.jsonc` (currently empty, confirmed by direct inspection) and one new scheduled handler querying for eligible purchases and calling the existing email-sending service. **Operational note this Board adds:** the handler must be idempotent (safe to run more than once without double-sending), the same discipline already applied to every webhook-handling code path in this platform's history; this should be an explicit, tested requirement in whatever implementation proceeds, not merely assumed from precedent.

---

## Security Review of the Proposed Architecture

The account-reconciliation flow is the one item touching identity and, indirectly, financial history. This Board confirms the security property M5A's own Risk Assessment claims: `purchase_sessions.customer_email` is populated only from the payment provider's own confirmed payer email at verification time, never trusted from the client (confirmed by the column's own schema comment). This means the email a reconciliation flow would match against was already verified once, at the time of the original purchase, by Paystack itself, not by anything the claiming user types in now. Combined with a token sent to that same email before any account or link is created (the same pattern the existing password-reset flow already uses), this Board finds no new trust boundary is introduced beyond what already exists and has already survived independent security review at Milestone M3 and Milestone M4.

## Scalability

Not a concern at current volume for any item in this scope. No item introduces a new scaling category.

---

## Required Architectural Work Before M5C Begins

None beyond the Platform Fee Engine documentation amendment already identified in `v3.3-m5b-platform-fee-strategy-review.md`, which does not affect this scope's own architecture.

## Verdict

**M5's recommended scope can be implemented using the current architecture with no framework change, no new infrastructure category beyond one narrowly-scoped Cron Trigger, and no new authentication primitive.** The one design detail this Board identified (the two-step create-or-find-customer-then-issue-token sequence for the reconciliation flow) is a clarification for the implementation team, not a blocker.
