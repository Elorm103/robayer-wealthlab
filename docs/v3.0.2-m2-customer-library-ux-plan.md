# Version 3.0.2 - Sprint M2A - M2 Customer Library UX Plan

Prepared using the UI/UX Pro Max Design Intelligence skill. Planning only - no page was built, no component was written.

**Framing note, consistent with the Architecture Compliance Report:** the Customer Library, Purchase History, and Receipts *pages* are ratified Milestone M3 scope ("Checkout Auto-Provisioning + Dashboard MVP"), not M2. This document plans the UX and data shape M2's APIs must support so that M3 can build these pages with zero redesign and no missing field discovered late - it is forward-looking interface planning, not a page-build task for this sprint.

---

## Design intelligence findings applied

Queried the skill's product-type database for "customer account dashboard order history" and "customer account dashboard purchase history fintech trust Ghana." The closest, most relevant match: **Banking/Traditional Finance** - Primary style Minimalism + Accessible & Ethical, secondary Trust & Authority, Dashboard Style "Financial Dashboard," color focus "Navy + Trust Blue + Gold accents." This is not a coincidence worth ignoring: it independently confirms what the ratified Blueprint's own Deliverable 8 already concluded when it applied the same skill's Trust & Authority pattern - "applied to substance, not literal color palette; Robayer WealthLab's own established navy/green/gold brand system stays exactly as-is."

**Governing rule for M3's eventual implementation: do not introduce a new visual system for the Library.** Reuse the site's existing tokens (`css/tokens.css`), component classes (`.card`, `.field`, `.btn`, `.alert`), and typography (Newsreader/Space Grotesk/Work Sans/IBM Plex Mono) already established across the M1 checkout/account pages. The skill's own "Style Selection" priority rule (#4, High impact) is "match product type, consistency" - for an already-branded, already-shipped product, consistency with the existing system *is* the correct application of that rule, not a generic dashboard template.

Supplementary UX-domain queries applied directly below: Confirmation Dialogs (High severity - "confirm before delete/irreversible actions"), Empty States (Medium severity - "show helpful message and action, never blank screens"), Loading States (High severity - "skeleton screens or spinners, never a frozen UI"), Focus/Hover/Active/Disabled States (all flagged High/Medium severity for accessibility and interaction clarity).

## Library layout

A single "My Library" view, one row per **purchase** (not per line item - a multi-item order shows as one row with an expandable line-item list, consistent with `receipts.line_items` being one JSON array per purchase session). Each row surfaces, without a click: product title and cover thumbnail, purchase date, amount paid, status badge, and two direct actions (Download, View Receipt) - the two things a returning customer most needs, available in one glance, matching the ratified Blueprint's own Deliverable 5 statement of My Library's purpose: "entry point, every product owned."

Desktop: a table-like list (not a dense data-grid - this is a handful of purchases per customer at realistic volume, not an admin-scale table, so card-like rows with generous spacing serve better than a compressed grid). Mobile: the same rows stack to a vertical card list, each action rendered as a full-width tappable button, not a small icon-only control - the skill's Touch & Interaction priority rule requires a 44x44px minimum target and explicitly flags icon-only buttons without labels as an anti-pattern.

## Purchase history

A separate, chronological view (or a filter/sort mode on the same Library data, implementation detail for M3) emphasizing transaction facts over product presentation: date, reference, amount, status. This is the "receipt drawer" mental model - a customer checking "did I actually pay for this, and when" versus the Library's "what do I own, let me open it" mental model. Both views read from the same `GET /api/customer/purchases` response; the distinction is presentational, not a second API.

## Receipt downloads

One-click download from both the Library row and the Purchase History row, hitting `GET /api/customer/receipts/:receiptNumber/download` directly (no mint-then-redeem step needed for the authenticated path - see API Planning Report). Loading feedback required during the request (the skill's Loading States rule is flagged High severity): a brief inline spinner on the button itself, not a full-page loading state, since this is a small, fast, single-resource fetch.

## Download history

Distinct from *purchase* history: this is "how many times have I downloaded this, and when." Sourced from `deliveries.downloads_used`/`last_download_at` (already live, M1-unchanged fields) - no new schema needed for this view. Shown as a secondary line under each Library row ("Downloaded 2 times, last on [date]"), not a separate page - the ratified Blueprint's Deliverable 5 lists Downloads as its own dashboard page for direct re-download access, but the *history* aspect of it is naturally a detail within the Library row rather than a reason for a whole separate view at this data volume.

## Purchase status

Every purchase surfaces one of four customer-safe status words, mapped from `purchase_sessions.status`, never the raw internal enum: **Processing** (`pending`), **Ready** (`verified`), **Payment failed** (`failed`/`expired`), **Refunded** (`refunded`, once the revocation-sync mechanism exists). This mirrors the existing, already-live discipline in `getFulfilmentStatus()` - "customer-safe status (processing/ready/unavailable), never internal state names" - extended to cover the two new outcomes M2 introduces (refunded) rather than inventing a new vocabulary.

## Empty states

**Mandatory, not optional, per the skill's own flagged severity and per AR-009's specific ratification.** A customer with zero purchases must see a warm, specific, actionable message - "Nothing here yet. Browse our guides to get started," with a direct link to `/books/` - never a blank card or an empty table. This is the exact language AR-009 itself specifies ("an honest, helpful message with a clear next action... never a blank screen") and the skill's Empty States rule independently confirms as a Medium-severity requirement. Since M2 ships only the API, the *data contract* implication is: `GET /api/customer/purchases` with zero rows must return `{success: true, data: {purchases: [], total: 0}}`, a clean empty array, never an error - so M3's page can trivially detect "genuinely zero" versus "something went wrong" and render the correct one of the two states.

## Interaction and feedback details for M3 to inherit unchanged

- **Confirmation dialogs** (skill-flagged High severity): any future destructive/irreversible action reachable from the Library (there is none in M2's own scope, but the admin revoke action's UI, whenever built, must follow this) requires an explicit "Are you sure" step, never a direct action on click - matching AR-009's own ratified requirement for session revocation and account-deletion.
- **Success/failure feedback**: a receipt-download failure (expired session, revoked entitlement, genuine server error) must show a specific, human message inline, matching the exact honest-failure pattern already proven in `buy-button.js`/`set-password-form.js` - never a silent failure, never a raw error.
- **Accessibility**: every status badge must carry text, not color alone (skill's Charts & Data rule - "never rely on color alone to convey meaning" - applies equally to a status pill as to a chart); every action button keyboard-reachable with a visible focus ring, matching the site's existing, already-audited focus-state treatment from the pre-M1 accessibility pass.

## What M2 must NOT build

No page, no route beyond the API endpoints already listed in the API Planning Report, no new CSS, no new JS component. This document exists so that when M3 begins, the page-building work has zero open UX questions and zero missing API field to discover mid-build - not to pull page work forward into M2.
