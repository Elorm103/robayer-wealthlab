## Blocking Findings Resolved

### B1 (Sprint M5D): Review-reminder Cron Trigger idempotency does not hold

**Resolved.** `services/customer/reviewReminderService.ts` was redesigned around a new atomic per-purchase claim table, `review_reminder_attempts` (migration `0022`). Full design in `docs/v3.3-m5d1-review-reminder-concurrency-design.md`. Both reproduced failure modes are fixed:

- A failed send is now classified (reusing `emailService.ts`'s own existing `permanentFailure` signal) as either `'failed'` (retry-eligible on a later scheduled run, up to `MAX_SEND_ATTEMPTS = 3`) or `'permanently_failed'` (terminal, with a new `customer.review_reminder_failed` audit log entry closing the previously-silent failure mode).
- Genuinely concurrent invocations now race on a single atomic `INSERT ... ON CONFLICT ... WHERE` statement whose `meta.changes` result determines whether this invocation actually won the claim — independently reproduced fixed, both in the automated test suite (`Promise.all`) and live against a real running Worker (`wrangler dev --test-scheduled`, two genuinely concurrent HTTP requests, verified via direct D1 inspection that only one claim was ever recorded).

**A second, related bug was found and fixed during this same remediation, not present in the original M5D finding**: the first version of the claim's staleness check compared a SQL-generated `datetime('now')` timestamp against a JS-generated `.toISOString()` cutoff, which is not a valid comparison (confirmed directly: the two formats sort inconsistently for same-day, different-time-of-day values) and silently defeated the fix's own concurrency protection. Caught by the same test that was written to verify the fix, before this report was written — see `docs/v3.3-m5d1-retry-idempotency-strategy.md` for the general principle this surfaces.

### B1's Lower-Severity Sibling (Sprint M5D Finding N4): Reconciliation concurrency

**Resolved.** `services/customer/reconciliationService.ts`'s linking `UPDATE` was already atomic; the bug was that the function never checked how many rows it actually changed before proceeding to audit-log and notify. It now does — `updateResult.meta.changes === 0` short-circuits the whole function for a losing concurrent call, and the actually-affected rows are re-derived via a follow-up `SELECT` (correct even in the theoretical case of a partial race, though this system's actual design makes only an all-or-nothing outcome reachable in practice). Independently reproduced fixed via a genuine `Promise.all` test: `audit=1 tokens=1 emails=1`, down from the previously-reproduced `audit=2 tokens=2 emails=2`.

## A New, Unrelated Issue Discovered During Remediation (Documented, Not Fixed)

While fixing the claim-timestamp comparison bug (above), this Board found that `findDueReminders()`'s own pre-existing `verified_at <= ?` eligibility cutoff has the identical class of format inconsistency (`verified_at` is stored via `commerceService.ts`'s `datetime('now')`; the cutoff is JS-`.toISOString()`-formatted). This happens to produce correct results today only because the comparison's 5-day granularity means the date portion of the two strings differs before the inconsistent time-of-day portion is ever reached — a latent, currently-harmless bug, not one of the two Blocking findings this sprint was scoped to fix, and therefore **not fixed here**, per this sprint's own explicit instruction ("if additional issues are discovered... document them but do not implement them"). Flagged in `docs/v3.3-m5d1-retry-idempotency-strategy.md` and `docs/v3.3-m5d1-known-limitations.md` for a future, narrowly-scoped cleanup.
