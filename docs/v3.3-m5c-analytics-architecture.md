# Version 3.3 Milestone M5C: Analytics Architecture

Covers Phase 4 (Customer Analytics) and the analytics portion of Phase 6 (Business Dashboard). See docs/v2-analytics-spec.md for the pre-existing analytics data-source boundary this sprint extends, not replaces.

## What was reused unchanged

Per the sprint brief's explicit "reuse existing analytics infrastructure where possible":

- `services/admin/analyticsService.ts`'s existing `countInRange()`/`revenueInRange()`/`toMetric()` helpers and `KpiMetric { current, previous, deltaPercent }` shape — every new metric returns this same shape.
- `routes/admin/analytics.ts`'s existing `requireAuth()` role gating, `READ_RATE_LIMIT`, and `parseRange()` date-validation helper.
- `js/components/admin/admin-analytics.js`'s existing `renderKpi()` function and `admin/analytics/index.html`'s existing `stat-card`/`data-kpi-{key}-value`/`data-kpi-{key}-meta` markup pattern.
- `customer_sessions.last_seen_at`, already updated on every authenticated request by `sessionService.ts`'s `validateSession()` — this is the dashboard-usage signal; zero new instrumentation was added to produce it.
- `email_log`'s existing `entity_type`/`entity_id` columns (see Database Changes) — used to detect whether a review reminder has already been sent for a purchase, with no new column.

## New metrics (Phase 4/6)

`services/admin/analyticsService.ts`'s new `getActivationSummary(env, range)`, exposed at `GET /api/admin/analytics/activation-summary`:

| Metric | Source | Definition |
|---|---|---|
| Checkout starts | `purchase_sessions.created_at` | Every session created in range, any outcome |
| Checkout completions | `purchase_sessions.verified_at` | `status = 'verified'` in range (same underlying fact as the existing "orders" metric, exposed distinctly here for the funnel view) |
| Checkout completion rate | Derived | completions ÷ starts, as a percentage, for the current period only (not a current-vs-previous comparison, since it's a ratio, not a count) |
| Coupon redemptions | `coupon_redemptions.redeemed_at` | Reuses the M4 coupon engine's own redemption table |
| Reviews submitted | `product_reviews.created_at` | Reuses the M4 review system's own table, any status |
| Dashboard-active customers | `customer_sessions.last_seen_at` | Distinct customers, not session count |
| Repeat purchases | `purchase_sessions` | A verified purchase by a customer who already had at least one strictly-earlier verified purchase (ties broken by `id`, since `datetime('now')`'s one-second resolution can otherwise leave two same-second purchases unable to tell which came first — caught by this sprint's own test suite) |
| Purchases reconciled | `audit_logs.created_at` | `action = 'customer.purchases_reconciled'` events, reusing the existing generic audit log |

All eight are period-over-period `KpiMetric`s except the completion rate.

## Cloudflare Web Analytics beacon (Known Limitation, resolved partially)

The admin dashboard has always linked out to Cloudflare Web Analytics for visitor/session/traffic-source data (`docs/v2-analytics-spec.md`'s stated boundary: this data lives only there, never faked in D1). Investigating this sprint found that no page on the site ever actually loaded the Cloudflare Web Analytics tracking beacon script — confirmed by grep, zero matches for `cloudflareinsights`/`beacon.min.js`/`__cfBeacon` anywhere in the codebase before this sprint. The dashboard's own link pointed at a report with no data behind it.

`js/main.js` now conditionally loads the real Cloudflare beacon script (`https://static.cloudflareinsights.com/beacon.min.js`) if `assets/config/site.json`'s `analytics.webAnalyticsToken` is set. That token is `null` today: creating a real Cloudflare Web Analytics site-tag requires a one-time manual step in the Cloudflare dashboard (Analytics & Logs → Web Analytics → Add a site) that this project's current Cloudflare API token scope does not grant programmatic access to, and there is no API for it regardless. This sprint does not fabricate a placeholder token — doing so would violate this project's own "never faked here" data-source principle. See Known Limitations for the required manual follow-up.
