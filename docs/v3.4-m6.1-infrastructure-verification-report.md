## Cache and asset versioning: the open question this phase specifically asks about

No, the deployment process does not currently guarantee that users receive updated JS and CSS after a release. This was proven, not assumed, during M6's own acceptance review: after deploying a real fix, different requests to the same JS file returned different, inconsistent versions for a period of time, traced to Cloudflare caching static assets for four hours (`Cache-Control: max-age=14400`) with no cross-edge consistency guarantee, versus the HTML document's own ten-minute cache. The fix applied there was a manually-added `?v=m6` query string on every changed file's reference, which works but does not scale: it requires a human to remember to bump it on every future change to every changed file, and forgetting it silently reintroduces the exact same multi-hour staleness window.

### Recommended permanent strategy, instead of manual query-string bumps

The standard, durable fix for this class of problem is **content-hashed filenames** (sometimes called cache-busting via fingerprinting): each static asset's filename or query string is derived automatically from a hash of its own contents at build/deploy time (for example, `product-loader.a3f9c1.js`), so a file's URL only ever changes when its content actually changes, and every reference to it is generated from the same source of truth rather than hand-edited. This site currently has no build step at all (confirmed throughout this project's history: plain HTML/CSS/JS, no bundler), so introducing this properly would mean either:

1. A small, purpose-built build step (even a short Node script run before `git push`, not a full bundler) that computes a content hash for each CSS/JS file, rewrites every HTML reference to include it, and fails the build if any reference is missed. This closes the gap completely and removes the human-memory dependency entirely.
2. Short of a build step, the next-best durable option is a single, sitewide version identifier (for example, the current git commit hash, injected at deploy time into a `?v=` suffix applied programmatically to every asset reference, rather than a milestone-specific string like `?v=m6` that a person has to remember to update by hand each time). This is weaker than per-file content hashing (it invalidates every asset on every deploy, not just changed ones) but is far cheaper to build than a real bundler and still removes the "did someone remember" risk entirely.

Either is a genuine improvement over the current state; the manual `?v=m6` pattern applied during M6's acceptance review should be treated as a one-time emergency fix, not the standing convention.
