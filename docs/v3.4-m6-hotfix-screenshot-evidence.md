# Version 3.4 Milestone M6 Acceptance Failure: Before and After Screenshot Pack

## A disclosure before this pack, not after it

This environment's screenshot tool was found, during this review, to produce visually misleading output at resized mobile viewports: it does not match what the browser's own layout engine reports via `getBoundingClientRect()` at the same moment, by roughly 350 pixels vertically, consistently and repeatably. Because of this, this pack does not present freshly captured tool screenshots as its primary evidence. It presents the two screenshots the user actually attached (real device evidence, not this tool's output) as the "before" record, and DOM geometry, measured directly against live production, as the "after" record, since geometry is what this review found to be trustworthy in this environment and screenshots were not.

## Before: the user's attached production screenshots

Two screenshots were attached directly to this conversation: an iPhone Safari capture in light mode (timestamp 9:11) and one in dark mode (timestamp 9:13), both against `robayerwealthlab.com`. Both show the same defect: the featured book's typographic placeholder text ("Robayer WealthLab," "Small Cedis, Big Wealth," "How Ordinary Ghanaians Can Build Real Wealth Starting With...") rendering below the real uploaded cover image and overlapping the hero's own eyebrow, headline, and subtitle text. This is genuine, reproducible production evidence, confirmed independently in this review by direct DOM measurement against the same live URL (see the Root Cause Analysis Report), not merely accepted at face value.

## After: DOM geometry proof, live production, not yet deployed

This is not a screenshot of a deployed fix, because nothing has been deployed yet (see the Production Deployment Verification Report). It is a direct measurement, taken against the current, unmodified production page, of what changes when the fix is present, using a temporary, non-persistent client-side style injection to apply the exact fix rule and re-measure:

| Measurement | Before fix | After fix |
|---|---|---|
| `.book-card__cover-placeholder-text` computed `display` | `flex` | `none` |
| `.book-card__cover-placeholder-text` occupies layout space | Yes (436 to 702) | No |
| `.hero__title` position | 590 to 705 | 590 to 705 (unchanged) |
| `.hero__subtitle` position | 721 to 849 | 721 to 849 (unchanged) |
| Overlap between placeholder subtitle and hero title | 70 pixels | None (placeholder removed from layout) |
| Dark mode: placeholder computed `display` | `flex` | `none` |
| Dark mode: `.hero__title` color | `rgb(255, 255, 255)` (already correct) | `rgb(255, 255, 255)` (unchanged, already correct) |

## What a genuine after-screenshot pack requires

A real, deployed-state screenshot pack (light and dark, mobile and desktop and tablet, before and after, per the brief's Phase 6) requires the fix to actually be live on production first. That has not happened. Once the fix is committed, pushed, and has propagated past GitHub Pages' and Cloudflare's caches, this pack should be regenerated with genuine post-deployment screenshots, ideally captured on a real device as the user's original evidence was, rather than through this environment's screenshot tool, given the reliability issue documented above.
