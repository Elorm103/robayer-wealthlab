# Version 3.2 - Sprint M4A - Implementation Strategy

Describes *how* M4 (and, by extension, M5/M6) should be executed, so that Milestone M4 begins with the same engineering discipline that delivered Versions 3.0 and 3.1.

---

## Governance Process (unchanged from M1-M3)

Reuse the exact sprint-lettering discipline this project has now run successfully three consecutive times:

- **M4A - Planning** (this sprint's own natural successor, once this package is approved): architecture review, UX strategy, API gap analysis, security review, database impact assessment, risk assessment, testing strategy, implementation roadmap - scoped specifically to Reviews + Coupons, not re-deriving this document's own findings.
- **M4B - Implementation**: build exactly the approved scope, no more.
- **M4C - Independent Acceptance Review**: a genuinely independent audit, not a self-review - this project's own track record shows this step has found a real, fixable defect in 2 of 2 milestones that have had one (M2's concurrency race, M3's session self-revocation gap). There is no reason to expect M4 will be the first milestone where this step finds nothing; budget for it finding something, and treat that as the process working, not failing.
- **M4D - Closeout**: resolve every M4C observation, nothing more.
- **M4E - Commit, Tag & Production Deployment**: identical process to M1E/M2E/M3E, including production verification using clearly-marked, temporary, cleanly-removable verification data rather than assumptions.
- **M4F - Documentation Publication**: identical process to M3F.

## Sequencing Within M4

Build Coupons first, Reviews second (or in parallel if two engineers are available) - Coupons has zero open design questions and can start immediately; Reviews benefits from a short design pass (exact moderation workflow, exact purchase-verification rule) that can happen while Coupons implementation is already underway, avoiding any idle time.

## Testing Strategy Discipline

This project has now learned the same lesson twice (M2C and M3C both found a Testing Strategy requirement that was written but not mechanically checked before declaring implementation complete). M4B should explicitly cross-check every bullet of M4A's own Testing Strategy against a real test file/test name before declaring implementation done - not as a new process, but as an actual application of a lesson this project has already paid to learn twice.

Explicitly required, given this review's own Technical Debt findings: real automated test coverage for both new admin surfaces (review moderation, coupon management) from the first implementation pass, not retrofitted after an acceptance review finds the gap a third time.

## Risk Management During Implementation

- **VAT question**: escalate to the Product Owner at M4A kickoff, independent of M4's own feature work, with an explicit decision deadline requested - not a blocking dependency for M4, but this review recommends treating "still unresolved" as itself worth surfacing at every subsequent milestone's own kickoff until it is closed, exactly as this project's own Retrospective already recommended and no prior milestone has yet acted on.
- **`platform_users` migration plan**: assign as a small, parallel, non-blocking planning task (not implementation) starting alongside M4A, so ADR-011's entry condition for M7 is satisfied well before M7 is reached rather than becoming a last-minute blocker.
- **Coupon fraud vector**: explicitly out of scope for M4, per the ARB's own prior acceptance of this risk - do not let M4B scope-creep into building fraud mitigation nobody asked for yet.

## Resourcing Note

The Sprint Readiness Report found several ratified milestones "parallel-capable" (M4 alongside M2/M3). The same logic applies here: the independent eBook-content-expansion track (more SKUs, more resources) identified in the Business Opportunity Report requires zero engineering time and can and should proceed continuously, in parallel with M4/M5/M6's engineering work, rather than waiting for any of them.

## Documentation Discipline

Continue this project's practice of producing a full planning/implementation/review/closeout/deployment documentation set per milestone. The one open item worth acting on now rather than deferring again: the Blueprint's own Executive Recommendation #5 (documentation consolidation) has now gone unaddressed across three full milestones. This review does not recommend blocking M4 on it, but does recommend scheduling a dedicated, small documentation-archival pass (likely as part of M4F or a standalone housekeeping sprint) before the `docs/` directory grows past its current ~185 files without any consolidation ever having actually happened.

## What NOT To Do

- Do not begin implementation of Reviews or Coupons before M4A's own dedicated planning sprint produces the same architecture/UX/security/testing detail every prior milestone has required - this planning package establishes *what* M4 is, not *how* to build it in code-level detail.
- Do not fold the course-platform cluster, wishlist, notifications, or any M5/M6 item into M4's scope opportunistically "since we're in there anyway" - this project's scope discipline (explicit "Explicitly NOT in M4" sections in every milestone's own documentation) is a proven strength, not bureaucracy for its own sake.
- Do not silently deviate from the ratified M4/M5/M6 sequence without the governance amendment named in the M4 Scope Recommendation - get the Product Owner's explicit sign-off on the Reviews addition and the M5/M6 re-sequencing before M4A begins, not after M4 ships.
