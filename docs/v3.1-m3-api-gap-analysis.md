## Missing endpoints / fields (genuine gaps, minimal additions recommended)

### Gap 1: Purchase detail does not expose download availability (assets)

**Finding:** `CustomerPurchaseSummary` (`purchaseHistoryService.ts`) returns `purchaseReference, productTitle, amountDisplay, status, createdAt, receiptNumber` - **no `assets` field**. The guest-facing `GET /api/purchases/:reference` *does* return `assets: [...]` (via `fulfilmentService.getFulfilmentStatus()`), but the customer-authenticated equivalent does not currently call the same logic.

**Impact:** the My Library page cannot render a per-purchase Download button without this - it needs to know which `assetId`(s) exist and are currently available (not revoked) for each purchase.

**Recommended minimal addition:** extend `getCustomerPurchase()` (and, since the UX Strategy's Library rows need this "in one glance" without a secondary per-row call, also `listCustomerPurchases()`) to include an `assets` field, populated by calling the *same, already-built* `getFulfilmentStatus()`-adjacent asset-resolution logic `fulfilmentService.ts` already has - not a new resolution mechanism, a new call site for an existing one. This is an additive field on an existing response, not a breaking change, matching the exact discipline `receiptNumber` was added to `GET /api/purchases/:reference` in M2.

### Gap 2: No per-asset download usage/limit/expiry exposed to the customer

**Finding:** `deliveries.downloads_used`, `deliveries.max_downloads`, `deliveries.access_expires_at` all already exist in the schema (live since before M1) but are not returned by any customer-authenticated endpoint today.

**Impact:** the UX Strategy's "Downloaded 2 times, last on [date]" line (folded into the Library row, not a separate page) has no data source yet.

**Recommended minimal addition:** include `downloadsUsed`, `maxDownloads` (nullable), and `lastDownloadAt` (nullable) alongside each entry in Gap 1's new `assets` field - same response, no second endpoint. This is a read-only projection of columns that already exist; no schema change (see Database Impact Assessment).

### Gap 3: No way for a customer to list or revoke their own active sessions

**Finding:** `services/customer/sessionService.ts` has `createSession`, `validateSession`, `revokeSession` (single, by token), and `revokeAllSessions` (all-at-once, used only internally after a password change) - **no function lists a customer's own active sessions individually**, and no route exposes any of this to the customer themselves.

**Impact:** the Account Security page's ratified requirement ("active sessions... log out other sessions") has no backing API today.

**Recommended minimal addition (the one genuinely new pair of endpoints M3 needs):**

| Endpoint | Method | Purpose |
|---|---|---|
| `GET /api/customer/sessions` | GET | Lists the authenticated customer's own active (non-revoked, non-expired) sessions: created-at, last-seen-at, a coarse device/browser hint if easily derivable from `user_agent` (best-effort only, never a security control), and whether each is "this session" (matched against the requesting session's own id). |
| `POST /api/customer/sessions/:sessionId/revoke` | POST | Revokes one specific session by its own id (not by token, which the client never has for another session) - ownership-checked (must belong to the requesting customer), requires the same CSRF discipline every other customer state-mutating action needs. |

Both are thin wrappers over logic `sessionService.ts` already mostly has (`revokeSession` exists; a new `listActiveSessions(customerId)` and a session-id-scoped variant of revoke are the only new service-layer functions needed) - not a new session-management concept, an extension of the existing one.

### Gap 4: No password-change endpoint for an already-logged-in customer

**Finding:** M1 built `POST /api/customer/auth/set-password` (token-based - used for initial setup *and* forgot-password reset) but no "I'm logged in right now and want to change my password" endpoint, which conventionally does not require a fresh emailed token, only the current session plus (recommended) the current password for re-authentication of the specific irreversible action.

**Impact:** the Account Security page's "change password" action has no direct backing endpoint - routing it through the existing forgot-password email flow would work functionally but is a worse experience for an already-authenticated customer (an unnecessary round trip through email for someone who already proved their identity via an active session) and was not what the ratified Blueprint's own Account Security page describes ("change password" as a direct action, not a re-request-via-email detour).

**Recommended minimal addition:** `POST /api/customer/auth/change-password` (session-gated via `requireCustomerAuth`, CSRF-protected), taking `{currentPassword, newPassword}`, verifying `currentPassword` against the stored hash before accepting `newPassword` - mirrors `authService.ts`'s existing password-strength-policy reuse (`utils/passwordPolicy.ts`) and revokes all other sessions on success, exactly matching `set-password`'s own existing "a password change invalidates all prior logins" behavior.

## Endpoints considered and explicitly NOT recommended (avoid unnecessary additions)

- **No new "dashboard summary/welcome" endpoint.** The My Library page (M3's entry point) can be served entirely by `GET /api/customer/purchases?limit=3` (or similar) for a "recent activity" widget, reusing the existing paginated endpoint rather than adding a bespoke aggregate one.
- **No new guest-facing endpoint changes.** Every gap above is customer-authenticated-only; the existing guest reference-scoped paths (`GET /api/purchases/:reference`, the receipt-download mint/redeem pair) need no change for M3.
- **No change to `POST /api/checkout/sessions` or the webhook handler.** M3 is entirely post-purchase; the order-creation pipeline is untouched.
- **No new "download history as a standalone list" endpoint**, per the UX Strategy's own conclusion that this is a per-row detail, not a separate page - Gap 2's addition to the existing purchase-detail/list response already covers it.

## Summary of recommended API work for M3

| Change | Type | Effort |
|---|---|---|
| Add `assets` (with per-asset download usage/limit/expiry) to `GET /api/customer/purchases` and `GET /api/customer/purchases/:reference` | Additive field on existing endpoints | Small - reuses existing `fulfilmentService.ts` logic |
| `GET /api/customer/sessions` | New endpoint | Small - new query only, no new table |
| `POST /api/customer/sessions/:sessionId/revoke` | New endpoint | Small - extends existing `revokeSession()` logic to be id-scoped and ownership-checked |
| `POST /api/customer/auth/change-password` | New endpoint | Small-Medium - reuses `passwordPolicy.ts` and the existing session-revocation-on-password-change behavior |

**Four additions total, all small, all additive, none requiring a schema change** (see Database Impact Assessment). No existing endpoint's request or response shape loses a field or changes meaning - full backward compatibility with M1/M2's live API surface is preserved.
