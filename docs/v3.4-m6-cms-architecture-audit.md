# Version 3.4 Milestone M6: CMS Architecture Audit Report

Scope: a direct inspection of every content-editing mechanism in the repository, what each is built on, and whether that architecture is the right one to keep building on. This is not a survey of admin UI screens; it is an audit of the underlying data flow behind every one of them.

## 1. The two architectures already in production

Robayer WealthLab already runs two genuinely CMS-driven mechanisms, both D1-backed, both update-without-deploy. Everything added in this milestone extends these two, rather than inventing a third.

### 1.1 Entity tables (products, blog posts, resources)

Each content type has its own D1 table (`products`, `product_files`, `blog_posts`, `resources`, plus supporting tables), a service module (`productCatalogService.ts`, and equivalents for blog/resources), a `backend/routes/admin/*.ts` CRUD route, and a public `backend/routes/*.ts` read route. Every field on these entities (title, price, cover image, SEO title, SEO description, canonical URL, body content) is genuinely admin-editable and takes effect immediately, since every public read route queries D1 directly on every request.

This is the correct shape for anything that is naturally a list of distinct records with its own lifecycle (a book can be drafted, published, archived; a blog post has its own slug and publish date). It should remain the pattern for any future entity of this kind (for example, a future testimonials table, see Section 3).

### 1.2 The `site_settings` key-value table

For content that is not a list of records but a handful of standalone values (a toggle, a sender name, a chunk of hero copy), the established pattern since Version 2.1 Phase 5 is a single `site_settings` table of `(key, value_json, updated_by, updated_at)` rows, read through `backend/services/admin/settingsService.ts`'s `DEFAULTS` object and `resolve()` helper, written through its `updateSettings()` with per-key audit logging.

This milestone added a seventh key, `hero_content` (see [settingsService.ts](../backend/services/admin/settingsService.ts)), reusing the exact same `DEFAULTS`/`resolve`/`PATCH_KEY_MAP`/`updateSettings` machinery already proven for maintenance mode, email sender identity, and the newsletter recipient cap. No new table, no new migration, no new validation framework: one new object shape, one new validation function, one new row in `PATCH_KEY_MAP`. This is the correct pattern for any future flat, singleton content and should keep being the default choice over inventing a new table for every new field.

A parallel table, `branding_*` keys inside the same `site_settings` table (via `brandingService.ts`), stores a `media_assets.id` per "slot" (primary logo, dark-mode logo, favicon, Open Graph logo, email logo, app icon). This is a deliberate variant of the same key-value idea: the slot stores a reference, not a value, because the real content (the image, its dimensions, its alt text) belongs in the Media Library, not duplicated into `site_settings`. This separation is correct and should be the model for any future "pick an asset" field (for example, a future page hero background image).

## 2. What was added or changed this milestone

- `hero_content` (site_settings key): headline, subheading, eyebrow, and both CTA buttons' text and destination, previously hardcoded directly in `index.html`. See the Editable Content Inventory for the full before/after.
- Branding slot `email`: previously stored but never consumed (`SLOT_IS_WIRED.email` was `false`); now genuinely wired into every transactional email's logo via `services/emailService.ts`'s new `resolveEmailLogo()`.
- Admin sidebar logo: previously an independent, hardcoded `<img>` (`partials/admin-sidebar.html`); now carries the same `.nav__logo-mark` class the public header/footer already use, so it participates in the existing branding CMS and dark-mode swap with zero new code, just a class addition.

None of this required a new table, a new migration, or a new content-delivery mechanism. That is the intended outcome of this audit: the two existing architectures were sufficient for everything this milestone's Phase 2 and Phase 3 asked for. The places that did not have that were places where a *reference to an existing mechanism* was simply missing (a class name, a slot check), not places needing new architecture.

## 3. Where a genuinely new architecture decision is still owed

The following are not fixed in this milestone. Each is a real content type with no current admin path at all, and each should get one of the two treatments above rather than a bespoke third mechanism when it is eventually built:

| Content | Recommended treatment | Why |
|---|---|---|
| Testimonials | Entity table (products/blog pattern) | A list of independent records, each with its own author, quote, and (eventually) rating. Deliberately removed in a past review for having no real content (`content/testimonials/README.md`); when real testimonials exist, they belong in a table, not a config file. |
| FAQs | Entity table | Currently hand-duplicated per page (a visible `<details>` accordion and a separate `FAQPage` JSON-LD block, kept in sync by hand across seven pages). A single `faqs` table with a `page` column would let one edit update both the visible accordion and the structured data at once, eliminating the duplication risk entirely, not just making it editable. |
| Navigation menu | New, narrowly-scoped table | Not a fit for either existing pattern as-is: it is an ordered list (unlike `site_settings`) but with only one "record" (the site has one nav), and it needs recursive/grouped items. This is genuinely new scope, not a same-milestone fix; see the Final Release Recommendation for why it is deferred rather than rushed. |
| Footer | New, narrowly-scoped table or `site_settings` object | Simpler than navigation (a footer is column groups of link, not a deep tree), so this could plausibly be a single `site_settings` key holding a small JSON structure, following the `hero_content` precedent rather than needing a table. |
| Global SEO settings | `site_settings` key | Per-item SEO (product/blog/resource `seo_title`/`seo_description`/`seo_canonical_url`) is already solved. What is missing is site-wide defaults (Organization schema fields, default OG image, Twitter handle) which are today static tags repeated in every page's `<head>`. A `site_seo_defaults` key following the `hero_content` precedent is the correct fit, not a new table. |

## 4. Architectural decisions this audit reviewed and chose not to change

- **The `site.json` static config file** (`assets/config/site.json`) remains deploy-only, feeding `js/content-inject.js`'s `[data-content]` mechanism for company/founder/contact/social facts. This milestone extended that same client-side mechanism to also serve the new `/api/hero` endpoint (see `content-inject.js`'s `initHeroContent()`), rather than writing a second, parallel fetch-and-populate script. This was a direct "if a better architecture exists, adopt it" call: the population logic (`resolvePath`/`applyContent`) does not care where the JSON came from, so it should not be duplicated for a second source.
- **The homepage cannot be server-rendered per-request.** The static site is served from GitHub Pages; only `/api/*`, `/books/*`, `/resources/*`, `/blog/*`, and `/free-guide/*` are intercepted by the Worker at the Cloudflare edge (confirmed via `curl -sI https://robayerwealthlab.com/` returning GitHub's own `x-github-request-id` header). This means `index.html` itself can never read `site_settings` directly at request time; every CMS-driven homepage field must be a client-side fetch after load, the same shape `branding.js` already established. `hero_content` follows this same shape by necessity, not by choice, and any future homepage CMS field must do the same.

## 5. Conclusion

The existing two-mechanism architecture (entity tables for lists, `site_settings` for singletons, with a slot-and-Media-Library variant for asset references) is sound and was reused rather than replaced. Nothing found in this audit justified inventing a third pattern. The remaining gaps (Section 3) are genuinely new content types needing their own schema decision, not omissions in wiring up what already exists.
