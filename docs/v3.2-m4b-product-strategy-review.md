# Version 3.2 - Sprint M4B - Product Strategy Review

**Independent Architecture & Product Review Board.** This review does not treat the M4A package's own conclusions as correct because they were produced by a prior planning pass - every claim below was checked against the actual production codebase and, where relevant, actual production data, not re-derived from M4A's own prose.

---

## Alignment With Long-Term Vision

M4A's recommended M4 (Reviews + Coupons) is evaluated here against the platform's stated long-term direction ("scalable digital education platform"), not just against the ratified short-term roadmap.

**Finding: the recommendation is sound, but for a reason M4A under-articulates.** M4A justifies deferring the course-platform cluster primarily by citing this project's own prior planning documents reaching the same conclusion twice (`v1.1-product-roadmap-v2.md`, `product-expansion-roadmap.md`). That is real evidence, but it is *secondhand* evidence - documents written before this platform had any real customers. This Board independently verified the *current* evidence, which is stronger and more directly relevant: production D1 today contains exactly **2 real customer accounts** and **17 verified purchases** (mostly guest, never provisioned into an account), and the platform's only real customer-submitted inquiry (one `consultation_requests` row) contains no product-education content of any kind (its description field reads `"asd"` - a placeholder or test submission, not a genuine inquiry). There is no course-demand signal in production, full stop, independent of what any planning document from years ago concluded. **This is a stronger justification for deferral than M4A itself presented**, and the Final Decision recommends M4A's own documents be updated to cite it.

## Customer Value

Reviews directly addresses a real, verified gap (zero trust/social-proof mechanism exists in code - confirmed by this Board's own grep of the codebase, not merely M4A's claim). Coupons directly addresses a real, verified gap (`receipts.discount_pesewas` exists as an unused column - confirmed).

**Board observation, not raised in M4A:** with only 2 real customers and 17 purchases, a newly-launched Reviews feature will very likely start with zero or one review. M4A's Scope Recommendation does not address this. A product page showing "No reviews yet" is honest and consistent with this project's established AR-009 empty-state discipline, but the Board recommends this be stated explicitly as a design requirement in M4A's own successor planning (M4C's technical planning), not left implicit - the platform's existing pattern of honest, non-manufactured-urgency copy (already established sitewide) is the correct model to follow, and should not be assumed, it should be specified.

## Revenue Impact

Coupons has a direct, immediate revenue mechanism (discount-driven conversion). Reviews has an indirect mechanism (trust → conversion, not directly measurable without visitor analytics, which this platform does not have - a real measurement gap this Board confirms is unresolved and will remain unresolved after M4 ships, since neither Reviews nor visitor analytics are the same feature).

## Retention

M4 itself does not directly address retention (correctly deferred to M5 per M4A's own analysis). The Board confirms this is the right call: retention mechanics without first having reviews (trust) or a monetization lever (coupons) in place would be optimizing a funnel stage before the stages feeding it are complete.

## Conversion

Both M4 features plausibly improve conversion. Neither is measurable without visitor analytics existing (see above) - the Board notes this as a real limitation on ever *validating* M4's own success, not a reason to change M4's scope.

## Scalability

Not materially affected by M4's scope - both features are additive and low-volume by nature at current scale. No scalability concern is introduced by M4.

## Implementation Cost

**Board finding, not adequately reflected in M4A:** the true implementation cost of Coupons is higher than M4A's "S effort" characterization, for a concrete, verified reason detailed in the Architecture Readiness Assessment - the coupon schema M4A cites as "already fully designed, ready to implement as-is" (`v3-database-design.md`) references a table (`platform_users`) that does not exist in the current schema and is explicitly gated behind an unplanned future migration (ADR-011). The actual schema needed for M4 must be freshly, if simply, designed. This does not change the recommendation to build Coupons in M4 - it changes the effort estimate from S to S-M and requires a specific correction before implementation planning begins. See the Architecture Readiness Assessment for full detail.

---

## Does M4 Address the Highest-Value Business Opportunities?

**Yes, with the above corrections.** Independent verification confirms M4A's central claim: the platform's real, current weakest points (near-zero trust signal, incomplete monetization) are cheaper and lower-risk to close than the alternative (a course platform with zero schema, zero demand evidence, and now independently re-confirmed zero production signal of any kind). The Board's own data inspection strengthens rather than weakens this conclusion.
