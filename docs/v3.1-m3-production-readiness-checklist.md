## 4. Rollback procedure

**No schema exists to roll back** - the simplest rollback profile of any milestone so far.

- **Worker rollback**: `wrangler rollback` to the pre-M3 deployment (`cae425ad-1bdf-41ba-b042-8f93aac2fee8`, recorded in Section 3) fully removes the three new endpoints and the `assets` field extension. No data-migration concern, since no M3-specific column or table exists to be orphaned or need cleanup.

The five new `/dashboard/*` pages simply stop resolving (back to `404`, the current state); no other page is affected, since M3 added new files and made only two small, additive edits to existing files (`checkout/callback/index.html`'s one sentence, `js/components/sign-in-form.js`'s redirect target), both trivially revertible.
- **Rollback readiness verdict: Ready.** Either rollback (Worker or static site) can be performed independently of the other with no ordering constraint, and neither requires any database action.

## 7. Cache considerations

- **API responses**: every customer-authenticated M3 endpoint (`GET /api/customer/sessions`, `POST /api/customer/sessions/:sessionId/revoke`, `POST /api/customer/auth/change-password`, and the extended `GET /api/customer/purchases*`) sends `Cache-Control: no-store, no-cache, must-revalidate` via the existing `withNoStore()` helper - confirmed by reading `routes/customer/sessions.ts` and `routes/customer/auth.ts` directly. No personalized/financial data from M3 can be cached by a browser, proxy, or CDN.
- **Static dashboard pages**: GitHub Pages applies its own default caching headers to static assets (out of this project's control - no `_headers`-file-equivalent mechanism exists for GitHub Pages, unlike Cloudflare Pages/Netlify). This is not a new consideration introduced by M3 - every existing `checkout/*` page already operates under the identical constraint, and it is safe here for the same reason: the HTML shell itself contains no personalized data (every dashboard page's content is populated client-side via `fetch()` against the always-fresh, never-cached API above), so a browser or intermediary caching the generic shell for a short period causes no data-leakage or staleness risk to a different customer.
- **No CDN purge/invalidation step is required** for this deployment - the static site has no build step or content hash in its filenames, and GitHub Pages' own default cache lifetime is short enough that M1's and M2's deployments did not find it necessary to document a manual purge step either.
