# Version 5.0 — Milestone 2.1 Production Verification Report

**Knowledge Base indexing scale fixes: root cause, remediation, and production verification.**

## 1. What Milestone 2.1 Covers

Milestone 2 (Knowledge Base) implementation, testing, and documentation were completed and approved. Production deployment then surfaced two real, sequential production incidents that Milestone 2's own testing could not have caught (both involve the real Cloudflare API surface, which local test doubles necessarily approximate). This report documents both incidents — root cause, evidence, fix, and verification — plus the final Phase 3 retrieval verification against the live, fully-indexed Knowledge Base.

## 2. Incident 1 — Worker Subrequest Limit

### Symptom
The first production Full Rebuild indexed 12 of 38 documents; the remaining 26 failed with `Too many subrequests by single Worker invocation`. A second attempt (after a partial fix) reached 21/38 before failing identically, leaving one document (`real-estate-investing`) permanently stuck in `pending` status — its Vectorize upsert had succeeded but the invocation was hard-killed before the corresponding D1 write completed, and before the run's own summary row was ever finalized (confirmed: that run's `knowledge_indexing_runs` row shows `status='running'` with all-zero counters, and has zero corresponding `audit_logs` entries — proof the invocation died mid-flight, not that it merely returned an error).

### Root cause (measured, not assumed)
Cloudflare counts **D1, KV, R2, and Vectorize binding calls against the same per-invocation subrequest budget as `fetch()`** — confirmed directly against Cloudflare's own documentation. Counting every call in the original synchronous design: `getSpendSnapshot()`/`getAiGatewayBudgetConfig()`/`getAiGatewayRetentionConfig()`/provider-budget lookups inside every `embedText()` call (~8 subrequests per call, independent of batch size), plus each document's finalization (Vectorize upsert, D1 chunk/faq writes, status updates, old-vector cleanup — ~5-7 subrequests, irreducible), plus a per-document existence-check `SELECT` that ran for every one of the 38 documents regardless of outcome. A 38-document full rebuild totalled roughly 300+ subrequests inside one `ctx.waitUntil()` invocation — linear in catalog size with no ceiling. This was never going to scale to "hundreds or thousands of documents," regardless of how the calls inside that one invocation were optimized.

### Fix
Split indexing into two phases running as separate Worker invocations, each with its own fresh subrequest budget:
1. **Planning** (`planIncrementalIndex`/`planFullRebuild`) — gathers documents, hash-compares against one bulk query instead of one `SELECT` per document, and enqueues one Cloudflare Queue message per document needing work.
2. **Consuming** (`processIndexingQueueBatch`, the Worker's new `queue()` handler) — processes small batches (5 documents) per invocation. Every consumer invocation Cloudflare delivers is a genuinely separate invocation with a full subrequest budget — this is the mechanism that makes indexing scale, not a bigger batch size.

New columns `knowledge_indexing_runs.documents_enqueued`/`documents_resolved` (migration `0037`) track a run's progress across however many consumer invocations it takes to drain, giving real checkpointing: an interrupted consumer invocation just leaves some queue messages unprocessed, and Cloudflare's own retry mechanism (`max_retries: 3`) redelivers them.

### Verification
34 unit tests (planning phase against real D1 state; consumer phase against hand-built queue messages reconstructed via the real document readers/chunker — not duplicated logic) plus a dedicated regression test proving embed calls batch across an entire queue batch into one provider call. Full backend regression: 372-374 passed / 21 failed across iterations, the 21 being the same pre-existing, unrelated baseline throughout. Deployed and confirmed live via `wrangler tail`: a real trigger produced `POST .../rebuild` → 8 `Queue robayer-knowledge-index-queue` consumer invocations (7×5 + 1×3 = 38 messages) → run completed in 73 seconds.

## 3. Incident 2 — Vectorize Write-Rate Limit

### Symptom
After Incident 1's fix, the next Full Rebuild reached 36/38 — a real improvement — but 2 documents (Business Financial Advisory, Retirement Planning Guidance) failed with `VECTOR_UPSERT_ERROR (40014): Too Many Requests`.

### Root cause
A genuine Vectorize write-rate limit, distinct from Incident 1. Cloudflare's Vectorize documentation does not publish an exact requests-per-second ceiling, but explicitly recommends "batch more vectors into fewer requests... important for write-heavy workloads." Even after Incident 1's fix, every document in a 5-document consumer batch still issued its own separate `upsert()` call, and the queue consumer's concurrency was left at Cloudflare's auto-scaled maximum (unset `max_concurrency`) — multiple consumer invocations could fire close together and collectively burst past the index's write-rate ceiling.

### Fix
1. Every document's vectors in one consumer batch are now upserted in **one combined call**, not one call per document — up to a 5x reduction in Vectorize write-call volume per invocation.
2. `wrangler.jsonc`'s queue consumer now sets an explicit `max_concurrency: 2` instead of leaving it unbounded, capping how many invocations can hit the index at once.
3. A bounded exponential-backoff retry (`withVectorizeRateLimitRetry`, up to 4 attempts) was added specifically for `40014`/`429`/"Too Many Requests" errors — a safety net on top of (1) and (2), not a substitute for them. Any other Vectorize error (bad dimensions, malformed id) is deliberately **not** retried, since retrying a non-transient error would just fail identically.

### Verification
2 new unit tests confirm: a rate-limited upsert that succeeds on retry leaves the document correctly indexed (not permanently failed) after exactly 2 upsert attempts; a non-rate-limit error fails immediately after exactly 1 attempt, with no wasted retry. The full suite (34 tests) and full regression (374/395, same baseline) passed before deploy.

## 4. Incident 3 — Vectorize `returnMetadata` API Mismatch (found during Phase 3, before certification)

### Symptom
Once indexing succeeded, every Search Diagnostics query failed identically with `VECTOR_QUERY_ERROR (code = 40026): Failed to parse the request body as JSON: returnMetadata: expected value at line 1 column 29`.

### Root cause
Current Vectorize (V2) requires `query()`'s `returnMetadata` option to be the string `'none' | 'indexed' | 'all'` — a boolean is only valid on legacy V1 indexes. `searchService.ts` passed `returnMetadata: false`, which is why every query failed at the API layer before ever touching indexed data. This was never caught by Milestone 2's own tests because the fake Vectorize test double accepted any shape for that option without validating it — a genuine gap in test fidelity, not a logic bug the tests were even positioned to catch.

### Fix
Changed to `returnMetadata: 'none'` (the correct and most efficient value, since `searchKnowledge()` already joins back to D1 for every field it needs and never reads vector metadata). The test double was also hardened to validate this exact constraint — the same class of API-shape bug will now fail a test instead of passing silently until production.

## 5. Final Production State (measured directly, not estimated)

Queried directly against production D1/Vectorize after the redeployed fixes and a fresh Full Rebuild:

| Metric | Value |
|---|---|
| Documents seen | 38 |
| Documents indexed | **38** |
| Documents unchanged | 0 |
| Documents failed | **0** |
| Documents pending | **0** |
| Chunks created (this run) | 89 |
| Run duration | 73 seconds (18:54:16 → 18:55:29 UTC), across 8 queue-consumer invocations |
| Vectorize vector count | 92 |

**The 92-vs-89 discrepancy, explained honestly:** the run history shows a now-superseded run (the Incident 1 architecture's hard-killed invocation) genuinely indexed ~21 documents before dying, including `real-estate-investing`, whose Vectorize upsert most likely succeeded moments before the D1 chunk write that would have recorded its `vector_id` never happened. Every later run's old-vector cleanup is driven by what's recorded in `knowledge_chunks` in D1 — a vector Vectorize has but D1 never learned about can't be found and deleted by that mechanism. This is a small (3-vector), inert storage artifact with **no effect on search correctness**: `searchKnowledge()` always joins Vectorize matches back to `knowledge_chunks` in D1, so an orphaned vector with no matching D1 row is automatically excluded from every result. Cleaning it up would require enumerating all live vector ids (Vectorize has no bulk-list API) — not worth the effort for 3 inert rows; documented here rather than chased further.

Every query returned 5 results, all real, correctly-cited, live platform content — no fabricated or hallucinated text, since every result is a literal extracted chunk joined from D1, not model-generated. All 7 queries logged correctly to `knowledge_search_log` with matching latency/scores, confirmed by direct D1 query. Latency ranged 450ms–1.45s (each query makes one live OpenAI embedding call).

**Two honest findings from real data:**

1. **Confidence thresholds are miscalibrated, confirmed with evidence.** The Privacy Policy query's top-2 results are the Privacy Policy page verbatim — an unambiguous exact match — yet scored "low" confidence (0.332–0.482, under the 0.5 cutoff). This was already flagged as an engineering-judgment placeholder in the Milestone 2 report; this is now real evidence to recalibrate against, not a hypothetical concern.
2. **"What resources are available?" retrieved topically-adjacent but not ideal content** — Learning Hub, Financial Literacy Workshops, and coaching Services pages, rather than the actual `/resources/` catalog or individual resource items (which did surface correctly for a different query). All 5 results are real, live, correctly cited — just not the best possible ranking for that specific phrasing.

## 7. Phase 4 — Knowledge Quality Audit Scope

The original brief called for 100–200 representative test questions. Since driving the admin UI requires a human in the loop (no programmatic access to the authenticated Search Diagnostics tool was available to this engineering session), the founder chose to scale this down: the 7 queries in §6 stand as a representative smoke test — covering books, blog-adjacent investment topics, resources, and both policy pages — rather than a full systematic audit. A fuller audit (aiming for the original 100–200 question target) is a tracked follow-up, not a certification blocker.

Permission enforcement (public vs. admin-only separation) and `data_classification` filtering were verified directly in `searchService.test.ts` (visibility scoping, `PRODUCTION`-only filtering, `sourceTypes` filtering, confidence-bucket ranking) rather than manually in production, since Milestone 2 indexes exclusively public content today — there is no `admin_only` document yet to test against in the live index. That test coverage is the honest evidentiary basis for this claim, not a live production trial with real admin-only content.

## 8. Known Limitations (unchanged from Milestone 2, plus two new ones from this milestone)

Carried forward from the Milestone 2 Engineering Report:
- Crawl-based staleness for static pages (re-indexing requires re-running the crawl, not automatic on content change).
- No Cloudflare Queue for the *gathering* phase itself — if static-page count grows by an order of magnitude, `gatherAllDocuments()`'s own sequential fetch loop becomes the next scaling concern (a separate axis from the indexing-write scaling this milestone fixed).
- Embedding cost is ongoing per run, not one-time.
- Resources have no individual citation page (shared listing + anchor).

New from Milestone 2.1:
- **Confidence thresholds (0.75/0.5) are now confirmed miscalibrated with real evidence** (§6) — recalibration against accumulated `knowledge_search_log` history is a clear next step, higher priority than previously assessed.
- **No dead-letter queue configured** for the indexing Queue — a document-level failure is already caught before it can throw (so genuine queue-level retries are reserved for real infrastructure blips), but a message that exhausts all 3 retries is currently dropped silently rather than surfaced. Acceptable at today's volume; worth adding before much larger catalogs.
- **3 orphaned vectors in Vectorize** (§5) — inert, does not affect search correctness, not worth the effort to hunt down given Vectorize's lack of a bulk-list API.
- **The retrieval smoke test (§6) is not the full 100–200 question audit** the original brief specified — a deliberate, founder-approved scope reduction, not an oversight.

## 9. Certification Recommendation

**Milestone 2 (Knowledge Base): certify complete.** All infrastructure is live (Vectorize index, Cloudflare Queue, migrations 0036/0037), all 38 real platform documents are indexed with zero failures, and retrieval demonstrably returns correct, real, cited content for representative queries across every indexed content type.

**Milestone 2.1 (Knowledge Verification / scale fixes): certify complete**, on the basis of the smoke-test-scope retrieval verification in §6-7 rather than the originally-specified full audit — a founder-approved trade-off, documented honestly here rather than silently substituted.

Recommend **not** beginning Milestone 3 (Customer AI) work until the confidence-threshold recalibration (§8) is addressed, since Customer AI will likely surface confidence directly to end users, and today's thresholds are confirmed to under-report even exact-match results.
