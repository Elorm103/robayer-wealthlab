# Version 3.0.2 - Milestone M2 Implementation Report

**Milestone:** M2 - Orders, Receipts & Customer Library
**Status:** Complete (code); not yet deployed to production.
**Scope discipline:** Implemented exactly the scope approved in Sprint M2A's readiness review and the Product Owner's subsequent Architecture Decision Approval. No coupons, promotions, DRM, licensing enhancements beyond the `personal` license type, marketplace, creator, affiliate, or customer-facing refund workflow was built.

---

## Executive Summary

M2 adds the ownership layer the ratified Blueprint's Deliverable 3 specified: `order_items`, `licenses`, and `receipts`, all created automatically the moment a purchase verifies, alongside the existing download entitlement M1 already granted. A receipt is a real, generated PDF (via `pdf-lib`, confirmed compatible with the Worker runtime by a same-day spike), stored once in R2 and served many times. A license is revocable, and revocation is synchronized (ADR-003): an admin-triggered refund sets `licenses.revoked_at` and `deliveries.status = 'revoked'` in one atomic D1 batch, and a subsequent download attempt against that entitlement is correctly denied - verified directly by an automated test, not merely asserted. The Customer Library's data layer (purchase history, receipts, licenses) is now live behind the existing customer session/CSRF middleware from M1, unchanged; the dashboard pages themselves remain M3 scope, as planned.

Per the Product Owner's explicit approval: internal, admin-triggered revocation shipped; a customer-facing refund request workflow, portal, and approval queue did not. Per the same approval: the `pdf-lib` spike passed, so true PDF receipts shipped rather than the HTML fallback. VAT-ready architecture shipped; the business is treated as not VAT-registered by default, overridable via a `site_settings` row, per the explicit instruction to assume non-registration unless configuration says otherwise.

Deliverables: 1 migration (4 new tables, 0 altered), 6 new backend services/utilities, 8 new or extended API endpoints, 1 extended admin endpoint, and this documentation set. Testing: 19 unit tests + 20 integration tests at M2B (39 total, alongside M1's unchanged 49), plus 18 more added at the M2C/M2D closeout (negative/adversarial, rate-limit, and true-concurrency coverage) - **106/106 passing** as of closeout.

**Sprint M2D closeout note:** the independent M2C Milestone Acceptance Review (`v3.0.2-m2-acceptance-report.md`) concluded "Accepted with Minor Observations" - no blocking defect, but five non-blocking items. All five were resolved in this closeout sprint: `pdf-lib` moved from `devDependencies` to `dependencies`; `revokePurchase()` reworked to be idempotent under genuine concurrency (`Promise.all`), not only sequential re-calls; the multi-seat receipt line-item rounding drift fixed; `audit_logs.entity_id` populated for refund events; and the two identified test-coverage gaps (negative/adversarial input, rate limiting) closed. See `v3.0.2-m2-closeout-report.md` for the full resolution record.

## Features Implemented

- **Order artifacts**: `order_items`, `licenses` (one per seat, per ADR-009), and `receipts` created automatically inside the existing webhook-verified flow, immediately after M1's customer-provisioning step, following the same "log, never undo a real payment" discipline already established for that step and for `fulfilPurchase()`.
- **Receipt PDF generation**: real, generated PDFs via `pdf-lib`, stored once in R2 (`receipts/{receiptNumber}.pdf`), served many times. Self-healing: `getOrCreateReceiptPdf()` is idempotent - a generation failure at issuance time is retried automatically on the next download request, with no new scheduled infrastructure.
- **Receipt numbering**: `formatReceiptNumber()`, a direct sibling of `purchaseReference.ts`, reusing the identical row-id-based, collision-free approach.
- **Tax breakdown / VAT readiness**: `receipts.tax_breakdown` (JSON array) and `receipts.tax_pesewas` populated by `taxService.ts`. Defaults to an honest empty array; a `site_settings` key (`vat_registered`) can flip this to `true`, at which point the computation logic (not yet implemented, since the real rates are still unconfirmed) would need to be filled in - this is a documented, not a hidden, limitation.
- **Revocation-sync**: `revocationService.ts`'s `revokePurchase()`, the only function anywhere in this codebase that sets `licenses.revoked_at`, always alongside `deliveries.status = 'revoked'` and `purchase_sessions.status = 'refunded'`, in one D1 batch. Idempotent.
- **Admin refund action**: `POST /api/admin/orders/:reference/refund`, added to the existing `routes/admin/orders.ts` module (not a new module), `EDITOR_ROLES`-gated, CSRF-protected, audited via the existing `auditService.record()` with action `order.refunded` (the exact action string `audit_logs`' own schema comment had already anticipated as an example, before M2 existed).
- **Customer Library APIs**: `GET /api/customer/purchases`, `/purchases/:reference`, `/receipts`, `/receipts/:receiptNumber/download`, `/licenses` - all session-gated via M1's unchanged `requireCustomerAuth`, all ownership-filtered server-side.
- **Guest reference-scoped receipt download**: `POST /api/purchases/:reference/receipt-download` (mint) and `GET /api/download-receipt/:token` (redeem), mirroring the existing asset-download mint/redeem pattern exactly, preserving ADR-003's "no account ever required" guarantee for a purchase's receipt, not just its download.
- **`GET /api/purchases/:reference`** (existing, unauthenticated, reference-scoped endpoint) now additionally returns `receiptNumber` once issued - additive, non-breaking.
- **`CustomerFacingStatus`** extended with `'refunded'` (a live `purchase_sessions.status` enum value since before M1, never previously surfaced distinctly to a visitor).

## Security Measures

- **Ownership enforcement**: every customer-authenticated query filters by the session's own `customerId`, server-side, never client-supplied. A resource belonging to a different customer returns the identical `NOT_FOUND`/`RECEIPT_NOT_FOUND` response a genuinely nonexistent one would - verified by a dedicated test, not merely asserted.
- **Guest receipt download**: single-use, short-TTL, 256-bit random token (`receipt_download_tokens`, a sibling of `download_tokens`, not a weakening of it), mirroring the existing entitlement-download security properties exactly.
- **Admin refund authorization**: reuses the existing admin session/CSRF/role middleware unchanged - no new authentication mechanism was introduced.
- **Revocation correctness**: verified end-to-end, not just at the database-write level - a download-permission request against a revoked entitlement is denied at two independent layers (the purchase session's own status, and the delivery's own status), confirmed by a real test exercising the actual `entitlementService.ts` code path.
- **Revocation concurrency safety (added at M2D closeout)**: `revokePurchase()`'s `purchase_sessions` write is now itself a status-gated conditional `UPDATE` inside the same D1 batch as the licenses/deliveries writes, the same atomic-race-arbitration pattern `commerceService.ts`'s `verifySessionAtomic()` already uses. Two genuinely simultaneous refund requests for the same order (proven with real `Promise.all` concurrency, not sequential calls, at both the service and HTTP-route level) can now only ever produce one successful revocation and one audit-log entry.
- **Audit logging**: every refund is recorded via the existing `auditService.record()`, including the affected license/delivery ids in its metadata - queryable by any staff member with access to `audit_logs`, matching this project's existing security-logging posture exactly.

## Known Limitations

- **`deliveries` remains single-per-asset, not quantity-aware.** ADR-009's "N independent licenses and N independent deliveries entitlements" is fully implemented on the `licenses` side (a real loop, tested with a synthetic `quantity = 2` case, since no real product has `quantity > 1` today). The `deliveries` side is unchanged from M1/pre-M1 - `fulfilmentService.ts`'s `UNIQUE(purchase_session_id, asset_id)` constraint means at most one delivery entitlement exists per asset per purchase, regardless of `order_items.quantity`. Redesigning the download-entitlement model for genuine multi-seat access (e.g. one entitlement per seat, not per asset) is a materially larger change than this milestone's named scope, and no real product needs it yet - flagged here explicitly, matching this project's own established practice of documenting a real gap rather than silently leaving it, rather than building it unrequested. **Carried forward from M2C's MAR unchanged - out of this closeout sprint's named scope.**
- **Tax computation logic is not implemented**, only its honest default (empty breakdown). If the business confirms VAT registration and sets `vat_registered = true`, `computeTaxBreakdown()` still returns an empty array today - a receipt would then be under-representing tax, not over-representing it, which was judged the safer failure direction, but this needs the real computation logic filled in before that setting is ever flipped to `true` in production. **Carried forward from M2C's MAR unchanged - the MAR flagged this as an operational sequencing risk, not a defect; no code change resolves an unconfirmed business fact.**
- **No customer dashboard pages** - by design, per the M2A readiness review's own scope split (M2 ships the data layer; M3 ships the pages). A customer cannot yet see their purchase history/receipts/licenses through any UI; the APIs exist and are tested, ready for M3 to consume.
- **PDF layout is minimal** - a single-page, plain, programmatically-drawn receipt (title, line items, tax breakdown, total). No logo image, no branded styling beyond typography. Functionally complete and legally sufficient as a receipt; a visual-polish pass is a reasonable candidate for a future iteration, not named in this milestone's scope.

**Resolved at Sprint M2D closeout (previously listed here as limitations/observations in the M2C Acceptance Report, now fixed - see `v3.0.2-m2-closeout-report.md`):** the multi-seat receipt line-item rounding drift; the true-concurrent double-refund race (audit-log double-write risk); the `pdf-lib` `devDependencies`/`dependencies` misclassification; `audit_logs.entity_id` left `null` for refund events; missing negative/rate-limit test coverage for M2's new endpoints.

## Recommendations Before Milestone M3

1. Confirm the VAT-registration business question before any receipt with a non-empty tax breakdown is expected - this has now been carried, unresolved, across M1's planning, M2A's planning, M2B's implementation, and M2C/M2D's review and closeout. Per the M2C Acceptance Report's specific recommendation: implement the real computation logic (or add a runtime guard) before the `vat_registered` flag is ever set `true` in any environment.
2. Decide whether the `deliveries` single-per-asset limitation needs to be resolved before any multi-seat/institutional product is actually listed for sale - not urgent today, but worth a deliberate decision rather than discovering it live.
3. M3's dashboard pages should consume the APIs documented here as-is; no further backend change is anticipated to support the UX plan already produced in Sprint M2A.
4. Consider a visual-polish pass on the receipt PDF (branding, logo) once the underlying generation architecture (already proven working) has had a production cycle to confirm it holds up under real load.
