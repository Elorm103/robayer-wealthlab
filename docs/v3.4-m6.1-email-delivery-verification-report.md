# Version 3.4 M6.1: Email Delivery Verification Report

## What "sent" actually proves

Every email triggered during this review was confirmed via `email_log.status = 'sent'` together with a genuine Resend `provider_id` (a real message ID, not a placeholder). This proves Resend's API accepted the send request and is attempting delivery. It does not, by itself, prove the message landed in an inbox rather than a spam folder, since that depends on the receiving mail provider's own filtering, which is outside what this system's own logs can see. No inbox was checked directly during this review (no credential to any inbox was available or appropriate to use); the DNS authentication findings below are the strongest evidence available from here about whether delivery is likely to succeed cleanly.

## DNS authentication: SPF, DKIM, DMARC

Checked directly against DNS (Cloudflare's own DNS-over-HTTPS resolver), not assumed from configuration screenshots or documentation.

- **Apex domain SPF** (`robayerwealthlab.com`): `v=spf1 include:_spf.mx.cloudflare.net ~all`. This governs mail sent to look like it originates directly from the apex domain (for example, Cloudflare Email Routing); it does not need to, and does not, include Resend, because Resend does not send through this path.
- **Resend's actual sending path SPF** (`send.robayerwealthlab.com`): `v=spf1 include:amazonses.com ~all`, with an MX record pointing to `feedback-smtp.eu-west-1.amazonses.com`. This is Resend's documented required setup (Resend sends through Amazon SES infrastructure) and is present and correct.
- **DKIM** (`resend._domainkey.robayerwealthlab.com`): a real, well-formed public key TXT record is present. My first check of this record appeared empty because of a display artifact in how I filtered the raw DNS response, not because the record is missing; the full record was confirmed on a second, more careful check.
- **DMARC** (`_dmarc.robayerwealthlab.com`): `v=DMARC1; p=quarantine; rua=mailto:hello@robayerwealthlab.com; pct=100; adkim=s; aspf=s`. Strict alignment is required for both SPF and DKIM. DKIM alignment should pass cleanly (Resend signs with a key on this exact domain). Strict SPF alignment, by definition, does not consider a subdomain (`send.robayerwealthlab.com`) an exact match for the visible From domain (`robayerwealthlab.com`); this is normal for this kind of setup and does not fail the message overall, because DMARC passes a message when either SPF or DKIM aligns, not only when both do.

## Conclusion on "if password emails are not received"

Based on direct DNS inspection, this system's email authentication setup for Resend is correctly configured: SPF is correct on Resend's actual sending subdomain, DKIM is present and well-formed, and DMARC's alignment requirements are satisfiable through DKIM alone even though strict SPF alignment does not technically apply to the subdomain relationship. There is no DNS-level misconfiguration found that would explain non-delivery. If a real user ever reports not receiving a password email, the more likely causes, in rough order of likelihood, are: the message landed in spam despite correct authentication (still possible, and worth checking the recipient's spam folder first), a typo in the entered email address, or a provider-specific delivery quirk that would need to be diagnosed against that specific message's headers, which requires access to the actual delivered message, not something derivable from this system's own logs alone.
