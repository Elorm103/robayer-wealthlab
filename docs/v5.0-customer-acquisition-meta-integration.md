# Version 5.0 — Customer Acquisition Phase 1: Meta Pixel + Conversions API Integration

**Status: Deployed to production. Browser-side tracking fully live and verified. Server-side Conversions API implemented, tested, and deployed, but dormant pending one credential (`META_CAPI_ACCESS_TOKEN`) only the founder can generate — see Known Limitations §7.**

---

## 1. Executive Summary

Robayer WealthLab now has a real, working Meta Pixel + Conversions API integration, built as a provider-agnostic **Analytics Abstraction Layer** (`backend/services/analytics/`) rather than a Meta-specific bolt-on — the explicit design requirement for this phase.

What's live today:

- The real Meta Pixel (Dataset ID `1556171269307402`) loads on every real customer-facing page and fires automatic `PageView`.
- `ViewContent` fires on every product, blog article, Investment Centre article, the Resources listing, and the Customer AI page.
- `InitiateCheckout`, `CouponApplied`, `AskAI`, `Lead` (newsletter + consultation), and a custom `Download` event fire at the correct real moments across the site.
- A server-side `Purchase` event is dispatched via Meta's Conversions API from the exact place a payment is confirmed genuinely successful (`commerceService.ts`), deduplicated against the browser Pixel's own `Purchase` fire via a shared, deterministic `event_id`.
- A new admin dashboard panel (Analytics → Conversion tracking) gives real visibility: Pixel/CAPI health, retry queue depth, failed events, and recent Purchases/Leads/Downloads — the last two honestly sourced from their real underlying business tables rather than a fabricated "sent to Meta" record this backend cannot actually observe for browser-only events.
- 10 new automated tests plus 2 pre-existing test files extended, all passing against real (mocked-network) infrastructure — not sketched, not skipped.

**What isn't live yet:** the server-side Conversions API dispatch is fully built, tested, and deployed, but requires a real Meta System User access token that only the founder can generate in Meta Events Manager. Until then, `Purchase` events fire from the browser Pixel only (still valuable signal), and the admin dashboard honestly shows "Not configured" rather than a fabricated status. See §7 and §9 for exactly what's needed to finish activation.

**Two real, pre-existing production bugs were found and fixed along the way** (not introduced by this work, but blocking it): the site's Content-Security-Policy was silently blocking all third-party scripts including the dormant Cloudflare Web Analytics beacon, and — separately — blocking the inline data signal this integration's ViewContent event first tried to use. Both are fixed; see §2.5.

## 2. Engineering Report

### 2.1 What was studied before writing any code

- `services/payments/` (the `PaymentProvider` interface + `paystackProvider.ts` + `index.ts` selector) — the exact provider-abstraction shape this integration mirrors.
- `services/emailService.ts`'s `sendEmail()` — the retry-with-backoff-then-log pattern `conversionDispatchService.ts` mirrors exactly (one immediate retry, never throws back to the caller, always logs the outcome).
- `services/commerceService.ts`'s `completeVerifiedPurchase()` — the single, real call site where a purchase is known to have genuinely succeeded; the only place Phase 7 needed to touch.
- `docs/v5.0-analytics-architecture.md` — a pre-existing planning document that had already proposed `services/analytics/conversionDispatchService.ts` by name, "one dispatch service, not five." This work fulfils that plan's Phase 1.
- The frontend's real script-inclusion architecture: there is no single global template. 108 static HTML pages and ~5 Worker-rendered route templates (`books.ts`, `blog.ts`, `resources.ts`, `free-guide.ts`) each hand-list their own `<script>` tags. The one genuinely universal inclusion point is `js/main.js`, present on every real customer-facing page (confirmed: absent only from `admin/*` pages, which correctly should never carry an ad-tracking pixel) — and already used for exactly this purpose (`loadCloudflareWebAnalytics()`, Version 3.3 Milestone M5C). The Pixel loader (`loadMetaPixel()`) was added there, following that exact precedent, rather than editing 100+ individual pages.

### 2.2 The Analytics Abstraction Layer

```
backend/services/analytics/
  types.ts                    — AnalyticsProvider interface, ConversionEventName, ServerEventInput
  hashing.ts                  — SHA-256 email hashing (Meta's own required normalization)
  metaProvider.ts             — Meta's Conversions API adapter
  index.ts                    — getAnalyticsProviders(env): a fan-out REGISTRY, not a single selector
  conversionDispatchService.ts — the one call site: dispatchServerEvent(), dispatchPurchase(), retryFailedConversions()
```

Unlike `getPaymentProvider()` (returns exactly one active provider), `getAnalyticsProviders()` returns every *configured* provider — Meta today, a future Google/TikTok/LinkedIn adapter tomorrow requires one new file and one new registry entry, never a change to the dispatch service, `commerceService.ts`, or any route. This was the explicit design requirement ("Analytics Abstraction Layer rather than a Meta-specific integration") and is structurally enforced, not just documented.

### 2.3 Client-side: `js/components/meta-pixel.js`

One file, two responsibilities:
1. The real Meta base Pixel snippet, initialized with the real Pixel ID, firing automatic `PageView`.
2. `window.RobayerTracking.track(eventName, params, options)` — the extensible custom-event layer (Phase 6). A `STANDARD_EVENTS` allowlist (`PageView`, `ViewContent`, `InitiateCheckout`, `Purchase`, `Lead`) routes to `fbq('track', ...)`; anything else routes to `fbq('trackCustom', ...)`. Adding a future event (`BookPreview`, `SearchKnowledgeBase`, a future course's own event) is one `RobayerTracking.track('EventName', {...})` call at that feature's own success point — nothing in this file ever needs to change for it.

Wired into 6 real trigger points across 5 existing component files:

| Event | File | Trigger |
|---|---|---|
| `ViewContent` | `meta-pixel.js` | Reads a `<meta name="robayer-page-content">` tag every relevant page emits |
| `InitiateCheckout` | `buy-button.js` | After validation passes, before the checkout API call |
| `CouponApplied` | `buy-button.js` | After a coupon is server-validated as genuinely applicable |
| `Purchase` (browser half) | `fulfilment-status.js` | Once, on `showReady()`, deduped via `localStorage` so a page refresh never double-fires |
| `Download` (custom) | `fulfilment-status.js` | Once a real, single-use download link is minted |
| `Lead` | `newsletter-form.js`, `consultation-form.js` | On genuine server-confirmed success only |
| `AskAI` (custom) | `ai-assistant.js` | On a genuinely answered turn (never on `declined`/`error`) — carries only the confidence tier, never the question text |

### 2.4 Server-side: Conversions API (Phase 7)

`commerceService.ts`'s `completeVerifiedPurchase()` — the one place a payment is confirmed genuinely successful (atomic, idempotent, called from both the webhook path and the admin-reprocess path) — now also calls `dispatchPurchase()`, alongside the existing fulfilment/email dispatch, with the same "never throws, never undoes an already-successful payment" discipline.

**Deduplication**: both halves use the identical `event_id`: `` `purchase:${purchaseReference}` ``. This is Meta's own documented, real deduplication mechanism (same `event_name` + `event_id` from both Pixel and CAPI within the dedup window collapses to one conversion) — not a bespoke mechanism built here.

### 2.5 Two real production bugs found and fixed

1. **CSP blocked all third-party scripts.** `backend/middleware/securityHeaders.ts`'s `script-src 'self'` (applied to every HTML response site-wide, since the Worker Route covers the entire zone) silently blocked `connect.facebook.net` — confirmed live via browser console after the first deploy (`fbq` never loaded). Fixed by adding `connect.facebook.net`/`www.facebook.com` to `script-src`/`connect-src`. **Found and fixed the identical, previously-undiscovered bug for Cloudflare Web Analytics** (`static.cloudflareinsights.com`) at the same time — a real, intended feature since Version 3.3 Milestone M5C that had been silently broken since the day it shipped, never caught because its token had stayed unset.
2. **Inline `<script>` also silently CSP-blocked.** The first `ViewContent` implementation set `window.__robayerPageContent` via an inline `<script>` block — also blocked by the same `script-src 'self'` policy (no `'unsafe-inline'`), confirmed live the same way. Fixed by switching to a `<meta name="robayer-page-content" content="...">` tag, which isn't subject to `script-src` at all — applied across `books.ts`, `blog.ts`, `resources.ts`, all 10 Investment Centre pages, and the Customer AI page.

Both were caught by live production browser verification (`fbq`/`RobayerTracking` inspection in a fresh tab), not assumed from code review — see §6.

## 3. Architecture Update

- **New table**: `analytics_conversion_log` (migration `0040`) — one row per (provider, event) dispatch attempt. Mirrors `email_log`'s exact shape (`status`/`attempt_count`/`last_error`/`provider_trace_id`). Backs both the retry sweep and the admin dashboard.
- **New Env bindings** (`backend/worker/env.ts`, `backend/wrangler.jsonc`): `META_PIXEL_ID` (real, non-secret — also embedded in `assets/config/site.json` for the browser), `META_GRAPH_API_BASE_URL`, `META_GRAPH_API_VERSION` (non-secret, configurable like `PAYSTACK_BASE_URL`), `META_CAPI_ACCESS_TOKEN` (secret, absent from `wrangler.jsonc` by design), `META_TEST_EVENT_CODE` (optional, verification-only).
- **New Cron work**: the existing single daily Cron Trigger (`0 6 * * *`) gained a fourth `ctx.waitUntil()` job, `retryFailedConversions()`, following the exact heartbeat-audit pattern the three existing jobs (review reminders, purchase follow-ups, AI Gateway retention cleanup) already use. No new Cloudflare Queue was provisioned — CAPI volume at this project's real scale doesn't justify one; the reasoning that *did* justify one for Knowledge Base indexing (per-invocation subrequest budget) doesn't apply here.
- **New admin endpoint**: `GET /api/admin/analytics/conversion-dispatch`, added to the existing `routes/admin/analytics.ts` alongside its siblings, same `requireAuth`/rate-limit/response-envelope conventions.

## 5. Operations Guide

**Where to look when something seems wrong**: Admin → Analytics → "Conversion tracking (Meta Pixel + Conversions API)" section.

- **"Meta Pixel + CAPI status"**: "Active" once `META_CAPI_ACCESS_TOKEN` is set; "Not configured" (with the exact command to fix it) until then.
- **"Last event sent"**: the most recent successful CAPI dispatch — "Never" is expected and correct until the token is set.
- **"Retry queue"**: rows currently `status = 'failed'`, eligible for tomorrow's 06:00 UTC cron sweep. A number here that never shrinks across several days is worth investigating (check `last_error` on the Failed events table below it).
- **"Failed events"**: every row that has exhausted its retries (`permanently_failed`) or is still awaiting one (`failed`), with the real error Meta returned.
- **"Recent Purchases sent"**: confirmed CAPI deliveries — the real, provider-confirmed record.
- **"Recent Leads" / "Recent Downloads"**: honestly *not* CAPI-confirmed (Lead and Download are browser-only events this backend never sees delivered) — these are the real underlying business events (`newsletter_subscribers`/`consultation_requests`, `download_tokens`) that trigger each browser-side fire, labeled as such.

**Verifying the Pixel is live on a page**: open the page, open DevTools console, run `typeof window.fbq` (should be `"function"`) and `window.RobayerTracking.standardEvents` (should list `PageView, ViewContent, InitiateCheckout, Purchase, Lead`). Meta's own **Pixel Helper** browser extension is the recommended day-to-day tool once the founder wants to spot-check specific pages.

**Verifying CAPI once activated**: set `META_TEST_EVENT_CODE` (via `wrangler secret put`, temporarily) to the code shown in Meta Events Manager → Test Events, make a real purchase (or use a near-zero coupon), and confirm the event appears in Meta's Test Events tab with the correct fields. Remove the test event code afterward — it should never be set in real production traffic.

## 7. Known Limitations

1. **Conversions API is dormant pending a credential.** `META_CAPI_ACCESS_TOKEN` was never provided and cannot be fabricated. Every server-side `Purchase` dispatch is currently skipped (logged as `analytics.dispatch_skipped_no_providers`, never a fake success). Client-side `Purchase` tracking (browser Pixel) is fully live regardless.
2. **Server-side dispatch is scoped to `Purchase` only**, per this phase's own explicit instruction ("Server-side Purchase events should originate from the Worker"). `Lead`, `Download`, `ViewContent`, `InitiateCheckout`, `CouponApplied`, and `AskAI` are browser-Pixel-only — consistent with `js/components/analytics.js`'s own existing first-party-beacon architecture, and with Meta's own guidance that CAPI redundancy matters most for the highest-value, revenue-bearing event.
3. **`BookPreview` and `SearchKnowledgeBase` are supported by the extensible `track()` layer but not wired to anything.** No "book preview" or standalone "search" feature exists on the live site today to instrument — fabricating a fake trigger for a feature that doesn't exist would violate this codebase's own "never fake a data source" principle (see `docs/v2-analytics-spec.md`). The moment either feature ships, wiring it in is one `RobayerTracking.track()` call.
4. **Google Ads Enhanced Conversions, TikTok Events API, LinkedIn, Microsoft Ads** — out of scope for this phase by the user's own instructions (Meta only). The Analytics Abstraction Layer is structurally ready for each (one new provider file, one registry entry) per `docs/v5.0-analytics-architecture.md`'s own sequencing recommendation.
5. **20 pre-existing, unrelated test failures** in `tests/unit/knowledge/indexingService.test.ts` were discovered during full-suite verification. Confirmed unrelated to this work (touches only Knowledge Base indexing, last modified in an earlier, unrelated session phase). Flagged as a separate follow-up task, not fixed here.
6. **Cross-device/cross-session attribution** is out of scope, per the same privacy posture `docs/v5.0-analytics-architecture.md` already established for this project (anonymous-by-design; a purchase is only ever linked to the browser that completed it, via the standard Pixel+CAPI mechanism, never to an anonymous prior session).
