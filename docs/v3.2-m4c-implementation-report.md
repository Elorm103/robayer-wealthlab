**Milestone:** M4 - Commerce & Trust Foundations
**Sprint:** M4C (Reviews & Coupons Implementation, incorporating M4B amendments)
**Status:** Complete (code + tests + docs); not yet committed, tagged, deployed, or accepted.

No marketplace concepts, no promotional/loyalty engine beyond the two approved coupon types, no course platform, no video lessons - matching M4B's own explicit scope boundary.

## Executive Summary

M4C had two jobs, in order: resolve the three amendments M4B's Independent Architecture & Scope Approval Review made mandatory before any feature code was written, then implement Reviews and Coupons on top of the corrected foundation. Both are done.

**Amendment 1** replaced the original, now-superseded coupon schema (which referenced a `platform_users` table that does not exist in this codebase's single-seller architecture) with a corrected design that reuses the real, live `admin_users`/`customers`/`purchase_sessions`/`audit_logs` tables and introduces no marketplace concepts. **Amendment 2** produced a full threat-model review before any coupon code was written, and its central finding - the redemption-limit race between two simultaneous payments both holding the last redemption of a limited coupon - drove the two-phase `validateCoupon()`/`redeemCoupon()` design described in full in the Coupon Architecture Report. **Amendment 3** expanded the mandatory test list to explicitly name every new admin endpoint and a dedicated true-concurrency race-condition test; all seven named files exist and pass.

Reviews are purchase-gated by construction - `submitOrUpdateReview()` looks up the customer's own latest verified purchase server-side, never trusting a client-supplied purchase reference, the same "never trust the client for what matters" discipline this codebase already applies to price. One review per (product, customer) is enforced at the database layer via `UNIQUE(product_id, customer_id)` and an atomic `INSERT ... ON CONFLICT DO UPDATE`; editing a review resets it to `pending`, requiring re-moderation.

Coupons extend, not violate, `routes/checkout.ts`'s standing "never accept price from the client" invariant: the client sends only a `couponCode` string, and the discount is always computed server-side from the coupon's own stored data, both at the discount-preview endpoint and again, authoritatively, at checkout-session creation. The receipt/order pipeline was threaded through to recover and display the original, pre-discount subtotal alongside the discount as its own line, while leaving the pre-existing "total always equals what was actually charged" financial invariant completely unchanged.

Deliverables: 1 migration (3 new tables, 2 new columns on `purchase_sessions`), 2 new backend services, 5 new backend route modules, 9 new API endpoints, 2 new frontend components, 2 new admin pages, 2 modified existing frontend files (`buy-button.js`, `backend/routes/books.ts`), 7 new test files (40 unit + 37 integration = 77 new tests, all passing). Full regression suite: **212/212 passing** (135 carried unchanged from M1-M3D). `npx tsc --noEmit` clean. Notably, `receipts.discount_pesewas` required no schema change at all - M2's own migration 0019 had already reserved that column for a future coupon system; M4C is simply the first code to populate and render it.

- **Amendment 2** - full threat-model review covering price tampering, unauthorized application, expired coupons, replay, stacking, the redemption-limit race, and `first_purchase_only` enforcement, written before any service code existed. See [`v3.2-m4c-amendment-2-coupon-security-review.md`](v3.2-m4c-amendment-2-coupon-security-review.md) and this report's own Coupon Architecture Report companion doc.
- **Amendment 3** - the mandatory test-file list, all seven of which exist and pass as of this report. See [`v3.2-m4c-amendment-3-testing-requirements.md`](v3.2-m4c-amendment-3-testing-requirements.md) and [`v3.2-m4c-test-results.md`](v3.2-m4c-test-results.md).

### Product Reviews
- `backend/services/reviewService.ts` - purchase-gated submission/edit (`submitOrUpdateReview`), public approved-only listing with a computed `averageRating` (`listPublicReviews`), a customer's own reviews regardless of status (`listCustomerOwnReviews`), and admin moderation (`listReviewsForModeration`, `moderateReview`).
- `backend/routes/reviews.ts`, `backend/routes/customer/reviews.ts`, `backend/routes/admin/reviews.ts` - the public read endpoint, the customer submit/list endpoints, and the admin moderation endpoints, respectively.
- `backend/routes/books.ts` - the product detail page now server-renders the aggregate star rating and the list of approved reviews directly from `listPublicReviews()`, plus a schema.org `aggregateRating` block on the existing `Book` JSON-LD (only emitted when at least one approved review exists).
- `js/components/product-reviews.js` (new) - the one part of the review experience that genuinely needs client-side state: it checks the visitor's own customer-session cookie and renders either a "sign in to review" prompt or a submit/edit form, self-contained rather than depending on `dashboard-auth.js` (that helper's `requireSession()` forces a redirect, which is correct for `/dashboard/*` but wrong on an otherwise-public product page).
- `admin/reviews/index.html` + `js/components/admin/admin-reviews.js` (new) - a status-filterable moderation table with inline Approve/Reject actions, following the established `admin-consultations.js` pagination/`adminFetch()` conventions but without a detail drawer, since moderation here is a single binary decision per row.

### Coupon Engine
- `backend/services/couponService.ts` - discount computation (`computeDiscountPesewas`, always server-side, capped so a discount can never exceed the charge), the two-phase `validateCoupon()`/`redeemCoupon()` redemption design (full rationale in the Coupon Architecture Report), best-effort `checkFirstPurchaseOnlyViolation()`, and admin CRUD (`createCoupon`, `updateCoupon`, `listCoupons`).
- `backend/routes/coupons.ts` - the public, non-mutating discount-preview endpoint.
- `backend/routes/admin/coupons.ts` - admin list/create/update, `EDITOR_ROLES`-gated for every mutation (a coupon is a direct financial-discount instrument, the same reasoning already applied to Products' pricing writes).
- `backend/routes/checkout.ts` + `backend/services/commerceService.ts` - checkout now accepts an optional `couponCode` string (never a price or discount amount); `createCheckoutSession()` validates it server-side and locks the resulting discounted `amountPesewas` into `purchase_sessions` before Paystack is ever contacted. `handlePaymentWebhook()` calls `redeemCoupon()` and `checkFirstPurchaseOnlyViolation()` only after `verifySessionAtomic()` has already confirmed a real payment - never before.
- `backend/services/orders/orderService.ts` + `receiptPdfService.ts` - the discount is threaded through to `receipts.discount_pesewas`, recovering the original pre-discount subtotal (`amountPesewas + discountPesewas`) for line-item display, while tax and total continue to be computed from the actual, already-discounted charged amount - the pre-M4 "total always equals what was actually charged" invariant is unchanged. The downloadable PDF receipt now renders a "Discount: -X" line whenever a coupon was applied, and is omitted entirely for an ordinary, non-coupon purchase.
- `js/components/buy-button.js` - a page-singleton coupon-code input (`#purchase-coupon-code`, following the same established pattern as the existing marketing-opt-in checkbox) with an "Apply" button that calls the discount-preview endpoint and shows the computed discount before checkout starts; the actual checkout POST always includes whatever code is present, previewed or not, since `createCheckoutSession()` re-validates it independently either way.
- `admin/coupons/index.html` + `js/components/admin/admin-coupons.js` (new) - a list/create/activate-deactivate management page. Code, discount type, discount value, and product scope are all immutable after creation (only `status`, `maxRedemptions`, and `expiresAt` can change) - deliberately, since a coupon's meaning may already have been shown to a customer.

See [`v3.2-m4c-api-changes.md`](v3.2-m4c-api-changes.md) for full request/response detail on all nine new endpoints.

## Security Measures

- **Purchase-gated reviews**: never trusts a client-supplied purchase reference - `submitOrUpdateReview()` resolves the customer's own latest verified purchase for the target product server-side.
- **One review per (product, customer)**: enforced at the database layer (`UNIQUE(product_id, customer_id)`), not just in application logic, via an atomic upsert - no check-then-write race is possible.
- **Review moderation is editor-only**: `EDITOR_ROLES` (`super_admin`, `editor`), matching the existing Orders refund-action precedent - a moderation decision has real customer-facing/trust consequences.
- **Price never trusted from the client**: `couponCode` is the only coupon-related field `routes/checkout.ts` accepts; the discount is always computed server-side, twice independently (preview, then checkout-lock).
- **Two-phase coupon redemption**: `validateCoupon()` is a non-mutating soft check; `redeemCoupon()` is the only place `redemptions_count` is atomically, conditionally incremented, and it is called only after a real payment is already confirmed - a payment is never reversed once genuinely charged, even if the redemption limit was already reached by the time payment confirmation arrived. See the Coupon Architecture Report for the full reasoning and `couponRaceConditions.test.ts` for the true-concurrency verification.
- **`first_purchase_only` is best-effort, detection-only**: cannot be enforced pre-payment in this guest-checkout architecture (the customer's email is unknown until Paystack confirms it); a violation is logged, never blocking, mirroring this project's own prior, documented acceptance of this exact risk category from the V3.0 planning cycle.
- **Coupon mutations are editor-only + CSRF-protected + audit-logged**: `coupon.created`/`coupon.updated` audit entries via the existing `auditService.record()`, matching every other admin-mutation surface in this codebase.

## Recommendations Before Acceptance Review / M4D

1. No further backend change is anticipated for Reviews or Coupons as currently scoped; a future milestone extending either (e.g. stacked coupons, review photos, verified-purchase badges) should treat this report and its companion architecture docs as the baseline, not re-derive the design from scratch.
2. Consider whether the admin Coupons page's "Applies to" product dropdown should paginate or search once the catalog grows well past 100 products (`GET /api/admin/products?pageSize=100` is currently fetched in full) - not a defect today, given the catalog's real current size, but worth a note for whoever picks this up next.
3. As with M3's own equivalent recommendation, a scripted or documented local-dev-seed process (this sprint used ad hoc scratch SQL, cleaned up after verification) would help if Reviews/Coupons UI verification becomes a recurring need across future sprints.
