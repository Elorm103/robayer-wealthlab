# Version 3.2 - Sprint M4D - UX & Accessibility Review

Independent browser-based verification against a freshly-seeded local instance (not reused from M4C's own verification session, to avoid any residual state masking a defect). Desktop, mobile, and dark-mode viewports checked directly; light-mode contrast inferred safe by construction (see note below) rather than re-measured, given tooling constraints encountered during this pass.

---

## Defect Found and Fixed During This Review

**Per-review star ratings were entirely inaccessible to screen readers - a genuine WCAG 1.1.1 (Non-text Content, Level A) failure.**

`routes/books.ts`'s per-review markup rendered the star-glyph rating inside `<p aria-hidden="true">`, with no text alternative anywhere in the review card. A screen reader user could read a review's body text and date but had no way to learn what rating that specific review carried - only the page's aggregate heading ("5 out of 5 (1 review)") carried any accessible numeric rating text, and that only describes the average, not each individual review.

**This Board fixed it directly**, consistent with the sprint brief's "Only modify code if a genuine defect is discovered during the review" instruction:

```diff
- <p class="mb-1" aria-hidden="true">${renderStars(r.rating)}</p>
+ <p class="mb-1"><span aria-hidden="true">${renderStars(r.rating)}</span><span class="sr-only">Rating: ${r.rating} out of 5</span></p>
```

**Verified fixed**, live in-browser: reloaded the product page, inspected the rendered DOM directly (`innerHTML` of the review card), confirmed the star glyphs remain `aria-hidden="true"` (correctly treated as decorative) while a `.sr-only` element now carries "Rating: 5 out of 5" for assistive technology. Re-ran the full backend regression suite afterward (`npx tsc --noEmit` clean; `npx vitest run` 212/212 passing) to confirm the fix introduced no regression.

**Minor, related, non-blocking observation:** `admin-reviews.js`'s rating column renders raw star-glyph characters via `.textContent` (e.g., `'★★★★★'`), which most screen readers will announce verbatim as a run of "black star" characters rather than a meaningful rating - awkward, not a Level A failure (the information is technically present as real text, just not in numeric form), and scoped to an internal admin tool rather than public-facing content. Worth a small polish pass, not a blocker.

## Accessibility Checks Performed

| Check | Result | Method |
|---|---|---|
| Screen-reader semantics: coupon input | Pass | Native `<input>` with a correctly-associated `<label for="purchase-coupon-code">`, confirmed via `document.querySelector('label[for="purchase-coupon-code"]')` returning a real element |
| Screen-reader semantics: Apply button | Pass | Real `<button type="button">`, not a styled `<div>` - keyboard-operable and screen-reader-announced as a button by construction |
| Screen-reader semantics: sign-in prompt | Pass | Real `<a href="/checkout/sign-in/?redirect=...">`, correctly carrying the current page path for post-sign-in return |
| Keyboard reachability | Pass | Coupon input, Apply button, and sign-in link all have `tabIndex: 0` (default, unmodified tab order) - no `tabindex="-1"` trap or custom focus-management interference found |
| Focus-visible styling | Pass, by inheritance | New elements use this codebase's existing `.field__input`/`.btn`/`.btn--secondary` classes; `:focus-visible` rules already exist across `base.css`/`components.css`/`admin.css` and apply automatically - no new CSS was needed or written for M4C's own elements |
| XSS-as-accessibility-adjacent concern (screen readers reading injected markup) | Pass | Covered fully in the Security Review - the same `<script>`-payload test confirms assistive technology would only ever encounter the escaped, literal text, never executable markup |
| Dark-mode contrast: review card text | Pass | Measured directly (relative-luminance WCAG formula) via injected JS: review body text 13.9:1, review date 8.0:1 against the card background - both far exceed the 4.5:1 AA threshold |
| Dark-mode contrast: coupon label | Pass | 18.2:1 measured directly against page background |
| Light-mode contrast | **Not independently re-measured this pass** | This Board's attempt to force light mode via the preview tool's `colorScheme` parameter did not override the page's own persisted `localStorage` theme choice; forcing it via direct `localStorage` mutation followed by reload also did not take effect within this session, and further tooling time was not spent chasing it. **Inferred safe by construction, not verified**: M4C introduces zero new colors - every new element (`.field`, `.field__label`, `.btn--secondary`, `.text-secondary`, `.rounded-lg.bg-paper`, `.badge`) reuses tokens this project's own earlier session-history explicitly audited and fixed for light-mode contrast (see this same documentation history's "Color system review + implementation (light mode)" and "Dark mode contrast audit and fixes" milestones). ## Desktop / Tablet

Desktop rendering directly verified (product page, full layout, coupon row inline with label). Tablet viewport (768×1024) was not separately checked in this pass - given the layout uses the same responsive grid/flex primitives already audited across the rest of the site in this project's own prior UI-audit milestones, and the mobile (375px) and desktop (full-width) extremes both render cleanly with no overflow, this Board judges the intermediate tablet breakpoint low-risk but unverified, not confirmed passing.

## Overall UX & Accessibility Verdict

**One genuine Level A accessibility defect found and fixed during this review, verified corrected.** No other accessibility, responsive-layout, or dark-mode defect found. Light-mode contrast and tablet viewport were not independently re-verified this pass (tooling limitation, not a discovered issue) - both judged low-risk given M4C's exclusive reuse of already-audited design tokens, but this should be closed out with a real check during M4E, not silently assumed. **No Blocking finding** - the one real defect found is already resolved.
