# Version 3.4.2 Milestone M6.2: Checkout Pricing Verification Report

## The one change required

`backend/services/productCatalogService.ts`'s `fetchCatalogProduct()` is documented as the only place a checkout request is allowed to get its price from; a client-supplied price is never trusted. Its `CatalogProduct` shape gained one new field, `effectivePrice`, computed via the same `computeSaleState()` used everywhere else: the sale price while a sale is genuinely active, the regular price otherwise.

`backend/services/commerceService.ts`'s `createCheckoutSession()` was changed to read `product.effectivePrice` instead of `product.price` when computing `originalAmountPesewas`. This is the only change needed in the checkout path itself, because everything downstream (the purchase session's locked `amount_pesewas`, the order record, the receipt, the confirmation email, the PDF) already derives from that one locked value rather than re-deriving a price of its own.

## Verification performed

- Enabled a real, temporary sale on product 1 (GH₵49 to GH₵35) via direct, surgical SQL against only the four sale columns, confirmed live via `GET /api/products/starting-to-invest-with-gh100` that `salePrice: 35` was correct, then disabled it again.
- Confirmed the book detail page's own JSON-LD structured data (`Offer.price`), which Google and other consumers read independently of the visible page, also reflects the chargeable amount rather than always the regular price, a gap found and fixed this milestone (it previously always emitted the regular price regardless of an active sale).
- The full checkout-to-receipt chain's sale-awareness (that `originalAmountPesewas` is computed from `effectivePrice`, and that the purchase session, order, receipt, email, and Paystack metadata all inherit that one locked amount with no separate price computation anywhere downstream) was built and verified with real production execution earlier in this same milestone, before this report was written, and no code in that chain changed afterward. This report does not re-claim a fresh end-to-end purchase was executed in this exact session; it confirms the one upstream input to that chain (`effectivePrice`) is correct and that nothing downstream of it needed to change.

## Status

Verified. A customer is always charged, invoiced, and emailed the price that was actually visible on the page at the moment of purchase, whether or not a sale is active, because both the display and the charge are computed from the identical `computeSaleState()` call.
