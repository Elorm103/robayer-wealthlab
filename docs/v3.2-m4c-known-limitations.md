# Version 3.2 - Milestone M4C Known Limitations

**Milestone:** M4 - Commerce & Trust Foundations
**Sprint:** M4C (updated at M4E Closeout)

This list distinguishes deliberately-accepted, previously-reviewed risk categories (carried forward, not new) from genuinely new gaps this sprint introduced, and from scope this sprint intentionally left for a future milestone.

**M4E closeout note:** the disclosure below regarding Reviews' launch-time collection mechanism was added at M4E closeout, resolving a specific gap `v3.2-m4d-documentation-review.md` (Finding 3) identified: `v3.2-m4b-customer-journey-validation.md` required this exact disclosure and it was missing from this document's original M4C version. The M4D-identified automated-test-coverage gap for the discount→receipt→PDF pipeline was closed with new tests during M4E (see `tests/unit/orderService.test.ts`, `tests/unit/receiptPdfService.test.ts`, and `tests/integration/couponReceiptPipeline.test.ts`) rather than being recorded here as a limitation - it is resolved, not deferred.

---

## Carried-Forward, Deliberately Accepted (Not New to M4C)

- **The redemption-limit race's "loser still gets the discount" outcome.** When two payments race for the last redemption of a limited coupon, the atomic counter correctly caps `redemptions_count` at `max_redemptions`, but the "losing" payment is never reversed or denied - the customer already paid the discounted price they were shown. This was the explicit, primary finding of Amendment 2's security review, reasoned through and accepted *before* any code was written, not discovered as a defect afterward. Verified under true HTTP concurrency in `couponRaceConditions.test.ts`. See the Coupon Architecture Report's "Two-Phase Redemption Design" section for the full reasoning.
- **`first_purchase_only` is detection-only, not preventable.** A guest-checkout architecture cannot know a customer's real identity until Paystack's webhook confirms it, so this flag can only be checked *after* payment, and a violation is only ever logged, never blocked. This mirrors the ARB's own prior, explicit acceptance of this exact risk category from the original V3.0 checkout architecture review - not a new limitation this sprint introduced.

## Scope Deliberately Left Out (Per M4B's Approved Boundary)

- **No coupon stacking.** Checkout accepts exactly one `couponCode`; there is no concept of applying two coupons to one purchase. Not requested by M4B's approved scope.
- **No promotional/loyalty engine beyond the two approved discount types** (percentage, fixed-amount). M4B's own review explicitly rejected broader promotional-engine scope for this milestone.
- **No review photos, verified-purchase badges, or reviewer display names.** `listPublicReviews()` deliberately exposes no customer identity at all (see the Reviews Architecture Report's "Public Visibility" section) - a future milestone wanting attributed reviews needs a deliberate, separate privacy decision, not an incremental addition to this endpoint.
- **No review helpfulness voting, reply-from-seller, or sorting/filtering on the public reviews list** beyond newest-first. Not part of M4B's approved scope.
- **Reviews launches with no automated post-purchase collection trigger.** M4 (Reviews, this milestone) ships before M5's own review-request trigger. Between M4 and M5, a customer can only leave a review by proactively navigating back to a product page they've already purchased - no post-purchase email or dashboard prompt exists yet to invite them to do so. `v3.2-m4b-customer-journey-validation.md` explicitly required this be stated as a known, accepted limitation of M4's own scope, not left implicit; M4A's own Implementation Strategy already anticipated the trigger as an M5 item "feeding M4's Reviews feature." See [`v3.2-m4c-reviews-sparse-launch-state-ux.md`](v3.2-m4c-reviews-sparse-launch-state-ux.md) for the UX design this limitation sits alongside (an honest empty state, not a workaround for the missing trigger).

## Genuine Gaps From This Sprint (New, Worth Tracking)

- **Admin Coupons' "Applies to" product dropdown fetches up to 100 products in one request** (`GET /api/admin/products?pageSize=100`), with no search or pagination in the dropdown itself. Not a defect against this catalog's actual current size, but will need a search-as-you-type affordance if the catalog grows well past 100 titles.
- **No admin bulk actions for coupons or reviews** (e.g. approve-all-pending, bulk-deactivate). Each admin page's actions are one row at a time - acceptable at today's realistic review/coupon volumes, worth revisiting if either grows into the hundreds of pending items at once.
- **Authenticated admin-page browser verification (moderating a review, creating/deactivating a coupon through the actual admin UI, not just the API) was not performed in this sprint** - it required either hand-crafting a valid PBKDF2 password hash for a local test admin account or building a local-dev seed/bootstrap flow that doesn't currently exist in this codebase, both out of this sprint's scope. The equivalent server-side logic is fully covered by `adminReviews.test.ts`/`adminCoupons.test.ts`'s real-HTTP integration tests, which exercise the identical route handlers these pages call - but a rendering/interaction defect specific to the admin JS itself (as opposed to the API it calls) would not be caught by that coverage alone. See [`v3.2-m4c-test-results.md`](v3.2-m4c-test-results.md)'s "Browser Verification" section for exactly what *was* verified in-browser.
- **No dedicated "My Reviews" dashboard page.** `GET /api/customer/reviews` exists and is tested (a customer can already see their own reviews, any status, via this API), but no `/dashboard/reviews/` page was built to surface it in the UI - a customer can currently only manage a review from the product page itself, not from a central dashboard list. Not named as a required M4C deliverable, but worth flagging as a natural, small follow-up.
- **Coupon `starts_at`/`expires_at` are accepted as raw strings from the admin create/update forms** (`<input type="date">` on the create form, giving `"YYYY-MM-DD"`), compared directly against `new Date().toISOString()` inside `validateCoupon()`. A date-only string compares correctly against a full ISO timestamp for `>`/`<` purposes in practice (lexicographic string comparison works because ISO date strings share a common prefix format), but this was not exhaustively tested against timezone-boundary edge cases (e.g. a coupon set to expire "today" in one timezone while the Worker's clock reads a different calendar day in UTC). Worth a dedicated look if precise-to-the-hour coupon windows become a real business requirement; today's use case (whole-day validity windows) is unaffected.
