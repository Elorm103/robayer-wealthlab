# Version 3.3 Milestone M5: Final Known Limitations

Authoritative, closeout-final version, superseding `docs/v3.3-m5c-known-limitations.md` and `docs/v3.3-m5d1-known-limitations.md`. Consolidates both, corrects the one cross-reference gap Sprint M5D.2 found (a discovered issue claimed to be documented in two places but only present in one), and reflects this closeout sprint's own ratification of Sprint M5D's Finding N1.

---

## Cloudflare Web Analytics Token Is Not Yet Set

`assets/config/site.json`'s `analytics.webAnalyticsToken` is `null`. The beacon-loading logic in `js/main.js` is real and functional but a no-op until a human with Cloudflare dashboard access generates a real Web Analytics site-tag (a one-time manual action; no API exists for it, and this project's current Cloudflare API token scope does not grant it). **Required follow-up**, unchanged since Milestone M5C.

## Two of Nine Named Analytics Metrics Produce No Real Data

"Landing-page visits" and "product views," named in the M5C sprint brief's own Phase 4, depend entirely on the Cloudflare Web Analytics token above and produce no queryable data until it is set. The other seven named metrics (checkout starts/completions, coupon usage, review participation, dashboard usage, repeat purchases, account reconciliation success) are all real, live D1 aggregates, independently verified correct. **Tracked, not resolved by Version 3.3** — deferred, per Sprint M5E's own closeout ratification, to a future milestone's evidence-based prioritization rather than built speculatively now.

## No "Customer Growth" Metric Exists

The admin dashboard's "Activation & customer growth" section (Milestone M5C Phase 6) does not include a metric measuring new customer-account creation over time — no such metric exists anywhere in this codebase, before or after Milestone M5. The section's own name promises more than it currently delivers. **Tracked, not resolved by Version 3.3**, same disposition as the item above.

## Review-Reminder Idempotency: Corrected Design, With Its Own Disclosed Limits

Milestone M5D.1 replaced the original, defective eligibility check with an atomic per-purchase claim table (`review_reminder_attempts`, migration `0022`), independently verified correct under live 5-way concurrency stress testing (Sprint M5D.2). Remaining, honestly-disclosed limitations of the corrected design:

- **A purchase whose send fails 3 times (`MAX_SEND_ATTEMPTS`) stops retrying and is marked `permanently_failed`**, even if the underlying cause was ultimately transient (e.g., a multi-day Resend outage). Deliberate, not an oversight — an unbounded retry risks masking a genuinely bad recipient address forever. Now correctly produces a findable `customer.review_reminder_failed` audit log entry, closing the audit-visibility gap Sprint M5D originally found.
- **The claim-staleness window (`CLAIM_STALE_MINUTES = 10`) is a fixed constant**, chosen to comfortably exceed any single Worker invocation's own CPU/wall-time budget. Revisit only if this platform's own scheduled-job duration profile changes materially.
- **A latent, currently-harmless timestamp-format inconsistency exists in `findDueReminders()`'s own `verified_at <= ?` eligibility cutoff** (`verified_at` is stored via `commerceService.ts`'s SQL `datetime('now')`; the cutoff is JS-`.toISOString()`-formatted — the same class of bug that briefly defeated the claim-staleness fix itself before being caught and corrected during Sprint M5D.1). This produces correct results today only because the 5-day comparison granularity means the date portion of the two strings differs before the inconsistent time-of-day portion is ever reached. **Discovered during Sprint M5D.1, correctly left unfixed as out-of-scope for that remediation sprint, and — correcting a completeness gap Sprint M5D.2 found in that sprint's own documentation — is recorded here, in this authoritative final document, as a tracked item for a future, narrowly-scoped cleanup.**

## Review-Reminder Batch Size Is Capped, Not Queued

`MAX_REMINDERS_PER_RUN = 200` bounds a single scheduled invocation. Any remainder is picked up by a later scheduled run — the eligibility query (and now the claim table) are idempotent, not a one-shot queue, so nothing is lost, only delayed. Not a practical concern at this platform's current volume.

## Review-Reminder Delivery Is Sequential, Not Parallel

Deliberate: parallelizing would risk tripping Resend's own rate limits and complicate the existing retry/log discipline. Not a performance concern at current volume.

## Repeat-Purchase Metric Counts Events, Not Customers

`repeatPurchasesInRange()` counts repeat-purchase events in the selected range, not a lifetime count of customers who have ever repurchased. Deliberate, for consistency with every other period-over-period metric in this milestone.

## Reconciliation's Concurrency Fix Is Narrower Than Review Reminders' Own Fix, By Design

Reconciliation uses a `meta.changes` check on its existing linking `UPDATE`, not a dedicated claim table — correct and sufficient for the realistic race this system can actually produce (concurrent HTTP requests, no multi-day retry requirement), and deliberately not over-engineered to match the heavier mechanism review reminders needed for a structurally different problem (a recurring, unattended Cron Trigger with a genuine need to retry across days).

## Reconciliation Opt-Out UX Has No Dedicated Frontend Page

`GET /api/customer/review-reminders/opt-out` renders directly as server-rendered HTML from the Worker, matching an existing project precedent for a simple standalone page, rather than a fully-styled static frontend page. Deliberate scope decision given the action's low stakes; revisit only if visual consistency becomes a concern.
