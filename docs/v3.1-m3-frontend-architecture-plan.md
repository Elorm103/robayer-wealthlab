# Version 3.1 - Sprint M3A - M3 Frontend Architecture Plan

Planning only. No page was built, no component was written, no route was added.

---

## Governing constraint: extend the existing architecture, do not introduce a new one

Confirmed by direct inspection: this site has no JS framework, no build step beyond static HTML/CSS/JS files, no client-side router, and no bundler-driven component system. Every page is a real, separate `.html` file; every interactive behavior is a small, self-initializing vanilla-JS file in `js/components/`. M3 must extend this pattern, not replace it with a framework - introducing React/Vue/etc. for six dashboard pages would be a disproportionate architectural change this planning sprint does not recommend and was not asked to consider.

---

## Page/route plan

| Route | File | Purpose |
|---|---|---|
| `/dashboard/` | `dashboard/index.html` | My Library (the dashboard's entry point, per the UX Strategy) |
| `/dashboard/purchases/` | `dashboard/purchases/index.html` | Purchase History |
| `/dashboard/receipts/` | `dashboard/receipts/index.html` | Receipts |
| `/dashboard/licenses/` | `dashboard/licenses/index.html` | Licenses |
| `/dashboard/security/` | `dashboard/security/index.html` | Account Security |

**Downloads is not a separate route** - per the UX Strategy's own conclusion, it is a secondary line within each My Library row, not a seventh page. This keeps the route count at five, not six, without losing any required capability.

**Naming note:** `/dashboard/` is proposed over `/account/` to avoid ambiguity with the existing `/checkout/*` auth pages (`sign-in`, `set-password`, `forgot-password`), which remain exactly where they are - M3 does not move or rename any M1 page. A customer's journey becomes: `/checkout/sign-in/` (existing, unchanged) -> successful login -> `/dashboard/` (new).

## Shared dashboard shell

A single new component, `js/components/dashboard-nav.js`, renders the six-item navigation (Section 3 of the UX Strategy) and the "currently signed in as {email}" indicator, included via the existing `data-include` partial mechanism (`js/includes.js`) as `partials/dashboard-nav.html` - a direct sibling of the existing `partials/header.html`/`partials/footer.html` pattern, not a new inclusion mechanism.

Every dashboard page also needs a **session guard** that runs before the page's own content renders: call `GET /api/customer/auth/session` (already live, M1) on load; if it returns `401`, redirect immediately to `/checkout/sign-in/?redirect={current path}` rather than rendering an empty or broken authenticated page. This is a new, small shared script, `js/components/dashboard-auth-guard.js`, included on every `/dashboard/*` page before any page-specific component - the one genuinely new piece of shared frontend infrastructure M3 needs.

## Component inventory (new files)

| File | Mirrors (existing precedent) | Responsibility |
|---|---|---|
| `js/components/dashboard-auth-guard.js` | New - no direct precedent, but built from the same `fetch()` + redirect-on-failure pattern already used throughout | Session check + redirect gate, included first on every dashboard page |
| `js/components/dashboard-nav.js` | `js/components/nav.js` (the existing public-site nav) | Renders the six-item dashboard nav + signed-in indicator |
| `js/components/library-list.js` | `js/components/fulfilment-status.js` (state-driven `[data-*]` hooks, mint-then-navigate download pattern) | My Library: fetch, render rows/cards, wire Download/View Receipt actions |
| `js/components/purchase-history-list.js` | Same pattern as `library-list.js`, presentational variant only (per the UX Strategy's "same API, different presentation" conclusion) | Purchase History page |
| `js/components/receipts-list.js` | Same pattern; download action calls the customer-authenticated receipt endpoint directly (no mint-then-redeem needed, unlike the guest path) | Receipts page |
| `js/components/licenses-list.js` | Same pattern, read-only | Licenses page |
| `js/components/account-security.js` | `js/components/set-password-form.js` (form + confirmation + error handling) | Password change form, session list, "log out other sessions" with a confirmation dialog (per AR-009) |

**No new CSS file is planned.** Every component above should be buildable entirely from `css/tokens.css` + `css/components.css`'s existing classes (`.card`, `.btn`, `.grid`, `.stack`, `.alert`, `.badge`-equivalent if one exists, else a small additive class following the same token-only discipline). If a genuinely new component class is needed (e.g., a status-badge treatment that doesn't already exist), it should be added to the existing `css/components.css`, not a new stylesheet.

## Data-fetching pattern (reused, not reinvented)

Every list component follows `fulfilment-status.js`'s exact shape:

1. On `partials:loaded`/`DOMContentLoaded`, guard against double-init (`data-bound` attribute check).
2. `fetch()` the relevant `GET /api/customer/*` endpoint - same-origin, no CORS/credentials handling needed (per the Architecture Review's own confirmation).
3. Render exactly one of: loading state (initial, static markup) -> populated list, empty state, or error state - never a partial/ambiguous render.
4. Any action (download, view receipt) mints a fresh request at click time; never a pre-fetched or embedded URL, matching the existing "email never contains a permanent link" discipline extended to dashboard buttons.

## Changes to existing files (small, already identified in the Architecture Review)

1. `js/components/sign-in-form.js` - change the post-login redirect from `/?signed-in=1` to `/dashboard/`.
2. `checkout/callback/index.html` - the static password-set note's copy can optionally reference the dashboard once it exists; not a structural change, a copy tweak, and not blocking for M3's own launch (can ship in the same PR or a fast-follow).

No other existing file requires a structural change.

---

## Browser/device support

Unchanged from the rest of the site - no new browser-support requirement is introduced by the dashboard; it uses the same `fetch()`/`URLSearchParams`/vanilla-DOM APIs every existing page already depends on.

---

## What this plan deliberately does not include

- No client-side state-management library (Redux, etc.) - unnecessary for six read-mostly pages with no cross-page shared state beyond the session itself.
- No client-side router - every page is a real, separate HTML file, per the site's existing architecture.
- No new build tooling - the project's zero-build-step static-site approach is unchanged.
