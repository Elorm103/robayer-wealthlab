# Version 3.2 - Sprint M4B - Recommendations

Consolidated, actionable list from this Board's full review. Each item classified Blocking (must resolve before M4C implementation proceeds) or Non-blocking (track, address during or after M4).

---

## Blocking

1. **Produce a corrected `coupons`/`coupon_redemptions` schema**, scoped to the current single-seller platform (drop `scope`/`creator_id` from the `coupons` table as designed in `v3-database-design.md`; reference `admin_users`, not the nonexistent `platform_users`, for `created_by`). Owner: whoever leads M4's technical planning. Effort: small, contained - not a reason to delay M4C's start meaningfully, but must exist before any migration is written.
2. **M4C's Security Review must name the payment-amount-locking/webhook-verification change (`commerceService.ts`) as its primary focus**, with explicit sign-off that: the discount is computed and locked at checkout-creation time only; the webhook verifies against the discounted, locked amount; no post-creation coupon modification is possible without invalidating the session.
3. **Admin-panel test coverage for review moderation and coupon management must be written as part of M4C's first implementation pass**, not retrofitted after M4C's own acceptance review finds the gap - this exact pattern has already recurred twice in this project's history (M2, M3) and should not become three.

## Non-Blocking

4. Design Reviews' empty/sparse launch state explicitly (near-zero real customers/purchases today) - honest "no reviews yet" copy, consistent with this project's existing AR-009 precedent, not left implicit.
5. If Wishlist's ADR-006 tension is resolved in M5, treat that resolution with the same governance weight ADR-006 itself received (a reviewed amendment), not as an informal in-sprint decision.
6. Correct `v3.2-m4-scope-recommendation.md` and `v3.2-m4-feature-prioritization-matrix.md`'s "no new design work needed"/"zero open design questions" language for Coupons, so the record doesn't carry a claim this review has since corrected.
7. On the VAT-registration question (now unresolved across seven consecutive planning passes): if still unresolved by M4's closeout, require a written explanation from the Product Owner of what is specifically blocking a decision, rather than another documentation mention recommending escalation.
8. Continue the `platform_users` migration/rollback planning (ADR-011) in parallel with M4, as M4A already recommended - this Board found no reason to change that recommendation, and notes it also unblocks a *future*, real, `platform_users`-referencing version of the coupon schema (creator-scoped coupons) once M7 is reached.
9. Continue the independent eBook-content-expansion track in parallel, as M4A recommended - no change.

---

## Priority Order for Whoever Picks This Up Next

1. Item 1 (schema correction) - do this first, it unblocks everything else.
2. Items 2-3 (security focus, test coverage) - fold into M4C's own opening Testing/Security Strategy documents, not separate work.
3. Items 4-9 - track normally, no urgency beyond their own stated timing.
