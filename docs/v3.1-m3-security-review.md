# Version 3.1 - Sprint M3A - M3 Security Review

Planning only. Reviews every new UI flow and API addition proposed in the M3 Frontend Architecture Plan and API Gap Analysis against this project's existing, proven security patterns - no new security primitive is proposed anywhere in this document.

---

## Authentication

- Every dashboard page requires an active `customer_session` cookie, enforced by the new `dashboard-auth-guard.js` calling the existing, unchanged `GET /api/customer/auth/session`. A missing or expired session redirects to `/checkout/sign-in/`, never renders a degraded or partial authenticated view.
- The proposed `POST /api/customer/auth/change-password` (API Gap Analysis, Gap 4) requires the customer's **current password** before accepting a new one, even though a valid session already exists - re-authentication for a specific irreversible action, mirroring the same discipline `admin`-side password changes already use, not a new pattern.
- No change is proposed to `validateSession()`, `createSession()`, or the underlying `customer_sessions` table's own validity rules (exists, not revoked, not expired, owning customer active/not deleted) - M3 is a consumer of this logic, not a modifier of it.

## Authorization

- Every new or extended endpoint filters by the session's own `customerId`, server-side, never a client-supplied value - the same discipline every M2 endpoint already established, re-applied here without exception.
- The proposed `GET /api/customer/sessions` and `POST /api/customer/sessions/:sessionId/revoke` (Gap 3) must verify the target `sessionId` belongs to the requesting customer before any read or write - a customer must never be able to list or revoke another customer's session by guessing a numeric id. This is a new ownership check (session-id-scoped, not customer-id-scoped like every other M2 endpoint), and is called out explicitly here as the one genuinely new authorization shape M3 introduces, precisely so it gets its own dedicated test (see Testing Strategy).
- A purchase/receipt/license belonging to a different customer must continue to return the identical `NOT_FOUND`/`RECEIPT_NOT_FOUND` a nonexistent one would, on every extended endpoint (Gap 1/2's additive fields change *what* is returned for an owned resource, never *whether* a resource is disclosed to a non-owner) - no enumeration behavior is weakened by adding fields to an existing, already-ownership-checked response.

## CSRF

- Every new state-changing endpoint (`POST /api/customer/auth/change-password`, `POST /api/customer/sessions/:sessionId/revoke`) requires the existing double-submit `customer_csrf` cookie / `X-Customer-CSRF-Token` header pattern, exactly as M1's `POST /api/customer/auth/logout` already does - no new CSRF mechanism, an application of the existing one to two new mutating routes.
- Read-only endpoints (`GET /api/customer/sessions`, the extended `GET /api/customer/purchases*`) correctly require no CSRF token, consistent with every other GET endpoint in this codebase.

## Session handling

- No change to session lifetime (12h absolute TTL), revocation semantics, or the sliding `last_seen_at` update - M3 only adds a way for a customer to *see* and *selectively revoke* their own sessions, not a new session-handling rule.
- The "log out other sessions" action (Gap 3) must never allow revoking the *current* session through this specific control (that is what the existing `POST /api/customer/auth/logout` already does) - the new endpoint should either exclude the current session from the revocable list in the response, or explicitly reject an attempt to revoke it via this route, so the two actions (logout vs. revoke-other-sessions) remain distinct and neither can be used to accidentally lock a customer out of their own dashboard mid-session.

## Customer isolation

- Verified by direct re-reading of `purchaseHistoryService.ts`: every existing query already filters by `customerId` in its `WHERE` clause, never joins across customers. The two new fields (Gap 1/2) are populated from `deliveries`/asset-resolution logic keyed off the already-ownership-verified `purchase_session_id`, so no new cross-customer query path is introduced.
- Recommend a dedicated test (Testing Strategy) proving a different customer's session cannot see or revoke a session that isn't theirs via Gap 3's new endpoints, mirroring the exact "different customer, identical not-found response" pattern M2's own MARB process already established as the standard for this codebase.

## Download security

- **Unchanged.** The Library page's Download action reuses the existing `POST /api/purchases/:reference/downloads` -> `GET /api/download/:token` pair exactly as the guest confirmation page already does - single-use, short-TTL, 256-bit tokens, minted fresh at click time, never embedded ahead of time. M3 introduces no second, dashboard-specific download mechanism that could drift out of sync with the proven one.
- The Receipts page's download action similarly reuses the existing, direct-stream `GET /api/customer/receipts/:receiptNumber/download` unchanged.
- Revocation (a refunded purchase) continues to deny both paths identically - M3 adds no new code path that could bypass the `deliveries.status != 'revoked'` gate ADR-003 requires.

## Payment security

- **Not applicable / unaffected.** M3 touches no payment, checkout, or webhook code. The single most safety-critical boundary in the system (webhook-only trust) is not touched by this milestone at all.

## New attack surface introduced by M3, summarized

| New surface | Mitigation |
|---|---|
| `GET /api/customer/sessions` - lists session metadata | Ownership-filtered by `customerId`; `user_agent`/`ip_created` already documented elsewhere in this codebase as "audit/anomaly context only, never an access decision" - the same framing applies to what's displayed here. |
| `POST /api/customer/sessions/:sessionId/revoke` - a new *id-scoped* (not customer-scoped) mutation | The one new authorization shape in M3 - needs its own explicit ownership-check test, not just a copy of the customer-id-filtering pattern used everywhere else. |
| `POST /api/customer/auth/change-password` - a new authenticated mutation accepting a customer-supplied "current password" | Standard password-verification-before-change pattern, already proven in `authService.ts`'s login path; no new hashing/storage mechanism. |
| Dashboard pages render more purchase/delivery detail than the guest confirmation page did (download counts, expiry) | All of this data already belongs to the authenticated customer themselves (never another customer's data) and none of it is more sensitive than what the guest confirmation page already exposes for a *known reference* - this is exposing owned data to its owner, not a new disclosure risk. |

**No high-risk or unresolved security question is introduced by M3.** Every new endpoint reuses an existing, proven authentication/authorization/CSRF pattern; the one genuinely new authorization shape (session-id ownership, not customer-id filtering) is explicitly flagged for its own dedicated test rather than assumed safe by analogy alone.
