# Version 3.3 Sprint M5D.1: Retry and Idempotency Strategy

Documents the general strategy chosen to satisfy Sprint M5D's requirement that "Cloudflare Cron's documented at-least-once execution model must be treated as a design requirement," and the concurrency-safety approach applied to both remediated workflows.

---

## The Design Requirement, Restated

Cloudflare's own documentation (confirmed via the `cloudflare` skill's `references/cron-triggers/gotchas.md`) states Cron Trigger execution is at-least-once, for every plan tier — not a rare failure mode to tolerate, but an expected operational property to design for from the start. Any state this project's scheduled jobs mutate must be safe to mutate twice for the same logical event.

## Strategy: Atomic Claim, Not External Locking

Two approaches were considered:

1. **A KV-based execution-id lock** (the pattern the `cloudflare` skill's own cron-triggers reference suggests as a general-purpose default: `env.EXECUTIONS.get/put(executionId)`). This deduplicates by *scheduled invocation* (the whole cron firing), not by *business entity* (an individual purchase). It would prevent two overlapping runs of the entire job from both executing, but does nothing for the actual failure mode this project needed to fix: a single run's own eligibility query returning stale or ambiguous results for individual purchases across DIFFERENT days' runs (the permanent-suppression bug), which has nothing to do with overlapping invocations of the same trigger.
2. **A per-entity atomic claim in D1** (the approach actually taken). Rather than locking the job as a whole, each individual purchase is claimed independently, atomically, at the moment it's about to be processed — correct regardless of whether the "duplicate" comes from two overlapping runs of the same scheduled trigger, or from two runs on different days that both consider the same purchase eligible.

**Decision: per-entity atomic claim, not a global execution lock.** It directly addresses the actual granularity of the problem (one purchase's reminder state, not "did this cron fire twice") and reuses this codebase's own already-proven idiom (atomic UPDATE, check `meta.changes`) rather than introducing a new KV-based coordination mechanism for a problem D1 can already solve natively.

## Applying the Same Strategy to Two Structurally Different Workflows

Both `services/customer/reviewReminderService.ts` (Cron-triggered, batch, many purchases per run) and `services/customer/reconciliationService.ts` (HTTP-triggered, single email, at most a handful of purchases per call) needed a concurrency fix, but the SAME fix shape was not appropriate to both — this was a deliberate judgment call, not an oversight:

| | Review Reminders | Reconciliation |
|---|---|---|
| Trigger | Cloudflare Cron (at-least-once, unattended, recurring) | Customer-initiated HTTP request (at most a double-click or client retry) |
| Failure modes to cover | Both a failed-then-abandoned attempt AND concurrent duplicate sends | Only concurrent duplicate notification (no analogous "permanently stuck" state — a purchase either gets linked or it doesn't, in one atomic step) |
| Retry needed across days? | Yes — a transient outage today should not permanently forfeit a reminder | No — reconciliation either succeeds now or the customer can just resubmit the same form |
| Fix shape | A new, dedicated claim/status table (`review_reminder_attempts`) with an explicit state machine, since "already attempted but should retry later" is a real, necessary state | A single `meta.changes` check on the existing linking `UPDATE`, since the linking operation is already naturally atomic and all-or-nothing for the realistic two-caller race this system can produce |

Using the heavier claim-table mechanism for reconciliation too would have been over-engineering: reconciliation has no multi-day retry requirement and no batch of many purchases to individually track state for across scheduled runs. Using the lighter `meta.changes`-only fix for review reminders would not have solved the failed-send-permanently-suppresses-forever problem, since that requires a genuine state machine (attempted-and-failed must remain distinguishable from attempted-and-succeeded across runs that may be days apart), not just a single-statement atomicity check.

## A General Principle This Sprint Surfaced (Applies Beyond Both Fixes)

**Never compare a SQL-generated timestamp (`datetime('now')`) against a JS-generated one (`new Date().toISOString()`), or vice versa, in the same condition.** The two formats are lexicographically incompatible for same-day comparisons (confirmed directly: `datetime('now') < '<same-day>T00:00:00.000Z'` evaluates `true` regardless of actual time), and this defeated the very staleness check meant to prevent duplicate claims during this remediation's own first attempt, before being caught by direct testing. `sessionService.ts`'s existing `expires_at`/`now` handling already followed the correct convention (always JS-ISO, both sides); `reviewReminderService.ts` now does too. **A related, pre-existing instance of this same inconsistency was found in `findDueReminders()`'s own `verified_at <= ?` cutoff comparison (`verified_at` is stored via `commerceService.ts`'s `datetime('now')`, compared against a JS-ISO cutoff) — this happens to produce correct results today only because the comparison's granularity (5 days) means the DATE portion of the two strings differs before the format-inconsistent time portion is ever reached. This is a latent, currently-harmless inconsistency, not fixed by this remediation sprint (out of scope — unrelated to the two Blocking findings) but flagged here and in the Remediation Report as a discovered issue worth a future, narrowly-scoped cleanup.**

## Why Not Cloudflare Queues or Workflows

Both were considered and rejected as disproportionate to this project's actual scale and problem shape. Queues solve fan-out/back-pressure for high-volume async work; Workflows solve durable multi-step orchestration with automatic retry/checkpointing. This project's review-reminder volume (bounded by `MAX_REMINDERS_PER_RUN = 200`, and realistically far below that at this platform's current transaction volume) and the problem itself (per-row atomic idempotency, not multi-step orchestration) are both well within what a single D1 table and a single Cron Trigger already handle correctly once the claim mechanism is right. Introducing either would be new infrastructure this project's own stated bar ("no new Cron Trigger without a specific, narrow, named reason," extended here to "no new infrastructure category without a specific, narrow, named reason") does not currently justify.
