## New Tables

### `product_reviews`

```sql
CREATE TABLE product_reviews (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  product_id          INTEGER NOT NULL REFERENCES products(id),
  customer_id         INTEGER NOT NULL REFERENCES customers(id),
  purchase_session_id INTEGER NOT NULL REFERENCES purchase_sessions(id),
  rating              INTEGER NOT NULL CHECK (rating BETWEEN 1 AND 5),
  body                TEXT NOT NULL,
  status              TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'approved', 'rejected')),
  moderated_by        INTEGER REFERENCES admin_users(id),
  moderated_at        TEXT,
  created_at          TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at          TEXT NOT NULL DEFAULT (datetime('now')),

  UNIQUE(product_id, customer_id)
);
```

- `purchase_session_id` is `NOT NULL` and always points at the specific verified purchase that justified the review at submission/last-edit time - not merely evidence a purchase existed at some point, a specific, auditable one.
- `UNIQUE(product_id, customer_id)` is the database-layer enforcement of "one review per product per customer," backing the atomic `INSERT ... ON CONFLICT DO UPDATE` upsert in `reviewService.submitOrUpdateReview()` (see the Reviews Architecture Report).
- `moderated_by`/`moderated_at` are both `NULL` until an admin acts, and are explicitly reset to `NULL` on every edit - a stale moderation decision must never survive a content change.

### `coupons`

```sql
CREATE TABLE coupons (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  code                TEXT NOT NULL UNIQUE,
  product_id          INTEGER REFERENCES products(id),
  discount_type       TEXT NOT NULL CHECK (discount_type IN ('percentage', 'fixed')),
  discount_value      INTEGER NOT NULL CHECK (discount_value > 0),
  max_redemptions     INTEGER,
  redemptions_count   INTEGER NOT NULL DEFAULT 0,
  first_purchase_only INTEGER NOT NULL DEFAULT 0,
  starts_at           TEXT,
  expires_at          TEXT,
  status              TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'disabled', 'expired')),
  created_by          INTEGER NOT NULL REFERENCES admin_users(id),
  created_at          TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at          TEXT NOT NULL DEFAULT (datetime('now'))
);
```

- `created_by REFERENCES admin_users(id)` - the corrected reference from Amendment 1, replacing the original design's nonexistent `platform_users`. See [`v3.2-m4c-amendment-1-resolution.md`](v3.2-m4c-amendment-1-resolution.md) for the full before/after.
- `product_id` nullable: `NULL` means platform-wide, a specific id means scoped to exactly one product. No `scope` enum, no `creator_id` - both existed in the original, superseded design and were removed entirely, not repurposed.
- `discount_value` is a plain `INTEGER` for both discount types: a percentage (`0-100`, enforced in `couponService.createCoupon()`, not at the schema layer) or a pesewa amount for `fixed` - the column itself doesn't know which, `discount_type` disambiguates at read time.
- `redemptions_count` starts at `0` and is only ever incremented by `couponService.redeemCoupon()`'s atomic conditional `UPDATE`, never by any other code path.
- `status` includes `'expired'` as a settable value distinct from a coupon whose `expires_at` has simply passed - `validateCoupon()` checks `expires_at` live (returns reason `'expired'` regardless of the `status` column), while `status = 'expired'` is available for an admin to explicitly retire a coupon rather than merely wait for its date to pass. In practice, admin coupon-management today only ever toggles between `'active'`/`'disabled'` via the UI; `'expired'` as a status value exists in the enum for completeness and is intentionally excluded from the toggle affordance once already set (see `admin-coupons.js`).

### `coupon_redemptions`

```sql
CREATE TABLE coupon_redemptions (
  id                   INTEGER PRIMARY KEY AUTOINCREMENT,
  coupon_id            INTEGER NOT NULL REFERENCES coupons(id),
  purchase_session_id  INTEGER NOT NULL REFERENCES purchase_sessions(id),
  customer_email       TEXT NOT NULL,
  discount_pesewas     INTEGER NOT NULL CHECK (discount_pesewas >= 0),
  redeemed_at          TEXT NOT NULL DEFAULT (datetime('now')),

  UNIQUE(purchase_session_id)
);
```

- Not part of the original design at all - added during Amendment 1's resolution specifically for audit purposes: a durable, per-purchase record of exactly which discount was actually applied and charged, independent of whether the coupon's own `redemptions_count` increment happened to win or lose the redemption-limit race (see the Coupon Architecture Report's "Two-Phase Redemption Design" section for why a row is written here regardless of that outcome).
- `UNIQUE(purchase_session_id)` - one redemption record per purchase, matching the "each purchase_sessions row is only ever verified once" invariant the webhook's own idempotency layers already guarantee elsewhere in this codebase.

## Extended Tables

### `purchase_sessions` (2 new columns)

```sql
ALTER TABLE purchase_sessions ADD COLUMN coupon_id INTEGER REFERENCES coupons(id);
ALTER TABLE purchase_sessions ADD COLUMN discount_pesewas INTEGER NOT NULL DEFAULT 0 CHECK (discount_pesewas >= 0);
```

- `coupon_id` is `NULL` for the vast majority of purchases (no coupon applied) and is set at checkout-session creation time, locked alongside the discounted `amount_pesewas`.
- `discount_pesewas` deliberately has **no** cross-column `CHECK (discount_pesewas <= amount_pesewas)` - SQLite's `ALTER TABLE ADD COLUMN` support for `CHECK` constraints referencing other existing columns is unreliable across versions (unlike a fresh `CREATE TABLE`, where it works fine). The invariant is enforced at the application layer instead (`computeDiscountPesewas()` always caps the discount at the pre-discount amount), the same precedent `receipts.total_pesewas` already established for an equivalent cross-column relationship.
- `amount_pesewas` itself is unchanged in meaning - it is still, as before M4, the actual amount that will be charged. A coupon discount is subtracted from the catalog price *before* `amount_pesewas` is ever written, not stored separately and reconciled later.

### `receipts.discount_pesewas` - not a new column, newly populated

No migration in this sprint touches `receipts` at all. `receipts.discount_pesewas` was already added, unused, by **migration 0019** (`0019_ownership_layer.sql`, Milestone M2) with its own comment: `-- always 0 in M2 — no coupon system exists yet`. M2's own schema design anticipated a future coupon system and reserved the column for it rather than requiring a schema change later. M4C is simply the first code that ever writes a non-zero value there (`orderService.ts`) and the first that ever reads and renders it (`receiptPdfService.ts`). Lets a receipt recover and display the original, pre-discount subtotal as a separate line from the discount, standard invoice convention - `subtotal_pesewas` represents the pre-discount price (`amount_pesewas + discount_pesewas`), while `tax_pesewas`/`total_pesewas` continue to be computed from the actual, already-discounted `amount_pesewas`, exactly as before M4.

## Indexes

```sql
CREATE INDEX idx_coupons_code ON coupons(code);
CREATE INDEX idx_coupons_product ON coupons(product_id);
CREATE INDEX idx_coupons_status ON coupons(status);
```

`code` is looked up on every checkout and every discount-preview request (`findActiveCouponByCode()`), making it the highest-value index of the three. `product_id` and `status` support the admin list/filter views.

## Migration Application Note

`wrangler d1 migrations apply --local` continues to fail against this project's local D1 instance with the same pre-existing tracking-table/actual-schema mismatch documented throughout this project's history (the local instance has every table already, from an earlier full-`schema.sql` apply that bypassed the `d1_migrations` bookkeeping table). This migration was applied the same established way: `wrangler d1 execute --local --file database/migrations/0020_reviews_and_coupons.sql`, verified directly via `sqlite_master` inspection. This is a local-development environment artifact, not a defect in the migration file itself, and does not affect a genuine `--remote` migration apply against a fresh tracking table.
