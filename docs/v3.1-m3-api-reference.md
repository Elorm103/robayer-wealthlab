# Version 3.1 - Milestone M3 API Reference / Changes Summary

Checkout Auto-Provisioning & Dashboard MVP. Covers the three new
customer-authenticated endpoints, the one additive field on an existing
endpoint, and the one new error code. Written at M3B, corrected and
extended at M3C (Acceptance Review) and M3D (Closeout) - see the
inline notes throughout marking what changed at each sprint. All
responses use the project's standard envelope: `{ success: true, data:
{...} }` or `{ success: false, error: { code, message } }`. No breaking
change was made to any existing endpoint's shape - every consumer of
the pre-M3 API continues to work unmodified.

## Summary

| Change | Type | Endpoint / Code |
|---|---|---|
| New | Endpoint | `GET /api/customer/sessions` |
| New | Endpoint | `POST /api/customer/sessions/:sessionId/revoke` |
| New | Endpoint | `POST /api/customer/auth/change-password` |

| New (added M3C) | Error code | `CANNOT_REVOKE_CURRENT_SESSION` (400) - returned by `POST /api/customer/sessions/:sessionId/revoke` when the target id is the caller's own current session |

## New: `GET /api/customer/sessions`

**Auth**: `customer_session` cookie. **Rate limit**: 60/15min/IP.

**Success (200)**:
```json
{
  "sessions": [
    {
      "id": 42,
      "userAgent": "Mozilla/5.0 (Windows NT 10.0; ...) Chrome/...",
      "lastSeenAt": "2026-07-25T10:00:00Z",
      "isCurrent": true
    }
  ]
}
```
Only the caller's own sessions are ever returned - filtered server-side
by `customerId`, never client-supplied. `isCurrent` is derived from the
requesting session's own id, so the UI can decide not to offer a revoke
action for it (see below).

**Errors**: `NOT_AUTHENTICATED` (401); `RATE_LIMITED` (429).

## New: `POST /api/customer/sessions/:sessionId/revoke`

**Auth**: `customer_session` cookie + `X-Customer-CSRF-Token` header.
**Rate limit**: 20/15min/IP.

**Success (200)**: `{ "revoked": true }`

**Authorization**: filtered by both `customerId` (from the session
cookie) and `sessionId` (the path parameter) - the one new
authorization shape M3 introduces, since every other M1/M2 customer
endpoint filters by `customerId` alone. Attempting to revoke a session
belonging to a different customer, or a nonexistent session id, both
return the identical `NOT_FOUND` (404) - never a distinct "forbidden"
signal, matching this project's established cross-customer-access
convention.

**The caller's own current session cannot be revoked via this route**
(`CANNOT_REVOKE_CURRENT_SESSION`, 400) - use
`POST /api/customer/auth/logout` instead. Added during the M3C
Acceptance Review: the initial M3B implementation relied only on the
dashboard UI never rendering a revoke control for the session marked
`isCurrent`, matching the existing `services/admin/sessionService.ts`
precedent - but the M3A Security Review's Session handling section
explicitly required this route itself to reject the attempt, and a
live check during acceptance review confirmed the gap was real (a
direct API call could revoke the caller's own session and immediately
invalidate the cookie making the request). Fixed in
`routes/customer/sessions.ts`.

**Errors**: `NOT_FOUND` (404); `CANNOT_REVOKE_CURRENT_SESSION` (400);
`VALIDATION_ERROR` (400) for a non-numeric `:sessionId`;
`NOT_AUTHENTICATED` (401); `INVALID_CSRF_TOKEN` (403); `RATE_LIMITED`
(429).

## New: `POST /api/customer/auth/change-password`

**Auth**: `customer_session` cookie + `X-Customer-CSRF-Token` header.
**Rate limit**: 10/15min/IP.

**Request body**:
```json
{ "currentPassword": "...", "newPassword": "..." }
```

**Success (200)**: `{ "changed": true }`. Every *other* active session
for this customer is revoked as a side effect (via the existing
`sessionService.revokeAllSessionsExcept()`) - the caller's own current
session is deliberately left alive, so a customer changing their
password from their own device is never signed out mid-action.

**Errors**: `INVALID_CREDENTIALS` (401) - current password does not
match (verified via the existing timing-safe `DUMMY_PASSWORD_HASH`
comparison pattern, so a wrong-password response takes the same time
as a correct one); `VALIDATION_ERROR` (400) - new password fails the
existing password-strength policy; `NOT_AUTHENTICATED` (401);
`INVALID_CSRF_TOKEN` (403); `RATE_LIMITED` (429).

## Additive: `assets` field on `GET /api/customer/purchases` and `GET /api/customer/purchases/:reference`

Both endpoints' existing response shape is unchanged except for one new
field per purchase:

```json
{
  "purchaseReference": "RWL-2026-900001",
  "productTitle": "Dev Verification Guide",
  "status": "ready",
  "assets": [
    {
      "assetId": "asset-dev-guide-pdf-v1",
      "displayName": "Dev Verification Guide (PDF)",
      "fileType": "PDF",
      "revoked": false,
      "downloadsUsed": 1,
      "maxDownloads": 5,
      "lastDownloadAt": "2026-07-25T09:00:00Z"
    }
  ]
}
```
(Corrected at M3D closeout: the field is `revoked` (boolean, `true`
once a refund has revoked this specific entitlement per
`services/orders/revocationService.ts` - the Library UI must never
offer a Download action for an asset with `revoked: true`) plus
`fileType`, not a `status` string - the M3B/M3C draft of this example
incorrectly showed a `"status": "delivered"` field that does not exist
on the actual `AssetDeliveryInfo` shape. See
`services/fulfilmentService.ts`'s `AssetDeliveryInfo` interface for the
authoritative shape.)

`assets` is populated only when `status === 'ready'` - a
`processing`/`unavailable`/`refunded` purchase always returns `assets:
[]`, matching the existing pattern where a not-yet-fulfilled purchase
never exposes download entitlement detail. A `ready` purchase can still
contain a `revoked: true` asset (e.g. one asset revoked individually
without the whole purchase being refunded) - the array is never
filtered down before being returned; the customer-facing UI is
responsible for hiding the Download action per-asset, not the API.
Powered by a new function, `resolveAssetsWithDeliveryInfo()`
(`services/fulfilmentService.ts`), which joins the existing published
product-file list against the existing `deliveries` table. This is
kept deliberately separate from the pre-existing, guest-facing
`getFulfilmentStatus()`'s own narrower `assets` field - no change was
made to that guest-facing contract.

**No new error codes** on either of these two endpoints specifically.
The milestone's one new error code overall, `CANNOT_REVOKE_CURRENT_SESSION`,
belongs to `POST /api/customer/sessions/:sessionId/revoke` above, not
to this `assets` field addition. No change to either endpoint's
authentication, rate-limit, or authorization behaviour.
