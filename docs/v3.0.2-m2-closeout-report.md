## Executive Summary

Sprint M2D resolved every one of the five acceptance items named in the M2C Milestone Acceptance Review, all of which were classified there as Non-blocking. Concretely:

- **Runtime dependency**: confirmed `pdf-lib` was misclassified under `devDependencies` while being imported by production Worker code (`services/orders/receiptPdfService.ts`). Moved it to a new `dependencies` block in `backend/package.json`, re-synced `package-lock.json`, corrected a now-stale `wrangler.jsonc` comment that still claimed "zero runtime npm dependencies," and re-verified the TypeScript build stays clean.
- **Test coverage**: added 18 new tests across two new files (`tests/integration/negativeM2.test.ts`, 10 tests; `tests/integration/rateLimitingM2.test.ts`, 5 tests) plus 3 tests added to existing files, closing every gap the MAR named: malformed/oversized/SQL-injection-shaped path parameters on every new M2 endpoint, rate-limit enforcement on the guest and customer-authenticated M2 endpoints, and - the item requiring an actual code fix, not just a test - true concurrent refund idempotency proven with real `Promise.all` execution at both the service and HTTP-route level.
- **Audit traceability**: `services/admin/orderService.ts`'s `refundOrder()` now passes the affected `purchase_sessions.id` as `audit_logs.entity_id` (previously `null`), making refund events findable via the existing `idx_audit_logs_entity` index, not only by scanning `metadata`.
- **Receipt rounding**: fixed, not merely documented. `createOrderArtifacts()` now sets a receipt's line-item total directly to the actual charged amount rather than recomputing it from a rounded per-seat unit price - eliminating a latent pesewa-level drift for any future `quantity > 1` purchase whose amount does not divide evenly by the seat count. Proven by a new test seeding exactly that non-evenly-divisible case (10000 pesewas / 3 seats).
- **A sixth, related defect was found and fixed while resolving the test-coverage item, not separately named in the MAR**: `revokePurchase()`'s idempotency was only proven safe under *sequential* re-calls; under genuine concurrency (two simultaneous refund requests), both could pass the initial read before either wrote, risking a double audit-log entry. Reworked to use a status-gated conditional `UPDATE` inside the existing D1 batch - the same atomic-race-arbitration pattern `commerceService.ts`'s `verifySessionAtomic()` already established - so only one of any number of simultaneous callers can ever succeed. Proven with real `Promise.all` tests at both layers.

Ran a full regression pass after all changes: TypeScript typechecking clean, full automated suite passing (106/106, up from 88/88), re-run three consecutive times with identical results, no regressions introduced, no architecture or schema change made.

No new defect was introduced by this sprint's own changes - every fix was independently re-verified by a passing, purpose-written test, not merely asserted.

## MAR Observations and Resolution Status

Every item below is copied from the Milestone Acceptance Review's Section 13 (Recommendations) and Section 14 (Remediation List), in the same order, with this sprint's resolution status and supporting evidence.

### Item 1: Confirm `pdf-lib`'s `package.json` classification (production dependency, not devDependency)

**Status: Resolved.**

The MAR had already confirmed this directly (not speculative) - `pdf-lib` was listed only under `devDependencies`. Evidence of the fix:

- `backend/package.json`: added a new `"dependencies": { "pdf-lib": "^1.17.1" }` block; removed the `pdf-lib` entry from `devDependencies`.
- `backend/package-lock.json`: re-synced via `npm install --package-lock-only`; `git diff --stat` confirmed only the `dev` classification changed for `pdf-lib`'s entry, no package version or resolved dependency tree changed.
- `backend/wrangler.jsonc`: the `compatibility_flags: []` comment ("this Worker has zero runtime npm dependencies") was stale as of M2B and has been corrected to explain that `pdf-lib` is now a genuine runtime dependency but still needs no `nodejs_compat` flag (pure JavaScript, confirmed by the M2B spike).
- `npx tsc --noEmit` re-run clean immediately after the `package.json` change, confirming the build was unaffected.
- **Why this change was required**: `wrangler deploy` bundles from local `node_modules` regardless of which `package.json` section a package is listed under, so this was not an active break under the project's current manual deploy process - but it was a real latent risk (a future CI runner or a production-only `npm ci --omit=dev` step would fail to resolve `pdf-lib` with no warning until that exact moment). `pdf-lib`'s actual role changed with Milestone M2 - it moved from a local, build-time-only script dependency to a genuine Worker-runtime dependency - and its `package.json` classification now accurately reflects that.

### Item 2: Add negative/adversarial and rate-limit test coverage for M2's new endpoints

**Status: Resolved.**

- **`tests/integration/negativeM2.test.ts`** (new, 10 tests): malformed and SQL-injection-shaped values, plus oversized (100,000-character) strings, tested against `:reference` on `GET /api/customer/purchases/:reference`, `POST /api/purchases/:reference/receipt-download`, and `POST /api/admin/orders/:reference/refund`; against `:receiptNumber` on `GET /api/customer/receipts/:receiptNumber/download`; and against `:token` on `GET /api/download-receipt/:token`. Every case asserts a clean, typed error response (never a 500) and, where applicable, that the underlying table is untouched - proving the existing regex-gate validation (`isPlausibleReference`, `isPlausibleReceiptNumber`, `REFERENCE_PATTERN`) holds under adversarial input, not merely by inspection as the MAR had left it.
- **`tests/integration/rateLimitingM2.test.ts`** (new, 5 tests): the 21st request within the window is rejected with `RATE_LIMITED` for `POST /api/purchases/:reference/receipt-download` (20/min), `GET /api/download-receipt/:token` (20/min), and `GET /api/customer/receipts/:receiptNumber/download` (20/15min); the 61st request is rejected for `GET /api/customer/purchases` (60/15min); and one test confirms rate-limit buckets are correctly isolated per endpoint (exhausting one endpoint's limit does not affect another's for the same IP).
- All 15 tests pass; all ran clean on first attempt except one assertion in the rate-limiting file that was corrected to match the route's actual (and correct) behavior - `POST /api/purchases/:reference/receipt-download` returns `RECEIPT_NOT_FOUND` for a well-formed-but-nonexistent reference, not `PURCHASE_NOT_FOUND` (that code is reserved for a malformed reference that never passes the pattern gate at all). This was a test-authoring correction, not a code change.

### Item 3: Add a true concurrent refund idempotency test (`Promise.all`, not sequential)

**Status: Resolved - and a real defect was found and fixed in the process, not merely tested around.**

Writing this test surfaced the actual gap the MAR had flagged as a risk rather than a confirmed defect (Section 4, Section 11 Item 5 of the Acceptance Report): the pre-existing idempotency test only proved safety under *sequential* double-calls, and `revokePurchase()`'s original implementation read `purchase_sessions.status` before writing, with no atomic guard on the write itself - a genuine TOCTOU race under real concurrency.

**Fix, in `services/orders/revocationService.ts`:** the `purchase_sessions` statement inside the existing `env.DB.batch()` call is now itself a status-gated conditional `UPDATE ... WHERE id = ? AND status = 'verified'`, mirroring `commerceService.ts`'s `verifySessionAtomic()` pattern exactly. The function inspects that statement's own `meta.changes` from the batch result (not the earlier, advisory-only read) to decide whether this call actually won the right to revoke - the same "informational pre-check, atomic real check" split `entitlementService.ts`'s `consumeTokenAtomic()` already established elsewhere in this codebase. `RevokePurchaseResult`'s `ok: true` branch now also carries `purchaseSessionId`, which item 4 below uses.

**Tests added:**
- `tests/unit/revocationService.test.ts`: a new test fires two `revokePurchase()` calls via `Promise.all` for the same purchase, asserts exactly one succeeds and one returns `already_revoked`, and confirms the end state (licenses revoked, delivery revoked, session refunded) is identical to a single successful call - no partial or double-applied state.
- `tests/integration/adminRefund.test.ts`: a new test fires two real `POST /api/admin/orders/:reference/refund` HTTP requests via `Promise.all`, asserts exactly one response reports success, and - the property that actually matters operationally - confirms exactly one `audit_logs` row with `action = 'order.refunded'` exists afterward, not two.

Both tests pass, confirming the fix closes the race under this environment's real D1/`workerd` concurrency semantics, not merely by code inspection.

### Item 4: Improve refund audit logging - record `entity_id` where supported

**Status: Resolved.**

`services/admin/orderService.ts`'s `refundOrder()` now passes `entityId: result.purchaseSessionId` (available directly from `revokePurchase()`'s result as of item 3's fix, no extra query needed) instead of `entityId: null`. A refund event is now findable via `idx_audit_logs_entity` like every other entity-scoped audit event in this codebase, not only by scanning `metadata.reference`. No audit-system redesign was made or needed - this is a one-field population fix using data the function already had in hand once item 3's fix threaded `purchaseSessionId` through the result type.

### Item 5: Review the multi-seat receipt rounding edge case - fix or document as acceptable

**Status: Resolved by fixing the implementation**, not merely documenting it as acceptable.

Root cause: `createOrderArtifacts()` computed a rounded per-seat `unitPricePesewas` (`Math.round(amountPesewas / quantity)`) and then derived the receipt's line-item total as `unitPricePesewas * quantity` - a recomputation that could drift from the actual charged amount by up to `quantity - 1` pesewas whenever `amountPesewas` does not divide evenly by `quantity`.

**Fix, in `services/orders/orderService.ts`:** since `createOrderArtifacts()` only ever creates one `order_items` row per call (one product per order today), that single line item's `lineTotalPesewas` is now set directly to `input.amountPesewas` - the exact, already-charged amount - never recomputed from the rounded per-seat price. `unitPricePesewas` remains a rounded, informational per-seat value (still stored on `order_items.unit_price_pesewas` for display/reporting), but is no longer the source the financial total is derived from.

**Test added:** `tests/unit/orderService.test.ts` gained a case seeding `amountPesewas: 10000, quantity: 3` (10000 / 3 = 3333.33..., the exact non-evenly-divisible shape that exposed the bug) and asserts the receipt's `line_items[0].lineTotalPesewas` equals `10000` exactly - matching both `subtotal_pesewas` and `total_pesewas` - never `9999`.

This was chosen over "document as acceptable" because the fix was small, contained entirely within `createOrderArtifacts()`'s existing line-item construction, required no schema change, and removes a real (if currently dormant) financial-record inaccuracy rather than carrying it forward - consistent with this sprint's "fix if required to resolve an accepted observation" instruction, and with the observation's own severity note in the Acceptance Report (a receipt's line-item arithmetic disagreeing with its own total is the kind of thing worth fixing once identified, even at low current likelihood).
