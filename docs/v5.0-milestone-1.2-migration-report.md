# Version 5.0 Milestone 1.2 — AI Governance & Safety

**Migration Report**

## `0035_ai_gateway_governance.sql`

Additive only — every change is `ALTER TABLE ... ADD COLUMN` (all nullable or `NOT NULL DEFAULT`) plus two new indexes. No existing column is modified or dropped. No other table is touched.

```sql
ALTER TABLE ai_usage_log ADD COLUMN sensitivity_classification TEXT NOT NULL DEFAULT 'INTERNAL'
  CHECK (sensitivity_classification IN ('PUBLIC', 'INTERNAL', 'CONFIDENTIAL', 'FINANCIAL', 'PERSONAL', 'HIGHLY_SENSITIVE'));
ALTER TABLE ai_usage_log ADD COLUMN gateway_version TEXT;
ALTER TABLE ai_usage_log ADD COLUMN policy_version TEXT;
ALTER TABLE ai_usage_log ADD COLUMN provider_decision TEXT;
ALTER TABLE ai_usage_log ADD COLUMN budget_decision TEXT;
ALTER TABLE ai_usage_log ADD COLUMN retention_decision TEXT;
ALTER TABLE ai_usage_log ADD COLUMN masking_applied INTEGER NOT NULL DEFAULT 0 CHECK (masking_applied IN (0, 1));
ALTER TABLE ai_usage_log ADD COLUMN cleanup_eligible_date TEXT;
ALTER TABLE ai_usage_log ADD COLUMN purged_at TEXT;

CREATE INDEX idx_ai_usage_log_sensitivity ON ai_usage_log(sensitivity_classification);
CREATE INDEX idx_ai_usage_log_cleanup_eligible ON ai_usage_log(cleanup_eligible_date);
```

## Backfill reasoning

`sensitivity_classification` is `NOT NULL`, so every pre-existing row (Milestone 1/1.1's diagnostic-test history) needed a real value at migration time, not a placeholder. It defaults to `'INTERNAL'` — correct, because the only feature that has ever run (`internal.gateway-diagnostic`) is, definitionally, an internal operational check, not customer or business data. This is a factually accurate backfill, not a guess.

`gateway_version`/`policy_version`/`provider_decision`/`budget_decision`/`retention_decision` are left `NULL` for pre-existing rows — there is no honest value to backfill (those concepts didn't exist yet when those rows were written), and `NULL` correctly represents "not recorded," distinct from an empty string or a fabricated value.

`masking_applied` defaults to `0` for historical rows — also accurate, since masking never ran against them (nothing was ever redacted).

`cleanup_eligible_date`/`purged_at` are `NULL` for historical rows, correctly meaning "never scheduled for cleanup" (they predate the retention-policy mechanism entirely) — they will not be swept up by the scheduled cleanup job, which only ever acts on rows where `cleanup_eligible_date IS NOT NULL`.

## New site_settings keys

No schema change required — `site_settings` is a generic key/value table. New keys, all with code-defined defaults (`services/ai/aiGatewayConfig.ts`), applied automatically the first time they're read if never explicitly written:

- `ai_gateway_provider_budgets_usd_micros` (default `{}`)
- `ai_gateway_platform_budget_usd_micros` (default `100000000` / $100.00)
- `ai_gateway_retention_storage_mode` (default `"metadata_only"`)
- `ai_gateway_retention_days` (default `90`)

Two Milestone 1.1 keys (`ai_gateway_daily_budget_usd_micros`, `ai_gateway_monthly_budget_usd_micros`) keep their names but change DEFAULT semantics: previously `null` (unconfigured/warning-only), now real numeric defaults ($1.00/$20.00) since Task 1/2 require every feature to inherit a real, protective default automatically. An admin who explicitly set either to `null` before this milestone will find it defaults back to the new numeric value after this migration, since the key was never actually written to `site_settings` in the "unconfigured" case (the old code path treated an absent key as `null` via its own default, not a stored `null` value) — this repository's production `site_settings` table has never had these keys written (confirmed: Milestone 1.1 shipped with no admin having touched these fields yet), so this is a theoretical case, not a real one for this deployment.

## Rollback

The nine added columns are additive/nullable-or-defaulted and safe to leave in place indefinitely even if this milestone were reverted. A true rollback (dropping them) would use SQLite's standard recreate-copy-swap pattern, since SQLite has no `DROP COLUMN` prior to fairly recent versions and this project's own migration-history convention already avoids relying on it. No other table or foreign key references these columns, so this is low-risk if ever needed.
