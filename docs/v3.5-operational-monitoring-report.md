# Version 3.5: Operational Monitoring Report

## Recent activity feeds (Phase 5)

Ten most recent rows each, all read live from the same tables their own admin list pages already use, each with a "View All" link to that real page (recent orders → Orders, recent reviews → Reviews, recent contacts → Contacts, recent consultations → Consultations, recent newsletter signups → Newsletter, recent admin logins → Users, recent product changes → Products). Failed logins, password resets, and admin activity have no dedicated list page today, so no "View All" link is shown for those three — a link to nowhere would be worse than no link.

| Feed | Source |
|---|---|
| Recent orders | `purchase_sessions` where `status = 'verified'`, newest first |
| Recent reviews | `product_reviews` joined to `products` for the title |
| Recent contact messages | `contact_messages`, message body truncated to 80 characters for the feed preview |
| Recent consultations | `consultation_requests` |
| Recent newsletter signups | `newsletter_subscribers` |
| Recent admin logins (success) | `login_history` joined to `admin_users`, `outcome = 'success'` |
| Recent failed logins | Same table, `outcome != 'success'` (covers `failed_password`, `failed_locked`, `failed_inactive`) |
| Recent password resets | `email_log` where template is one of `customer-password-reset` / `password-reset` (admin) / `customer-purchase-reconciliation`, status `sent` |
| Recent admin activity | `audit_logs` where `actor_type = 'admin'` |
| Recent product changes | `audit_logs` where `entity_type = 'product'` |

A real bug was found and fixed while building this: the initial `contact_messages` query assumed a `subject` column that does not exist in this schema (the table only has `name`/`email`/`phone`/`message`/`status`). Caught immediately via a live D1 query against production before the endpoint was ever exposed to the frontend — see the git history for the one-line fix (`substr(message, 1, 80) AS messagePreview`).

## Business alerts (Phase 6)

Every alert is a real, computed condition against live data. An alert type with nothing wrong contributes zero items — there is no synthetic "all clear" row.

| Alert | Condition | Severity |
|---|---|---|
| Low review count | An active product with fewer than 3 approved reviews | warning |
| Failed email delivery | Any `email_log` row `failed`/`permanently_failed` in the last 7 days | warning |
| Failed webhook | Any `payment_transactions` row `status = 'failed'` in the last 7 days | critical |
| Missing product cover | An **active** product with no cover image (coming-soon excluded — see the KPI Definitions Report) | critical |
| Product without download file | An active, paid product with no `product_files` row in `published` status | critical |
| Product hidden/unavailable | Any product currently in `hidden` or `unavailable` status | warning |
| Newsletter queue failure | Any `newsletter_campaigns` row `status = 'failed'` in the last 30 days | warning |
| Cron has not run | No `cron.heartbeat` row ever recorded, or the most recent one is more than 30 hours old | warning / critical |

### Two items from the brief handled differently than a literal reading might suggest

- **"Worker deployment older than expected"** — not implemented as an alert. Cloudflare Workers exposes no binding-accessible "when was this deployed" value; the only honest source (`DEPLOYED_AT`, an existing Version 2.1 Phase 5 convention) is an optional `--var` passed at deploy time, deliberately never committed to `wrangler.jsonc` because a committed value goes stale the instant it's written. The Business Health panel already surfaces the Worker version string; adding a threshold-based "too old" alert on top of an optionally-absent value would produce more noise than signal.
- **"Database migration pending"** — deliberately not implemented as a live alert, despite being straightforward to fake. The only way to know the *expected* migration count from inside a running Worker is a hardcoded constant, maintained by hand, bumped every time a new migration file is added. Such a constant drifts the moment someone adds a migration file without also touching this one — at that point the alert would report **false confidence** ("no migration pending") when one is, in fact, pending, which is a worse failure mode than having no such alert at all. Migration drift is instead caught by this project's existing pre-deploy discipline (`wrangler d1 migrations apply` as a required step before every `wrangler deploy`, per `backend/config/README.md`). The Business Health panel's Schema version field still shows the real, current migration name for manual cross-checking.

## Cron heartbeat (new instrumentation this milestone)

`backend/worker/index.ts`'s `scheduled()` handler now writes an `audit_logs` row (`actor_type: 'system'`, `action: 'cron.heartbeat'`) on every invocation, unconditionally — whether the run found reminders due or not, and whether it succeeded or threw. Before this milestone, "did Cron run today" had no real answer: the Cron Trigger only ever produced a side effect when it found something to send, so a quiet day was indistinguishable from the trigger never firing. Verified live: the health panel and alerts correctly report "No Cron execution has been recorded yet" right now, since this instrumentation was only just added — this will read as a genuine, dated timestamp starting with the next scheduled run (`0 6 * * *`, per `wrangler.jsonc`).
